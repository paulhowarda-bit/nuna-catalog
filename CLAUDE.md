# nuna-catalog: rules for every agent

At work, start with `docs/install-at-work.md`: it says which facts below describe Paul's home machine.

## Code changes go through a worktree

- Any agent that changes code works in its own git worktree on its own branch: a session started with `use_worktree: true`, or a subagent with `isolation: "worktree"`. Never edit code in the main checkout (`C:/Users/paulh/code/nuna-catalog`), except in place (below).
- **In place:** when Paul says "in place", make the change in the main checkout itself, with no worktree or branch (Paul, 2026-11-14).
  - Start only if `git status --porcelain` there prints nothing; otherwise another session is working there, so ask.
  - Run the fast build as a landing would (none for Markdown only).
  - Commit straight to `main`, ending the message with the attribution line. If the change touches `backlog/`, run `./backlog.sh log > BACKLOG.md` first and commit it too: only `land.sh` refreshes it otherwise.
- Bite runs (break a check, see its test fail, restore and hash-check) count as code changes, so they run inside the agent's own worktree, never in the main checkout, even in place.
- Never push unless Paul asks.

## Backlog and claims

- The backlog is `backlog/`, one file per item, `backlog/<n>.md`. `backlog/README.md` gives the format and the whole process; `./backlog.sh list` shows the open items and who holds each.
- `BACKLOG.md` at the repo root is the whole backlog in one log for Paul to review: the open items with their effort, each in full, then the done and dropped ones. `./backlog.sh log` makes it from the item files, and `land.sh` puts it in every landing's merge. Never edit it: edit the item.
- Add an item with `./backlog.sh add "<title>"` in your worktree (it takes the next number atomically), write a `Touches:` line (the folders and files the work will change), an `Effort:` line (S, M, L or XL and why: `backlog/README.md`), what is wrong, the evidence and what done looks like, then land it.
- Claim an item before working on it: `./backlog.sh claim <n>` in the worktree that will carry the work. It fails if another agent holds the item, or holds one whose area overlaps this one's (the `Touches:` line, or the areas you name: `./backlog.sh claim <n> demo/ CLAUDE.md`), so two agents never change the same code at once: take another item. Claim only what you are about to start, and change only what you claimed.
- When the work is done: `./backlog.sh done <n>`, write what was done, commit, land, then `./backlog.sh release <n>`. If you stop without finishing, release it; it stays open.
- A worktree subagent cannot land, so the session that starts it claims the item first and releases it after landing.
- Only Paul drops, defers or rescopes an item, or answers a question it puts to him. Record each decision in `decision-ledger.md` (an amendment to the D row it touches, quoting him with the date, or a new row) and add `Decided: <date>, <row>` to the item, in one branch: work reads the ledger, never the chats.
- Record what a branch did in a file of its own, `status/<date>-<name>.md` (`status/README.md`), never in `build-plan.md`: every branch adding to one log there made most of the conflicts.
- `./backlog.sh sweep` releases claims whose item is finished or whose worktree is gone with nothing left to land, and lists the rest; `backlog/README.md` says how to judge those.

## Builds

- `./gradlew build` is the fast build, and it needs no Docker (Paul, 2026-11-19; D44): it compiles everything, checks the bites and runs every test that needs only Java (about 1,580 tests). It leaves out tests tagged `heavy`, which is every test that starts a container (PostgreSQL, the S3 store, Kafka, Keycloak, Chrome): the PostgreSQL store suite and the server's routes among them, the whole Oracle, MongoDB and CockroachDB suites, and every fault-injection test. They run in the heavy build, which the overnight run runs every night code changed, so a landing that breaks one is found the next morning. It also leaves out the `overnight` and `cas` tests below.
- **Test locally while working; run the fast build once, at landing** (Paul, 2026-11-23; backlog 176). While changing code, run the tests of what changed: `./gradlew :<module>:test --tests <Class>`, or `./gradlew :<module>:test` (a module's tests took a median of 23 s). Run the whole fast build only in Landing step 1, after merging `main`, or once for a batch. Measured on 2026-11-23 with the nuna-demo stack up: 18 to 43 s when nothing changed (every test from the build cache), and 5 minutes after one line changed in `catalog-core`, since every module built on it runs its tests again. Sessions had been running the whole build again and again before landing, one of them 15 times in a day.
- The fast build also checks that every recorded bite still applies (`:bitesApply`); see Bites. It checks again only the bites whose patch, or a file the patch touches, changed since they last applied: each bite that applies leaves a marker named by a hash of those bytes in `~/.gradle/nuna/bites-applied`, which every worktree shares. That takes about 3 s; the first build on a machine checks all 571, about 2 minutes (backlog 176).
- `./gradlew build -Pheavy` runs every test, all four databases included, except the `overnight` tests and the CAS test. With `-Pheavy` or `-Pnightly` every test task runs afresh, never from the build cache.
- Tests tagged `overnight` never run in a build, fast or heavy: all of `catalog-tests-load` (the M8 load, resilience and SLO runs), `EngineMatrixTest`, `catalog-maintenance`'s `LargeExpiryTest`, `LargeOrphanScanTest` and `PrivateCaCompactionTest`, and the two `MutationSuite` sweeps that repeat a lost answer and a link cut before COMMIT for every mutation type. Paul moved them out of the heavy build on 2026-11-11 to shorten it. The heavy build keeps the single lost-answer, lost-COMMIT, in-flight and failover tests on every database.
- The CAS test (`CommitSuite#exactlyOneWriterWinsEachRound`, tagged `cas`) never runs in a build, fast or heavy, and never in a build-and-test cycle: it takes too long. Paul's rule, 2026-11-10. It runs only overnight: `./gradlew build -Pnightly` runs the `overnight` tests and that test, on all four backends at 1,000 rounds (Paul cut it from 10,000 on 2026-11-11). `./nightly.sh` runs the same tests in two steps, the engine matrix on its own, and prints how many tests each module ran, zeros included; record each run in `status/`. Don't run `-Pnightly`, `./nightly.sh` or the CAS test by hand unless Paul asks: the overnight run (below) runs them.
- Every test that needs S3 uses one store, chosen with `-Ps3=silo|ceph|aws` (default `silo`). `aws` also needs `-Pnuna.aws.profile=<CLI profile>`; the run makes its own buckets and role there and deletes them at the end.
- A new test that starts a container, waits on purpose or needs a multi-node cluster gets `@Tag("heavy")`: without it, the fast build fails wherever Docker is off. One that runs for minutes (load, soak, SLO, a sweep over every case) gets `@Tag("overnight")`.
- A test's container stops when its tests are done, not when the JVM exits. `catalog-server` keeps one Spring context at a time (`spring.properties`), and a container an initializer starts registers its stop with `StopWithContext`. The console tests' Chrome is shared by the classes on one server and stops when their context closes (`ConsoleBrowser.StopWithServer`, backlog 209). Before that (backlog 123), its JVM held every context's containers to the end, about 4 GB idle, which beside another module's stack filled Docker's memory and swap: waits on Kafka and Keycloak ran out.
- `gradle.properties` sets `org.gradle.workers.max=2`: two tasks run at once, so at most two modules are under test at a time. Not more: Docker has 8 GB, and a three-node cluster plus one other stack is what fits. The CockroachDB suite lives in `catalog-store-sql-raft`, which nothing depends on; no module's tests wait for another module's tests, so it runs beside the others instead of ahead of them. `./nightly.sh` runs its first step one module at a time (`--max-workers=1`, Paul, 2026-11-22): with two, Windows ran out of RAM and paged the Docker VM out (backlog 135). When a container-backed test loses a wait, check Windows too (`Get-Counter '\Memory\Available MBytes','\Memory\Pages Input/sec'`): the VM's own numbers do not show it being paged out.
- The nuna-demo stack (`demo/README.md`) runs in the same Docker Desktop and takes about 6 GB of it, 7.5 GB with its CDC leg, which leaves a heavy build's containers too little. Every test failure seen beside it has been a wait that ran out: the audit consumer's 30 s, Flyway's 30 s for a PostgreSQL connection, Kafka never reaching RUNNING, Ryuk unreachable. When a build fails that way, look for `nuna-demo` pods in `docker ps` before suspecting the change. Rerun once; if it fails again with the demo up, report the branch as ready and say the demo held Docker. The console's browser tests (`ConsoleBrowser`) refuse to start while the demo's pods run, saying so, since beside it they ran past half an hour; `-Pnuna.demo-beside` runs them anyway (backlog 209).
- **Tell every active agent when the demo goes down and when it comes back** (Paul, 2026-11-23; D49). No agent asks Paul first: when the work needs the demo down (tests that Docker cannot fit beside it, a rebuild to check a landing live), take it down, as long as every active agent is told. Whoever runs `demo/demo.sh down` or `up` (a rebuild is both) sends a message to every interactive session that `ListAgents` shows on this machine, busy or idle, before the down and again when `up` ends: which commit it runs, and whether `up` finished or where it stopped. Sessions shown offline or in the cloud are skipped. The overnight run takes the demo down at midnight and brings it up at the end of its run, and sends no message.
- **The overnight run** (Paul, 2026-11-14): `overnight.sh`, started at midnight by Windows Task Scheduler (the task `nuna overnight`, which `overnight-task.ps1 -Register` makes), when a file other than Markdown changed on `main` since its last run. In a worktree of its own (`.overnight/worktree` in the main checkout, detached at `main`'s tip and locked, so worktree cleanup leaves it alone; backlog 166; `.overnight/` is gitignored and holds everything a run makes) it runs the heavy build, the Ceph leg and `./nightly.sh`, then bites one at a time until 06:30, starting each night where the last stopped. One failing test stops none of it (Paul, 2026-11-23; backlog 164): the Gradle legs run with `--continue`, a test task that hangs fails at its timeout, and the bites run whatever the tests did, leaving out those whose test class failed or whose module hung that night. If the nuna-demo stack is running, it takes it down first (`demo/demo.sh down`) and rebuilds it at the end (`demo/demo.sh up`: fresh sample data, no CDC leg; the demo keeps no volumes, so nothing in it survives). At 07:00 a Claude scheduled task reads `.overnight/runs/<date>/summary.md`, records the run in `status/` and adds a backlog item for each failure no agent took.
  - **Agents for failing tests** (Paul, 2026-11-23; backlog 165): after each leg the run starts a headless Claude session for each module with a failing or hung test (at most 3 a night), in its own worktree, `.claude/worktrees/overnight-fix-<date>-<module>`. It claims or adds the backlog item and commits a fix while the run goes on, running no build; once the run has removed its lock, the run resumes each in turn to merge `main`, run the fast build and land, until 07:45. `.overnight/runs/<date>/agents.md` says what each did; the next run removes their worktrees and branches once their work is on `main`. They need the `claude` CLI signed in (`claude auth login`); when it is not, none starts and the summary says so.
  - While `.overnight/running` exists in the main checkout, Docker belongs to the run: start no build. A build that fails then failed for that reason; say so and rerun it after the run ends.
  - A nightly or heavy run by hand (`./nightly.sh`, `./heavy.sh`, in a worktree) holds the same lock (backlog 136): it writes `.overnight/running` in the main checkout with its pid when no live run holds it, and removes it when it ends. Under the overnight run, `nightly.sh` finds the run's lock and leaves it alone. An overnight run that starts while a run by hand holds the lock stops at once ("another overnight run is going"), and that night tests nothing.

## Landing

- Every landing uses the fast build, whatever the branch changes, except a branch whose every changed file is Markdown: it lands without a build (Paul, 2026-11-14). Nothing the build compiles, tests or applies is a `.md` file. Check with `git diff --name-only main...<branch>`. Don't run `-Pheavy` by hand: the overnight run does, every night that code changed.
- When the work is finished and its build is green (or it changes only Markdown), land it without asking Paul:
  1. Merge the current `main` into the branch and run the fast build, `./gradlew build` (skipped for a Markdown-only branch). If that merge conflicts, settle it there, in the branch, as the agent that did the work, and run the build again. Never resolve a conflict in the main checkout.
  2. Run `./land.sh <branch> "<message>"`, with a "Land …" message ending with the attribution line. It takes its turn with any other landing, merges into `main` with `--no-ff` only if `main` has not moved since step 1, so the merge cannot conflict, or has moved only in Markdown, which nothing the build reads, so step 1's build still holds (backlog 176). It writes `BACKLOG.md` into that merge and checks `git cherry`. If `main` has moved in other files, it refuses: go back to step 1. A Markdown merge that conflicts (two edits to one item) leaves `main` as it was: go back to step 1 too. If the main checkout has changes, another session is working there: report the branch as ready instead. After changing `land.sh`, run `./test-land.sh`: it checks these cases in a scratch repository.
  3. Release the backlog items the branch finished: `./backlog.sh release <n>`.
- **Batch branches that are ready together** (Paul, 2026-11-22; D47). When a session has two or more finished branches, land them in one go instead of one at a time, so the fast build runs once, not once per branch after each landing moves `main`:
  1. Cut a landing branch from the current `main` (`land-<date>-<what>`) and merge each ready branch into it. If two branches conflict, leave the later one out: the agent that did it settles the conflict in its own branch and it goes in the next batch. Never settle one in the landing branch.
  2. Run the fast build once on the landing branch (skipped if every changed file is Markdown). If it fails, find the branch that broke it (rebuild without each suspect, or read the failure), drop that branch from the batch and send it back to its agent.
  3. Land the landing branch with `./land.sh`, its message naming every item. If `main` has moved in files other than Markdown, merge it in, build again, and land.
  4. Check each original branch with `git cherry -v main <branch>` (no line starting `+`), release each item from its own worktree, and archive and delete each branch and the landing branch.
- After a branch lands, the session that started the agent archives it, which removes its worktree, then deletes the branch. Neither step needs asking.

## Bites

- A branch that adds a guarded check records its bite instead of running it: `bites/<milestone>/<id>.patch`, made with `git diff` of the broken check, headed by a `Module:` line and a `Test:` line (the test that must fail: `Class`, `Class#method` or `Class#method+method`). The two patches in `bites/M2/` show the form. Check it with `git apply --check`, then restore the file.
- The fast build fails when any recorded bite no longer applies (`:bitesApply`). A branch whose change moves the code a bite breaks records that bite again, with the same break, against its own code.
- `bites/run.sh` with no arguments runs every bite, in every folder under `bites/`: it applies each patch, runs its test with `-Pbites` (every test but CAS, so `overnight` tests can be selected too), expects a failure, reverts, and checks every tracked file's hash is restored.
- Its verdicts: BITES when a selected test fails on its own (an assertion, or the code under test throwing); NO BITE when they pass; SETUP when the run proves neither: the patch did not apply or compile, no test ran, or every failure came from starting the tests' fixtures (Gradle's `initializationError` or `executionError`, a Spring context that did not load, Testcontainers on the stack). SETUP fails the run as NO BITE does, and the last line counts it among the failures: "`<n> bites, <f> not biting or not restored (<s> of them SETUP)`". Read a SETUP bite's log in `build/bites/`, fix what stopped the fixtures (often the nuna-demo stack holding Docker) and run that bite again. A break that stops a Spring context loading is SETUP too: record such a bite against a test that fails on an assertion. `bites/test-run.sh` checks the verdicts against recorded result files, without Gradle or Docker; run it after changing `judge` or `tally`.
