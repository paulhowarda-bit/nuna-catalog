Nuna console · redesign for review

A console that shows what nuna does for every table, every night.

Three directions for the home screen, then 14 screens in the recommended one, built in its real palette, type and components, plus 3 phone screens and the design system. Every panel carries a pin that says where its data comes from. Nothing shown here claims a capability nuna lacks.

How to read the pins

1

Exists today. An existing route serves it; the note names the route.

2

Needs a new route. nuna has the data or the capability, but no route gives it to the console yet; the note names the route it needs.

3

Proposed. Beyond v1: decided in the backlog but not built, such as compaction on request. Drawn dashed and disabled, never as working.

Recommendation

Build A. Borrow B's answer-first headline and C's waterline for the sign-in screen.

People open a console many times a day, and a selling screen that slows the twentieth visit stops selling. A is calm where the work is frequent and expressive in one place only, the ice line, which is a real index of the estate rather than an illustration. It works in light and dark, it is plain CSS and SVG, and its numbers come from routes nuna has or can add cheaply.

  1. Real product first. A's hero is the estate itself: every table, its state, what the worker will do. Business buyers trust the real interface over illustration.
  2. Delight earned and rare. One 0.9 s entrance that reports success (last night's fixes), never motion on frequent actions.
  3. Honest by construction. Each figure on A's home names its route. C's strata would need byte totals nuna does not keep today.

2.1 · Sign-in

Sign-in: the one poster moment, then out of the way

Everyone sees this page once a session, so it can carry the product's four true claims and C's waterline. The form stays the existing OIDC flow with PKCE; the token box shows only when the server allows it.

https://nuna.example.com/ui/Illustrative data
1 nuna

The Iceberg catalog that keeps every table in shape and every change on record.

  • Four interchangeable stores. PostgreSQL, Oracle, MongoDB or CockroachDB, each passing the same fault-injection suite.
  • Maintenance that respects the rules. Snapshot expiry, orphan-file removal and compaction run under holds, freezes and recovery windows.
  • Every read, change and refusal audited. Changes reach a hash-chained archive kept at least five years.
  • Credentials per table. Short-lived storage credentials, scoped to the table's own prefix, only to callers allowed to read it.
