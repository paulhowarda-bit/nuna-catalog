Use Oracle

Prepare an Oracle schema, a service with Transaction Guard and the grants the catalog server needs, connect to it, and pass the safety self-check the server runs before it starts.

For platform operators and database administrators Tested nightly

Set nuna.database.backend: oracle. The server runs on a single instance, RAC or Exadata; nuna's tests run on Oracle Database Free 23.26.3. The server decides every lost commit answer itself, so it needs Transaction Guard and must never let the driver replay a transaction.

Before you begin

  • You can create users and services and grant system privileges, or you work with someone who can.
  • The primary has a Data Guard standby, synchronized in MAXIMUM AVAILABILITY or MAXIMUM PROTECTION.

Prepare the database

  1. Create the server's user, able to create tables in its own schema.

    CREATE USER nuna_catalog IDENTIFIED BY "…";
GRANT CREATE SESSION, RESOURCE TO nuna_catalog;
ALTER USER nuna_catalog QUOTA UNLIMITED ON USERS;

    The first server of a release creates the schema's tables, indexes, a procedure, a view and a Scheduler job in the user's schema.

  2. Grant what the server needs beyond its own schema.

    GRANT EXECUTE ON SYS.DBMS_APP_CONT TO nuna_catalog;
GRANT SELECT ON SYS.V_$DATABASE TO nuna_catalog;
GRANT SELECT ON SYS.V_$SERVICES TO nuna_catalog;
GRANT SELECT ON SYS.V_$PARAMETER TO nuna_catalog;
GRANT CREATE JOB TO nuna_catalog;

    DBMS_APP_CONT asks Transaction Guard for a lost commit's outcome. The three views feed the self-check. CREATE JOB lets the schema migration create the Scheduler job JOURNAL_PARTITIONS_AHEAD, which creates the journal's monthly partitions ahead of time, once a day.

    Not documented yet: whether RESOURCE covers creating the schema's view on every Oracle version. The tests' user also comes from the container image's own setup, so no test shows the least set of privileges.

  3. Create a service for the catalog with COMMIT_OUTCOME on and no FAILOVER_TYPE.

    DECLARE
  parameters DBMS_SERVICE.SVC_PARAMETER_ARRAY;
BEGIN
  parameters('COMMIT_OUTCOME') := 'true';
  parameters('RETENTION_TIMEOUT') := 86400;
  DBMS_SERVICE.CREATE_SERVICE('nuna_catalog', 'nuna_catalog', parameters);
  DBMS_SERVICE.START_SERVICE('nuna_catalog');
END;

    This is the form the tests use. FAILOVER_TYPE TRANSACTION or AUTO turns on Application Continuity, which can replay a transaction; the server refuses it.

  4. Keep JOB_QUEUE_PROCESSES above 0 and COMMIT_WAIT unset or WAIT.

Connect the server

The URL names the catalog's own service. Set the driver's read timeout, which bounds every wait on the database, in config: YAML keeps the key's case, and an environment variable would not.

config:
  spring:
    datasource:
      url: jdbc:oracle:thin:@//oracle.example:1521/nuna_catalog
      username: nuna_catalog
      hikari:
        data-source-properties:
          oracle.jdbc.ReadTimeout: 60000
  nuna:
    database:
      backend: oracle

The read timeout is in milliseconds. The password goes in the server's Secret as spring.datasource.password. Sessions must sort with NLS_SORT = BINARY, which follows the JVM's locale; the image's English locale gives it.

Not documented yet: TLS to Oracle (TCPS and a wallet). Nothing in the chart or the tests sets it up.

The safety self-check

Before it migrates the schema, each server checks these. Any finding stops it with The catalog's database is unsafe, so the server does not start, followed by each code: detail.

Oracle findings
CodeDetail the server logsWhat to do
ora.no-data-guardprotection level is level (mode mode); a Data Guard standby must be synchronized in MAXIMUM AVAILABILITY or MAXIMUM PROTECTIONRun a synchronized standby. The check reads the level, so a standby that fell behind shows here.
ora.no-transaction-guardservice name has COMMIT_OUTCOME value; the catalog service needs COMMIT_OUTCOME = TRUE for Transaction GuardSet COMMIT_OUTCOME on the service the URL names.
ora.commit-replayservice name has FAILOVER_TYPE value; Application Continuity can replay a transaction whose outcome the store must decide itselfRemove FAILOVER_TYPE from the service.
ora.commit-nowait…; COMMIT must wait until its redo is written (COMMIT_WAIT unset or WAIT)Unset COMMIT_WAIT or set it to WAIT.
ora.linguistic-sortNLS_SORT is value; names must sort and compare as bytes, so sessions need NLS_SORT = BINARY (the driver sets NLS_LANGUAGE from the JVM locale, and NLS_SORT follows it)Run the server with an English locale, or set NLS_SORT to BINARY for the user's sessions.
ora.journal-job-downEach cause with its fix, then Until the job runs, each month's first commit creates its own journal partition, 0.5 to 2.6 s on Free, which can pass the pool's read timeout and fail that commitFollow the fix it names (below).

The causes ora.journal-job-down names, each with its fix in the message:

  • JOB_QUEUE_PROCESSES is 0, so no Scheduler job runs: set it above 0
  • the Scheduler job JOURNAL_PARTITIONS_AHEAD is missing: create it again as migration V5 (V5__journal_partitions_ahead.sql) does
  • JOURNAL_PARTITIONS_AHEAD is BROKEN, disabled by Oracle after failing too often: fix why its runs fail (USER_SCHEDULER_JOB_RUN_DETAILS), then DBMS_SCHEDULER.ENABLE('JOURNAL_PARTITIONS_AHEAD')
  • JOURNAL_PARTITIONS_AHEAD is state and will not run again: drop it and create it again as migration V5 (V5__journal_partitions_ahead.sql) does
  • JOURNAL_PARTITIONS_AHEAD is disabled: DBMS_SCHEDULER.ENABLE('JOURNAL_PARTITIONS_AHEAD')
  • JOURNAL_PARTITIONS_AHEAD's last 2 runs failed, with the newest error, and the fix: DBMS_SCHEDULER.RUN_JOB('JOURNAL_PARTITIONS_AHEAD', use_current_session => FALSE) once the cause is fixed.

The migration file is catalog-store-oracle/src/main/resources/nuna/store/oracle/migration/V5__journal_partitions_ahead.sql in the source. nuna.database.allow-unsafe names findings the server starts despite; leave it empty in production (Database settings).

The server reports Oracle

As a platform operator, GET /management/v1/health/server?store=true shows "configured": "oracle" and an empty allowed list (Check the install).
