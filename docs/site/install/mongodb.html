Use MongoDB

Prepare a MongoDB replica set, database and user for the catalog server, pass the connection string in a Secret, and pass the safety self-check the server runs before it starts.

For platform operators and database administrators Tested nightly

Set nuna.database.backend: mongodb. The server needs a replica set, since it commits in transactions with majority writes; nuna's tests run on MongoDB 8.0.34. With MongoDB the server has no JDBC database at all, so spring.datasource stays empty and the chart does not ask for its URL.

Before you begin

  • A replica set with at least 3 voting, data-bearing members (arbiters do not count).
  • You can create users and change the cluster's default write concern, or you work with someone who can.

Prepare the replica set

  1. Set the default write concern to majority.

    db.adminCommand({setDefaultRWConcern: 1, defaultWriteConcern: {w: "majority"}})

    Leave writeConcernMajorityJournalDefault at true in the replica set's configuration, so majority writes are journaled.

  2. Create the server's user with readWrite on the catalog's database and clusterMonitor.

    db.getSiblingDB("admin").createUser({
  user: "nuna_catalog",
  pwd: passwordPrompt(),
  roles: [{role: "readWrite", db: "catalog"}, {role: "clusterMonitor", db: "admin"}]
})

    clusterMonitor lets the self-check read the replica set's configuration and default write concern, and lets the server find a lost commit's outcome. The server creates its collections and records its schema steps in a collection of its own; servers that start at the same moment are safe.

Connect the server

The connection string carries the password, so it goes in the server's Secret, as nuna.database.mongodb.uri. It must name the database and set socketTimeoutMS, which bounds every wait on the database. Set MONGO_USER and MONGO_PASSWORD in your shell first.

kubectl -n nuna create secret generic nuna-catalog-secrets \
  --from-literal=nuna.database.mongodb.uri="mongodb://$MONGO_USER:$MONGO_PASSWORD@db1.example,db2.example,db3.example/catalog?replicaSet=rs0&socketTimeoutMS=60000&authSource=admin&tls=true"
config:
  nuna:
    database:
      backend: mongodb
secrets:
  existingSecret: nuna-catalog-secrets

authSource=admin matches a user created in admin, as above, and tls=true is the driver's standard option for TLS.

Not documented yet: MongoDB with TLS and a private certificate authority. Nothing in the chart or the tests sets it up.

The safety self-check

Before it creates or migrates its collections, each server checks these. Any finding stops it with The catalog's database is unsafe, so the server does not start, followed by each code: detail.

MongoDB findings
CodeDetail the server logsWhat to do
mongo.not-replica-setthe server is not a replica set member; transactions and majority writes need a replica setRun a replica set and name it in replicaSet.
mongo.too-few-votersthe replica set has n voting data-bearing members; at least 3 are needed for a majority to survive losing oneAdd voting, data-bearing members.
mongo.weak-write-concernthe default write concern is concern (source) and writeConcernMajorityJournalDefault is value; the default must be majority and majority writes must be journaledSet the default write concern to majority and keep writeConcernMajorityJournalDefault true.

nuna.database.allow-unsafe names findings the server starts despite; leave it empty in production (Database settings).

The server reports MongoDB

As a platform operator, GET /management/v1/health/server?store=true shows "configured": "mongodb" and an empty allowed list (Check the install).
