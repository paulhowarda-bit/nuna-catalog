Connect an identity provider

Tell the catalog server which token issuers to trust and which claims hold the user, the groups and the client, name the platform operator and grant admin groups, and register the console's sign-in client, with a Keycloak example.

For platform operators

The server accepts only bearer tokens, JWTs signed by an issuer on its allow-list. It never signs anyone in itself: engines and scripts bring a token, and the console gets one from the identity provider with the authorization code flow and PKCE. Who may do what then follows from the token's groups (Identity and access).

Before you begin

  • You can create clients, scopes and groups at the identity provider, or you work with someone who can.
  • You can change the catalog server's Helm release (Install the catalog server with Helm).

Trust an issuer

  1. Make the identity provider put nuna's audience and the groups in its access tokens.

    Each token must carry an aud the server accepts (the examples use nuna-catalog), an exp, a claim with the user's id, a claim with the client's id, and a groups claim that is a list of group names as strings. A token that sends its groups elsewhere because there are too many (_claim_names, as Entra ID does) is refused.

  2. Add the issuer to config.nuna.security.issuers.

    config:
  nuna:
    security:
      issuers:
        - issuer: https://idp.example/realms/data
          jwks-uri: https://idp.example/realms/data/protocol/openid-connect/certs
          audiences: [nuna-catalog]
          algorithms: [RS256]
          user-id-claim: preferred_username
          groups-claim: groups
          client-id-claim: azp
      grant-admin-groups: [grant-admins]
      platform-operator-groups: [platform-operators]
    An issuer's fields, all required
    FieldMeaning
    issuerThe token's iss, exactly.
    jwks-uriWhere the server fetches the issuer's signing keys. The server does not read the discovery document, so name this URL itself.
    audiencesThe aud values the server accepts from this issuer.
    algorithmsThe signature algorithms it accepts, such as RS256 or ES256.
    user-id-claimThe claim that holds the principal's id, which audit records and maintenance-principals use.
    groups-claimThe claim that holds the groups.
    client-id-claimThe claim that holds the client's id, such as azp.

    List more than one issuer to trust several identity providers.

  3. Name the groups that hold the server-wide roles.

    Members of grant-admin-groups may grant and revoke in every catalog. Members of platform-operator-groups may read the health routes and the operator's management routes. The worker's principal goes in maintenance-principals (Install the maintenance worker). Every setting is on Security settings.

The server checks each token's issuer against the list, its signature against the issuer's keys with an allowed algorithm, its audience, and its exp and any nbf within nuna.security.clock-skew (60 s by default). It caches an issuer's keys for 5 minutes, waits at most 5 s for them, and fetches them at most twice in 30 s.

Register the console's client

The console signs people in through the identity provider's discovery document, at issuer/.well-known/openid-configuration, from the browser.

  1. Create a public client for the console.

    It has no secret, uses the authorization code flow with PKCE (S256), and its access tokens carry the audience and groups the server expects.

  2. Allow the console's page as a redirect URI and as a post-logout redirect URI.

    The page is https://nuna.example/ui/. Open the token endpoint to the console's origin, https://nuna.example (CORS). On sign-out the console sends the browser to the identity provider's end_session_endpoint with client_id and post_logout_redirect_uri; it keeps no ID token, so it sends no id_token_hint, and some identity providers then ask the person to confirm.

  3. Name the client in config.nuna.ui.oidc.

    config:
  nuna:
    ui:
      oidc:
        issuer: https://idp.example/realms/data
        client-id: nuna-console

    scopes defaults to [openid]. redirect-uri defaults to the console's own /ui/ address; set it if the browser reaches the console at another address. Leave nuna.ui.dev-token-login off: it adds a box for pasting a token, for local use only.

A Keycloak example

These clients come from the realm files the local kind install and the demo import into Keycloak 26.8.2. With them, the issuer is keycloak/realms/realm, the JWKS URL is the issuer plus /protocol/openid-connect/certs, and user-id-claim is preferred_username.

The console's client

{
  "clientId": "nuna-console",
  "publicClient": true,
  "standardFlowEnabled": true,
  "attributes": {
    "pkce.code.challenge.method": "S256",
    "post.logout.redirect.uris": "https://nuna.example/ui/*"
  },
  "redirectUris": ["https://nuna.example/ui/*"],
  "webOrigins": ["https://nuna.example"],
  "protocolMappers": [
    {
      "name": "nuna-audience",
      "protocol": "openid-connect",
      "protocolMapper": "oidc-audience-mapper",
      "config": {"included.custom.audience": "nuna-catalog", "access.token.claim": "true"}
    },
    {
      "name": "groups",
      "protocol": "openid-connect",
      "protocolMapper": "oidc-group-membership-mapper",
      "config": {"claim.name": "groups", "full.path": "false", "access.token.claim": "true"}
    }
  ]
}

full.path: false puts plain group names in the claim, such as trading-analysts, not /trading-analysts.

The maintenance worker's client

A confidential client with only the client-credentials grant (serviceAccountsEnabled), an optional scope nuna-catalog that the worker asks for, and the same audience and groups mappers. Keycloak fills the secret from an environment variable when it imports the realm.

{
  "clientId": "nuna-maintenance",
  "publicClient": false,
  "clientAuthenticatorType": "client-secret",
  "secret": "${NUNA_MAINTENANCE_CLIENT_SECRET}",
  "serviceAccountsEnabled": true,
  "standardFlowEnabled": false,
  "directAccessGrantsEnabled": false,
  "defaultClientScopes": [],
  "optionalClientScopes": ["nuna-catalog"]
}

Its service account signs in as service-account-nuna-maintenance; put that user in the worker's group. The audit tables writer needs a client of the same shape.

The server answers 401 without a token and 200 with one

curl -sS -i "$NUNA/v1/config" answers 401 with WWW-Authenticate: Bearer. With a token from the issuer, curl -sS "$NUNA/v1/config?warehouse=trading" -H "Authorization: Bearer $TOKEN" answers 200. The console's /ui/config.json, which needs no token, shows the oidc settings it signs in with.

If it fails

A refused token always gets the same 401 body; the reason goes only to the audit record.

{"error":{"message":"Not authorized: the bearer token is missing or was not accepted","type":"NotAuthorizedException","code":401}}
What you seeWhyWhat to do
401 with WWW-Authenticate: Bearer error="invalid_token"The token's issuer, signature, algorithm, audience, expiry or groups claim was not accepted.Decode the token and compare iss, aud, alg and the groups claim with the issuer's settings. Read the denial's audit record for the reason.
503 with The token could not be checked: its issuer's signing keys could not be fetched; retry laterThe server cannot reach jwks-uri.Check the network path and the URL. The answer carries Retry-After.
403 on a route for platform operatorsThe token's groups hold none of platform-operator-groups.Check the groups claim's values against the setting.
nuna.security.issuers names no trusted token issuer; the catalog accepts no request without one at start-upNo issuer is configured.Add one.
nuna.security.issuers[].jwks-uri of issuer at start-upA required field of that issuer is missing; the message names it.Set the field.
nuna.ui.oidc.issuer must be an http(s) URL, not …The console's issuer is not a URL.Use the issuer's URL.
The console's sign-in fails with a redirect error at the identity provider.The console's page is not an allowed redirect URI.Allow https://nuna.example/ui/ as a redirect URI and as a post-logout redirect URI.
