Uninstall nuna

Remove the three Helm releases, and know what stays behind: the database, the table files and audit archive in the object store, the bucket policies, and the Secrets and namespaces you made.

For platform operators

Uninstalling a release removes only the Kubernetes objects its chart made. The catalogs, tables and audit records live in the database and the object store, which nuna never deletes on its way out, so a new install pointed at them carries on where the old one stopped.

Before you begin

  • Engines and people have stopped using the catalog.
  • If the audit trail must be kept, check that the audit tables and any Object Lock archive are complete (Run the audit pipeline).

Remove the releases

  1. Uninstall the audit tables writer, if you run it.

    helm uninstall nuna-audit-tables -n nuna --wait

  2. Uninstall the maintenance worker.

    helm uninstall nuna-maintenance -n nuna --wait

    This also removes the Role, RoleBinding and Jobs' service account the chart made in the Jobs' namespace. Jobs the worker launched are not part of the release: each finished Job deletes itself a day after it ends, with its Secret and ConfigMap.

  3. Uninstall the catalog server.

    helm uninstall nuna-catalog -n nuna --wait

  4. Delete the Secrets, ConfigMaps and namespaces you made yourself.

    kubectl delete namespace nuna-compaction nuna

    Deleting a namespace deletes everything left in it, including Secrets you made with secrets.existingSecret in mind and any Job still there.

No nuna release remains

helm list -A shows none of nuna-catalog, nuna-maintenance and nuna-audit-tables.

What stays

What uninstalling leaves
WhereWhat
The databaseThe schema and every catalog, namespace, table pointer, grant, ref and audit outbox row. Drop the database or the user's schema to remove them.
The object storeEvery table's data and metadata files beneath the profiles' prefixes, including dropped tables not yet purged, and the audit tables' files.
The audit archiveAn Object Lock bucket keeps each object until its retention ends; no one can delete it sooner.
Bucket and user policiesThe delete policies you applied. While they stand, only the worker's identity can delete beneath the prefixes, and only it can change lifecycle rules (and, on AWS S3 and MinIO, the bucket policy).
The identity provider and store identitiesThe clients, groups, roles and users you made for nuna.

Deleting the database and the files cannot be undone

Once the database is dropped, nothing knows which files belong to which table. Remove the files only when no table or audit record in them must be kept, and the delete policies first, as the identity that applied them.

Not documented yet: an ordered teardown of the store's data that respects legal holds and retention. nuna has no command for it, so an uninstall that must honour holds needs the holds' records read first (Place and lift a legal hold).

If it fails

What you seeWhyWhat to do
A namespace stays Terminating.An object in it has a finalizer that has not finished.Read kubectl get namespace name -o yaml for what it waits on.
Deleting files beneath a prefix is refused.The delete policies are still applied.Remove the policies first, as the identity that applied them, or delete as the worker's identity.
