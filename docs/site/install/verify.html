Check the install

Check a new install end to end: the servers answer, the health routes show the database and its self-check, a token is accepted, a first table can be created, loaded with vended credentials and dropped, and the worker scans.

For platform operators Needs a platform operator

Before you begin

  • The catalog server and the maintenance worker are installed (Install the catalog server with Helm, Install the maintenance worker).
  • You have two tokens from the identity provider: one for a platform operator, and one for a group that holds create on the catalog (Get a token, Grant and revoke access).
  • NUNA and TOKEN are set as Use the APIs with curl describes. The steps say which token TOKEN holds.

Check that the servers answer

  1. See that every server is ready.

    kubectl -n nuna get pods -l app.kubernetes.io/instance=nuna-catalog

    Each pod is Running and 1/1 ready. The probes read /ui/config.json, so ready means the server is up and answering, not that the database is.

  2. Call the API without a token.

    curl -sS -i "$NUNA/v1/config"
    HTTP/1.1 401
WWW-Authenticate: Bearer
Content-Type: application/json

{"error":{"message":"Not authorized: the bearer token is missing or was not accepted","type":"NotAuthorizedException","code":401}}

Read the health routes

Two routes answer platform operators only; anyone else gets 403. Set TOKEN to the platform operator's token.

  1. Read one server's health, with its database.

    curl -sS "$NUNA/management/v1/health/server?store=true" \
  -H "Authorization: Bearer $TOKEN"

    The answer comes from whichever server the balancer picked. The figures object holds many more counts than the two shown here.

    {
  "server": {
    "id": "bb06eee7-159b-493c-a12b-918371ef3622",
    "name": "nuna-catalog-6c65d6c9dd-lw69w",
    "started-at": "2026-11-26T23:42:24.801033892Z"
  },
  "from": "2026-11-26T23:42:24.801033892Z",
  "to": "2026-11-27T03:35:03.069525959Z",
  "figures": {
    "commit": 3.0,
    "load": 3101.0
  },
  "store": {
    "configured": "postgresql",
    "backend": "PostgreSQL",
    "version": "18.7",
    "pitr-window-seconds": 604800,
    "self-check": {
      "at": "2026-11-26T23:42:22.744177875Z",
      "allowed": []
    }
  }
}

    store.backend and version are what the database reports, pitr-window-seconds is nuna.governance.pitr-window, and self-check.allowed lists each finding the server started despite because nuna.database.allow-unsafe named it. In production it is empty.

  2. Read the whole deployment's health.

    curl -sS "$NUNA/management/v1/health/catalog" \
  -H "Authorization: Bearer $TOKEN"

    The server that answers asks every other server through the headless Service. answered counts the servers that replied and silent those that did not; with three replicas, expect "answered":3,"silent":0. Health describes every field.

Create and drop a first table

Set TOKEN to the token whose group holds create on trading. The steps follow the local install's own smoke test.

  1. Read the catalog's configuration.

    curl -sS "$NUNA/v1/config?warehouse=trading" \
  -H "Authorization: Bearer $TOKEN"

    It answers 200.

  2. Create a namespace.

    curl -sS -X POST "$NUNA/v1/trading/namespaces" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace": ["install_check"]}'

  3. Create a table in it.

    curl -sS -X POST "$NUNA/v1/trading/namespaces/install_check/tables" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "events", "schema": {"type": "struct", "schema-id": 0, "fields": [
        {"id": 1, "name": "id", "required": true, "type": "long"},
        {"id": 2, "name": "at", "required": false, "type": "timestamptz"}]}}'

    The server writes the table's first metadata file to the object store with its own identity, so this step also checks the server's access to the store.

  4. Load the table with vended credentials.

    curl -sS "$NUNA/v1/trading/namespaces/install_check/tables/events" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Iceberg-Access-Delegation: vended-credentials"

    The answer's config holds s3.access-key-id, s3.secret-access-key and s3.session-token. This checks the STS role and its trust policy.

  5. Drop the table.

    curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE \
  "$NUNA/v1/trading/namespaces/install_check/tables/events" \
  -H "Authorization: Bearer $TOKEN"

    It prints 204. The table can be restored until its drop retention passes, and then the worker purges its files.

  6. Drop the namespace.

    curl -sS -o /dev/null -w '%{http_code}\n' -X DELETE \
  "$NUNA/v1/trading/namespaces/install_check" \
  -H "Authorization: Bearer $TOKEN"

    It prints 204.

To be sure every server works, not only the one the balancer picked, run the steps against each pod in turn with kubectl -n nuna port-forward pod/pod 8181:8181 and NUNA=http://localhost:8181.

Check that the worker scans

kubectl -n nuna logs deployment/nuna-maintenance --since=30m

The worker logs the prefixes it read from the server when it starts, then a line for each scan, every scan-interval (10 minutes by default), and a warning for each failed job. Compaction and orphan scans wait for the cleanup window.

The install is working

Every server is ready, the health route shows your database with no allowed findings, a token is accepted, a table was created, loaded with vended credentials and dropped, and the worker logs its scans with no failed jobs.

If it fails

What you seeWhyWhat to do
{"error":{"message":"only platform operators may call readServerHealth","type":"ForbiddenException","code":403}}The token's groups hold none of platform-operator-groups.Use a platform operator's token, or fix the setting (Connect an identity provider).
401 with a tokenThe token was not accepted.See Connect an identity provider.
400 on /v1/config without warehousenuna.rest.default-warehouse is not set.Name the catalog with ?warehouse=, or set the default.
403 on creating the namespaceThe token's groups hold no create on the catalog.Grant it (Grant and revoke access).
The load answers without s3.access-key-id, or an error about the storeThe server could not assume the STS role.Check sts-role and its trust policy (Set up object storage).
Fewer servers answered than runA server cannot reach another on port 8181 through the -peers Service.Check network policies between the pods.
The worker logs failed scans with 403Its principal or grant is missing.See Install the maintenance worker.
