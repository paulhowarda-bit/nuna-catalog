Set up object storage

Prepare the buckets and identities on AWS S3, Ceph or Silo, declare them as storage profiles, let the server vend credentials, and keep delete rights for the maintenance worker alone.

For platform operators Needs a platform operator

A storage profile names one object store, the root under which new tables go, and the prefixes the server may hand out credentials for. Each catalog uses one profile. The server writes metadata files with its own identity, and gives engines vended credentials: short-lived keys limited by a session policy to one table's location. No credentials the server vends can delete; only the maintenance worker deletes, with an identity of its own.

Before you begin

  • You can create buckets, users or roles, and bucket or user policies on the store.
  • You can change the catalog server's Helm release (Install the catalog server with Helm).
  • For the curl examples, NUNA and TOKEN are set as Use the APIs with curl describes, with a platform operator's token.

Prepare the store

Each store needs a bucket, the server's own identity, and the worker's own identity. The server's identity never deletes and must hold no right to change the bucket's policy or lifecycle rules.

  1. Create the bucket in the region the profile will name.

  2. Give the server an AWS identity of its own.

    On EKS, annotate the chart's service account with an IAM role (IRSA): serviceAccount.annotations: {eks.amazonaws.com/role-arn: …}. The AWS SDK's default chain then uses it for every profile that names no keys. Otherwise put the profile's access-key-id in config and its secret-access-key in the Secret.

  3. Create the role the server assumes to vend credentials.

    Its permissions allow s3:GetObject, s3:PutObject, s3:AbortMultipartUpload, s3:ListMultipartUploadParts and s3:ListBucket beneath the profile's prefixes; each vend narrows them further with a session policy. Its trust policy must let the server's identity call both sts:AssumeRole and sts:TagSession: every vend tags its session with whom it is for, and AWS refuses a tagged AssumeRole without the second. The profile names the role in sts-role.

  4. Create the worker's IAM role or user.

    Its own policies allow no s3:DeleteObject, s3:DeleteObjectVersion or s3:ListBucket in the bucket, and name no wildcard bucket: in the bucket's own account, the bucket policy you apply later grants all it needs. Its ARN is the profile's maintenance-principal.

  5. Choose a KMS key, if writes must be encrypted with one.

    An AWS S3 profile may name one customer-managed key ARN in kms-key, in the profile's region. The server writes metadata files with it, vended credentials may write only with SSE-KMS under exactly that key, and loads tell engines to use it. The key's policy must let the server's identity and the STS role use kms:GenerateDataKey and kms:Decrypt.

  1. Create the bucket as an operator's user, never the server's.

    A Ceph bucket's owner can always replace its policy, and on Ceph the generated policy denies lifecycle rules but not policy changes.

  2. Create a user for the server, and its keys.

    The profile's access-key-id goes in config, its secret-access-key in the Secret. The server calls the RADOS Gateway's STS on the store's own endpoint with these keys.

  3. Create the role the server assumes to vend credentials.

    A Ceph role ARN has an empty account, such as arn:aws:iam:::role/nuna-vend. As on AWS, its trust policy must allow the server's user both sts:AssumeRole and sts:TagSession. The profile names it in sts-role.

  4. Create a user for the worker.

    It owns no bucket, and no bucket ACL or user policy grants it, or all authenticated users, write. Its ARN, arn:aws:iam::tenant:user/uid with the tenant empty for none, is the profile's maintenance-principal.

  1. Create the bucket.

    Silo answers as MinIO does, so its profiles use the kind MINIO, and buckets are addressed by path.

  2. Create a user for the server, never the root user.

    MinIO's root user ignores every policy. The server's user name is the profile's access-key-id, its secret the secret-access-key in the Secret. A MinIO profile names no sts-role: the server vends from its own user through the store's STS.

  3. Create a user for the worker.

    It is not root, is in no group, uses keys of its own rather than a service account of a broader user, and will hold only the worker's policy. Its user name is the profile's maintenance-principal.

Declare the storage profile

Add the profile under config.nuna.storage.profiles and point a catalog at it. Secret keys go in the Secret as nuna.storage.profiles.name.secret-access-key.

config:
  nuna:
    storage:
      profiles:
        onprem:
          kind: S3
          endpoint: https://s3.eu-west-2.amazonaws.com
          region: eu-west-2
          table-root: s3://trading-eu-west-2/tables
          allowed-prefixes: [s3://trading-eu-west-2/tables]
          sts-role: arn:aws:iam::111122223333:role/nuna-vend
          maintenance-principal: arn:aws:iam::111122223333:role/nuna-maintenance
          kms-key: arn:aws:kms:eu-west-2:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab
      catalogs:
        trading:
          profile: onprem
          kms-key-set: trading-keys
          legal-entity: Example Markets Ltd
config:
  nuna:
    storage:
      profiles:
        onprem:
          kind: CEPH
          endpoint: https://s3.example
          table-root: s3://trading/tables
          allowed-prefixes: [s3://trading/tables]
          sts-role: arn:aws:iam:::role/nuna-vend
          access-key-id: nuna-catalog
          maintenance-principal: arn:aws:iam:::user/nuna-maintenance
      catalogs:
        trading:
          profile: onprem
          kms-key-set: trading-keys
          legal-entity: Example Markets Ltd
config:
  nuna:
    storage:
      profiles:
        onprem:
          kind: MINIO
          endpoint: https://s3.example
          table-root: s3://trading/tables
          allowed-prefixes: [s3://trading/tables]
          access-key-id: nuna-catalog
          maintenance-principal: nuna-maintenance
      catalogs:
        trading:
          profile: onprem
          kms-key-set: trading-keys
          legal-entity: Example Markets Ltd
A profile's fields
FieldMeaning
kindS3, MINIO or CEPH. Required.
endpointThe store's S3 endpoint, http(s)://host[:port]; https while nuna.storage.require-tls is on (the default). Required.
regionThe region; us-east-1 by default.
table-rootWhere new tables go. It must lie within an allowed prefix. Required.
allowed-prefixesWhere tables of this profile may live, and so where the server vends credentials. Two profiles' prefixes must not overlap. Required.
sts-roleThe role the server assumes to vend credentials. Required on S3 and CEPH; not used on MINIO.
access-key-id, secret-access-keyThe server's own keys. On AWS, leave both out to use the SDK's default chain (IRSA).
maintenance-principalThe worker's storage identity: an IAM ARN on S3 and CEPH, a user name on MINIO. A profile without one is not maintained, and its delete policy is listed as unprotected.
ca-bundleA PEM file of the private CA that signed the store's certificate (below).
kms-keyOne KMS key ARN, S3 only.

Credentials live nuna.storage.credential-lifetime, 30 minutes by default and 15 to 60 minutes at most. Every field and limit is on Storage settings. A catalog's profile, kms-key-set and legal-entity never change once the catalog exists (Create a catalog).

Trust a private certificate authority

If a private CA signed the store's certificate, put its PEM file in a ConfigMap, one key per store, and name it in the chart's storageCaConfigMap.name. The chart mounts it at /etc/nuna/storage-ca, and the profile's ca-bundle names the file there:

kubectl -n nuna create configmap nuna-storage-ca --from-file=onprem.crt=store-ca.pem
storageCaConfigMap:
  name: nuna-storage-ca
config:
  nuna:
    storage:
      profiles:
        onprem:
          ca-bundle: /etc/nuna/storage-ca/onprem.crt

That profile's S3 and STS clients trust the bundle beside the JVM's CAs; nothing else does. Vended credentials carry the endpoint, not the CA, so engines must trust the store through their own setup. Give the worker's chart the same ConfigMap and the store the same ca-bundle.

Keep delete rights for the worker

Once the servers run with the profile, a platform operator reads the delete policies the server generates and applies each one, as an identity that may. The server never applies them itself, since its own credentials would then need the right to undo them.

  1. Read the policies.

    curl -sS "$NUNA/management/v1/maintenance/delete-policies" \
  -H "Authorization: Bearer $TOKEN"

    GET /management/v1/maintenance/storage-setup gives the same policies per profile with the commands that apply them (Maintenance API).

  2. Apply each entry to its store.

    An entry of form bucket-policy. A bucket holds one policy, so merge its statements into any the bucket already has:

    aws s3api put-bucket-policy --bucket trading-eu-west-2 --policy file://policy.json

    An entry of form bucket-policy, applied at the store's endpoint:

    aws s3api put-bucket-policy --bucket trading --policy file://policy.json \
  --endpoint-url https://s3.example

    Two entries of form user-policy, since MinIO enforces no bucket policy on signed requests. Create the one with except and attach it to every user but the worker, the server's own included; create the one with to and attach it to the worker's user alone:

    mc admin policy create store nuna-no-delete no-delete.json
mc admin policy attach store nuna-no-delete --user nuna-catalog
mc admin policy create store nuna-maintenance maintenance.json
mc admin policy attach store nuna-maintenance --user nuna-maintenance

    Each policy denies delete beneath the profiles' prefixes to every principal but the worker, allows the worker to delete there and to list beneath its prefixes, and denies everyone else setting lifecycle rules on the bucket (and, on AWS S3 and MinIO, changing the bucket policy).

  3. Apply them again whenever a profile's prefixes change.

An engine's load carries vended credentials

Load a table with X-Iceberg-Access-Delegation: vended-credentials: the response's config holds s3.access-key-id, s3.secret-access-key and s3.session-token. With them, a write beneath the table succeeds and a delete answers 403. Check the install walks through it.

If it fails

The server checks every profile at start-up and refuses to start on the first problem, naming the profile.
