Upgrade nuna

Roll a new release of the catalog server one server at a time while the first new server migrates the database schema, then upgrade the maintenance worker and the audit tables writer.

For platform operators

An upgrade is a new image tag and a helm upgrade. The catalog server's Deployment rolls one new server at a time and stops no old server until its replacement is ready (maxSurge: 1, maxUnavailable: 0). The first new server migrates the schema before it reports ready, while the old servers keep serving.

Before you begin

  • The new images are built and pushed under a new tag (Container images). Helm sees no change in a new image under the same tag.
  • Read the release notes for the new version (Release notes), and compare the charts' values.yaml with your values for new or renamed keys.
  • The database has a recent backup or a point-in-time-recovery window that covers the upgrade.

Upgrade the catalog server

  1. Render the new chart with your values.

    helm template nuna-catalog deploy/helm/nuna-catalog -n nuna -f values.yaml \
  --set image.tag=0.2.0 > /dev/null

    A new required value stops it with an error naming the value.

  2. Upgrade the release.

    helm upgrade nuna-catalog deploy/helm/nuna-catalog -n nuna -f values.yaml --set image.tag=0.2.0

  3. Watch the roll.

    kubectl -n nuna rollout status deployment/nuna-catalog --timeout=20m

    The first new server runs the self-check, then the schema migrations. Other new servers that start while it migrates wait for its lock, for up to 5 minutes, and the start-up probe allows each server 10 minutes. Each old server pauses 5 s before it shuts down, so the Service stops routing to it first.

Upgrade the worker and the writer

Upgrade them after the catalog server, the same way:

helm upgrade nuna-maintenance deploy/helm/nuna-maintenance -n nuna -f worker-values.yaml --set image.tag=0.2.0
helm upgrade nuna-audit-tables deploy/helm/nuna-audit-tables -n nuna -f audit-tables-values.yaml --set image.tag=0.2.0

Both use the Recreate strategy, so the old pod stops before the new one starts and two never overlap. A compaction Job already running keeps its own image until it ends.

Every server runs the new version

kubectl -n nuna get pods -l app.kubernetes.io/instance=nuna-catalog -o jsonpath='{.items[*].spec.containers[0].image}' shows only the new tag, and Check the install passes.

Rolling back

Not documented yet: rolling back to an older release after its schema migrated. The migrations only move forward and no test runs an older server on a newer schema, so restoring the database from before the upgrade is the only path the code supports.

If it fails

What you seeWhyWhat to do
The roll stops with one new pod in CrashLoopBackOff.The new server refused to start; the old ones keep serving.Read its log. Fix the values and run helm upgrade again.
schema migration failedA migration failed on the database.Read the cause logged with it. The old servers keep serving the old schema.
A new server is killed by its start-up probe during the migration.The migration took longer than 10 minutes.Raise startupProbe.failureThreshold for the upgrade.
Nothing rolls.The tag did not change.Use a new tag, or run kubectl -n nuna rollout restart deployment/nuna-catalog.
