Requirements

What must exist before you install nuna: a Kubernetes cluster and Helm, one database, an object store, an identity provider, the network paths between them, and the resources each program asks for.

For platform operators

The three Helm charts run nuna's own programs only: the catalog server, the maintenance worker and the audit tables writer. The database, the object store, the identity provider, Kafka and any telemetry collector run elsewhere, and the charts' values name them.

A database

One database per deployment, which every catalog server of the release shares. nuna.database.backend names its kind (Database settings). The first server of a release creates or migrates the schema, so the server's role needs the right to create tables in it. Before it migrates, each server checks the database's safety settings and refuses to start on a finding, so a production database needs a synchronous standby or its equivalent (Choosing a database).

Tables' data and metadata files live in an S3-compatible object store, which Set up object storage prepares. Each storage profile names one of three kinds:

Besides the buckets, the store must hold two identities: the server's own, which never deletes, and the worker's, which alone may delete. Endpoints must use https unless nuna.storage.require-tls is turned off.

An identity provider

Every request to the server carries a bearer token (a JWT) from an OpenID Connect identity provider that the server trusts. Connect an identity provider sets it up. You need:

  • For each trusted issuer, its iss, its JWKS URL, the audience its tokens carry for nuna, and the claims that hold the user id, the groups and the client id.
  • A group for platform operators and a group for grant admins.
  • A confidential client for the maintenance worker, with the client-credentials grant and a scope.
  • A public client for the console, with the authorization code flow and PKCE.
  • For the audit tables writer, a client of its own with the client-credentials grant.

nuna's tests use Keycloak 26.8.2.

Kafka, if you want it

Kafka is optional. Without it, every audit record goes to the server's nuna.audit log only, and there is no audit topic or change stream. With nuna.audit.kafka-bootstrap-servers set, the server also sends each record to the audit topic and each change to the change stream (Audit settings). The audit tables writer reads either the topic or the server's log (Install the audit tables writer). nuna's tests use apache/kafka:4.2.2.

Sizes

Each chart asks for these by default. They are starting points, not measurements: size them on your own hardware.

Default replicas and resources
ProgramReplicasCPU requestMemory request and limit
Catalog server312 GiB

Each compaction Jobup to 2 at oncenone seta 2 GiB limit, with 1 GB of it for Spark's driver
Audit tables writer1250m1 GiB

Each Java program's heap is 75 % of its memory limit (-XX:MaxRAMPercentage=75), and it exits on running out of memory (-XX:+ExitOnOutOfMemoryError), so Kubernetes restarts it. Each of the server's metadata caches holds up to nuna.rest.metadata-cache-chars characters (Server settings).

Not documented yet: how large the database and the object store grow per table or per commit. No measurement records it.

Clocks

Keep the catalog servers' clocks in sync, within well under an hour. Before it deletes a file, the maintenance worker allows a one-hour margin for refs made around the time the deletion was recorded; servers further apart than that could let it delete a file a new ref still names. Token checks allow nuna.security.clock-skew (60 s by default) between the servers and the identity provider.
