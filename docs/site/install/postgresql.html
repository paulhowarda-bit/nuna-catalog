Use PostgreSQL

Prepare a PostgreSQL database and role for the catalog server, connect to it over TLS with a password or a client certificate, and pass the safety self-check the server runs before it starts.

For platform operators and database administrators Tested nightly

PostgreSQL is the default backend (nuna.database.backend: postgresql). nuna's tests run on PostgreSQL 18.7. The server keeps every catalog's state in one database, decides each commit there, and creates and migrates its own schema.

Before you begin

  • You can create roles and databases on the PostgreSQL cluster, and change its pg_hba.conf and settings, or you work with someone who can.
  • The cluster has a synchronous standby. Without one the server refuses to start (The safety self-check).
  • You know the database's point-in-time-recovery window, for nuna.governance.pitr-window.

Create the role and the database

  1. Create the catalog server's role, a member of pg_monitor.

    CREATE ROLE nuna_catalog LOGIN IN ROLE pg_monitor;

    pg_monitor lets the role see pg_stat_replication, which the self-check reads to count the standbys streaming in sync. Without it the role sees none, and the server refuses to start with pg.no-sync-standby. To sign in by password, give the role one; to sign in by client certificate, leave it without (below).

  2. Create the database, owned by the role.

    CREATE DATABASE catalog OWNER nuna_catalog;

    The first server of a release creates the schema's tables, a sequence, a function and a view in the role's current schema, and later releases migrate it. Owning the database gives the role the right to create them in public.

  3. Set the role's timeouts to 0.

    ALTER ROLE nuna_catalog SET statement_timeout = 0;
ALTER ROLE nuna_catalog SET idle_in_transaction_session_timeout = 0;

    The self-check reads both as the server's sessions see them, however they were set: a timeout can cancel a COMMIT's wait for the standby. The server bounds its own waits.

Connect the server

Set the JDBC URL and the role in the chart's config, and the password in the Secret as spring.datasource.password:

config:
  spring:
    datasource:
      url: jdbc:postgresql://db.example:5432/catalog?sslmode=verify-full
      username: nuna_catalog
  nuna:
    database:
      backend: postgresql
kubectl -n nuna create secret generic nuna-catalog-secrets \
  --from-literal=spring.datasource.password=…

sslmode=verify-full encrypts the connection and checks that the database's certificate names the URL's host. If a private certificate authority signed it, add its certificates as sslrootcert, as the next section does.

Sign in by a client certificate

The server can sign in by a client certificate instead of a password, so the role has no password to keep or leak.

  1. Have the certificate authority the database trusts for client certificates issue one to the server.

    That is the CA in the database's ssl_ca_file. The certificate's common name is the role, nuna_catalog, with extended key usage clientAuth.

  2. Let the role in by its certificate alone.

    Add a line to pg_hba.conf ahead of any password rule for the role, with the cluster's addresses, and reload the configuration:

    hostssl catalog nuna_catalog 10.0.0.0/8 cert

  3. Take the role's password away.

    ALTER ROLE nuna_catalog PASSWORD NULL;

  4. Convert the private key to unencrypted PKCS #8 DER.

    openssl pkcs8 -topk8 -inform PEM -outform DER -nocrypt -in client.key -out client.pk8

    From a .pfx file, take the certificate and key out first with openssl pkcs12 -in catalog.pfx -nokeys -out client.crt and openssl pkcs12 -in catalog.pfx -nocerts -nodes -out client.key.

  5. Put the three files in a Secret of their own.

    kubectl -n nuna create secret generic nuna-catalog-db-tls \
  --from-file=ca.crt=db-ca.pem \
  --from-file=client.crt=client.crt \
  --from-file=client.pk8=client.pk8
    The Secret's keys
    KeyWhat it is
    ca.crtThe certificates of the CA that issued the database's certificate, to its root (PEM). The driver checks the database against them.
    client.crtThe server's certificate, then any intermediate certificates (PEM).
    client.pk8Its private key, unencrypted, as PKCS #8 DER.

    Delete client.key and other copies of the key once the Secret holds it.

  6. Name the Secret in the chart and the files in the URL.

    config:
  spring:
    datasource:
      url: jdbc:postgresql://db.example:5432/catalog?sslmode=verify-full&sslrootcert=/etc/nuna/db-tls/ca.crt&sslcert=/etc/nuna/db-tls/client.crt&sslkey=/etc/nuna/db-tls/client.pk8
      username: nuna_catalog
databaseTls:
  secretName: nuna-catalog-db-tls

    The chart mounts the Secret at databaseTls.mountPath (/etc/nuna/db-tls), apart from the config tree, with mode 0440 (databaseTls.mode): the JDBC driver refuses a key file that others can read. Leave spring.datasource.password out of the server's Secret.

An expired certificate stops new connections

Renew the certificate before it ends: replace the Secret, then run kubectl -n nuna rollout restart deployment/nuna-catalog.

To check from the database side, as an administrator:

SELECT ssl, version, client_dn
FROM pg_stat_ssl JOIN pg_stat_activity USING (pid)
WHERE usename = 'nuna_catalog';

Every connection shows ssl true and the server's common name, and a connection as the role without the certificate is refused.

The safety self-check

Before it migrates the schema, each server checks the database's safety settings. Any finding stops the server before it changes anything in the database, with an error that starts The catalog's database is unsafe, so the server does not start and names each finding as code: detail, separated by semicolons. A self-check that cannot run stops it too.

PostgreSQL findings
CodeDetail the server logsWhat to do
pg.sync-commit-offsynchronous_commit is value; it must be on or remote_applySet synchronous_commit to on or remote_apply.
pg.no-sync-standbysynchronous_standby_names is 'names' and n standbys stream in sync or quorum state (the catalog role needs pg_monitor to see them)Set synchronous_standby_names and run a standby that streams in sync or quorum state. Make the role a member of pg_monitor.
pg.fsync-offfsync is value and full_page_writes is value; both must be onTurn both on.
pg.commit-cancel-timeoutstatement_timeout is value and idle_in_transaction_session_timeout is value; a timeout can cancel a COMMIT's wait for the standby, so both must be 0Set both to 0 for the role, as above.

nuna.database.allow-unsafe lists findings, by code, that the server starts despite, logging each as The catalog's database is unsafe, allowed by nuna.database.allow-unsafe: code: detail. It is empty by default. Only a test or demo database on one node sets it, as the local kind install does with [pg.no-sync-standby]. Leave it empty in production. A platform operator sees the findings allowed in GET /management/v1/health/server?store=true (Check the install).

The server reports PostgreSQL and no allowed findings

As a platform operator, GET /management/v1/health/server?store=true shows "configured": "postgresql", "backend": "PostgreSQL", the database's version, and an empty allowed list under self-check.

How the server uses the database

  • The schema is migrated with Flyway, on the first server of a release to start. Servers that start at the same moment wait for its lock for up to 5 minutes, and a schema step may run for up to 30 minutes.
  • The server keeps the journal of commits in monthly partitions and creates them ahead of time.
  • The connection pool must never replay a statement on its own: the server decides what a lost answer to a COMMIT means.
