Container images

Build the catalog server, maintenance worker and audit tables writer images from source, and push them to the registry your cluster pulls from.

For platform operators

nuna publishes no images. Each image holds one program's runnable jar, unpacked into Spring Boot's layers, so a code change re-ships only the small application layers: the 111 libraries make one layer of about 70 MB, and nuna's own code about 1 MB.

All three run as user and group 10001, write only to /tmp, and start with java org.springframework.boot.loader.launch.JarLauncher in /app. Only nuna-catalog exposes a port, 8181. The maintenance worker's compaction Jobs run a fourth image, a Spark image, which you build too if you want compaction.

Before you begin

  • You have a checkout of the nuna repository, JDK 25, and Docker or Podman (Requirements).
  • You can push to the registry your cluster pulls from. The examples call it registry.example and tag the images 0.1.0.
  • On a network with no outbound access, mirror the base images and Maven repositories first (Install on a locked-down network).

Build the Java images

  1. Build the three runnable jars.

    ./gradlew :catalog-server:bootJar :catalog-maintenance:bootJar :catalog-audit-tables:bootJar

    Each lands in its module's build/libs folder as *-exec.jar. The Dockerfiles copy only that file, so the build context sends nothing else.

  2. Build the catalog server's image.

    docker build -f deploy/image/Dockerfile \
  -t registry.example/nuna-catalog:0.1.0 catalog-server/build/libs

  3. Build the maintenance worker's image.

    docker build -f deploy/image/maintenance.Dockerfile \
  -t registry.example/nuna-maintenance:0.1.0 catalog-maintenance/build/libs

  4. Build the audit tables writer's image, if you will run it.

    docker build -f deploy/image/audit-tables.Dockerfile \
  -t registry.example/nuna-audit-tables:0.1.0 catalog-audit-tables/build/libs

Choose the base image

Every Dockerfile starts from ARG BASE_IMAGE=eclipse-temurin:25.0.5_8-jre-noble. To use another Java 25 runtime, such as one your organization approves, pass it to each build:

docker build -f deploy/image/Dockerfile \
  --build-arg BASE_IMAGE=registry.example/java-runtime:25 \
  -t registry.example/nuna-catalog:0.1.0 catalog-server/build/libs

The base image must have java on the path, which both build stages run, and sleep, which the catalog chart's 5 s pause before shutdown runs.

Build the Spark image for compaction

The worker launches each compaction as a Kubernetes Job that runs the repository's Spark image with rewrite_data_files. Its Dockerfile is catalog-tests-engines/images/spark/Dockerfile: it starts from apache/spark:4.1.4-scala2.13-java21-python3-ubuntu and downloads the Iceberg 1.12.0 Spark runtime and AWS bundle from Maven Central.

docker build -t registry.example/nuna-spark:0.1.0 catalog-tests-engines/images/spark

The image must keep JAVA_HOME and keytool, as the apache/spark images have: a Job for a table on a store with a private certificate authority builds its trust store with them. Its user id is 185, which the worker's compaction.run-as-user setting assumes by default.

Push the images

docker push registry.example/nuna-catalog:0.1.0
docker push registry.example/nuna-maintenance:0.1.0
docker push registry.example/nuna-audit-tables:0.1.0
docker push registry.example/nuna-spark:0.1.0

Then name them in each chart's values. The charts' image.tag defaults to the chart's appVersion, 0.1.0-SNAPSHOT, so set it. If the registry needs credentials, name a pull Secret in imagePullSecrets.

image:
  repository: registry.example/nuna-catalog
  tag: "0.1.0"
imagePullSecrets:
  - name: registry-pull

The worker takes the Spark image in its settings, not as a chart image: config.nuna.maintenance.compaction.image (Install the maintenance worker).

The image runs as user 10001

Inspect the image you built. It prints the user, the entry point and the exposed port:

docker image inspect registry.example/nuna-catalog:0.1.0 \
  --format '{{.Config.User}} | {{.Config.Entrypoint}} | {{.Config.ExposedPorts}}'
10001:10001 | [java org.springframework.boot.loader.launch.JarLauncher] | map[8181/tcp:{}]

If it fails

What you seeWhyWhat to do
The build's COPY *-exec.jar step finds no file.The jar was not built, or the build context is not its build/libs folder.Run the bootJar task for the module and pass its build/libs folder as the context.
Gradle cannot find a Java 25 toolchain.The build never downloads a JDK.Install JDK 25 on the build machine.
A pod stays in ErrImagePull or ImagePullBackOff.The cluster cannot pull the image: a wrong name or tag, or a registry that needs credentials.Check image.repository and image.tag, and set imagePullSecrets.
The pod is refused with a message about running as root.A base image or security context that overrides the user.Keep the Dockerfile's USER 10001:10001 and the chart's podSecurityContext.
