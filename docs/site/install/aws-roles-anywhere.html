Reach AWS with IAM Roles Anywhere

What is known about letting the catalog server and the maintenance worker reach AWS with a certificate through IAM Roles Anywhere instead of access keys, and what is not yet supported or tested.

For platform operators Not tested by nuna

IAM Roles Anywhere lets a workload outside AWS exchange an X.509 certificate for short-lived AWS credentials, through AWS's aws_signing_helper program. nuna has no setting for it. This page says what the code does and leaves the rest as gaps.

Before you begin

  • Read Set up object storage: the AWS S3 profile and the STS role it vends from.
  • On EKS, prefer IRSA: annotate the chart's service account with the role (serviceAccount.annotations). It needs no certificate.

What the code does

  • An AWS S3 storage profile that names no access-key-id uses the AWS SDK's default credential chain for the server's own identity. The same holds for a worker store with neither key under nuna.maintenance.storage.store.
  • The default chain reads, among other sources, a profile in an AWS config file that names a credential_process, which is how aws_signing_helper is usually wired in.
  • The images hold no aws_signing_helper, no AWS config file and no certificate, and the charts mount none.

What is not documented yet

Not documented yet: running the server or the worker with IAM Roles Anywhere. It would need an image with aws_signing_helper added, the certificate and key mounted from a Secret, an AWS config file naming them in credential_process, and AWS_CONFIG_FILE and AWS_PROFILE set through the chart's env. No test or install has tried this, so no step here is verified.

Not documented yet: whether the server's vending, which assumes the profile's sts-role with session tags, works from credentials that Roles Anywhere issued. The role those credentials belong to would need sts:AssumeRole and sts:TagSession on the vending role, as any server identity does.

nuna's own test suite signs in to AWS this way on a developer's machine, for the tests that run against real S3; that setup is for the tests, not for the server.

A vended load proves the server's AWS identity works

Whatever identity you give the server, a load with X-Iceberg-Access-Delegation: vended-credentials that returns s3.access-key-id shows the server reached STS and assumed the vending role (Check the install).

If it fails

What you seeWhyWhat to do
Vending fails with an AWS error that no credentials were found.The default chain found no source: no keys, no IRSA, no config file.Give the server one of them.
Vending fails with access denied on AssumeRole.The vending role's trust policy does not allow the server's identity both sts:AssumeRole and sts:TagSession.Allow both.
