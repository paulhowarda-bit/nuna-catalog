Install the maintenance worker

Give the maintenance worker its own identity in the catalog, the identity provider and each object store, then install it with the nuna-maintenance chart, with or without compaction Jobs.

For platform operators Needs a platform operator

The worker scans every catalog, expires snapshots, deletes files no table needs, purges dropped tables and, with compaction on, launches a Kubernetes Job per table that needs compacting (Maintenance). It is the only principal that can delete table files, so it signs in with an identity of its own everywhere. Install one release beside each catalog server release. It has no HTTP port.

Before you begin

  • The catalog server is installed (Install the catalog server with Helm), and the nuna-maintenance image, and the Spark image if you want compaction, are in your registry (Container images).
  • You can change the catalog server's release, and you are in one of its platform-operator-groups.
  • For compaction, you can create a namespace for the Jobs.
  • For the curl examples, NUNA and TOKEN are set as Use the APIs with curl describes.

Give the worker its identity

  1. Create a confidential client for the worker at the identity provider.

    It needs the client-credentials grant, a scope (the examples use nuna-catalog), the audience the server accepts, and a groups claim that puts its service account in a group of its own. The token's user id claim is the worker's principal id: with Keycloak and preferred_username, a client nuna-maintenance signs in as service-account-nuna-maintenance. Connect an identity provider shows the Keycloak client.

  2. Name the worker's principal in the catalog server's maintenance-principals.

    config:
  nuna:
    security:
      maintenance-principals: [service-account-nuna-maintenance]

    Upgrade the catalog server's release so the servers read it.

  3. Grant the worker's group write on every catalog it maintains.

    See Grant and revoke access. The worker always acts as itself, never for an end user. The credentials the server vends it read and write table files but never delete.

  4. Give the worker a storage identity of its own on each store.

    An IAM role or user on AWS S3, a user on Ceph, a user on MinIO or Silo, never the root user. Name it in each storage profile's maintenance-principal on the catalog server (Set up object storage). It needs s3:ListBucket and s3:DeleteObject beneath the profile's prefixes and no other right to list or delete.

  5. Apply the delete policies the server generates.

    curl -sS "$NUNA/management/v1/maintenance/delete-policies" \
  -H "Authorization: Bearer $TOKEN"

    Apply each entry once, as an identity that may, and again after any change to a profile's prefixes: a bucket policy on AWS S3 and Ceph, two user policies on MinIO. They take delete from every other principal, the server's own included, and give the worker its two rights. The server never applies them itself. Set up object storage gives the commands.

Install the release

  1. Create the Jobs' namespace, if you want compaction.

    kubectl create namespace nuna-compaction

    Use it for the Jobs alone, never the catalog server's or the worker's: a pod may run as any service account and mount any Secret of its namespace.

  2. Create the worker's Secret.

    kubectl -n nuna create secret generic nuna-maintenance-secrets \
  --from-literal=nuna.maintenance.token.client-secret=… \
  --from-literal=nuna.maintenance.storage.onprem.secret-access-key=…

    Each key is a property name, as for the catalog server. On AWS with IRSA, leave out the store's keys and annotate the chart's service account instead (serviceAccount.annotations).

  3. Write the values file.

    image:
  repository: registry.example/nuna-maintenance
  tag: "0.1.0"
config:
  nuna:
    maintenance:
      catalog-uri: http://nuna-catalog.nuna.svc:8181/
      cleanup-window:
        start: "22:30"
        end: "04:00"
        zone: Europe/London
      token:
        endpoint: https://idp.example/realms/data/protocol/openid-connect/token
        client-id: nuna-maintenance
        scope: nuna-catalog
        audience: nuna-catalog
      storage:
        onprem:
          kind: ceph
          endpoint: https://s3.example
          access-key-id: nuna-maintenance
      compaction:
        image: registry.example/nuna-spark:0.1.0
        namespace: nuna-compaction
secrets:
  existingSecret: nuna-maintenance-secrets
    • cleanup-window has no default: compaction and orphan scans start only inside it, in local times of zone. Quote the times in YAML; the chart quotes them again in the worker's own file.
    • Each store under storage names its kind (s3, minio or ceph) and its endpoint exactly as the catalog server's profiles on that store write theirs: the worker serves a profile with the one store of the same kind and endpoint. The prefixes come from the server at each scan, never from here.
    • Compaction is off until compaction.image is set. It needs the client-credentials grant with a scope, since each Job signs in with it, not token.file.
    • The Jobs run in another namespace, so name every in-cluster service in catalog-uri, the token endpoint and the store endpoint as service.namespace.svc.

  4. Install the release.

    helm install nuna-maintenance deploy/helm/nuna-maintenance -n nuna -f worker-values.yaml

The worker logs a line per scan

kubectl -n nuna logs deployment/nuna-maintenance shows the prefixes it read from the server and a line for each scan, every scan-interval (10 minutes by default), with no failed jobs. A platform operator's GET /management/v1/maintenance/storage-setup shows each profile's delete policy and any store the worker's last report says it does not reach.

What the chart creates

  • A Deployment of one replica with the Recreate strategy, so two workers never overlap during an upgrade, and a grace period of 70 s.
  • A ConfigMap with application.yaml from config, a Secret when secrets.values is set and secrets.existingSecret is not, and a ServiceAccount, whose token is mounted only when compaction is on.
  • With compaction.image set, in the Jobs' namespace: a Role name-compaction that may get and create Jobs and create Secrets, and create ConfigMaps when a store names a ca-bundle; a RoleBinding of it to the worker's service account; and the Jobs' service account, nuna-compaction by default, with no rights and no token mounted.

What the chart refuses

The chart's refusals
Error
config.nuna.maintenance.catalog-uri is required: the catalog the worker maintains
config.nuna.maintenance.storage needs at least one store: the worker's own storage identity on it
config.nuna.maintenance.storage.name.kind is required: the worker serves a catalog storage profile with the store of its kind and endpoint, written as the profile writes it, and the same for endpoint
config.nuna.maintenance.storage.name.prefixes: the worker reads its prefixes from the catalog's storage profiles at each scan; name the store's kind and endpoint instead (deploy/README.md, "Delete rights")
config.nuna.maintenance.cleanup-window.start is required: the nightly window in which compaction and orphan scans run (start and end as local times such as "01:00", zone a named zone such as Europe/London), and the same for end and zone
config.nuna.maintenance.compaction.namespace is required when compaction runs: a namespace for the Jobs alone, created beforehand
config.nuna.maintenance.compaction.namespace must not be the release's namespace: a pod may run as any service account and mount any Secret of its namespace, the worker's included
config.nuna.maintenance.compaction.job-service-account is required when compaction runs

If it fails

What you seeWhyWhat to do
A chart error from the table above.A required value is missing or wrong.Set it and run the command again.
nuna.maintenance.token: set file, or endpoint, client-id and client-secretThe worker has no way to sign in.Set the client-credentials grant, with the secret in the Secret.
nuna.maintenance.token: set exactly one of file and endpointBoth are set.Keep one.
The worker refuses to start because the cleanup window's start is a number.An unquoted 22:30 in YAML 1.1 is a number in base 60.Quote the times.
Scans get 403 from the server.The worker's principal is not in maintenance-principals, or its group holds no write on the catalog.Check the token's user id claim against maintenance-principals, and the grant.
A Job fails with UnknownHostException.A short Service name does not resolve from the Jobs' namespace.Use service.namespace.svc.
A Job fails with PKIX path building failed, or Unable to execute HTTP request: Network is unreachable.The Job does not trust the store's certificate.Name the store's ca-bundle and give the chart the same storageCaConfigMap.name as the catalog server.
