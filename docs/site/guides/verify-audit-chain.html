Verify the audit chain

Check that an audit record holds its place in its server run's hash chain in the archive, and read what an unverified or missing record means.

For auditors Needs select on the audit catalog Audited

Each catalog server run numbers its audit records and chains them: every record carries its number in the run and the hash of the record before it. The audit tables writer copies each record, byte for byte, into the archive bucket, in segments locked against change until their retention ends. A check walks every chain hourly. A record that verifies proves it was archived as written, and that every earlier record of its run is there.

Before you begin

  • The archive is configured: the server's nuna.audit.archive.bucket, and the audit tables writer's archive.bucket with the source otlp (Audit tables writer settings). Without it the console says No archive is configured on this server, so no chain is checked.
  • Your groups hold select on the audit catalog, as for the feed (Query the audit trail).

Check the whole archive

On the console's Audit page, the Hash chain panel (checked hourly) gives the last check's verdict: Whole at a time, Records missing, Not intact or Not checked yet. It lists how many Runs were verified, the newest Checkpoints, the Archive location and the Last check, and, under What was found, each chain with a problem. With curl, GET /management/v1/audit/archive answers the same.

Check one record

  1. Find the record on the Audit page and select Show record.

    Its line carries a pill: Chain verified, Not verified yet, Earlier record missing or Missing from archive. Hash chain in the record says the same in words.

  2. Under Archive, select Check this record.

    The console reads the record's segment from the archive and shows Hash matches or Hash does not match, its place in its run's chain, the hashes before and after it, and the segment's key. A record the archive has not yet received shows Not archived yet.

Take the record's log-run, log-seq and event-id from the audit feed, then ask for its place in the chain.

curl -sS "$NUNA/management/v1/audit/chains/3f9b2c71-5e0a-4d86-a1c4-7b2d9e60f415/records/4812?event-id=0b7e5d1c-6a2f-4e39-8c41-5f2a9d7e3b10" \
  -H "Authorization: Bearer $TOKEN"
{
  "chain": "3f9b2c71-5e0a-4d86-a1c4-7b2d9e60f415",
  "log-run": "3f9b2c71-5e0a-4d86-a1c4-7b2d9e60f415",
  "log-seq": 4812,
  "event-id": "0b7e5d1c-6a2f-4e39-8c41-5f2a9d7e3b10",
  "archived": true,
  "position": 4812,
  "hash": "…",
  "previous-hash": "…",
  "next-hash": "…",
  "link-holds": true,
  "verified": true,
  "checked-at": "2026-11-25T18:00:00Z",
  "segment": {"key": "audit/runs/3f9b2c71-5e0a-4d86-a1c4-7b2d9e60f415/0000000000000004801.log", "first-position": 4801, "last-position": 4900}
}

link-holds says whether the record's hash of the one before it matches; verified, whether the hourly check has verified the chain through it.

The response above follows the route's field names; it was not read from a running server, since the local demo has no archive. Which fields an unarchived record's answer carries was not confirmed.

What each state means

A record's chain states
In the consoleIn the feed (chain.status)Meaning
Chain verifiedverifiedThe check verified the record with every earlier record of its server run.
Not verified yetunverifiedThe check has not yet reached the record. It verifies at a later check.
Earlier record missingunverified, with missing below the record's numberRecords earlier in its run never reached the archive. The record stays unverified until they arrive, which may be never.
Missing from archiveunverified, with missing covering the record's numberThe archive does not have this record.
No pillno-archive or no-placeNo archive is configured, or the record cannot be placed: the Kafka copy does not say which server run logged it, or an older server did not number it.

A missing or mismatched record is evidence

Hash does not match, Not intact or a record missing from the archive means the archive does not hold what the server wrote. Keep the record's run, number and segment key, and report it to whoever owns the audit archive.

Records that are only Not verified yet need nothing: the next hourly check reaches them.

The record is proven

Hash matches with the check having verified the chain through it: the archive holds the record as written, with every record of its run before it.

If it fails

What you see, why, and what to do
What you seeWhyWhat to do
503 The audit archive is not configured on this server (nuna.audit.archive.bucket)The server has no archive bucket set.Ask an operator to configure the archive.
503 The audit archive cannot be read now; retry laterThe archive bucket did not answer.Retry.
400 number must be the record's number in its run, a whole number from 1, not …The number is not a positive whole number.Use the record's log-seq.
400 run must be a UUID, not … or event-id must be a UUID, not …The run or event id is malformed.Copy log-run and event-id from the feed.
