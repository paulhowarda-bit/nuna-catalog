Drop, restore and purge a table

Drop a table or view, restore it within the undrop window with its id, grants and history, and know when and how the maintenance worker purges it.

For data engineers and data stewards Needs modify to drop, create to restore Audited

Every drop is soft. A dropped table keeps its id, its files, its grants and its journal, and its name is free at once. Until the undrop window closes, nuna.rest.drop-retention after the drop (default 30 days), it can be restored. After that the maintenance worker purges it: it deletes the table's files with its own storage identity and marks the table purged, keeping its record as history.

Before you begin

  • Dropping needs modify on the table or view. Restoring needs create on the namespace it was dropped from. Listing dropped tables needs describe on the namespace.
  • Drops happen on main; a branch or tag refuses them.
  • For the curl examples, NUNA and TOKEN are set as Use the APIs with curl describes.

Drop the table

curl -sS -X DELETE "$NUNA/v1/trading/namespaces/equities/tables/orders" \
  -H "Authorization: Bearer $TOKEN"

The server answers 204. purgeRequested=true is ignored: the drop is soft whatever it says. A view is dropped at …/views/<name>.

DROP TABLE trading.equities.orders;

DROP TABLE … PURGE is soft too.

A catalog branch or tag made before the drop still reads the table under its old name, and its purge waits until no ref names it.

Restore the table

The console has no restore control; restore with the API. First find the table's id among the namespace's dropped tables.

  1. List the namespace's dropped tables and views.

    curl -sS "$NUNA/management/v1/catalogs/trading/namespaces/equities/dropped" \
  -H "Authorization: Bearer $TOKEN"
    {
  "dropped": [
    {
      "id": "9a3e51c7-0d24-4b8f-b6e1-52c7a9f03d18",
      "catalog": "trading",
      "kind": "table",
      "name": "orders",
      "namespace-id": "…",
      "state": "dropped",
      "dropped-at": "2026-11-25T16:20:41.007Z",
      "purge-after": "2026-12-25T16:20:41.007Z",
      "location": "s3://lake-trading/tables/9a3e51c7-0d24-4b8f-b6e1-52c7a9f03d18"
    }
  ]
}

  2. Restore it by its id.

    curl -sS -X POST "$NUNA/management/v1/catalogs/trading/objects/9a3e51c7-0d24-4b8f-b6e1-52c7a9f03d18/undrop" \
  -H "Authorization: Bearer $TOKEN"

    The server answers 200 with the table, now "state": "active". If another table has taken the name, send {"name": "orders_restored"} as the body to restore it under another name. It comes back in the namespace it was dropped from.

Registering the metadata file a dropped table left at also restores it, as an undrop (Register an existing table).

Purge

Nobody purges by hand. Once a dropped table's purge-after has passed, the maintenance worker claims its purge, deletes its files and completes the purge. Only a maintenance principal may claim or complete a purge, and each server allows at most a set number of purges a minute. From the claim on, the table cannot be restored.

A purge is refused while a legal hold or DR freeze covers the table, a namespace above it or the catalog, and waits while a catalog branch or tag names the table.

A purge cannot be undone

Once purged, the table's files are gone. To keep a table past the undrop window, restore it before purge-after, or place a legal hold on it (Place and lift a legal hold).

Unregistering is different from dropping: POST /v1/trading/namespaces/equities/tables/orders/unregister (needs modify) stops nuna tracking the table and deletes nothing, ever. The table is never purged; registering its metadata file again brings it back.

The table is back

After a restore the table reads as it did before the drop, with its grants and history. The audit trail holds a nuna.catalog.drop record for the drop and a nuna.catalog.undrop record for the restore.
