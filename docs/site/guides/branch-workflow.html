Write, audit and publish with a branch

Make a catalog branch, write to it from an engine, check what changed, then merge it into main in one transaction or delete it.

For engine users and data stewards Needs create on the catalog Audited

A catalog branch is the whole catalog at one point, taking commits of its own. Engines write to it as a warehouse of its own, trading@dev, and main does not move. When the change is checked, a merge moves every table the branch changed onto main in one transaction, or none of them. This is write-audit-publish for a whole catalog; Catalog branches and tags explains how it works.

Before you begin

  • Making, renewing, merging and deleting a branch need create on the catalog. Listing branches, reading them and previewing a merge need any grant in the catalog.
  • Writing to the branch needs write on the table for a change of data, or modify for a change of schema, partitioning or properties. A grant of write or modify may name one branch, so that a group can commit there and nowhere else (Grant and revoke access).
  • The merge needs, on each table it moves, what a commit of the same change on main would need: write for data alone, modify for a change of definition. A view always needs modify.
  • The tables you will change exist on main. A branch takes commits to existing tables and views only; creating, dropping and renaming happen on main.
  • Your engine is set up to reach nuna (Spark, Trino, PyIceberg). For the curl examples, NUNA and TOKEN are set as Use the APIs with curl describes.

Make the branch

  1. Select Branches and tags in the rail.

  2. Select Make a branch or tag.

    The console offers the button only when your groups hold create on the catalog. Without it, the page says what making a branch needs.

  3. Choose Branch, enter its name, and leave From at main, as it is now.

    Under Purpose (optional), say why the branch exists in one line. Everyone who can see the catalog's branches and tags reads it, and the audit record keeps it.

  4. Select Make it.

    The dialog shows the server's answer and links to the branch's page and to reading the catalog through it.

curl -sS -X POST "$NUNA/management/v1/catalogs/trading/refs" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "dev", "kind": "branch", "from": "main", "description": "Restated fills for 2026-11-25"}'

The server answers 201 with the branch. from is optional and defaults to main.

{
  "id": "6f1c2a9e-3b7d-4c52-9a10-2d8e4f6b7c31",
  "name": "dev",
  "kind": "branch",
  "from": "main",
  "created-at": "2026-11-26T09:12:40.118Z",

A ref's name may not contain @ or /, may not be main, and compares without case. A branch expires 30 days after it was made, last committed to or renewed, and never later than 180 days after it was made; these are the defaults of nuna.refs.branch-idle-expiry and nuna.refs.branch-max-life.

Write to the branch

Point an engine catalog at the warehouse trading@dev. One engine catalog reads one ref, so keep a second catalog on trading to compare with main. Every write through it lands on the branch.

spark.sql.catalog.dev=org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.dev.type=rest
spark.sql.catalog.dev.uri=https://nuna.example/
spark.sql.catalog.dev.warehouse=trading@dev
spark.sql.catalog.dev.token=…
spark.sql.catalog.dev.header.X-Iceberg-Access-Delegation=vended-credentials
spark.sql.catalog.dev.io-impl=org.apache.iceberg.aws.s3.S3FileIO
DELETE FROM dev.equities.fills WHERE trade_date = DATE '2026-11-25';
INSERT INTO dev.equities.fills SELECT * FROM trading.equities.fills_restated;
connector.name=iceberg
iceberg.catalog.type=rest
iceberg.rest-catalog.uri=https://nuna.example
iceberg.rest-catalog.warehouse=trading@dev
iceberg.rest-catalog.security=OAUTH2
iceberg.rest-catalog.oauth2.token=${ENV:NUNA_TOKEN}
iceberg.rest-catalog.vended-credentials-enabled=true
iceberg.rest-catalog.nested-namespace-enabled=true
DELETE FROM trading_dev.equities.fills WHERE trade_date = DATE '2026-11-25';
from pyiceberg.catalog import load_catalog

dev = load_catalog("dev", type="rest", uri="https://nuna.example", warehouse="trading@dev",
                   token=token, **{"header.X-Iceberg-Access-Delegation": "vended-credentials"})
fills = dev.load_table("equities.fills")
fills.append(restated)  # a pyarrow Table

On the branch, a table's metadata file is the branch's own, and its version on the branch starts at 1. Every rule of main applies to each commit (legal holds, the minimum snapshot age and the rest), except a DR freeze, which binds only the merge. Each commit that lands moves the branch's expiry ahead. A branch may change at most nuna.refs.max-merge-tables tables and views (default 100), so that one transaction can merge them.

Check what changed

Compare the branch with main from your engine: query the same table through both catalogs. The branch itself lists the tables it changed.

  1. Open the branch from Branches and tags.

    Its Changes tab lists each table and view the branch changed, with its commits on the branch and on main since the point.

  2. Select Read on the branch's line to browse the catalog through it.

    The header's Reading control names the ref every catalog, namespace, table and view page reads, and switches back to main.

curl -sS "$NUNA/management/v1/catalogs/trading/refs/dev" \
  -H "Authorization: Bearer $TOKEN"
{
  "id": "6f1c2a9e-3b7d-4c52-9a10-2d8e4f6b7c31",
  "name": "dev",
  "kind": "branch",
  "from": "main",
  "created-at": "2026-11-26T09:12:40.118Z",
  "created-by": "trading-etl",
  "description": "Restated fills for 2026-11-25",
  "expires-at": "2026-12-26T09:31:02.540Z",
  "max-expires-at": "2027-05-25T09:12:40.118Z",
  "expiring": false,
  "cut-at": "2026-11-26T09:12:40.118Z",
  "changed": [
    {"namespace": ["equities"], "name": "fills", "kind": "table", "cut-version": 4, "version": 2}
  ],
  "may": {"create": true}
}

cut-version is main's version of the table at the point; version is its version on the branch. created-by is shown only to a caller holding create on the catalog.

Preview the merge

A preview, the merge's dry run, writes nothing. It says what the merge would answer now, which tables would move or conflict, and whether you hold what the merge needs.

Open the branch's Merge tab. Under Table by table it draws each table's commits on the branch and on main since the point; under In one transaction it lists what the merge would do, with the button Merge @dev into main. The button is off while a table conflicts or your groups lack a right the merge needs, and the page says which.

curl -sS -X POST "$NUNA/management/v1/catalogs/trading/refs/dev/merge?dry-run=true" \

answer is what the merge would answer now: {"code": 200}, or the error's code, type and message. A table that conflicts has "moves": false and a conflict saying why. hidden counts the tables you may not see, which are never named.

How each table is judged:

  • If main has not moved since the point, main takes the branch's version.
  • If main moved only by its own maintenance (compaction and manifest rewrites, which add only replace snapshots, and snapshot expiry), the table still moves and is marked rebased.
  • If main changed the table in any other way (new data, a schema, partitioning, sort order, properties, an Iceberg ref made or moved), or dropped it, or replaced a view, the table conflicts.

Merge into main

  1. On the branch's Merge tab, select Merge @dev into main.

    The dialog lists each table with its version on main now and after.

  2. Select Merge into main.

    Focus starts on Cancel, so one press of Enter never merges. After the merge the page shows What main has now: each table's version before and after.

curl -sS -X POST "$NUNA/management/v1/catalogs/trading/refs/dev/merge" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: merge-dev-2026-11-26"
{
  "ref": {
    "id": "6f1c2a9e-3b7d-4c52-9a10-2d8e4f6b7c31",
    "name": "dev",
    "kind": "branch",
    "from": "main",
    "created-at": "2026-11-26T09:12:40.118Z",
    "created-by": "trading-etl",
    "description": "Restated fills for 2026-11-25",
    "expires-at": "2026-12-26T09:31:02.540Z",
    "max-expires-at": "2027-05-25T09:12:40.118Z",
    "expiring": false,
    "cut-at": "2026-11-26T09:12:40.118Z"
  },
  "tables": [
    {
      "namespace": ["equities"],
      "name": "fills",
      "kind": "table",
      "cut-version": 4,
      "main-version": 4,
      "branch-version": 2,
      "moves": true,
      "version": 5,
      "rebased": false,
      "metadata-location": "s3://…/metadata/00005-….metadata.json"
    }
  ]
}

The Idempotency-Key header is optional; with it, a retry after a lost answer gets the first answer again instead of a second merge.

The merge ends the branch: its name is free and trading@dev answers 404. For each table, main writes its own copy of the branch's metadata at its next version. The audit trail gets one nuna.catalog.ref record for the merge and one nuna.catalog.commit record for each table on main.

Or delete the branch

If the change is not to reach main, delete the branch. Its changes are lost; main never took them.

On the branch's page, select Delete, then Delete @dev in the dialog Delete the branch @dev.

curl -sS -X DELETE "$NUNA/management/v1/catalogs/trading/refs/dev" \
  -H "Authorization: Bearer $TOKEN"

The server answers 204.

Deleting a branch loses its unmerged changes

The name is free at once, and the branch's own table pointers go with it. Files that no other ref names are left to the maintenance worker's cleanup.

A branch you neither merge nor delete expires. Renew it before then from its page (Renew) or with POST /management/v1/catalogs/trading/refs/dev/renew; a renewal moves the expiry ahead by nuna.refs.branch-idle-expiry, never past the branch's whole life.

Main now holds the branch's change

Querying the table through the trading catalog returns what the branch held. The table's History tab on main shows the new version, and the catalog's audit feed shows the merge and one commit per table, each with the merge's request id.
