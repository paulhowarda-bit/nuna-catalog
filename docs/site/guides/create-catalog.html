Create a catalog

Declare a catalog in the server's settings with its storage profile, roll the servers so they create it, and grant its first groups access.

For platform operators and grant admins Needs a grant admin Audited

There is no API or console action that creates a catalog. The server creates each catalog named under nuna.storage.catalogs when it starts, if the database does not hold it yet. Once a catalog exists, its storage profile, KMS key set and legal entity never change.

Before you begin

  • You can change the catalog server's Helm release, or whatever else sets its application.yaml. See Install the catalog server with Helm.
  • The storage profile the catalog will use is declared under nuna.storage.profiles. See Set up object storage and Storage settings.
  • For the grants, you are in a group named in nuna.security.grant-admin-groups, or one of your groups holds manage-grants on the catalog. A new catalog holds no grants, so at first only grant admins can grant there.
  • For the curl examples, NUNA and TOKEN are set as Use the APIs with curl describes.

Declare the catalog

  1. Choose the catalog's name.

    Engines use it as the warehouse, and the REST prefix is the name itself. It must not contain @, which the prefix catalog@ref keeps for a branch or tag. Names compare without case: the server keeps the name as you write it and looks it up in lower case.

  2. Add the catalog under nuna.storage.catalogs in the release's values.

    Each catalog needs all three fields: profile names a storage profile declared on the same server, and kms-key-set and legal-entity are recorded with the catalog as its boundary.

    config:
  nuna:
    storage:
      catalogs:
        trading:
          profile: onprem
          kms-key-set: trading-keys
          legal-entity: Example Markets Ltd

  3. Upgrade the release.

    helm upgrade nuna-catalog deploy/helm/nuna-catalog -f values.yaml

    The chart writes config into the server's ConfigMap and puts a checksum of it on the pods, so a changed config rolls the servers. The first server to start writes the catalog to the database, with an audit record of type nuna.catalog.storage-setup (action CATALOG_CREATED, principal nuna-configuration). The others find it there and check that it holds the same profile, key set and legal entity.

A catalog's boundary is fixed once it exists

If you later change a declared catalog's profile, kms-key-set or legal-entity, the server refuses to start. To use another store, declare a new catalog.

Check that it exists

Grant admins and platform operators see every catalog the server declares. As one of them, list the catalogs:

curl -sS "$NUNA/management/v1/catalogs" \
  -H "Authorization: Bearer $TOKEN"
{
  "may": {"operate": false, "read-audit-feed": false},
  "catalogs": [
    {
      "audit": false,
      "name": "trading",
      "may": {"manage-grants": true, "manage-tags": false, "modify": false, "select": false}
    }
  ]
}

In the console, the new catalog appears in the catalog picker in the header.

Grant the first groups access

A new catalog holds no grants, so no engine user can see it yet. Grant each group the privileges its work needs on the catalog itself; a grant on the catalog reaches every namespace, table and view in it. A typical start gives one group create and modify, and another select.

  1. Choose the catalog in the catalog picker.

  2. Select Grants in the rail.

  3. Select Grant access.

    The dialog Grant access in trading opens. Enter the group, choose the access, and select Grant. The dialog says what the group will be able to do before you grant, and shows the server's refusal word for word if it refuses.

The console words each privilege as a rung of a ladder, from See it to Manage grants. Grant and revoke access walks through the dialog.

Send one grant per group and privilege. Each answers 204 with no body, also when the group already holds the grant.

curl -sS -X POST "$NUNA/management/v1/catalogs/trading/grants" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"securable": {"type": "catalog"}, "group": "trading-engineers", "privilege": "create"}'
curl -sS -X POST "$NUNA/management/v1/catalogs/trading/grants" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"securable": {"type": "catalog"}, "group": "trading-engineers", "privilege": "modify"}'
curl -sS -X POST "$NUNA/management/v1/catalogs/trading/grants" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"securable": {"type": "catalog"}, "group": "trading-analysts", "privilege": "select"}'

If the maintenance worker will maintain the catalog, its group also needs write on the catalog. The Maintenance page's setup checklist shows whether the worker can maintain the catalog, and Set a catalog's maintenance policy turns its jobs on.

An engine user in a granted group can now use the catalog

Signed in as a member of trading-analysts, GET /v1/config?warehouse=trading answers 200 with "prefix": "trading" in its overrides, and GET /management/v1/catalogs lists trading.

If it fails

The first four messages are start-up failures: the server logs them and stops, and Kubernetes shows the pod restarting. The rest are answers to a grant.

What you see, why, and what to do
What you seeWhyWhat to do
nuna.storage.catalogs.trading needs profile, kms-key-set and legal-entityOne of the three fields is missing.Set all three.
nuna.storage.catalogs.trading.profile names no profile: onpremNo profile of that name is declared under nuna.storage.profiles on this server.Declare the profile, or correct the name.
nuna.storage.catalogs.trading@x: a catalog's name holds no @, which the REST prefix catalog@ref keeps for a branch or tagThe name contains @.Choose a name without @.
catalog trading is bound to … in the store, but configured as …; a catalog's boundary never changesThe catalog exists with another profile, key set or legal entity than the settings now say.Put the settings back as they were. A catalog's boundary cannot be changed; declare a new catalog instead.
400 A grant names the group it goes to; grants never go to individuals …The body has no group.Name a group from the identity provider's token.
403 no one grants to a group they belong to: trading-engineersYou are a member of the group you are granting to.Ask another grant admin to make the grant.
403 group trading-engineers holds modify in this catalog, a data duty that manage-tags (tags) must stay separate fromSeparation of duties: one group may not hold conflicting duties anywhere in one catalog. Changing data conflicts with tagging, and managing grants conflicts with everything. The message names the privilege the group already holds.Grant the privilege to another group. Grant and revoke access covers every separation refusal.
403 group grant-admins administers grants on every catalog and may hold no other grantThe group is a deployment grant-admin group.Grant to another group.
404 NoSuchWarehouseException The given warehouse does not exist: tradingThe server does not hold the catalog yet, or your groups hold nothing in it and you are not a grant admin or platform operator.Check the servers restarted with the new settings, and that your token carries a grant-admin group.
