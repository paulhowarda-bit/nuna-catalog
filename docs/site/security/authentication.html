Authentication

Authentication is how the server establishes who a request acts as: it checks the request's bearer token against the identity providers you trust, and never issues a token itself.

What it is

Every request to the server carries a bearer token in its Authorization header, issued by an identity provider you name in nuna.security.issuers. The server checks the token's signature, issuer, audience and lifetime, then reads three claims: the user id, which names the principal; the groups, which decide what the principal may do; and the client id, which names the program that asked for the token. Nothing else about a person is stored or trusted.

Only the console's own files, the OPA decision endpoints and /v1/oauth/tokens skip this check. The OPA endpoints check the end user's token themselves (see Use OPA). /v1/oauth/tokens never issues a token: it answers 400 with error unsupported_grant_type and a description that begins This catalog does not issue tokens. and names where to get one.

How it works

Checking a token

The server reads the token's iss claim to choose the issuer, then verifies the token against that issuer's settings:

  • The issuer must be one of nuna.security.issuers; any other is refused.
  • The signature must verify with a key from the issuer's jwks-uri, by an algorithm in its algorithms list. Only asymmetric algorithms can be named, so unsigned and shared-secret tokens are always refused.
  • The aud claim must include one of the issuer's audiences.
  • The token must have an exp claim. exp and nbf are checked with the clock skew nuna.security.clock-skew allows, 60 s by default.
  • The claims named by user-id-claim and client-id-claim must be present. A token without the groups-claim belongs to no group.

The server never uses OpenID discovery: it reads keys only from the configured jwks-uri. It caches them for 5 minutes and refreshes them ahead of expiry. A token signed with a key id it has not seen makes it fetch the keys once more, which is how a key rotation reaches it; it fetches at most twice in 30 s. A fetch waits at most 500 ms to connect and 5 s for the answer.

A token from an identity provider that moved the groups claim elsewhere because the user has too many groups (a _claim_names entry for it) is refused: the application registered for the catalog must emit only the groups assigned to it.

Engines acting for people

A shared engine such as Trino serves many people with one connection. The server decides such a request for the end user, not for the engine, when the engine is a trusted engine: one a platform operator has registered by its issuer and client id at /management/v1/engines. A trusted engine names its end user in one of two ways:

  • It sends its own token in Authorization and names the user in X-Nuna-End-User (the user id as the issuer's user-id claim carries it), with the user's groups in X-Nuna-End-User-Groups, comma-separated and each percent-encoded.
  • It passes the user's own token in Authorization and sends its own token in X-Nuna-Engine-Authorization. Both tokens are verified, and the user's groups come from the user's token. This is how Trino works with iceberg.rest-catalog.session=USER. The same token in both headers is the engine acting as itself.

An engine that is not registered and names an end user is refused with 403. A trusted engine that names no end user acts as itself, with its own token's groups.

Service identities

Programs that act for no person sign in with a token of their own, usually by the OAuth client-credentials grant at the identity provider (see Get a token). The maintenance worker is such a program: its principal id is listed in nuna.security.maintenance-principals, which gives it the maintenance role when it acts as itself (see Authorization).

Developer tokens in the console

The console signs people in through the identity provider named in nuna.ui.oidc, by the authorization code flow with PKCE. With nuna.ui.dev-token-login set to true, it also offers a box to paste a bearer token. That box is for local development only, and it is off by default. A pasted token is checked like any other, so it gives no more than its own claims.

The demo turns developer tokens on

The local demo sets nuna.ui.dev-token-login to true and trusts an issuer of its own whose tokens it mints for its users. Neither belongs in a production install.

What it guarantees and what it does not

  • No request reaches a route without a token the server verified, except the paths named above.
  • Every refused token leaves an audit record of type nuna.catalog.auth-failure with the issuer, the claimed subject, the client id, the reason, the request id and the remote address. The token itself is never recorded.
  • The reason is recorded and logged, but not sent to the client. A refused token always answers the same body, so a caller learns nothing about why.
  • The server does not check whether a token was revoked at the identity provider before it expires. Keep token lifetimes short at the identity provider.
  • When the identity provider's keys cannot be fetched, the server answers 503, not 401, so engines retry instead of dropping their credentials.

Where you see it

A request without a token, or with one the server refuses, answers 401:

{"error":{"message":"Not authorized: the bearer token is missing or was not accepted","type":"NotAuthorizedException","code":401}}

Its WWW-Authenticate header is Bearer when no token was sent, Bearer error="invalid_token" when the token was refused, and Bearer error="invalid_request" when the request's headers are malformed.

Limits

  • The server starts only with at least one issuer: nuna.security.issuers names no trusted token issuer; the catalog accepts no request without one.
  • Each issuer needs all seven fields: issuer, jwks-uri, audiences, algorithms, user-id-claim, groups-claim and client-id-claim. An empty algorithms or audiences list stops the server from starting.
  • The trusted-engine registry stores an end-user-claim and flags for each engine, but no decision reads them.
