Authorization

Authorization is how the server decides whether the principal of a request may do what it asks: from the privileges its groups were granted on the object or above it, the roles your settings give groups, and the governance rules on the object.

What it is

The server decides every request for its subject: the principal its token names, or the end user a trusted engine acts for (see Authentication). Each operation needs one of seven privileges on the object it touches. The subject holds that privilege when one of its groups was granted a privilege that includes it, on the object or on anything above it: the catalog, then each namespace down to the object.

Grants go to groups from the identity provider's token, never to people. There is no DENY grant and no superuser: nothing takes away what a grant gives, and no setting gives every privilege everywhere.

How it works

Privileges and inheritance

The privileges are describe, select, write, modify, create, manage-grants and manage-tags. modify includes write and select, write includes select, and every privilege includes describe. A grant on a namespace reaches every namespace, table and view in it, including those created later. Privileges lists what each allows and which operation needs which.

A grant can name a catalog branch. It then counts only for requests through that branch, and only write and modify can be granted that way. Every other grant counts through every ref, main included.

Separation of duties

The privileges fall into four duties: reading (describe, select), data (write, modify, create), grants (manage-grants) and tags (manage-tags). Within one catalog, one group may not hold two duties that conflict:

  • A group that manages grants holds no other duty.
  • Data and tags never share a group.
  • Reading goes with data or with tags.

The server checks this across the whole catalog for the group, inside the same database write as the grant, so two grants made at the same moment cannot break it together. A grant that would break it is refused with 403, for example group trading-engineers holds create in this catalog, a data duty that manage-tags (tags) must stay separate from. The message names the first conflicting privilege the group already holds.

The self-grant rule

No one grants to a group they belong to, and no one sets a row filter or column mask for one. The refusals are no one grants to a group they belong to: group and no one sets row filters or column masks for a group they belong to: group, both 403 and audited. The principals listed in nuna.security.own-group-principals are exempt from this rule only; separation of duties still applies to them. Leave that list empty in production.

Grant admins

Members of a group in nuna.security.grant-admin-groups hold manage-grants on every catalog by configuration, not by a grant, and see every catalog. Such a group may hold no other grant: group group administers grants on every catalog and may hold no other grant. Any group can also be granted manage-grants on one catalog, namespace, table or view.

Platform operators

Members of a group in nuna.security.platform-operator-groups run the deployment: the trusted-engine registry, DR freezes, the maintenance worker's scans and storage set-up, and the delete policies. They see every catalog but hold no privilege on its data, and their group may hold no grant: group group operates the platform and may hold no grant. An operation only they may call refuses everyone else with only platform operators may call operation; the engine registry says only platform operators run the trusted-engine registry. A group in both lists stops the server from starting.

Maintenance principals

A principal whose id is in nuna.security.maintenance-principals, acting as itself and for no end user, is a maintenance principal. Only it may call the worker's endpoints (purges, pending deletions, scan reports); anyone else is refused with only a maintenance principal may call operation. It still needs grants for ordinary operations. It alone, besides trusted engines, gets storage access to a table flagged for row and column rules, and each such access is audited first as a maintenance exemption. On main it may also remove old schemas and partition specs with only write.

Governance rules

After a grant allows an operation on a table or view, three rules apply in this order:

  1. A table without a classification of its own, in a regulated area (the table, a namespace above it or its catalog has regulated set to true), is refused everything but describe and manage-tags: table name is in a regulated area and has no classification; it is closed until it is classified.
  2. A table flagged with row-column-policy gives storage access (load, credentials, commits) only to trusted engines and maintenance principals: table name has a row/column policy; only a trusted engine that enforces it gets storage access.
  3. With nuna.security.refuse-identity-less-commits set to true, a trusted engine that names no end user may not write in a regulated area: engine client named no end user, and writes to regulated areas must name one. The setting is off by default.

Legal holds, DR freezes and retention classes are checked by the operations they stop, not here; see Governance.

What a refusal tells you

A refusal for want of a privilege answers 403 with type ForbiddenException and names the subject, the privilege checked and the operation, in the form subject holds no privilege that gives select for loadTable. Through a branch or tag it adds on this branch or tag.

Names are hidden from those who hold nothing on them. A subject whose groups hold nothing on a namespace, table or view gets the answer for one that does not exist, such as 404 NoSuchTableException. A subject whose groups hold nothing in a catalog, and who is no grant admin or platform operator, gets 404 NoSuchWarehouseException The given warehouse does not exist: catalog. Every refusal, hidden or not, is audited as a nuna.catalog.denial record.

What it guarantees and what it does not

  • Every Iceberg and management request is decided before its work starts, and every refusal is audited.
  • A privilege name the server does not know, stored by a newer version, gives nothing.
  • The server does not read the directory. It knows a group only from grants and from the groups in tokens, so it cannot tell you who is in a group.
  • The server decides access to catalog objects; access to the files themselves depends on the vended credentials it issues and on your object store's own policies (see Credential vending).

Where you see it

In the console, the Grants page lists and changes a catalog's grants, and each object's Access tab shows the grants that reach it and What you may do. The endpoints are in the Grants API; the settings are in Security settings.

Limits

  • create means nothing on a table or view, and write means nothing on a view; the server refuses such grants with 400.
  • A grant that names a branch gives only write or modify, and a tag cannot be named.
