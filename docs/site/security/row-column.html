Row-level security and column masking

Row-level security and column masking is the path by which a group's row filter and column masks on a flagged table reach the trusted engine that applies them, and the storage access the server withholds from every other caller.

What it is

The model, who sets what and how rules combine, is in Row filters and column masks. This page follows the enforcement: what the server checks on each request to a flagged table, which engines enforce the rules, and what is withheld from the rest.

How it works

Storage access to a flagged table

A table whose own row-column-policy attribute is true is flagged. The operations that hand out or use its files are loadTable, loadCredentials, updateTable and commitTransaction. The server allows them only to:

  • a trusted engine, whether it acts for an end user or as itself, which must still hold the privilege through its groups or the end user's;
  • a maintenance principal acting as itself, for maintenance. Each such access is first audited as a nuna.catalog.maintenance-exemption record; if that record cannot be written, the access is refused with 503 Storage access under the maintenance exemption cannot be audited now; retry later.

Everyone else, the console included, is refused with 403 table name has a row/column policy; only a trusted engine that enforces it gets storage access, audited as a denial with reason flagged_table. describe operations, such as listing the table or reading its schema in the console, are not withheld.

Which engines enforce the rules

Trino enforces them, through its OPA access control pointed at the server's decision endpoints. No other engine applies them. Register an engine as trusted only when it applies the rules: a trusted engine that ignores them reads every row.

Not documented yet: whether any engine other than Trino has been tested against the decision endpoints. No test outside the Trino set-up in the demo says.

One Trino query, step by step

  1. Trino, with iceberg.rest-catalog.session=USER, calls the Iceberg REST API with the person's own token in Authorization and its own token in X-Nuna-Engine-Authorization. The server checks both, decides the load for the person, and hands Trino the table and its vended credentials because Trino is a trusted engine.
  2. Trino's OPA access control posts to /opa/v1/allow, which always answers {"result":true}: the catalog has already decided access.
  3. It posts to /opa/v1/row-filters and /opa/v1/column-masks, passing the person's token as the extra credential token. The server verifies that token itself and ignores the user and groups Trino names. It answers with the combined filter and the masks for the person's groups.
  4. Trino reads the files and applies the filter and masks before it returns rows.

Failing closed

The decision endpoints answer so that a fault shows less, never more. For a Trino catalog that nuna.opa.catalogs maps to a nuna catalog, a missing or refused token, a table the server cannot find, or one the person holds nothing on answers the filter false and masks every column with NULL. If Trino asks about only some of a table's masked columns in one call, every column in the call reads NULL. When the identity provider's keys cannot be fetched, the endpoints answer 503 The user's token could not be checked; retry later. A Trino catalog that is not mapped gets no rules at all, so map every Trino catalog that reaches nuna.

What it guarantees and what it does not

  • No caller other than a trusted engine or a maintenance principal receives a flagged table's metadata location or vended credentials from the server.
  • The server does not stop someone who already has other access to the object store from reading the files. Restrict the bucket to the server's vending role and the maintenance worker; see Hardening checklist.
  • A rule is only as strong as the engine that applies it.

Where you see it

A table's Access tab in the console shows the rules to grant admins, and to a reader the panel Your view of this table, which says Read through Trino only. The endpoints are in the Row and column rules API and the OPA decisions API. The trusted engines are listed at GET /management/v1/engines, for platform operators.

Limits

  • Expressions are Trino SQL, checked by Trino's parser; another engine's dialect is not accepted.
  • The flag is a table's own; flags set on catalogs, namespaces or views are removed when the server starts.
