Credential vending

Credential vending is how the server hands an engine short-lived object store credentials scoped to one table's files, so that engines never hold standing keys to the store.

What it is

When an engine loads a table, or asks for fresh credentials for one, the server can return vended credentials beside the table's metadata: a temporary access key, secret and session token for the object store. They reach only the table's own location, and only for a while. The engine reads and writes the files itself; the server never carries data.

How it works

Read or read-write

A caller that may commit to the table (it holds write on it) receives read-write credentials; any other caller with select receives read-only ones.

What each access allows
AccessObject store actions
Reads3:GetObject, and s3:ListBucket limited to the table's prefix
Read-writes3:GetObject, s3:PutObject, s3:AbortMultipartUpload, s3:ListMultipartUploadParts, and s3:ListBucket limited to the table's prefix

No vended credential can delete an object, not even for maintenance. Only the maintenance worker, with its own storage identity, deletes files. A caller that may write only through one catalog branch can write only beneath that branch's prefix in the table's location.

The session policy

The server calls the store's STS AssumeRole with a session policy that names only the table's location. AWS S3 and Ceph profiles must name the role in sts-role, or the server refuses to start; a MinIO profile needs none. The role's trust policy must allow sts:AssumeRole and sts:TagSession. The session is named from the subject and the request id, and tagged with nuna-principal, nuna-end-user when there is one, nuna-engine, nuna-request, nuna-catalog and nuna-table, so the store's own logs show who each session was for. A profile with a KMS key adds a condition that every write uses that key (see Encryption and keys).

Lifetime and refresh

Credentials last nuna.storage.credential-lifetime, 30 minutes by default, and the server accepts 15 to 60 minutes. The load answer tells the engine when they expire and where to refresh them: client.refresh-credentials-endpoint names v1/prefix/namespaces/namespace/tables/table/credentials. The server reuses a credential for the same caller, table and access for a quarter of its lifetime, from a cache of nuna.storage.credential-cache-entries entries.

Opting out

An engine that has its own access to the store sends X-Iceberg-Access-Delegation: none. The server then vends nothing, calls no STS and records no credential issue.

What is recorded

Before it hands credentials out, the server writes an audit record of type nuna.catalog.credential-issue: the table, the storage profile, the location prefix, the access (READ or READ_WRITE), the STS session name, the expiry, who asked, and the write prefix when it is narrower than the table. The credentials themselves are never recorded. If the record cannot be written, the credentials are discarded and the request answers 503 Storage credentials cannot be issued now; retry later.

What it guarantees and what it does not

  • An engine never receives a credential for anything outside the table's location. A table whose location lies outside its storage profile is refused: Table location location is outside storage profile profile.
  • A flagged table's credentials go only to trusted engines and maintenance principals (see Row-level security and column masking).
  • A credential cannot be withdrawn before it expires. Revoking a grant stops new credentials, not ones already handed out.

Where you see it

The credentials arrive in the config of a table load as s3.access-key-id, s3.secret-access-key, s3.session-token and s3.session-token-expires-at-ms, with client.region, and s3.endpoint and s3.path-style-access for a store other than AWS S3. See the Iceberg REST tables API and the settings in Storage settings.
