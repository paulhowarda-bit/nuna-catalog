Encryption and keys

How data and metadata are encrypted on the way between nuna's parts and at rest in the object store, and how a storage profile's KMS key is enforced on every write.

What it is

nuna holds no data of its own: table data and metadata files sit in your object store, and the catalog's pointers sit in your database. Encryption at rest is therefore the store's and the database's. What the server adds is a check that every connection it makes to the store uses TLS, and, on AWS S3, a single KMS key that every write must use.

How it works

In transit

  • To the object store. With nuna.storage.require-tls at its default, true, the server refuses to start with a storage profile whose endpoint is plain http. A store whose certificate a private certificate authority signed is trusted through the profile's ca-bundle, for that profile's S3 and STS clients only.
  • To the database. The JDBC URL's TLS parameters name the files of a client certificate, mounted from the chart's databaseTls Secret. For MongoDB, TLS is set in the connection string.
  • From engines and browsers. The server listens on port 8181; the chart's ingress carries the TLS certificate (ingress.tls).
  • Telemetry. An https OTLP endpoint is trusted through telemetry.caConfigMap.

At rest, with a KMS key

An AWS S3 storage profile can name kms-key: the ARN of one KMS key, in the profile's region. With it:

  • Every vended session policy allows s3:PutObject only with server-side encryption by that key, and allows kms:Decrypt, with kms:GenerateDataKey for writers.
  • Each table load tells the engine to write with it: s3.sse.type is kms and s3.sse.key names the key.
  • The server's own metadata files name it.

Without kms-key, writes are encrypted as the bucket's default encryption says. A table's encryption.key-id property is fixed when the table is created: Property encryption.key-id is fixed when the table is created.

What it guarantees and what it does not

  • A credential the server vends cannot write an object without the profile's key, when the profile names one.
  • The server does not encrypt files itself, and it does not check the bucket's default encryption.
  • Each catalog records the KMS key set named in its settings (kms-key-set), and that never changes; the key the store uses comes from the profile's kms-key.

Not documented yet: whether the server itself listens on TLS when no ingress is used. The chart's service is plain port 8181, and no server setting for a certificate was found.

Where you see it

The settings are in Storage settings and Helm chart values. A profile's key appears in its nuna.catalog.storage-setup audit record as kms-key.

Limits

  • Only an AWS S3 profile names a KMS key: only an AWS S3 profile names a KMS key, not a CEPH profile.
  • The key is an ARN, not an alias or a bare key id: must be a KMS key ARN, arn:<partition>:kms:<region>:<account>:key/<key id>, not an alias or a bare key id; got ….
  • The key is in the profile's region: the key … is not in the profile's region …: S3 encrypts only with a key in the bucket's region.
