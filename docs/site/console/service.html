The Service page

The Service page answers, for platform operators, how the whole deployment did over the last day: whether its latency objectives were met, whether every server answered, how audit copying and credential vending went, what alerts fired, and how the maintenance worker, DR replication and the database stand.

Who sees it

Platform operators only: the rail shows Service to them alone, and every route behind it refuses anyone else with only platform operators may call operation, audited as a denial. Anyone else who opens it sees "Service is shown to platform operators only, and your groups include none. The catalog answered:" and the refusal. The page covers every catalog, so the catalog picker is hidden.

The head

The title says All N servers answered. or a of t servers answered., then Every latency objective was met., N latency objectives were missed. or No request was timed in the window. "Each server counts its own last day; this page adds them up. A server that does not answer is named here and its figures are left out, never guessed."

Latency objectives

Met when 99 in 100 requests finish within the objective. Rows Table loads and exports, Loads that found no change and Commits, each with its Objective, Count, Within it, the share on a 97 to 100% scale, p99 and Verdict: met, missed or no requests in the last day.

Audit

"Each request's audit record is written to the log nuna.audit before the catalog answers it." Copied to Kafka, Mean time to copy, p99 and Copies failed. "A copy that fails blocks nothing: the log already holds the record."

Credential vending

Issued, Served from the cache, Declined by the caller and Failed, with each kind of failure and how many vends it hit.

Alerts fired

The last day's counts of three alerts: Metadata integrity ("A metadata file no longer hashes to what its pointer recorded. Pages."), Regulated schema change ("A commit changed a regulated table's schema or partition spec.") and Large metadata ("A loaded table's metadata is over the size or snapshot limit."). "Paging stays in your alerting; these are the last day's counts."

Servers

Each server the figures came from, marked this server, answered or no answer with why, and since when it has run.

Worker scans

Last successful scan, Scans in the last day, Failed jobs in the last day and Latest failed scan, then each scan's Started, Took, Outcome (Succeeded, Succeeded, some jobs failed or Failed) and Failures. Show the last N scans shows up to 50. "A failure on one table never stops the scan; the next scan retries that table." With none: "The maintenance worker has not reported a scan. Check that it is running."

Worker storage

One row per storage profile: its Catalogs, Prefixes, the Worker's identity (Has an identity, No identity, No report yet), the Store as the worker found it (Listed time, Listing refused, Deletes refused, No answer, Not checked) and the Delete policy.

What to set up opens Set up the worker's storage for profile: first the worker's settings as YAML (Copy the settings), then the store's policy (Copy the policy or the commands). "The catalog writes these policies but never applies them: its own keys would then need the right to undo them."

DR replication

Tables behind their watermark, Never verified, Most versions behind and Longest lag, against each table's DR watermark. "No table or view is behind its DR watermark: the verifier found each whole in the DR store at its current version." With no verifier report: "No DR verifier has reported on them." Only the first 1,000 tables are checked. This panel and the next are hidden on phones.

Store

The database as this server finds it: Backend (PostgreSQL or CockroachDB, Oracle, MongoDB), Self-check at start (passed, or started despite findings) and Point-in-time recovery window as declared. "The database did not answer: …" when it does not.
