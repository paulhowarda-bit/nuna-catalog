The table page

A table's page answers everything about one table: its current state, its schemas and partitioning, every commit, what each group may do with it, how it is governed, how it is maintained, its audit trail and its settings. Engine users, data stewards, grant admins and auditors each use different tabs.

Who sees it

The page opens for anyone whose groups hold describe on the table or above. Each tab is checked on its own:

  • Overview, Schema and History load the table, which needs select. A refused load shows the server's refusal and "You may still open Access, Maintenance and Audit: each tab is checked on its own." A grant admin, who holds manage-grants and no select, lands on Access.
  • On a table flagged for row and column rules, only a trusted engine reads its files: "Its data is read through Trino, which applies each group's rule. The console shows no rows."
  • Maintenance needs select. Compact now and Scan for orphans now need modify.
  • Audit appears only to those who manage the catalog's grants; the server answers it only with manage-grants on the table.
  • Changing a setting needs modify. Governance changes need manage-tags.

Every load of a table is audited. The console keeps a load for a minute before reading it again.

The head

The head shows the table's path and iceberg vN, with marks for Needs compaction (which opens Maintenance), a waiting Compaction requested or Orphan scan requested, Held, Frozen and the classification. Its buttons are Copy link, Settings (the Settings drawer), Export metadata and, for those who may modify the table, Compact now, never offered through a branch or tag. The tabs are Overview, Schema, History, Access, Maintenance and Audit.

Export metadata opens Export name: "The current metadata, every snapshot and snapshot ref, and the catalog's commit journal for this table, as one JSON file. The data files stay where they are; a restore registers it again from this file." Select Download the file or Copy the JSON. It needs select and is audited.

Overview

Four figures: Rows with the size, Data files with the delete files, Snapshots with the table's own Iceberg refs, and Schemas with how many changes (as created when none).

Current state
The current snapshot (its id, operation, time, engine and who made it), or none: the table has no data yet; Table UUID; Location; Metadata file; Schema, spec, order; Last sequence number; Next row id; Last updated; and Properties with Show all N properties.
Maintenance
Not assessed yet, Needs compaction · score N with its place in tonight's queue, or No compaction needed; then the last compaction and its outcome, or No compaction has run for this table.
Governance
Legal hold, DR freeze, Classification and Owner.
Engine-level refs in this table's metadata
"Iceberg's own branches and tags, set by engines inside this table, not the catalog's." Each with its snapshot and how long it is kept.

Schema

Schemas lists the table's schemas, the current one first (the newest six of many). Pick two to compare: the diff panel shows each field's Id, Field, Type, Required and Doc, marked added, removed or was old name. "Iceberg keeps no date for a schema. The commit that added one is on History, with who made it."

Each partition spec (Spec N, the current one marked Default) lists its fields or says unpartitioned; each sort order (Sort order N) its fields, or "Unsorted: files keep the order rows arrived in." "Old files keep the spec they were written with. Compaction writes the default spec, so older files move to spec N as the worker rewrites them."

History

Snapshots and Iceberg refs
A timeline of the snapshots and the table's own refs. With none: No snapshot yet, "No commit has written data to the table."
Commits
Every commit the catalog's journal keeps, newest first, 25 at a time (Show the next 25): Version, Written, Change, Snapshot, Rows, By and Iceberg refs. "The catalog keeps every commit, even after the table's own list drops its file." The change reads, for example, created, registered, restored or Merged @ref (its version N).
Selected snapshot
The snapshot's summary, with Show the whole summary and Copy time-travel SQL, which copies SELECT * FROM catalog.path FOR VERSION AS OF id.
Snapshot expiry
On or Off, with Keep snapshots for and Keep at least. "A tagged snapshot stays as long as its tag keeps it."
Current file and Kept
The current metadata file, and how many earlier ones the table lists (Earlier metadata files listed, 100 by default). "A file that falls off the list is removed by the orphan scan."

Access

The Access tab shows, in order, Grant access (for those who manage grants), What you may do, Your view of this table, the governance panel, Kept by branches and tags, Row filters and column masks and the grants.

What you may do

What your groups' grants allow on the table, one line per level: See it, but not read its data, Read its data, Read its data and write rows to it, Read and write its data, and change it: its schema, properties and maintenance, Set its labels and holds, Grant on it, and see who holds what. With none: "Your groups hold no grant that reaches this table." "The catalog decides each request; this is what your grants allow."

On a flagged table, Your view of this table says "Read through Trino only." and then You see every row., Your rows are filtered. or You see no rows until the grant admin sets a rule for one of your groups., with the columns masked for you.

Governance

The status: DR freeze in force or No DR freeze ("Commits are allowed."), and N legal holds ("Snapshots cannot be removed; it cannot be dropped or purged.") or No legal hold. What the catalog enforces lists Commits, Snapshot expiry and Drop and purge, such as Refused · under legal hold. Legal holds lists every hold here or above, nearest first, with Release; Attributes lists Classification, Owner, Retention class and Flagged for row and column rules, each with its level, provenance and who set it.

Holders of manage-tags get these buttons. Each change is "recorded as set from the console, under your name, in the audit trail."

Kept by branches and tags

Each catalog branch and tag that reads the table and keeps its files from cleanup, or "No branch or tag keeps this table." Holders of manage-tags get Take out of branches and tags: each ref chosen stops keeping it, and reads through it answer 404. "This cannot be undone: no branch or tag can take it back." It is not offered under a legal hold or a DR freeze.

Row filters and column masks

Shown to those who manage grants or tags. Not flagged: "Rules need the flag. A steward sets it, so only trusted engines read the files." Flagged with no rules: "Flagged. No rules yet: Trino shows every row to anyone who may select; other tools get no files." A grant admin sees each rule's Group, Rows (Every row or Only rows where …), Masked columns and Set by, when, with Edit, Remove and Add a rule for a group. A steward sees only how many rules and for which groups.

The rule dialog takes a group, Every row or Only rows where with an SQL condition, and Masked columns (NULL, '***' or A custom expression). Its button is Save the rule. Adding the first rule warns "Groups without a rule will see no rows." A grant admin cannot set the rule of a group they belong to: "Another grant admin sets this group's rule." If another grant admin saved first: "Another grant admin changed this rule since you opened it. Close this; the list shows theirs."

Grants

Those who manage grants see Grants that reach this table, from the catalog down, with Granted on (here, the catalog or a namespace) and Revoke, and Who may: Read, Change data, Manage tags, Manage grants. "The ladder is describe, select, write, modify: each gives the ones before it. Revoke takes a grant away where it was made." Everyone else sees Your groups' grants.

Maintenance

Assessment
Needs compaction · score N with its reasons and its place in tonight's queue, or No compaction needed ("Under every threshold of its maintenance policy."), then Score, Data files, Small files, Delete files, Position-delete files, Deletion vectors and Equality-delete files. Unassessed: "The maintenance worker has not assessed this table yet."
Last compaction
Outcome, Started and Ended.
Policy for this table
Each policy key with its value and where it was set: built-in, guardrail, the catalog, a namespace above or this table.

Compact now and Scan for orphans now ask the worker to run a job at its next scan, "even outside the cleanup window." Each opens a dialog with the same button name. "Needs modify on the table. The catalog refuses it during a DR freeze, refuses an orphan scan while the table is on legal hold, and refuses a job the table's policy turns off." A request shows as waiting, then as started; a job's button is turned off while one of that job waits. Compact a table or scan for orphans now covers it in full.

Audit

The table's Audit trail, newest first. Filter by Kind (All, Grants, Row and column rules, Governance, Branches and tags, Commits, Other changes, Reads, Credentials, Refusals, Other), Who and How many (the latest 25, 50, 100 or 200; 50 by default), then Refresh. "Reading the trail is itself audited." Each row has Show record.

How far back this goes says whether the list is complete: "Yes: every record about it is shown, up to about a minute ago." or "No.", with a pointer to the SIEM for the full trail. The audit table's writer commits about once a minute, so the newest minute is not yet shown. With nothing found: "No audit record about this table in the scanned window."

The Settings drawer

Settings opens Settings of name. Esc closes it. "A change here is a commit to the table: the same rules apply as to an engine's commit, and it is audited." Each setting shows its value marked set or its default marked default, with Change (button Set it) and Reset (button Reset it, which removes the property).

Every property lists every key on the table; keys the console does not change are "Set outside the console, by an engine or tool. Read-only here."
