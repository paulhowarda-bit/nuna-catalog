# The nuna documentation site: design and writers' contract

Atelier, 2026-11-26. For the agents who write the site's pages, not for its readers. Read all of it before you
write a page. Sections 3 to 5 are a contract: the stylesheet and scripts are being built against exactly this
HTML while you write, so write only what is here. If you need something this file lacks, ask the session that
started you; do not invent a class, an attribute or a page.

Contents: 1 Decisions. 2 Site map. 3 Page types. 4 Page skeleton. 5 Content contract (every component, with
markup to copy). 6 Voice and wording. 7 Names, examples and variables. 8 Screenshots and diagrams. 9 Checking a
page before you hand it back.

---

## 1. Decisions

- **The site is the console's sibling.** It uses the console's Ice line look: the same OKLCH tokens, the same two
  fonts (Instrument Sans, Geist Mono), the same peak-and-ice mark, light and dark. A reader who moves from the docs to
  the console should feel no seam. Ice line landed with Paul on 2026-11-22; it is not reopened here.
- **Static files, no build step to read them.** Opening `docs/site/index.html` from disk works. Every script is a
  classic `<script>` file (Chrome blocks ES modules and `fetch` on `file://`). No third-party code, no CDN, no web
  fonts from the network, no request to any host.
- **Folders one level deep.** Every page is `docs/site/<section>/<page>.html`, except `index.html` and
  `all-pages.html` at the root. Nothing deeper. Shared files live in `docs/site/assets/` and pictures in
  `docs/site/img/`. Writers never edit `assets/`.
- **The chrome is drawn by script from one site map.** Each page holds only its own content plus empty placeholders
  for the header, the side navigation and the "On this page" list. `assets/nav.js` holds the site map (section 2) and
  `assets/docs.js` draws the header, navigation, breadcrumbs, the page list, previous and next links, copy buttons,
  tabs and search. Without script a page still reads in full, with a link to `all-pages.html`.
- **Search is local.** `assets/search-index.js` is generated from the pages by `docs/site/tools/index.py` (Python 3,
  standard library). It loads the first time a reader opens search. Press `/` to search, as in the console.
- **A check tool enforces this contract.** `docs/site/tools/check.py` (built in phase 2) checks every page against
  sections 4 and 5: skeleton, known classes only, heading ids, links that resolve, code languages, no inline style.
  Run it on your pages once it exists (section 9).
- **Screenshots are real, and writers declare them.** A writer places a pending screenshot figure that says what to
  capture (section 8). A later pass captures them from the running demo with headless Chrome, never taking the demo
  down.
- **Gaps are shown, never guessed.** When you cannot verify something, write a visible gap (section 5.20), not a
  plausible sentence. Paul's rule: flag, never guess.

### What the reader sees

Header: the nuna mark and "docs", search, theme switch. Left: the site map in four bands (Learn, Use, Run, Look up),
the current section open. Centre: the page, about 72 characters wide. Right, on wide screens: "On this page", from the
page's `h2` and `h3`. Foot of each page: previous and next in the site map, then "How this page was checked". On a
phone the navigation is a drawer and "On this page" folds into a menu under the title. Print drops the chrome and
shows every tab's content.

## 2. Site map

Files are relative to `docs/site/`. **Type** is a page type from section 3. **P** is priority: 1 pages make the
first release; 2 pages follow. **Sources** are repository-root paths to start reading from; they are where to begin,
not the limit of what you must check. Write only pages listed here; the title in the table is the page's `h1` and its
`<title>`. A short label for the navigation, where one differs, is in brackets.

The site map's four bands, in navigation order:

- **Learn**: Get started, Concepts, The demo.
- **Use**: Console guide, Guides, Command line and clients.
- **Run**: Install, Configure, Operate, Security.
- **Look up**: API reference, Reference, Building from source.

## 3. Page types

The type goes on the article: `<article class="doc" data-type="guide">`. Values: `home`, `section`, `tutorial`,
`guide`, `concept`, `console-page`, `reference`, `api`, `command`, `runbook`.

Every page has an `h1` (the title from the site map) and a lead (one or two sentences: what the page lets you do or
explains, and for whom). Every page except `home` and `section` ends with "See also" and "How this page was checked".

### section

A section's front page. The lead says what the section covers. Then a card list (5.16) of the section's pages in
site-map order, one sentence each. Optionally one paragraph before the cards on how to read the section. No other
content.

### tutorial

Learning by doing, on the demo, start to finish, one path, no choices except engine tabs.

1. Lead: what you will have at the end, and how long it takes.
2. `h2` "What you need" (`id="what-you-need"`): a list.
3. One `h2` per stage, numbered in the words ("Start the demo", not "Step 1"). Each stage is a steps list (5.6)
   and ends with a `check` callout saying what you should see.
4. `h2` "What you did" (`id="what-you-did"`): three to five sentences, and the next tutorial.

### guide

One task. The reader knows what they want.

1. Lead: the task and its outcome.
2. Meta badges (5.12): what it needs and who it is for.
3. `h2` "Before you begin" (`id="before-you-begin"`): privileges, set-up, links to what must be done first.
4. The steps, as a steps list or as `h2` stages for longer tasks. Variants go in tabs (5.7).
5. A `check` callout: how to know it worked.
6. `h2` "If it fails" (`id="if-it-fails"`): a table of what you see (the exact message), why, and what to do.
7. See also.

### concept

Explains what something is, how it works and why. No procedures beyond a two-line example.

1. Lead: a one-sentence definition.
2. A diagram near the top when there is a mechanism to show (section 8).
3. `h2` sections, in this order where they apply: what it is; how it works; what it guarantees and what it does not;
   where you see it (the console page, the API page, the settings); limits.
4. See also: the guides and reference pages that act on the concept.

### console-page

One console page, as reference: what every element means and does.

1. `h1` "The {Rail name} page"; lead: the question the page answers, and who it is for.
2. A screenshot (section 8).
3. `h2` "Who sees it" (`id="who-sees-it"`): which groups and privileges see the page, each panel, each action, and
   what everyone else sees instead.
4. One `h2` per tab or panel, in on-screen order. Under each: what it shows (each field and figure defined), each
   action (its button's exact words, what it does, what it needs, whether it can be undone), and its states: empty,
   not yet reported, switched off, refused. Quote on-screen words exactly from the source.
5. `h2` "From the command line" (`id="from-the-command-line"`): a table of each action and figure on the page and the
   endpoint that does or gives it, linked to its endpoint block.
6. See also.

### reference

Facts to look up, complete and exact. Tables or settings entries, in a stated order (alphabetical, or the order the
code defines). No narrative beyond a short paragraph per `h2`. Settings pages set `data-toc="h2"` on the article so
"On this page" lists groups, not every setting.

### api

1. Lead: what the resource is; the base path in code.
2. `h2` "Endpoints" (`id="endpoints"`): a summary table (method, path, what it does), each row linked to its block.
3. One endpoint block (5.11) per endpoint, under `h2` groups when there are more than six.
4. `h2` "Objects" (`id="objects"`): a field table per object the endpoints return.
5. See also. Iceberg REST pages link to `spec/rest-catalog-open-api.yaml`'s published form for what nuna does not
   change.

### command

A script or tool's reference. `h2` "Synopsis" with the usage line; one `h3` per subcommand (`<code>demo.sh up</code>`)
with what it does, its options table, what it prints, and an example; `h2` "Environment variables"; `h2` "Exit
status" where the script defines one.

### runbook

One `h2` per alert, with the alert rule's name in code as its heading. Under each, `h3` in this order: "What it
means", "Impact", "Check", "Fix", "If that does not fix it". Commands in code blocks; no step left as "investigate".

### home

Built by Atelier. Writers do not write it.

`install/helm-catalog`. `TYPE` is its page type. `TITLE` is its title from the site map. `LEAD` is its lead as plain
text (no markup) for the description. Keep the indentation; it costs nothing and diffs read better.

```html
<!doctype html>
<html lang="en" data-root="ROOT" data-page="PAGE">
<head>
  <meta charset="utf-8">

  <script src="ROOTassets/nav.js" defer></script>
  <script src="ROOTassets/docs.js" defer></script>
</head>
<body>
<a class="skip" href="#main">Skip to the content</a>
<header class="site-head" id="site-head">
  <a class="brand" href="ROOTindex.html">nuna docs</a>
  <a class="all-pages" href="ROOTall-pages.html">All pages</a>
</header>
<div class="site">
  <nav class="site-nav" id="site-nav" aria-label="Documentation"></nav>
  <main id="main" tabindex="-1">
    <article class="doc" data-type="TYPE">
      <header class="doc-head">
        <h1>TITLE</h1>
```

Rules:

- Breadcrumbs, the navigation, "On this page", previous and next, and the footer are drawn by `docs.js`. Never write

- Badges for the page as a whole (5.12) go in the `doc-head`, after the lead, in a `<p class="doc-meta">`.
- No `<style>`, no `style=` attribute, no `<script>` in a page, no `on…=` attribute, no `<link>` beyond the two in the
  skeleton, no `<iframe>`, no `<br>` for spacing.
- Links between pages are relative (`../concepts/commits.html#requirements`), never absolute, never `/`-rooted.
- The file is UTF-8. Write `&lt;`, `&gt;` and `&amp;` for those characters in text and inside code.

## 5. Content contract

The only elements and classes a page body may use. Anything not here fails the check.

**The snippets show markup, not facts.** Their values (defaults, limits, routes, what a setting does) are
illustrative and some are made up. Never copy a fact from this file into a page; take every fact from the code.

Plain elements, no classes: `p`, `ul`, `ol`, `li`, `a`, `code`, `strong`, `em`, `kbd`, `var`, `dl`, `dt`, `dd`,
`table`, `caption`, `thead`, `tbody`, `tr`, `th`, `td`, `h2`, `h3`, `h4` (only in `api` and `reference` pages),
`summary`, `figcaption`, `img`, `svg` and its children (section 8), `abbr`, `sup`. The elements that carry a
component (`b`, `span`, `div`, `aside`, `section`, `figure`, `details`, `pre`) appear only as section 5.22 lists them.

### 5.1 Headings

```html
<h2 id="before-you-begin">Before you begin</h2>
<h3 id="the-storage-profile">The storage profile</h3>
```

- Every `h2` and `h3` has an `id`. Every `h4` in an endpoint block or settings entry has one too.
- The id is the heading's words in lower case, joined by hyphens, ASCII letters, digits and hyphens only, at most 48
  characters; drop "a", "an" and "the" at the start. Unique within the page.
- Ids are public addresses: other pages link to them. Never rename one after it has been handed back.
- Fixed ids: `what-you-need`, `what-you-did`, `before-you-begin`, `if-it-fails`, `who-sees-it`,
  `from-the-command-line`, `endpoints`, `objects`, `synopsis`, `environment-variables`, `exit-status`, `see-also`.
- No heading levels skipped. No heading without text under it. No code or links inside headings, except a setting's,
  endpoint's or subcommand's name in `<code>`.

### 5.2 Lead

```html
<p class="lead">Grant a group a privilege on a catalog, namespace, table or view, and take it back.</p>
```

Exactly one, the first thing after the `h1`.

### 5.3 Paragraphs, lists, inline names

```html
<p>The server reads <code>nuna.security.issuers</code> at start-up. Set it in the chart's <code>config</code>.</p>
<ul>
  <li>A full sentence ends with a full stop.</li>
  <li>Every item in one list has the same form.</li>
</ul>
```

`<code>` is for anything a person types or the system prints by name: settings, paths, routes, field names, file
names, commands, environment variables, privilege names, group names, catalog and table names, property keys, HTTP
statuses with their numbers (`409`). `<var>` marks a part of a name the reader replaces, inside `<code>`:
`<code>/v1/<var>catalog</var>/namespaces</code>`. `<strong>` marks the one word a sentence turns on, rarely.
`<em>` is for a term at the place it is defined.

### 5.4 Console words and console paths

```html
<p>Select <b class="ui">Grant access</b>.</p>
<p>Go to <span class="ui-path"><b class="ui">Catalog</b> <b class="ui">orders</b> <b class="ui">Maintenance</b></span>.</p>
```

- `<b class="ui">` holds words exactly as the console shows them, with its capitals: buttons, tabs, rail items,
  field labels, menu items, headings of panels. Take them from the source in `catalog-server/src/main/resources/nuna/ui/`,
  never from memory or the prototype.
- `<span class="ui-path">` holds two or more `ui` items, separated by one space. The stylesheet draws the separators.
  Never write `>`, `→` or `/` between them.

### 5.5 Callouts

```html
<aside class="callout note">
  <p class="callout-title">The worker needs its own grant</p>
  <p>Without <code>modify</code> on the catalog, the worker scans the catalog but compacts nothing.</p>
</aside>
```

Kinds, as the second class:

| Class | Use for |
|---|---|
| `note` | Something the reader would otherwise miss. |
| `tip` | A better way, or a shortcut. |
| `warning` | A step that can fail or leave things in a state the reader must then fix. |
| `danger` | A step that deletes data or cannot be undone. |
| `demo` | Something true only in the local demo (developer tokens, the certificate, the demo's users). |
| `check` | How to know a step or task worked: what you should see. |

- `callout-title` is required and is a claim, not a label: "Purging cannot be undone", not "Warning".
- At most one callout in a row; never two callouts back to back. If a page needs many, the prose is wrong.
- Body: `p`, `ul`, `ol`, a code block. Nothing else.

### 5.6 Steps

```html
<ol class="steps">
  <li>
    <p class="step-title">Start the demo.</p>
    <div class="code" data-lang="bash">
<pre><code>demo/demo.sh up</code></pre>
    </div>
    <p>The first run builds every image and takes several minutes.</p>
  </li>
  <li>
    <p class="step-title">Open the console at <code>https://localhost:8181/ui/</code>.</p>
  </li>
</ol>
```

- `step-title` is one imperative sentence, ending with a full stop. It is the step; the rest of the `li` explains it.
- One action per step. A step with "and then" is two steps.
- `li` may hold `p`, a code block, a callout, tabs, a figure, a table.

### 5.7 Tabs for variants

```html
<div class="tabs" data-group="client">
  <section class="tab" data-tab="console" data-label="Console">
    <p>…</p>
  </section>
  <section class="tab" data-tab="curl" data-label="curl">
    <div class="code" data-lang="bash">…</div>
  </section>
</div>
```

- Use tabs only for the same task done in different ways. Never put different content behind tabs to save room.
- Groups and their tab values. Use these values only; a choice in one tab set applies to every tab set of its group,
  on every page, and is remembered.

| `data-group` | `data-tab` values, in this order, with their `data-label` |
|---|---|
| `client` | `console` Console, `curl` curl, `spark` Spark, `trino` Trino, `pyiceberg` PyIceberg, `kafka-connect` Kafka Connect, `singlestore` SingleStore, `java` Java |
| `os` | `bash` Linux and macOS, `powershell` Windows (PowerShell), `gitbash` Windows (Git Bash) |
| `db` | `postgresql` PostgreSQL, `cockroachdb` CockroachDB, `oracle` Oracle, `mongodb` MongoDB |
| `store` | `aws` AWS S3, `ceph` Ceph, `silo` Silo |

- Order the tabs as the table does, leaving out those that do not apply. Two tabs at least.
- Without script, every tab shows, each under its label. Write each tab to read on its own.

### 5.8 Code blocks

```html
<div class="code" data-lang="bash" data-title="Create a namespace">
<pre><code>curl -sS -X POST "$NUNA/v1/trading/namespaces" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace": ["equities"]}'</code></pre>
</div>
<div class="code" data-lang="json" data-kind="output" data-title="Response">
<pre><code>{
  "namespace": ["equities"],
  "properties": {}
}</code></pre>
</div>
```

- `data-lang` is required. Values: `bash`, `powershell`, `json`, `yaml`, `properties`, `http`, `sql`, `python`,
  `java`, `scala`, `xml`, `dockerfile`, `ini`, `text`.
- `data-title` is optional: a file name (`values.yaml`) or what the block does.
- `data-kind="output"` marks what a program prints: shown muted, with no copy button. Every other block gets a copy
  button.
- `<pre><code>` starts at column 0 and the code starts right after `<code>`, so no stray first line is copied.
- No prompts (`$ `, `PS> `) in commands; they break copying. Output goes in its own output block.
- Shell lines wrap with ` \` at about 80 characters. JSON and YAML are indented by two spaces.
- Show real shapes: field names and values as the code produces them. Cut long arrays to two items and say so in the
  sentence before the block, not in the block; keep JSON valid.
- Commands are copied and run as they are: test them, or take them from a test or script in the repo that runs them.

### 5.9 Tables

```html
<div class="table-wrap">
  <table>
    <caption>What each privilege allows</caption>
    <thead><tr><th scope="col">Privilege</th><th scope="col">Allows</th></tr></thead>
    <tbody>
      <tr><td><code>describe</code></td><td>Seeing that the object exists: listing it and loading a namespace.</td></tr>
    </tbody>
  </table>
</div>
```

- Every table sits in `<div class="table-wrap">`, has a `thead` with `th scope="col"`, and a `caption` unless an
  `h2` or `h3` right above it says the same.
- A row header, where the first column names the row, is `<th scope="row">`.
- Cells hold inline content, `p` and `ul`. Never a code block or a nested table.

### 5.10 Parameter and response tables

Inside endpoint blocks and commands:


## 6. Voice and wording

The reader is an engineer at a bank or brokerage: busy, expert in their own field, new to nuna, and wary of anything
that sounds like marketing. Paul reads every page. Write for both.

### 6.1 The rules

1. **Plain English, precise.** Short sentences, common words, one idea per sentence. The exact name of the thing,
   every time; no synonyms for variety.
2. **Every claim true to the code.** Read the code path that does the thing, not only the internal document about it;
   internal documents drift. Quote error messages and console words exactly from the source. If the code and a
   document disagree, the code wins, and tell the session which document is wrong.
3. **No hype.** Never: simply, just, easy, easily, seamless, powerful, robust, cutting-edge, world-class,
   best-in-class, blazing, effortless, leverage, utilize, enterprise-grade, out of the box, magic. Say what it does and
   let the reader judge.
4. **Full sentences.** No fragments ("Needs JDK 25."), no telegraphic notes, no arrow chains (`→`, `->`, `=>`, `>`)
   in prose, no "A / B" for "A or B", no "and/or", no stacked parentheses. A list item is either a full sentence with a
   full stop or, in a reference list, a noun phrase without one; never both kinds in one list.
5. **Second person, present tense, active voice.** "You grant", "the server refuses". The actor is named: "the worker
   deletes the files", not "the files are deleted".
6. **Lead with the outcome.** The first sentence of a page, a section and a step says what happens or what to do.
   Reasons come after.
7. **Must, can and may mean three things.** "Must" is a requirement. "Can" is an option. "May" is permission granted
   by privileges ("members of `stewards` may place a hold"), never possibility. For possibility, say "might" or state
   the condition.
8. **Say what happens when it fails.** Every action that can be refused says what the refusal looks like and what to do.
9. **No internal process.** Never mention backlog item numbers, decision-ledger rows (D45), milestones (M8), bites,
   landing, worktrees, agents, the overnight run's agents, Paul, Atelier, or the dates decisions were made. The
   internal documents are full of these; strip them. Only `develop/` and `reference/release-notes.html` may name
   milestones, and in reader terms.
10. **The demo is not production.** Anything that is true only in the demo (developer tokens, the self-signed
    certificate, `presenter`, the demo's groups and catalogs) carries a `demo` callout or badge, or sits in `demo/`.
11. **Console actions use "select".** Select a button, link, tab or row; choose an option from a menu; enter text in
    a field; turn a switch on or off. Never "click", "hit" or "press" for a control; "press" is for keys.
12. **Spell as the repository does:** behaviour, colour, cancelled, licence (noun); authorization, organization (with
    z, as the APIs spell them).

### 6.2 Headings and titles

- Sentence case: only the first word and names capitalized.
- Guide and tutorial titles start with a verb: "Grant and revoke access". Concept titles are nouns: "The audit trail".
  Reference titles name the thing: "Privileges". Console pages: "The Audit page".
- At most 60 characters. No question headings except in the FAQ. No headings ending in a colon or full stop.

### 6.3 Numbers, units and times

- Digits for every measurement and value: "3 replicas", "30 s", "8 GB", "1,000 rounds". Words for small counts in
  prose that are not measurements: "two charts", "three images".
- Thousands separated by commas in prose, never in code. Units after a space: `30 s`, `500 ms`, `8 GB`, `1,000 rows`.
- Dates as 2026-11-26. Times in 24-hour form with the zone: 02:00 UTC.
- Sizes as the code reports them; say whether a figure is bytes, files or rows.

  `route.js` builds it (`p` page, `c` catalog, `k` kind, `ns` namespace levels joined by `%1F`, `n` name, `tab`,
  `g`, `r` ref), with `&amp;` for each `&`. Take it from `route.js`, never guess it; the example's names are
  illustrative. `data-shot-user` is a demo user. `data-shot-width` is `1440` for desktop or `390` for phone.
- `data-shot-state` says what must be true in the demo for the shot to show what the caption says.

```html
<figure class="shot" id="fig-table-maintenance">
```
