Questions and answers

Short answers to the questions engineers ask first about nuna, each linked to the page that explains it.

Does nuna hold my data?

No. Data files stay in your object store, and engines read and write them directly. The server holds each table's pointer in its database and writes only metadata files. See How nuna fits together.

How do I create a catalog?

You declare it in the server's settings under nuna.storage.catalogs; the server creates it at start-up. No API creates one. See Catalogs, namespaces, tables and views.

What happens when two engines commit to one table at once?

The database lets one move the table's pointer. The server tries the other again against the new metadata; if its requirements no longer hold, the engine gets 409 and retries by its own setting. See How a commit works.

Can an engine delete files?

No. Vended credentials cannot delete. Only the maintenance worker deletes, with its own storage identity, after the point-in-time recovery window. See Storage profiles and credential vending.

Can I undo a drop?

Yes, for 30 days by default: every drop is soft, and a restore brings the object back with its id, history and grants. A purge after that cannot be undone. See Dropping, restoring and purging.

Is a catalog branch the same as an Iceberg branch?

No. A catalog branch spans every table of a catalog and is named in the warehouse as catalog@branch. An Iceberg table branch lives in one table's metadata. See Catalog branches and tags.

Do I need Kafka?

No. The server's log is the record of audit, and the audit tables writer can take records over OTLP. Kafka, where configured, gets a copy. See The audit trail.

Which databases can the server use?

PostgreSQL, CockroachDB, Oracle and MongoDB. The server checks each one's durability settings at start-up and refuses to start on a finding you have not allowed. See Choosing a database.

Does maintenance run by itself?

Only what a policy turns on: every job is off by default. See Maintenance.

Does nuna issue tokens?

No. Tokens come from your identity provider; /v1/oauth/tokens answers with an error that names it. See Get a token.
