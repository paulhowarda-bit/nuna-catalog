Change data capture in the demo

Run the demo's CDC leg: changes made in PostgreSQL, Oracle and CockroachDB reach Iceberg history tables in nuna within about 10 seconds, one row per change.

Demo only For developers

Before you begin

  • The demo is running. The engine matrix is not: the two do not fit together.
  • The first run pulls Oracle Database Free's image, about 5 GB.
  • While the leg runs, Trino, the maintenance worker and the brokerage world's generator are stopped for its memory, and the audit table writer too when SingleStore is on. While the writer is stopped, the console's Audit page misses the leg's records.

Six connectors run in the demo's Kafka Connect 4.2.2: Debezium 3.7.1's PostgreSQL, Oracle and CockroachDB source connectors, and an Apache Iceberg sink for each, writing through nuna as user cdc with vended credentials and committing every 5 seconds. CockroachDB's clearing tables hold the brokerage world's clearing books, loaded on each cdc as they stand after the world's last end of day (The brokerage world).

Start the leg and watch a change arrive

  1. Start it.

    demo/demo.sh cdc

    The command waits for each source's snapshot (4 rows from PostgreSQL and from Oracle), then updates, deletes and inserts rows in PostgreSQL and Oracle and waits for those changes too: 8 rows in PostgreSQL's history and 7 in Oracle's. A leg run before carries on from its kept databases and offsets, without a new snapshot.

  2. Make a change.

    Open a prompt on a source and change a row. In Oracle, end with COMMIT, or Debezium sees nothing.

    demo/demo.sh psql             # database backoffice, user backoffice
demo/demo.sh sqlplus          # user treasury in FREEPDB1
demo/demo.sh cockroach        # database custody, as root
demo/demo.sh psql ana         # or as a person, with their password

  3. Watch it arrive.

    kafbat on port 8182 shows Debezium's change event in the topic. In the console, the history table has a new snapshot for each sink commit.

Each change is one appended row

After demo/demo.sh cdc stop, read the history in CloudBeaver's Trino connection, oldest first. offset is a keyword in Trino, so it is quoted:

SELECT "_cdc".op, "_cdc".ts, instruction_id, status
FROM lakehouse."history.postgres.settlement".instructions
ORDER BY "_cdc"."offset";

The history tables

The sink only appends, so each table is a history, never updated. A view over it that keeps the newest row per key that is not a delete gives the rows as they are now. The sink adds a struct column _cdc:

FieldHolds
opI, U or D. A deleted row is written as it was before the delete.
tsWhen Debezium read the change.
offsetIts Kafka offset.
source, targetThe source table and the Iceberg table.
keyThe row's key.
  • Every timestamp lands as timestamptz, numbers with a scale as decimal(38, s), and Oracle's NUMBER(10) as long.
  • Oracle's upper-case column names become lower case, column by column; a column added later arrives in upper case.
  • CockroachDB's connector can send again the changes made shortly before a stop, so its history may repeat them.

Who may do what in the sources

The people sign in to all three databases with their Keycloak passwords, in a prompt or through their own CloudBeaver connections, such as backoffice (PostgreSQL, as ana). Their changes reach the history tables like any other.

Pause or reset the leg

CommandWhat it does
demo/demo.sh cdc stopStops the connectors, keeping their offsets, and the databases' pods, keeping their volumes; topics and history tables stay. Starts Trino, the audit table writer, the maintenance worker and the generator again. The next cdc carries on.
demo/demo.sh cdc resetDeletes the leg, running or paused: connectors and offsets, databases and their volumes, topics. The next cdc starts anew from the SQL files and drops the previous run's history tables.
demo/demo.sh downPauses the leg as cdc stop does.

  -K ~/.nuna-demo/secrets/connect.curlrc 'https://localhost:8186/connectors?expand=status'
