Trino and CloudBeaver in the demo

Query the demo's catalogs from Trino in CloudBeaver, signed in as a demo person. nuna sees that person in every query and applies their privileges, row filters and column masks.

Demo only For data users

Before you begin

  • The demo is running, and the CDC leg is not: Trino stops while it runs.
  • You have trusted the demo's certificate (HTTPS and the certificate).
  • You know a person's password, from ~/.nuna-demo/people (Demo users and sign-in).

How the query reaches nuna

CloudBeaver on port 8185 is a SQL editor in the browser. Each person has their own connections and sees only those; the Trino one is named like nuna (Trino, as ana). It sends Trino the person's own token as the extra credential token, and Trino passes it to nuna with each request (iceberg.rest-catalog.session=USER). Trino's own token goes with it, in the header X-Nuna-Engine-Authorization, and vouches for the person: Trino's client trino-demo is registered as a trusted engine, and its own group holds no grant.

Run a query

  1. Sign in to CloudBeaver.

    Go to https://localhost:8185 and sign in through Keycloak as ana.

  2. Open your Trino connection.

    Open nuna (Trino, as ana) and a SQL editor on it. The navigator lists every namespace at every depth as a schema named by its dotted path.

  3. Query a table.

    Quote the namespace, since it holds dots:

    SELECT * FROM lakehouse."markets.fx".rates;
SELECT * FROM lakehouse."markets.equities.eu.xetra".trades;

    The first query after Trino starts takes about 10 seconds; later ones about 2.

The query runs as you

The console's Audit page, read as gary or presenter, lists the read with the person as end user and Trino, engine trino-demo, acting for them.

What each person can do

  • ana reads and changes data and definitions: CREATE SCHEMA, CREATE TABLE, INSERT, UPDATE, DELETE, ALTER and DROP.
  • stella reads.
  • gary and oscar see the namespaces and tables listed, but every read fails, since they hold no grant on data: Failed to load table 'positions'.

Row filters and column masks

The table markets.desks.positions is flagged, and each group has a rule on it. Trino asks nuna for the rules through its OPA access control, forwarding the person's token, and applies them. Run the same query as ana and as stella:

SELECT * FROM lakehouse."markets.desks".positions;

Read without a trusted engine, such as from Spark with the person's own token, the table's data answers 403: only a trusted engine gets a flagged table's files. gary lists and changes the rules at /management/v1/catalogs/lakehouse/row-column-rules.

From the command line

Trino's CLI in its pod runs a query as a person. --debug prints the cause of a refusal:

MSYS_NO_PATHCONV=1 kubectl --context kind-nuna -n nuna-demo exec deployment/trino -- \
  trino --user ana --debug \
  --extra-credential "token=$(cat ~/.nuna-demo/tokens/ana.jwt)" \
  --execute 'SELECT * FROM lakehouse."markets.desks".positions'

The user name names the query in Trino; Trino checks no password. A query without a token fails: Trino then asks nuna to exchange one, and nuna issues none.

CloudBeaver's administration

oscar administers CloudBeaver: select Settings, then Administration. Scripts and settings last as long as CloudBeaver's pod, which engines and cdc restart; each new pod adds the people and their connections again. While the CDC leg runs, each person also has connections to its three databases (Change data capture in the demo).
