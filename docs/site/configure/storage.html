Storage settings

Name the object stores the catalog places tables in, the prefixes each may use, and how the server vends credentials for them.

For platform operators

A storage profile names one S3-compatible store and the prefixes in it that catalogs may use. Each catalog is bound to one profile (Catalog settings), and the server places every table of the catalog under that profile's table root and vends credentials only for that profile's store. Profiles are read at start-up; the server refuses to start on a profile it cannot use.

The deployment's storage profiles, keyed by name. A catalog names its profile by this name. No two profiles' allowed prefixes may overlap: one may not equal, contain or lie within another's, and the server refuses to start naming the first pair that does.

Each profile is written to the database at start-up when the database holds it otherwise, with an audit record of type storage-setup (action PROFILE_SET) naming the kind, endpoint, STS role, allowed prefixes and KMS key it sets.

A storage profile

Each profile needs kind, endpoint, table-root and allowed-prefixes; without any of them the server refuses to start with nuna.storage.profiles.name needs kind, endpoint, table-root and allowed-prefixes.

Read by
the server
Restart
Needed

Which kind of store the profile names:

  • S3: AWS S3, addressed by virtual host. Needs sts-role.
  • CEPH: Ceph RADOS Gateway, addressed by path. Needs sts-role.
  • MINIO: MinIO, addressed by path. Needs no STS role.

An S3 or Ceph profile without an STS role stops the server with KIND needs an STS role to vend credentials.

The store's S3 endpoint, as https://host or https://host:port, with no path. For AWS S3, the regional endpoint. Anything else stops the server with endpoint must be http(s)://host[:port], got endpoint; plain http is refused too unless nuna.storage.require-tls is off.

Engines are handed this endpoint (s3.endpoint) and told to address by path on Ceph and MinIO (s3.path-style-access).

The role STS assumes to vend credentials. S3 and Ceph profiles need one; a MinIO profile needs none. Each vend tags its session with the caller, so the role's trust policy must allow the catalog's own identity both sts:AssumeRole and sts:TagSession.

When STS refuses or cannot be reached, the request for credentials fails with 503 Storage credentials cannot be issued now; retry later.

Read by
the server
Restart
Needed

The maintenance worker's own storage identity, the one principal the profile's delete policy lets delete objects:

  • AWS S3: an IAM role or user ARN.
  • Ceph: a user ARN, arn:aws:iam::tenant:user/uid.
  • MinIO: a user name.

It may hold only letters, digits and +=,.@_:/-; anything else stops the server with nuna.storage.profiles.name.maintenance-principal: and the reason. Without it the profile has no delete policy, and the console's storage setup shows the profile as unprotected.

nuna.storage.profiles.name.ca-bundle

Type
path (a PEM file)
Default
none: the JVM's own CAs only
Environment variable
NUNA_STORAGE_PROFILES_NAME_CABUNDLE
Helm
config.nuna.storage.profiles.name.ca-bundle
Read by
the server
Restart
Needed

A PEM file of one or more CA certificates, for a store whose certificate a private CA signed. This profile's S3 and STS clients trust them beside the JVM's CAs, and no other client does. Vended credentials carry no trust: each engine trusts the store through its own setup.

The server refuses to start, with nuna.storage.profiles.name.ca-bundle: and the reason, when it cannot read the file, finds no certificate in it, or finds something other than PEM certificates. In the catalog chart, mount the bundle with storageCaConfigMap.name, at /etc/nuna/storage-ca.

nuna.storage.profiles.name.kms-key

Type
string (a KMS key ARN)
Default
none: writes are encrypted as the bucket's default says
Environment variable
NUNA_STORAGE_PROFILES_NAME_KMSKEY
Helm
config.nuna.storage.profiles.name.kms-key
Read by
the server
Restart
Needed

AWS S3 only: the SSE-KMS key every write to this profile must use. The server writes its metadata files with it, vended credentials may write with it alone (a write with no key or another key is refused), and the configuration handed to engines tells them to use it (s3.sse.type and s3.sse.key). The catalog's own identity and the STS role need kms:GenerateDataKey and kms:Decrypt on it.

The server refuses to start, with nuna.storage.profiles.name.kms-key: and the reason, on a Ceph or MinIO profile (only an AWS S3 profile names a KMS key, not a KIND profile), on anything but a key ARN (must be a KMS key ARN, arn:<partition>:kms:<region>:<account>:key/<key id>, not an alias or a bare key id), and on a key in another region (the key arn is not in the profile's region region: S3 encrypts only with a key in the bucket's region).

Examples

Ceph with a private CA

config:
  nuna:
    storage:
      profiles:
        onprem:
          kind: CEPH
          endpoint: https://s3.example
          table-root: s3://trading-tables/warehouse
          allowed-prefixes:
            - s3://trading-tables/warehouse
          sts-role: arn:aws:iam:::role/nuna-vend
          maintenance-principal: arn:aws:iam::data:user/nuna-maintenance
          ca-bundle: /etc/nuna/storage-ca/ca.crt
      catalogs:
        trading:
          profile: onprem
          kms-key-set: trading-keys
          legal-entity: example-securities
storageCaConfigMap:
  name: storage-ca

The catalog's own static credentials for the store go in the Secret:

kubectl -n nuna create secret generic nuna-catalog-secrets \
  --from-literal=nuna.storage.profiles.onprem.access-key-id="$S3_ACCESS_KEY_ID" \
  --from-literal=nuna.storage.profiles.onprem.secret-access-key="$S3_SECRET_ACCESS_KEY"

AWS S3 with a KMS key

config:
  nuna:
    storage:
      profiles:
        aws:
          kind: S3
          endpoint: https://s3.eu-west-1.amazonaws.com
          region: eu-west-1
          table-root: s3://example-trading/warehouse
          allowed-prefixes:
            - s3://example-trading/warehouse
          sts-role: arn:aws:iam::111122223333:role/nuna-vend
          kms-key: arn:aws:kms:eu-west-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab

With no access-key-id, the server takes its identity from the AWS SDK's default chain, such as the web identity of its service account (serviceAccount.annotations).
