Each program reads its settings once, at start-up, and refuses to start on one it cannot use, naming the setting. No setting changes while a program runs: change it and restart.

How settings reach a program

Each program is a Spring Boot application, and takes settings the ways Spring Boot does. The charts use three of them:

  • A YAML file. The chart renders its config value into application.yaml in a ConfigMap, mounts it at /etc/nuna/config and points SPRING_CONFIG_ADDITIONAL_LOCATION at it. Its settings beat the defaults in the program's own application.yaml.
  • A Secret as a config tree. The chart mounts the Secret named in secrets.existingSecret, or the one it makes from secrets.values, at /etc/nuna/secrets and imports it with SPRING_CONFIG_IMPORT=optional:configtree:/etc/nuna/secrets/. Each key of the Secret is a setting's full name, such as spring.datasource.password, and its value the setting's value.
  • Environment variables. The chart's env value adds them. An environment variable beats the YAML file and the config tree for the same setting.

Put each setting in one place. Secrets go only in the Secret: database passwords, the MongoDB connection string, storage keys, client secrets and the audit receiver's token.

Environment variable names

A setting's environment variable is its name in upper case, with each . turned into _ and each - removed: nuna.security.grant-admin-groups is NUNA_SECURITY_GRANTADMINGROUPS. A list entry takes its index, counting from 0: NUNA_SECURITY_ISSUERS_0_ISSUER. A map key in an environment variable is read in lower case and cannot hold a - or ., so set map entries, such as profiles, catalogs and maintenance defaults, in YAML.

Durations take ISO-8601 (PT10M, P1D) or a number and a unit: ns, us, ms, s, m, h, d. A bare number is milliseconds.
