Catalog settings

Declare the deployment's catalogs in the server's settings, each bound to one storage profile, KMS key set and legal entity for its whole life.

For platform operators

The server has no API that creates a catalog. Each catalog is declared in the server's settings, under nuna.storage.catalogs, and the server creates it at start-up. There are no nuna.catalog.* settings: everything about a catalog that is set at all is set here and on the pages this one links to.

How a declared catalog comes to exist

At start-up, before it takes requests, the server reads nuna.storage.catalogs and, for each catalog named there:

  1. Refuses to start if the name holds @, which the REST prefix catalog@ref keeps for a catalog branch or tag.
  2. Refuses to start if the entry lacks profile, kms-key-set or legal-entity, or if profile names no profile in nuna.storage.profiles.
  3. Creates the catalog when the database holds none of that name, and writes an audit record of type storage-setup (action CATALOG_CREATED) whose actor is nuna-configuration.
  4. Refuses to start when the database already holds the catalog bound to another profile, KMS key set or legal entity.

A catalog's binding to its storage profile, KMS key set and legal entity never changes once the catalog exists. Changing any of the three for an existing catalog stops every server that reads the new settings, with the message catalog name is bound to … in the store, but configured as …; a catalog's boundary never changes.

Catalog names are case-insensitive and keep the case they were declared with: Trading and trading are one catalog. Two servers that start together and both declare a new catalog create it once; the second checks that the catalog holds what it would have written.

Removing a catalog from nuna.storage.catalogs does not remove it from the database, but the catalog list (GET /management/v1/catalogs, which the console reads) shows only the catalogs the settings declare, so the console no longer offers it. Its tables still answer over the Iceberg REST API as long as the server configures the storage profile the catalog is bound to. A server that lacks that profile fails each request to the catalog with the message catalog id uses storage profile id, which this server does not configure.

Grants come after the catalog

A new catalog holds no grants, so only grant admins can act in it at first. Grant the first groups their privileges as Create a catalog describes. The one exception is the audit catalog, whose two groups the server grants at start-up from nuna.audit.tables.*.

The catalogs this deployment declares. The server creates each one that does not exist at start-up and checks each one that does. With none declared, the server starts and serves no catalog until one is.

Every server of a deployment reads the same database, so give every server the same declarations.

The storage profile the catalog's tables live in, by its name in nuna.storage.profiles. Every table of the catalog is placed under that profile's table-root, and every credential vended for the catalog is scoped to that profile's store.

The server refuses to start when it is missing, with nuna.storage.catalogs.name needs profile, kms-key-set and legal-entity, and when it names no profile, with nuna.storage.catalogs.name.profile names no profile: profile. It can never change for an existing catalog.

A name for the set of KMS keys the catalog's data is encrypted under, recorded with the catalog and shown in its properties (GET /management/v1/catalogs/{catalog}/properties, and the console's Catalog page). The server does not call KMS and does not encrypt with it: encryption at rest follows the storage profile's kms-key, or the bucket's default when the profile names none.

Required, and fixed once the catalog exists.

The legal entity whose data the catalog holds, recorded with the catalog and shown in its properties beside the KMS key set. The server records it and shows it; no rule reads it.

Required, and fixed once the catalog exists.

Example

Two catalogs on one profile, in the catalog chart's values. The profile itself is on Storage settings.

config:
  nuna:
    storage:
      catalogs:
        trading:
          profile: onprem
          kms-key-set: trading-keys
          legal-entity: example-securities
        nuna_audit:
          profile: onprem
          kms-key-set: audit-keys
          legal-entity: example-securities

After the servers start, GET /management/v1/catalogs lists the declared catalogs a caller holds something in (grant admins and platform operators see every one), and GET /management/v1/catalogs/trading/properties answers the catalog's binding: its name, KMS key set, legal entity and storage profile (name, kind, endpoint, region, table root, allowed prefixes and whether writes use a KMS key). Neither answer names a key, a role or a credential.
