Get a token

Get an access token from your identity provider to call nuna, let an engine renew its own, and know how long a token lasts. The server validates tokens; it never issues them.

For engine users and platform operators

Before you begin

  • You need a client registered at your organization's identity provider, with its client id and secret, whose tokens the server trusts. Platform operators name each trusted issuer in nuna.security.issuers (Security settings).
  • The token's groups decide what you may do. A grant admin grants privileges to those groups (Grant and revoke access).

What the server accepts

The server accepts a signed JWT as a bearer token when every one of these holds. There is no setting that turns the check off: a server with no trusted issuer refuses to start.

  • Its iss claim is exactly the issuer of one entry in nuna.security.issuers.
  • Its signature verifies against that issuer's keys, fetched from the entry's jwks-uri, with one of the entry's algorithms. The server does no OpenID Connect discovery.
  • Its aud claim names one of the entry's audiences.
  • It has an exp claim, and the server's clock is inside its exp and nbf window, give or take nuna.security.clock-skew (default 60s).
  • It carries the claim the entry's user-id-claim names (the principal) and the claim its client-id-claim names (the client). The claim groups-claim names holds the groups; a token with none has no groups.
  • Its groups are in the token itself. A token whose groups were moved out of it because there were too many (the group overage of Microsoft Entra ID, named in _claim_names) is refused.

Get a token with client credentials

A program that calls nuna as itself gets its token with the OAuth 2 client-credentials grant, from the identity provider's token endpoint. This example uses Keycloak's token endpoint for realm data; your provider's endpoint, and whether it needs scope or audience, may differ.

  1. Keep the client secret in a variable, not in the command.

    read -rs CLIENT_SECRET

  2. Ask the identity provider for a token.

    curl -sS -X POST "https://idp.example/realms/data/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "client_id=trading-loader" \
  --data-urlencode "client_secret=$CLIENT_SECRET"

    The answer is the provider's. The fields nuna's own programs read from it are access_token and expires_in, in seconds; Keycloak's answer holds more fields, cut here.

    {
  "access_token": "…",
  "expires_in": 300,
  "token_type": "Bearer"
}

  3. Put the access_token value in TOKEN.

    export TOKEN=…   # the access_token value

The server answers with a catalog's configuration

Run curl -sS "$NUNA/v1/config?warehouse=trading" -H "Authorization: Bearer $TOKEN". A JSON object with "prefix": "trading" means the token was accepted (Make a first request).

Let an engine renew its own token

An engine given a fixed token stops working when that token expires. Iceberg's REST client can instead run the client-credentials grant itself and renew the token as it nears expiry. Give it the client's id and secret and the identity provider's token endpoint:

Iceberg REST client properties for a renewing token
PropertyValue
credentialThe client id and secret, joined by a colon: client-id:secret.
oauth2-server-uriThe identity provider's token endpoint. Without it, the client asks the catalog's own /v1/oauth/tokens, which nuna refuses.
scopeThe scope your provider expects, if it expects one.
audienceThe audience your provider expects, if it expects one.

nuna's own Iceberg clients sign in this way: the maintenance worker gives its compaction jobs these four properties, and the audit table writer sets them for itself. The engine matrix runs the audit table writer against an identity provider's token endpoint every night code changes. Each engine's page shows where the properties go: Spark, PyIceberg, Trino.

Not documented yet: Spark, PyIceberg or Trino renewing a token this way against nuna. The engine matrix gives those engines a fixed token.

The /v1/oauth/tokens endpoint

The Iceberg REST standard describes a token endpoint on the catalog, /v1/oauth/tokens. nuna answers every call to it, with any method and without a token, with 400 and the same OAuth error, so a client that tries it learns where to go instead. /v1/config does not advertise it.

{
  "error": "unsupported_grant_type",
  "error_description": "This catalog does not issue tokens. Get an access token from the organisation's identity provider and send it as a bearer token."
}

Platform operators replace the words the organisation's identity provider with the provider's name or address in nuna.rest.identity-provider (Server settings).

How long a token lasts

The identity provider decides, by the token's exp claim; nuna sets no lifetime of its own. The server checks the token on every request and accepts it until exp plus the clock skew. Storage credentials the server vends with a table are separate: they last nuna.storage.credential-lifetime (default 30m) whatever the token's lifetime (Storage profiles and credential vending).

The demo's tokens last seven days

The demo signs its own tokens, with issuer https://idp.demo/nuna and audience nuna-catalog, one per demo user, valid for seven days. They are in ~/.nuna-demo/tokens/user.jwt. demo/demo.sh token prints the demo's addresses and two of the tokens; when the tokens have less than an hour left, it makes new ones first and restarts the demo's services that hold them (demo.sh reference, Demo users and sign-in).

Act for an end user

An engine that runs queries for many people, such as Trino, can call nuna as each person. The engine's client must be registered as a trusted engine; it then names the person in headers beside its own token, or sends the person's token with its own in X-Nuna-Engine-Authorization. API reference lists the headers, and Engines registers a client.

If it fails

What you seeWhyWhat to do
401, Not authorized: the bearer token is missing or was not acceptedThe token is missing, expired, signed by an issuer the server does not trust, meant for another audience, or lacks a claim the issuer's entry names. The answer never says which; the server's audit record of the failure does.Get a new token. If a fresh one is refused, ask a platform operator to compare its claims with nuna.security.issuers.
503, The token could not be checked: its issuer's signing keys could not be fetched; retry laterThe server could not fetch the issuer's keys from its jwks-uri. The token is not known to be bad.Send the request again after the Retry-After seconds. If it lasts, a platform operator checks the path from the server to the identity provider.
403, Forbidden: client … is not a registered trusted engine, so it may not act for another userThe request named an end user, but its client is not a registered trusted engine.Register the client (Engines), or send no end-user headers.
400, unsupported_grant_type from /v1/oauth/tokensThe client asked nuna for a token.Set oauth2-server-uri to the identity provider's token endpoint, or give the client a token.
