Use the APIs with curl

Call nuna's Iceberg REST API and management API from a shell with curl: the two variables every example on this site uses, the certificate, request ids, paging, idempotency keys, If-Match and errors.

For engine users, data stewards, grant admins and platform operators

Before you begin

  • You need curl and a POSIX shell: bash or zsh on Linux and macOS, Git Bash on Windows. Every example on this site is written for that shell; the line continuations (\) and quoting do not work in PowerShell.
  • You need an access token from your identity provider (Get a token). nuna issues no tokens of its own.
  • You need the server's address. Ask the platform operators who installed nuna, or read it from the Helm release (Install the catalog server with Helm).

Set the two shell variables

Every curl example on this site uses two shell variables: NUNA, the server's base URL with no trailing slash, and TOKEN, your access token. Set them once in the shell you run the examples in.

export NUNA=https://nuna.example
export TOKEN=…   # see Get a token

Every request but two carries the token as a bearer token: -H "Authorization: Bearer $TOKEN". The two exceptions are /v1/oauth/tokens, which answers every call with a fixed error, and the OPA decision endpoints under /opa/v1/, which read the user's token from the request body (OPA decisions).

The local demo uses its own address and tokens

In the demo, set NUNA=https://localhost:8181 and read a token from the demo's token files, for example TOKEN=$(cat ~/.nuna-demo/tokens/ana.jwt). Demo users and sign-in lists every demo user and what each may do.

Trust the server's certificate

The server is reached over HTTPS. When its certificate comes from a certificate authority your machine does not trust, such as your organization's internal one, give curl that authority's certificate in PEM form. Either add --cacert to each command, or set CURL_CA_BUNDLE once, so the examples on this site run as written.

export CURL_CA_BUNDLE=/path/to/internal-ca.pem

curl on Windows checks whether the certificate has been revoked. A certificate authority that publishes no revocation list makes that check fail with schannel: the revocation status is unknown; add --ssl-revoke-best-effort to the command for such an authority.

The demo's certificate authority is in ~/.nuna-demo/tls

The demo makes its own certificate authority, which can vouch only for localhost. Point curl at it, and on Windows add --ssl-revoke-best-effort:

export CURL_CA_BUNDLE=~/.nuna-demo/tls/ca.crt

Make a first request

Ask the server for a catalog's configuration. An engine makes this call first, and it needs only a token and a catalog name. The catalog is named by the warehouse query parameter.

curl -sS "$NUNA/v1/config?warehouse=trading" \
  -H "Authorization: Bearer $TOKEN"

The answer names the prefix every other Iceberg call uses, the endpoints the server serves, and how long it keeps an idempotency key's answer. The endpoint list is cut to two items here.

{
  "defaults": {},
  "overrides": {
    "prefix": "trading"
  },
  "endpoints": [
    "GET /v1/{prefix}/namespaces",
    "POST /v1/{prefix}/namespaces"
  ],
  "idempotency-key-lifetime": "PT24H"
}

From here, an Iceberg call puts the prefix after /v1/: "$NUNA/v1/trading/namespaces". A management call starts with /management/v1/: "$NUNA/management/v1/catalogs". API reference lists every endpoint of both.

Read the response headers

Add -i to see the status line and headers before the body. Three headers matter on nuna's answers.

Response headers worth reading
HeaderOnMeaning
X-Request-IDEvery responseThe request's id: yours if you sent one, or one the server made (Request ids).
ETagA table loadA tag for this exact answer. Send it back in If-None-Match and the server answers 304 with no body while the table and your access to it are unchanged (Load a table).
Retry-After503 and 429Seconds to wait before sending the same request again. A 503 with Retry-After means nothing was applied.
 
curl -sS -i "$NUNA/v1/trading/namespaces" \
  -H "Authorization: Bearer $TOKEN"
HTTP/1.1 200
Content-Type: application/json
X-Request-ID: b7346ef207d85c781f9b8ce274a64d7d

{"namespaces":[["equities"],["reference"]],"next-page-token":null}

Request ids

Every response carries X-Request-ID. Send your own in the request, 1 to 128 characters, and the server uses it; send none, or one that is blank or longer than 128 characters, and the server uses the request's trace id, or a random UUID when there is no trace. The id is in every log line the server writes while it handles the request (the requestId field) and in every audit record the request leaves, so it is what to quote when you ask an operator about one call (Traces, logs and the request id).

curl -sS -i "$NUNA/v1/trading/namespaces/equities" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Request-ID: nightly-load-2026-11-26-0042"

Page through a listing

The Iceberg listings (namespaces, tables, views) page only when you ask. Without pageToken, the server answers every item and "next-page-token": null, and ignores pageSize. To page, send pageToken empty for the first page, then each answer's next-page-token until it is null. pageSize defaults to 100; a larger size than 1000 gets 1000. Operators change both bounds with nuna.rest.default-page-size and nuna.rest.max-page-size (Server settings).

curl -sS "$NUNA/v1/trading/namespaces?pageToken=&pageSize=1" \
  -H "Authorization: Bearer $TOKEN"
{
  "namespaces": [["equities"]],
  "next-page-token": "AAAACGVxdWl0aWVz"
}
curl -sS "$NUNA/v1/trading/namespaces?pageToken=AAAACGVxdWl0aWVz&pageSize=1" \
  -H "Authorization: Bearer $TOKEN"
{
  "namespaces": [["reference"]],
  "next-page-token": null
}

A token the server did not give is refused with 400 and Invalid page token: …; a pageSize below 1 or not a number with 400 and Invalid page size: …. The management API pages the same way, with pageToken in the query and next-page-token in the body, but each listing sets its own size parameter and bounds; its page says which.

Send a write safely

A write that times out might or might not have been applied. Send an Idempotency-Key with every write, and send the same request with the same key again after a timeout: the server applies it once and answers every repeat with the first answer.

curl -sS -X POST "$NUNA/v1/trading/namespaces" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: create-equities-daily-1" \
  -d '{"namespace": ["equities", "daily"], "properties": {}}'
  • A key is 1 to 128 characters. A blank or longer key is refused with 400 and Invalid Idempotency-Key: must be 1 to 128 characters.
  • The server keeps a key's answer for 24 hours, as idempotency-key-lifetime in /v1/config says (PT24H).
  • A key is bound to your principal, the route, the path it acts on and the body. The same key with a different request is refused with 400 and Idempotency key … was used for a different request.
  • A repeat sent while the first request still runs waits for it, then gets its answer.
  • An answer of 500 or above is not kept: the key is released, and the repeat runs again.

The Iceberg routes take a key on every write: namespace create, drop and property changes, and table and view create, commit, replace, register, unregister, drop and rename, and the multi-table commit. In the management API, a branch's or tag's create, renewal and deletion take one (Branches and tags API).

If-Match guards one kind of change: a row filter or column mask. Send the rule's version as the rules list gives it, If-Match: "version", and the server writes nothing and answers 412 if someone else changed the rule since you read it (Row and column rules).

Read an error

Every error answer is JSON with one object, error, holding the message, the error type and the status again. The type is the Iceberg exception name an engine maps to its own error; Error responses lists every type.

curl -sS "$NUNA/v1/trading/namespaces/equities/tables/trades" \
  -H "Authorization: Bearer $TOKEN"
{
  "error": {
    "message": "Table does not exist: equities.trades",
    "type": "NoSuchTableException",
    "code": 404
  }
}

A 404 also answers a request for something you hold no privilege on, so the answer does not tell you whether it exists (Identity and access).

If it fails

What you seeWhyWhat to do
401, Not authorized: the bearer token is missing or was not acceptedNo Authorization header, a token that has expired, or one from an issuer the server does not trust.Check that TOKEN is set and get a new token (Get a token).
curl: (60) and a certificate messagecurl does not trust the server's certificate authority.Set CURL_CA_BUNDLE or add --cacert (Trust the server's certificate).
404, NoSuchWarehouseException, The given warehouse does not exist: …The catalog does not exist, or you hold nothing in it.Check the name, then ask a grant admin for a grant (Grant and revoke access).
400, Missing query parameter warehouse, and this server has no default warehouse/v1/config was called without warehouse, and the server has no default catalog.Add ?warehouse=catalog.
503 with Retry-AfterThe server could not reach its database, or the identity provider's signing keys, and applied nothing.Wait the seconds Retry-After gives, then send the same request again, with the same idempotency key.
