Other engines

Connect an engine nuna has not tested, such as DuckDB, StarRocks, Flink or Spice, with the standard Iceberg REST catalog settings, and know the problems seen when some were tried.

For engine users Not tested by nuna

No nuna test runs these engines

nuna serves the standard Iceberg REST API, so an engine that speaks it correctly can connect. But nothing on this page is checked on each change. The notes for DuckDB, StarRocks and Spice come from one trial of each against nuna's demo; versions differ, and your result may too. The tested engines are on Engine compatibility.

Before you begin

  • An access token (Get a token). The engine must take a bearer token, or run the client-credentials grant against your identity provider: nuna issues no tokens itself, so an engine that can only ask the catalog for one cannot connect.
  • Grants for the token's groups on the catalog (Privileges).

What every engine needs

SettingValue
Catalog typeIceberg REST.
URIThe server's address, https://nuna.example. The client adds /v1/….
WarehouseThe nuna catalog's name, or catalog@ref for a branch or tag. Required: the server answers 400 to a configuration request without one, unless a default is set.
TokenA bearer token, or the client id, secret and token endpoint of your identity provider.
Storage accessVended credentials. nuna sends them, with the object store's address (s3.endpoint, for any store but AWS) and s3.path-style-access, in each table's load answer, whether or not the engine sends X-Iceberg-Access-Delegation.
Nested namespacesTurn them on if the engine has a switch for it; many show only top-level namespaces otherwise.

Engines built on Iceberg's Java library or iceberg-rust take the object store's address from the load answer. Engines with their own storage layer may ignore it and send the credentials to AWS instead; give them the object store's address in their own settings.

DuckDB

Tried with DuckDB 2.0.0 and its iceberg extension.

CREATE SECRET nuna (TYPE iceberg, TOKEN '…');
ATTACH 'trading' AS trading (TYPE iceberg, SECRET nuna, URI 'https://nuna.example', SUPPORT_NESTED_NAMESPACES true);
SELECT * FROM trading."equities.daily".positions;
  • Without SUPPORT_NESTED_NAMESPACES true, only top-level namespaces' tables show. With it, each namespace is a schema named with dots, which must be quoted.
  • Vended credentials are the default, and DuckDB used the vended object store address with no S3 secret of its own.
  • Reads of v2 position deletes and v3 deletion vectors matched the data. CREATE SCHEMA, CREATE TABLE, INSERT and DELETE worked.
  • DuckDB asks for format version 2 when it creates a table; add WITH ('format-version' = 3) for v3.
  • A table you may not read fails only the query that reads it.

StarRocks

Tried with StarRocks 4.1.7.

CREATE EXTERNAL CATALOG trading PROPERTIES (
  "type" = "iceberg",
  "iceberg.catalog.type" = "rest",
  "iceberg.catalog.uri" = "https://nuna.example",
  "iceberg.catalog.warehouse" = "trading",
  "iceberg.catalog.security" = "oauth2",
  "iceberg.catalog.oauth2.token" = "…",
  "iceberg.catalog.vended-credentials-enabled" = "true",
  "iceberg.catalog.rest.nested-namespace-enabled" = "true",
  "aws.s3.region" = "us-east-1",
  "aws.s3.endpoint" = "https://s3.example",
  "aws.s3.enable_path_style_access" = "true"
);
  • StarRocks ignores the vended object store address: without aws.s3.endpoint, it sent the credentials to AWS and every read failed with an S3 400.
  • CREATE, INSERT and ADD COLUMN worked on v2 and v3 tables, and DELETE on v2. DELETE on a v3 table fails inside StarRocks (Must use DVs for position deletes in V3): nothing reaches nuna.
  • Nested namespaces appear as databases named with dots, which must be backquoted.

Spice

Tried with Spice.ai OSS 2.4.2. Give the catalog only iceberg_token and iceberg_warehouse in its parameters.

  • Spice refuses a vended object store address on a private network unless SPICE_URL_TABLE_ALLOW_PRIVATE_HOSTS=true is set for the runtime. Setting iceberg_s3_endpoint instead makes Spice drop the vended credentials.
  • A Spice catalog shows only the tables one level below its from namespace; deeper tables need one catalog per parent namespace.
  • One table you may not read keeps the whole catalog from loading; leave it out with exclude.
  • Spice reaches nuna under one identity per catalog: nuna's audit trail shows no end user.

Flink and the rest

Flink's Iceberg connector uses Iceberg's Java REST catalog, the same client Spark uses, so Spark's catalog settings carry over with Flink's 'catalog-type'='rest' form. For any other engine, use the settings in What every engine needs and the engine's own documentation.

Not documented yet: Flink's settings against nuna. Flink is not in the engine matrix, and no Flink run is recorded with its settings.
