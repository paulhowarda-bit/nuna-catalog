How nuna is tested

nuna's tests run in three tiers, chosen by JUnit tags: a fast build with no containers, a heavy build with every container, and nightly tests that run for hours.

What it is

The three tiers
CommandRuns
./gradlew buildEvery test not tagged heavy, overnight or cas: about 1,580 tests that need only Java.
./gradlew build -PheavyAlso every test tagged heavy: every test that starts a container (PostgreSQL, CockroachDB, Oracle, MongoDB, the S3 store, Kafka, Keycloak, Chrome), including the full store suite on all four databases and every fault-injection test.
./gradlew build -PnightlyOnly the tests tagged overnight and cas: the load and resilience runs, the engine matrix, the per-mutation fault sweeps, and the compare-and-swap test at 1,000 rounds on every database.

How it works

The shared store suite

Every database store passes one suite of tests from catalog-store-api. It injects lost answers and lost COMMITs, kills connections mid-commit and fails over, and checks that every acknowledged commit is present exactly once. The compare-and-swap test, CommitSuite#exactlyOneWriterWinsEachRound, races writers on one pointer round after round and checks that exactly one wins each round.

Conformance

catalog-tests-conformance runs the Iceberg REST Compatibility Kit against the server, and fails if a test that passed stops passing.

The engine matrix

catalog-tests-engines deploys the server with its Helm chart into a kind cluster and runs Spark, Kafka Connect, PyIceberg and SingleStore against it: create, write, read, evolve and drop format version 2 and 3 tables in a three-level namespace, row-level deletes, updates and merges, and reads of each other's tables.

The S3 store

Every test that needs S3 uses one store, chosen with -Ps3=silo (the default), ceph or aws; aws also needs -Pnuna.aws.profile=profile.

Bite runs

A test that guards a check is proved by a bite: a recorded patch, in bites/, that breaks the check. bites/run.sh applies each patch, runs its test, expects it to fail, reverts, and checks that every tracked file is restored. A bite's verdict is BITES when the test fails on its own, NO BITE when it passes, and SETUP when the run proves neither. The fast build checks that every recorded patch still applies.

What it guarantees and what it does not

  • The fast build runs anywhere a JDK 25 runs, with no container engine.
  • Heavy and nightly runs never take a result from the build cache: each run is a new sample.
  • A heavy test task that runs past 60 minutes, or a nightly one past 120 minutes, fails rather than hangs.
  • Latency figures from a laptop show relative behaviour only.

Limits

  • Two Gradle tasks run at once (org.gradle.workers.max=2), so at most two modules' containers run together.
  • Each test JVM gets 4 GB of heap.
