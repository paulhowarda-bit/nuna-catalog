Storage profiles and credential vending

A storage profile names the object store and prefixes a catalog's tables live in, and the server vends each engine short-lived credentials scoped to one table's prefix.

What it is

A storage profile is a named object store in the server's settings, under nuna.storage.profiles.name: its kind (s3, minio or ceph), endpoint and region, the table root new tables go under, and the prefixes tables may live in. Each catalog is bound to one profile. Vended credentials are the short-lived keys the server hands an engine with each table it loads.

How it works

Profiles

  • The table root must lie within one of the profile's allowed prefixes, and no two profiles' prefixes may overlap. A table location equal to a prefix is refused.
  • An AWS or Ceph profile names an STS role, sts-role, whose trust policy allows sts:AssumeRole and sts:TagSession; a MinIO profile needs none.
  • The server reaches the store with the profile's keys, or with the SDK's default credentials when the profile names none.
  • An endpoint must use TLS while nuna.storage.require-tls is true, the default. A profile can name a CA bundle for a private CA.
  • An AWS S3 profile can name a KMS key ARN, kms-key, in the profile's region. Its tables are then written with that key.
  • The profile names the maintenance-principal, the storage identity of the maintenance worker, the only identity that deletes.

Vending

When an engine loads a table, creates one, or asks for fresh credentials, the server assumes the profile's role with a session policy limited to the table's prefix: the objects under prefix/*, and listing the bucket under that prefix only. The policy is at most 2,048 characters.

  • A caller who may write the table's data gets read and write: s3:GetObject, s3:PutObject, s3:AbortMultipartUpload and s3:ListMultipartUploadParts. Anyone else gets s3:GetObject only.
  • No vended credential can delete.
  • With a KMS key, a write is allowed only with that key.
  • A caller who may write only on a catalog branch can write only beneath the branch's own folder of the table.
  • The session is named subject_request id and tagged with nuna-principal, nuna-end-user, nuna-engine, nuna-request, nuna-catalog and nuna-table, so the object store's own logs name who acted.

Credentials last nuna.storage.credential-lifetime, 30 minutes by default, between 15 and 60 minutes. The server caches them per caller and table and hands out the cached set until it nears expiry. The load answer carries them in the table's config as s3.access-key-id, s3.secret-access-key, s3.session-token and s3.session-token-expires-at-ms, with client.region, the endpoint and path-style access for a store other than AWS, and client.refresh-credentials-endpoint, the route the engine calls for a fresh set.

An engine that sends X-Iceberg-Access-Delegation: none gets no credentials and must reach the store with its own.

Every new set is audited first

The server writes a credential-issue audit record before it hands out a new set. If it cannot write the record, the engine gets 503 "Storage credentials cannot be issued now; retry later".

Tables with row filters or column masks

A table with a row or column policy gives storage access, through load, credentials or commit, only to a trusted engine, which enforces the policy, and to a maintenance principal acting as itself. Anyone else is refused with "table table has a row/column policy; only a trusted engine that enforces it gets storage access". Row filters and column masks explains why.

What it guarantees and what it does not

  • An engine never receives the server's own keys, and never receives credentials that reach beyond one table's prefix.
  • No engine can delete a file. Only the worker's own storage identity deletes, and the server publishes the bucket or user policies that make this so at GET /management/v1/maintenance/delete-policies.
  • The server does not apply those delete policies itself: an operator applies them to the store.
  • A location outside the profile is refused with 403 "Table location location is outside storage profile profile".
  • Credentials already handed out stay valid until they expire, even if the caller's grant is revoked.

Where you see it

  • Storage settings and Set up object storage.
  • The console's Service page, whose Credential vending panel counts the sets issued.
  • Credential vending, for the security view of the same mechanism.

Limits

  • One profile per catalog, fixed when the catalog is created.
  • A session policy of at most 2,048 characters.
  • Credential lifetimes between 15 and 60 minutes.
  • A KMS key on AWS S3 profiles only.
