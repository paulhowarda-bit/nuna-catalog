How a commit works

A commit applies an engine's updates to a table's current metadata if the engine's requirements still hold, and moves the table's pointer in one database transaction that only one commit can win.

What it is

An Iceberg commit request carries two lists. The requirements say what the engine assumed about the table, for example that its main table branch still points at the snapshot the engine started from. The updates say what to change, for example add a snapshot and point main at it. The server applies the updates only if every requirement holds against the table's current metadata. This is optimistic concurrency: nobody locks a table while writing data, and a conflict is found at commit time.

How it works

The commit loop

For a commit to one table or view, the server:

  1. Looks up the request's Idempotency-Key, if it has one, and answers again with the recorded answer if the key was used before for the same request.
  2. Reads the table's pointer from the database.
  3. Loads the metadata file the pointer names, from its cache or from the object store, checking the file against the SHA-256 the pointer records.
  4. Checks the requirements and applies the updates with Iceberg's own library. A requirement that fails ends the commit with 409 CommitFailedException. Updates that change nothing end it with the current metadata, and nothing is written.
  5. Judges its own rules, described below. A rule that refuses ends the commit with 400 or 403.
  6. Writes the new metadata file to the object store.
  7. In one database transaction, swaps the pointer to the new file, writes the commit's journal entry, its audit records and its idempotency answer.

If another commit moved the pointer between steps 2 and 7, the database refuses the swap and writes nothing. The server pauses and starts again at step 2, applying the same request to the new metadata. The requirements are checked again there, so a request whose assumptions no longer hold ends with 409, and the engine decides what to do.

How the database decides one winner

A pointer records the location of the current metadata file, a version number that starts at 1 and grows by 1 with each commit, and the file's SHA-256. The swap succeeds only if the stored pointer still has the location and version the server read. In the transaction, the server locks each pointer it swaps, always in the same order, so two transactions never wait on each other in a cycle. On a mismatch it rolls the transaction back. Two commits to one table can both write a metadata file, but only one moves the pointer; the other's file is never named by any pointer.

Retries and their bound

The server tries a commit at most 4 times, the first included, within 2 s. The first pause is 100 ms and each pause doubles, with up to 10% added at random so that racing servers spread out. These values are fixed in the server. When they are spent, the engine gets 409 CommitFailedException with the message "Commit lost to concurrent commits n times; the table changed too often to apply it". Iceberg engines treat a 409 as a conflict: they refresh the table and try again, up to their own retry setting.

A rule's refusal is 400 or 403, never 409, so an engine never retries a request that can only be refused again.

When the outcome is unknown

If the connection to the database fails after the server sent the transaction's COMMIT, the server cannot tell whether the commit landed. Every commit carries an id chosen before its first attempt, and the server asks the database whether that commit is recorded, after making sure the answer is durable. If it is recorded, the engine gets success. If it is not, the server tries again within the same bound. If the database cannot answer, the engine gets 500 CommitStateUnknownException with "Commit id may or may not have been applied: …". An Iceberg engine that receives it keeps the files it wrote, because the commit might have landed.

If the database cannot be reached before COMMIT, nothing was applied, and the engine gets 503 with Retry-After: 2 and "Catalog store unavailable; nothing was applied: …".

The server's rules

After Iceberg's own checks, the server judges these rules, in this order:

The governance refusals are written to the audit trail as denials, with the reason dr_freeze, legal_hold or snapshot_min_age. A schema or partition change on a regulated table is not refused; it is journaled and raises an alert.

Idempotency keys

An engine can send an Idempotency-Key header with any change. The server records the answer with the change, in the same transaction, and keeps it for 24 hours; /v1/config advertises this as idempotency-key-lifetime. The same key with the same request gets the recorded answer, and the change is not applied twice. A key is bound to the operation, the catalog, the namespace, the name, the end user, the body and the branch. The same key with a different request is refused with 400 "Idempotency key key was used for a different request". A 5xx answer releases the key so that the request can be repeated; a 4xx answer is recorded.

The journal and the metadata log

Every pointer move writes a journal entry in the database: the principal, the end user and engine if any, the requirements and updates as sent, the old and new metadata location and version, and the time. Iceberg's own metadata log inside each metadata file lists the files before it. The console's table History tab, the metadata log route and a table's export read the journal, and the journal stays readable after a drop.

Creates and registers

A create is one transaction that checks the namespace, takes the name and applies the first commit, at pointer version 1. If the name is taken, the engine gets 409 AlreadyExistsException, for example "Table already exists: equities.fills". A register makes a table from an existing metadata file, which keeps its own UUID and location; it is refused for a file written on a catalog branch.

Multi-table transactions

POST /v1/prefix/transactions/commit commits to several tables at once, all or nothing, in one database transaction. Every table's requirements and the server's rules are judged first; metadata files are written only when every table passes. A table that the transaction names but does not change is held too, so its requirements still hold when the others commit. A transaction can name at most 100 tables (nuna.rest.max-transaction-tables) and each table once. Success is 204. A transaction that keeps losing races ends with 409 "Transaction lost to concurrent commits n times; its tables changed too often to apply it".

What it guarantees and what it does not

  • Of two commits that start from the same version of a table, at most one moves the pointer to the next version. No acknowledged commit is lost or applied twice.
  • A commit the server acknowledges is durable in the database before the answer is sent.
  • A multi-table transaction never publishes some of its tables without the others.
  • A multi-table transaction does not give readers a view of all its tables at one instant: a reader that loads the tables one by one can see one before and another after.
  • The server does not merge conflicting changes. It applies the losing request again only where the engine's requirements still hold.

Where you see it

  • The console's table page, whose History tab lists each commit.
  • Iceberg REST: tables and Iceberg REST: transactions.
  • Error responses, for every status a commit can answer.

Limits

  • 4 attempts within 2 s for each commit, fixed in the server.
  • 100 tables in one transaction by default.
  • 24 hours for an idempotency key.
  • 1 minute of clock skew for a new snapshot's time stamp.
