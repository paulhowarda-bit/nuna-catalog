Dropping, restoring and purging

A drop removes a table or view's name but keeps its files for 30 days, during which you can restore it; after that the maintenance worker purges its files.

What it is

A drop frees an object's name and hides it from lists and loads. Its record, pointer, journal and files stay. A restore brings it back. A purge deletes its files for good.

How it works

Drop

Every drop is soft. The Iceberg query parameter purgeRequested is ignored. The server sets the object's purge time to the drop time plus nuna.rest.drop-retention, 30 days by default. A table under a legal hold cannot be dropped: 403 "Table table is under a legal hold and cannot be dropped". GET …/namespaces/namespace/dropped lists a namespace's dropped objects to a principal with describe.

Restore

POST …/objects/id/undrop restores an object, under its old name or a new one given as {"name": …}. It needs create on the namespace. Past the purge time: 409 UndropWindowClosedException "The undrop window of object closed at time; it is waiting to be purged". With the name taken: 409 AlreadyExistsException "The name name is taken in its namespace; undrop it under another name".

Purge

Only a maintenance principal purges, in two steps. It claims the object, which marks it purging; then it deletes the files in batches of 1,000 and completes the purge. The server refuses a claim before the purge time (409 PurgeNotDueException "object may not be purged before time"), on a held or frozen object, a dropped table that a catalog branch or tag still names, and more than nuna.governance.purges-per-minute claims a minute on one server (10 by default; 429 with Retry-After: 60). After the purge the record is kept as purged and its grants are deleted.

Reading a dropped object

A principal with select can still read a dropped object's export, GET …/objects/id/export, which gives its metadata and whole journal, and its metadata log, GET …/objects/id/metadata-log, newest first, 25 entries a page by default and at most 100.

What it guarantees and what it does not

  • No file of a dropped object is deleted before its purge time.
  • A purge cannot be undone.
  • A restore brings back the object with its id, location, history and grants.
  • A drop does not stop engines that loaded the table before it from using credentials they already hold until those expire.

Where you see it

  • The console's namespace page, which lists dropped objects.
  • Lifecycle API.

Limits

  • 30 days to restore by default.
  • 10 purge claims a minute on each server by default.
  • The restore window must be longer than nuna.governance.pitr-window; otherwise the server refuses to start.
