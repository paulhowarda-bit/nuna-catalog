Catalog branches and tags

A catalog branch or tag is a named cut of a whole catalog, every namespace, table and view at one moment, which engines read, and on a branch write, through the warehouse catalog@ref.

What it is

A ref names a cut of a whole catalog: every namespace, and every table and view with its pointer, taken in one consistent read of the database. Nothing is copied; the cut records pointers to metadata files that already exist. A tag is read-only and never expires. A catalog branch can take commits, and can be merged into main, the catalog itself.

Catalog refs are not Iceberg's table branches and table tags, which live inside one table's metadata file. A catalog branch spans every table of the catalog; a table branch is one table's own.

How it works

Reading through a ref

An engine names a ref in its warehouse as catalog@ref, for example trading@dev or trading@eod-2026-11-25, and /v1/config answers with that prefix. On a tag the server advertises only the read endpoints; on a branch, the reads and the table commits. A write through a tag is refused with 400 "operation is refused on tag tag of catalog catalog: a tag is read-only". An unknown or expired ref is 404 NoSuchWarehouseException, for example "The given warehouse does not exist: trading@dev (catalog trading has no branch or tag dev)".

A ref name cannot hold @ or /, cannot be main, and has at most 1,000 characters.

Commits on a branch

A commit through a branch writes the branch's own pointer for that table, whose version starts at 1, and a metadata file whose name is marked with the branch's id. Main does not move. Creates, drops, renames and namespace changes happen on main only and are refused on a branch with 400. A branch-only writer's vended credentials write only beneath table location/branches/branch id/. Namespace properties read through a ref are main's current ones.

Merging

A merge brings every table the branch changed into main, all or nothing, in one database transaction. For each table:

  • If main has not moved since the cut, main takes the branch's metadata.
  • If main has moved only by maintenance, such as snapshot expiry or a compaction's replaced files, the branch's changes are applied again on main's current metadata.
  • If main has moved in any other way, the merge is refused with 409 RefMergeConflictException.

Each table's merge is judged as a commit on main, with main's rules, and needs write for data changes or modify for definition changes. Main gets its own copy of the metadata, not marked as a branch's, and the journal records the entry as merge-branch. A merge with ?dry-run=true reports what it would do and changes nothing. A merge can change at most 100 tables (nuna.refs.max-merge-tables). A DR freeze refuses the merge, not the branch's own commits. After a merge, the branch is gone: "Branch dev is gone: merged, deleted or past its expiry".

Expiry

A branch expires after 30 days without a commit or a renewal, and in any case 180 days after it was created; owners are warned 7 days ahead. An expired branch keeps its name until the maintenance worker ends it. Tags never expire.

What a ref keeps

Every file a ref names is kept: maintenance does not expire the snapshots or delete the files a ref reaches, and a dropped table that a ref names is not purged until no ref names it. A namespace that holds an object a ref names cannot be dropped (409 NamespaceNotEmptyException). A principal with manage-tags can remove one object from every ref that names it.

What it guarantees and what it does not

  • A ref's cut is consistent: it records every table as of one read of the database.
  • A merge publishes every changed table or none.
  • A tag reads the same data for as long as it exists.
  • A ref does not copy data, and does not protect files from the object store's own lifecycle rules.
  • A merge does not combine two lines of data changes: if main took another engine's commit, the merge is refused and you decide.

Where you see it

  • The console's Branches and tags page.
  • Branches and tags API, under /management/v1/catalogs/catalog/refs. Creating, renewing, deleting and merging need create on the catalog; listing and reading need any privilege in it.
  • Governance and refs settings, for the limits below.

Limits

Ref limits and their settings
SettingDefaultMeaning
nuna.refs.max-branches50Branches in one catalog. Past it, 409 RefLimitException.
nuna.refs.max-tags1000Tags in one catalog.
nuna.refs.branch-idle-expiry30 daysTime without a commit or renewal before a branch expires.
nuna.refs.branch-max-life180 daysA branch's longest life.
nuna.refs.expiry-warning7 daysHow long before expiry the warning is written.
nuna.refs.max-merge-tables100Tables one merge can change.

A ref's description has at most 200 characters. Keep the database replicas' clocks within an hour of each other.
