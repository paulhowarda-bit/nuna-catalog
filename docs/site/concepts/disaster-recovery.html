Disaster recovery

Disaster recovery brings every table back, in a second region, to a version whose every file that region's object store holds, using the DR watermark the worker keeps.

What it is

The database and the object store each replicate to the DR region asynchronously, and neither waits for the other. After the primary region is lost, the DR database can name metadata or data files the DR store never received, and the DR store can hold files of commits the DR database never saw. nuna does not replicate either; it gives you the means to bring them back into agreement.

How it works

The DR watermark and the verifier

While the primary region runs, the maintenance worker's verifier checks the DR store every minute by default (nuna.maintenance.dr.verify-interval) and records, for each table and view, the DR watermark: the newest version whose every file the DR store holds, data files included. A view's version counts when its metadata file is there. The watermark is kept in the catalog database, so it reaches DR with the database, and it never moves back. The verifier is off until you name each store's DR replica under nuna.maintenance.dr.replicas, with read-only keys; it only lists and reads.

GET /management/v1/dr/watermarks lists the tables behind and their lag, and the alert NunaDrLagging fires when a commit has not been whole in DR for 15 minutes.

Recovering in the DR region

With the DR database promoted and the servers started in DR, a platform operator:

  1. Freezes every catalog, PUT /management/v1/catalogs/catalog/dr-freeze, so nothing writes or cleans up.
  2. Starts the worker in DR, its replicas naming the DR store itself, and waits for one verifier pass.
  3. Reads the plan, POST …/dr-reconcile with {"rewind": true}: each table above its watermark and the commits it would lose.
  4. Rewinds, with {"rewind": true, "apply": true}: each table moves back to its watermark in one journaled commit.
  5. Walks forward, with {"apply": true}: each table moves along later metadata files whose every file the DR store holds.
  6. Checks the refs the same answer lists, whose files the DR store lacks, and deletes or keeps them.
  7. Thaws, DELETE /management/v1/catalogs/catalog/dr-freeze.

Back up and recover gives each step in full.

What it guarantees and what it does not

  • After the rewind and walk, every table's pointer names a version whose files the DR store holds, so it reads whole.
  • The plan names every commit a rewind gives up, with its time and principal, for the owners to reconcile.
  • Nothing writes or deletes while the freeze stands.
  • Commits that the DR store never received are lost: nuna cannot recreate data it does not have.
  • Refs are reported, not rewound.

Where you see it

  • The console's Service page, whose DR replication panel shows the DR store against each watermark.
  • Disaster recovery API and Freeze and unfreeze for disaster recovery.

Limits

  • The verifier checks at most 100 versions of a table in one pass.
  • The DR store must hold the same buckets and paths as the primary, on another endpoint.
  • A register is refused under a freeze, so tables DR never knew are registered after the thaw.
