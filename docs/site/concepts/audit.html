The audit trail

The audit trail is the record of every read, change, refusal and credential the server gives, written as CloudEvents to its log, kept in a hash-chained archive and queryable as an Iceberg table.

What it is

Every audit record is a CloudEvent in JSON, of type nuna.catalog.name. The record names the principal, the end user and engine if any, the request id, the object, the operation and privilege, and for a refusal the reason. The kinds are: commit, grant, drop, break-glass, read, denial, auth-failure, credential-issue, namespace, rename, engine, storage-setup, governance, hold, undrop, purge, audit-read, unregister, label, purge-claim, file-deletion, maintenance-exemption, ref, row-column-rule and run-end. Audit record format gives each one's fields.

How it works

When records are written

  • Reads, refusals, authentication failures, audit reads and credential issues are written to the log before the server answers the request.
  • Changes are written to the database's outbox in the change's own transaction. A relay writes them to the log every 250 ms by default, at least once. A change whose server dies before its relay runs is written by the next relay.
  • A server that stops writes a run-end record as its last line.

Each record is one INFO line of the logger nuna.audit, carrying two extensions: nunarun, the id of the server run, and nunaseq, the line's number in that run from 1. The server refuses to start if nuna.audit is set coarser than INFO. The line goes to standard output and, where a logs endpoint is set, over OTLP.

Kafka, if you want it

With nuna.audit.kafka-bootstrap-servers set, every record also goes to the topic nuna.catalog.audit, and object changes to the change stream nuna.catalog.changes, best effort. A record that Kafka does not acknowledge within 5 s is in the log only, and for 10 s after a failure records skip Kafka. Nothing waits on Kafka and nothing is refused for want of it.

The hash-chained archive

The audit tables writer, taking the records over OTLP, writes every record byte for byte to an archive in a bucket created with Object Lock in compliance mode, locked for at least 2,557 days, seven years. Each server run is a chain: each line is the SHA-256 of the previous line's hash and the record, then the record's number, then the record. The writer writes segments of 10,000 records or a minute's worth, and a checkpoint every 5 minutes.

Every server checks the archive a minute after it starts and hourly after that. A record is verified when the check has followed its run's chain, without a gap, from the first number up to it. Each record the console shows carries one of four states: verified, unverified (a number before it has not arrived), no-archive (no archive is configured) or no-place (a record without a run, which no chain can hold).

The audit tables

The audit tables writer also writes the Iceberg table nuna_audit.audit.events, partitioned by day, which you can query from any engine. It runs about a minute behind. Its columns include event_id, time, type, principal, end_user, engine, request_id, catalog, object_path, operation, privilege, reason, branch, log_run and log_seq. The writer takes the records from Kafka (the default) or over OTLP, and leaves its own requests' records out of the table; the archive keeps them.

What it guarantees and what it does not

  • No read, refusal or credential is answered before its record is in the log, and no change commits without its record in the outbox.
  • Records in the archive cannot be changed or deleted while their lock lasts, and the check finds any record of a run that never arrived.
  • Past the log line, delivery is at most once. A pod that dies before its standard output is collected loses those lines; a full OTLP queue (2,048 records by default) drops records; a Kafka outage leaves gaps in the topics. The archive check shows every gap in the archive as missing numbers.
  • Records can arrive twice: the relay writes at least once, and the check counts repeats.

Where you see it

  • The console's Audit page, and the Audit tab of a namespace, table or view.
  • Audit API: the feed and summary need select on the audit catalog, at most 60 reads a minute from one caller on each server; an object's audit tab needs manage-grants on it.
  • Audit settings and Audit tables writer settings.

Limits

  • 60 audit reads a minute from one caller on each server by default (nuna.governance.audit-reads-per-minute); past it, 429.
  • The audit table is about a minute behind the log.
  • The archive is written only when the writer takes records over OTLP.
