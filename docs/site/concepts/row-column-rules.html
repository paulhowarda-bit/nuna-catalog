Row filters and column masks

A row filter limits which rows of a table a group sees, and a column mask replaces a column's values for it; the server keeps one rule per group on a flagged table, and a trusted engine applies them.

What it is

A rule belongs to one group on one table. It has a row filter, column masks, or both. The row filter is a Trino SQL expression: a reader in the group sees only the rows where it is true. Each column mask is a Trino SQL expression that replaces the column's value, such as NULL or '***'.

Rules apply only to a table flagged with the governance attribute row-column-policy set to true. A data steward, with manage-tags, sets the flag. A grant admin, with manage-grants, sets the rules, under the same self-grant rule as grants: no one sets a rule for a group they belong to.

How it works

What a reader sees

When a person reads a flagged table through a trusted engine, the server combines the rules of the groups they are in:

  • A table with no rules shows every row, unmasked, to anyone who may select.
  • Once a table has a rule, a reader in none of the rules' groups sees no rows.
  • The filters of the reader's groups are joined with OR. A rule with no filter admits every row.
  • A column stays unmasked if any of the reader's rules leaves it unmasked. If all of them mask it the same way, that mask applies; if they mask it differently, the column reads as NULL.

Why files are withheld

A rule only works if the engine applies it, and an engine that reads the files directly could skip it. So the server gives a flagged table's storage access (loading it, vending credentials, committing) only to trusted engines, registered by a platform operator, and to maintenance principals for maintenance. Any other engine, and the console, gets 403 table name has a row/column policy; only a trusted engine that enforces it gets storage access. See Row-level security and column masking for the path the rules take to the engine.

Who sees a rule's expressions

Grant admins with manage-grants on the table see each rule's expressions. Data stewards with manage-tags see how many rules there are and for which groups, not the expressions. A reader with select sees only their own outcome: whether their rows are filtered and which columns are masked for them.

What it guarantees and what it does not

  • Every expression is parsed as Trino SQL when it is set, and every column it names must exist in the table's current schema.
  • A schema change that renames or drops a column a rule names is refused, on main, on branches and in merges, until the grant admin changes the rule.
  • The flag cannot be removed or set to false while rules stand.
  • Every rule set or removed leaves an audit record of type nuna.catalog.row-column-rule.
  • The rules are applied by the engine, not by the server. Only Trino, through its OPA access control, applies them today.

Where you see it

In the console, a table's Access tab holds the panel Row filters and column masks, and a reader sees Your view of this table. The endpoints are in the Row and column rules API.

Limits

  • Each expression is at most 4,000 characters, with no NUL character.
  • A rule masks at most 500 columns.
  • The flag goes on a table, never on a catalog, namespace or view, and it is not inherited.
