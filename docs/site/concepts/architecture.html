How nuna fits together

nuna is an Iceberg REST catalog: a server that engines call to find, create and commit tables, with three programs of its own and four services it relies on.

What it is

nuna keeps track of where each Apache Iceberg table's current state lives, and decides which change to a table wins. Engines such as Spark, Trino and PyIceberg speak the Iceberg REST catalog protocol to it. The tables' data stays in your object store; nuna stores a small pointer for each table in a database.

A deployment has three programs of its own, each with its own container image and Helm chart:

  • The server answers engines, the console and the maintenance worker. Its chart runs 3 replicas by default.
  • The maintenance worker scans tables and runs expiry, compaction, orphan scans and purges. Its chart runs 1 replica.
  • The audit tables writer turns the audit trail into Iceberg tables you can query and into an archive that cannot be changed. Its chart runs 1 replica.

It relies on four services that run elsewhere: a database (PostgreSQL, CockroachDB, Oracle or MongoDB), an S3-compatible object store, an OpenID Connect identity provider, and, if you want them, Kafka and an OpenTelemetry collector.

How it works

The server

The server serves the Iceberg REST routes under /v1/, nuna's own management routes under /management/v1/, and the console under /ui/, all on port 8181. Every request but the console's static files carries a bearer token from a configured identity provider. The server checks the caller's grants, does the work, and writes an audit record.

Servers share nothing but the database. Each keeps its own caches of parsed metadata and of vended credentials, so any server can answer any request, and you add replicas to carry more load. The chart spreads the replicas over zones, keeps a pod disruption budget, and pauses 5 s before a pod stops so that in-flight requests finish.

The database

The database holds every catalog's namespaces, the record of each table and view, each table's pointer to its current metadata file, the commit journal, grants, governance, refs and the outbox of audit records waiting to be written. A commit is one database transaction that moves a pointer only if nobody moved it first, so the database is where every commit is decided. How a commit works explains this, and Choosing a database compares the four databases.

The object store

Each catalog is bound to one storage profile: an object store endpoint, a table root and the prefixes tables may live under. The server writes each new metadata file itself. Engines read and write data files directly, with vended credentials scoped to one table's prefix that last 30 minutes by default. No vended credential can delete. Only the maintenance worker deletes, with a storage identity of its own. Storage profiles and credential vending explains this.

The identity provider

Engines, people and the maintenance worker each get a token from your identity provider. The server validates it against the issuer's published keys, and maps the token's claims to a principal and its groups. Grants are made to groups. The server never issues tokens; /v1/oauth/tokens answers with an error that names the identity provider. Identity and access explains grants.

The maintenance worker

The worker is an Iceberg REST client of the server. It signs in as a maintenance principal, asks the server every 10 minutes for the work to do, and commits its changes through the server like any engine. Compaction runs as a Kubernetes Job that the worker starts. The worker's chart runs one replica and replaces it on upgrade, so two workers never run at once. Maintenance explains what it does.

The audit pipeline

Every audit record is one line of the server's log nuna.audit, written to standard output and, where a logs endpoint is set, over OTLP. Where Kafka is configured, each record also goes to the topic nuna.catalog.audit, and object changes to the change stream nuna.catalog.changes. The audit tables writer takes the records from Kafka or from the OTLP logs, writes them to the Iceberg table nuna_audit.audit.events through the server, and, when it takes them over OTLP, writes the hash-chained archive. The audit trail explains this.

The console

The console is a set of web pages the server serves at /ui/. People sign in through the identity provider with the authorization code flow and PKCE. The console calls the same routes an engine calls, with the person's token, so it shows exactly what the server allows that person, and every refusal as the server gave it. The console describes each page.

Engines

Any engine with an Iceberg REST catalog client can use nuna. Spark, Kafka Connect's Iceberg sink, PyIceberg and SingleStore run against it in nuna's own tests, and Trino runs in the local demo. An engine sets the catalog's name as its warehouse, sends a token, and receives vended credentials with each table it loads. Command line and clients shows each engine's settings.

What it guarantees and what it does not

  • The server never holds table data. Data files travel between engines and the object store; only metadata files pass through the server.
  • Every commit is decided by one database transaction. Two servers that receive commits to one table at once cannot both win.
  • Engines never receive the server's own storage keys, and no engine can delete a file.
  • The server does not replicate the database or the object store. Each replicates on its own, and Disaster recovery explains how nuna recovers when they disagree.
  • The server does not run queries. Row filters and column masks are enforced by the engines that you trust to enforce them, as Row filters and column masks explains.

Where you see it

  • The three Helm charts, nuna-catalog, nuna-maintenance and nuna-audit-tables, which Install covers.
  • The console's Service page, which shows which servers answered, the latency objectives, the database as the server finds it, and the worker's scans.
  • The local demo, which runs every part on one laptop in a kind cluster: The local demo.

Limits

  • The worker and the audit tables writer each run as one replica. They are not on the path of any engine's request, so a restart delays maintenance or the audit tables, not commits.
  • Servers must reach one database. A deployment across regions uses the database's own replication, and a second region recovers as Disaster recovery describes.
