Catalogs, namespaces, tables and views

A catalog holds namespaces, which nest and hold tables and views; the server names each object, assigns each table its location, and keeps a pointer to each one's current metadata file.

What it is

nuna keeps four kinds of object:

Catalog
The top of the tree. A catalog is bound to one storage profile, one KMS key set and one legal entity, and an engine names it as its warehouse.
Namespace
A level of the tree. A namespace holds tables, views and other namespaces, to any depth, and carries properties. equities.daily is the namespace daily inside equities.
Table
An Apache Iceberg table: a metadata file that names its schema, partitioning, properties and snapshots, and the data files those snapshots list.
View
An Apache Iceberg view: a metadata file that holds a query and its versions.

The table and view formats are the Iceberg table spec and the Iceberg view spec. nuna adds the tree around them, the names, and the rules for where files may live.

How it works

Catalogs come from the settings

You declare each catalog in the server's settings, under nuna.storage.catalogs.name, with its storage profile, its KMS key set and its legal entity. All three are required.

nuna:
  storage:
    catalogs:
      trading:
        profile: onprem
        kms-key-set: trading-keys
        legal-entity: example-securities

At start-up the server creates each declared catalog that does not exist yet and writes an audit record for it, with nuna-configuration as the principal. No API creates a catalog. A catalog's binding to its profile, key set and legal entity never changes: if the database holds the catalog with a different binding, the server refuses to start, and its log says "a catalog's boundary never changes". A catalog name cannot hold @, which the REST prefix keeps for catalog branches and tags.

Names

Names are case-insensitive and case-preserving. The server compares names after Unicode NFC normalization and lower-casing that does not depend on the locale, so Fills and fills are one name, and the server shows the name as it was first given. Within one namespace, tables and views share one set of names: a view cannot take the name of a table beside it. Only objects that have not been dropped hold a name, so a drop frees the name at once.

You can rename a table or view, and move it to another namespace of the same catalog. A rename keeps the object's id and its location. A namespace cannot be renamed.

Locations

The server assigns every new table its location: the storage profile's table root followed by the table's id, a UUID. The location never depends on the namespace or the name, so a rename or a move changes no file. A request that names another location is refused with 400 and the message "Location is assigned by the catalog: root, not location". The properties that steer where Iceberg writes, write.data.path, write.metadata.path, write.object-storage.path and write.folder-storage.path, must lie within the table's location. Properties that configure storage access, any key starting s3., client., http-client., gcs. or adls., and io-impl and py-io-impl, are refused: the server alone sets them.

Pointers and metadata files

Each commit writes a new metadata file under the table's location, named by the table's version number and a fresh UUID: location/metadata/00042-uuid.metadata.json. The database keeps the table's pointer: the location of the current metadata file, the version, and the file's SHA-256. When the server reads a metadata file, it checks the file against that hash. How a commit works explains how a pointer moves.

The REST prefix

An engine names a catalog as its warehouse. GET /v1/config?warehouse=trading answers with the prefix the engine puts in every later path, the catalog's name in lower case, with the endpoints this server supports and how long an idempotency key is kept:

{
  "defaults": {},
  "overrides": {
    "prefix": "trading"
  }
}

The block above leaves out the endpoints list and the idempotency key lifetime. A table's path is then /v1/trading/namespaces/equities/tables/fills. A nested namespace's levels are joined by the unit separator, written %1F in a path: /v1/trading/namespaces/equities%1Fdaily/tables/positions. The warehouse trading@dev names the catalog branch dev, as Catalog branches and tags explains. With nuna.rest.default-warehouse set, an engine that names no warehouse gets that catalog; without it, the server answers 400 "Missing query parameter warehouse, and this server has no default warehouse".

Format versions

A new table is Iceberg format version 3 unless the create request asks for another with the format-version property. Format versions 1 to 3 are accepted. An upgrade past 3 is refused with 400 "Table format version 4 is not supported; the highest is 3".

What it guarantees and what it does not

  • No two objects in one namespace that have not been dropped hold the same name, compared as the server compares names.
  • An object's id never changes, through renames and moves, and a table's location never changes.
  • Every table of a catalog lives under its storage profile's allowed prefixes. The server refuses a location outside them.
  • A caller who holds no privilege anywhere in a catalog gets the same answer as for a catalog that does not exist. The same holds for namespaces, tables and views.
  • The server does not check that the data files a snapshot lists exist; the engine that commits a snapshot wrote them.

Where you see it

  • In the console, the Catalog page, the namespace page, the table page and the view page.

Limits

  • A catalog's storage profile, KMS key set and legal entity are fixed once the catalog exists.
  • A namespace cannot be renamed.
  • A list answers 100 entries a page by default and at most 1,000; the next page is named by an opaque token that does not expire.
