Choosing a database

The server keeps its pointers in PostgreSQL, CockroachDB, Oracle or MongoDB; each decides commits the same way, and the server checks at start-up that each is set up to keep them.

What it is

You choose the database with nuna.database.backend: postgresql (the default, for PostgreSQL and CockroachDB, set with spring.datasource.* and told apart by the server), oracle, or mongodb (with nuna.database.mongodb.uri, which must name the database and set socketTimeoutMS). Every database passes the same shared test suite. YugabyteDB is refused at start-up.

How it works

Commits

On every database a commit is one transaction that locks each pointer it swaps in a fixed order, compares it with the version the server read, and writes the pointer, journal, outbox and idempotency answer together. PostgreSQL, CockroachDB and Oracle use READ COMMITTED with row locks; MongoDB uses a snapshot transaction with majority write concern. The server never lets a driver or pool repeat a COMMIT on its own.

An unknown outcome

When a connection fails after COMMIT, the server asks the database whether the commit landed, and answers only once the answer is durable.

The server locks the table's pointer row, looks for the commit in the journal, then writes to a counter so that synchronous commit waits for the standby before it answers.

The server locks the pointer row and looks for the commit in the journal. A retryable conflict before COMMIT is tried again up to 10 times.

The server asks Transaction Guard for the transaction's outcome by its logical transaction id. Without one, it locks the pointer row and looks in the journal.

The server retries the commit command, or writes a marker in a new transaction, then waits for a majority write before reading the journal with majority read concern.

The start-up self-check

Before it migrates the schema, the server checks that the database keeps what it acknowledges, and refuses to start on any finding not named in nuna.database.allow-unsafe; a finding allowed there is logged as a warning.

DatabaseFindings
PostgreSQLpg.sync-commit-off, pg.no-sync-standby, pg.fsync-off, pg.commit-cancel-timeout
CockroachDBcrdb.replicas, crdb.fsync-off, crdb.read-committed-off

What each needs

  • PostgreSQL: a synchronous standby, and the pg_monitor role so the check can see it; no statement_timeout or idle_in_transaction_session_timeout for the server's role.
  • CockroachDB: the VIEWCLUSTERSETTING privilege, the cluster setting sql.txn.read_committed_isolation.enabled, and a licence in production; without one, the cluster throttles after 7 days.
  • Oracle: Transaction Guard with COMMIT_OUTCOME on the service and no failover type, Data Guard, NLS_SORT=BINARY, and EXECUTE on DBMS_APP_CONT, SELECT on V_$DATABASE, V_$SERVICES and V_$PARAMETER, and CREATE JOB.
  • MongoDB: a replica set with enough voting members, majority write concern, and the clusterMonitor and readWrite roles.

Schema migrations

The first server of a new release migrates the schema as it starts. Every step only adds, so servers of the old release keep working beside it during a rolling upgrade.

What it guarantees and what it does not

  • On every database, an acknowledged commit is durable, and of two racing commits one wins.
  • The server refuses to start on a database set up to lose acknowledged writes, unless you allow the finding.
  • The server does not set up replication, backups or point-in-time recovery: you declare the recovery window in nuna.governance.pitr-window.

Where you see it

  • Database settings, and the install pages Use PostgreSQL, Use CockroachDB, Use Oracle and Use MongoDB.
  • The console's Service page, whose Store panel shows the database as the server finds it.

Limits

  • One database per deployment.
  • Paging tokens do not expire; they name a key, not a position.
