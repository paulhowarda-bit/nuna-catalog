Helm and kubectl recipes

The Helm and kubectl commands for status, logs, restarts after a Secret change and rollbacks, for each of nuna's three releases.

For platform operators

nuna runs as up to three Helm releases, each from its own chart in deploy/helm/:

The releases
ReleaseChartRuns
nuna-catalogdeploy/helm/nuna-catalogThe catalog servers: 3 replicas by default, rolled one at a time with none down (maxSurge 1, maxUnavailable 0), and a disruption budget allowing one down.
nuna-maintenancedeploy/helm/nuna-maintenanceThe maintenance worker: one replica, replaced with the Recreate strategy.
nuna-audit-tablesdeploy/helm/nuna-audit-tablesThe audit tables writer: one replica, Recreate, so an upgrade never runs two.

When the release name contains the chart's name, as these do, the Deployment has the release's name. Each pod carries the labels app.kubernetes.io/name (the chart) and app.kubernetes.io/instance (the release).

Synopsis

helm install|upgrade <release> deploy/helm/<chart> -n "$NS" -f <values.yaml>
kubectl -n "$NS" get|logs|describe|rollout ... deployment/<release>

Install or upgrade a release

helm install nuna-catalog deploy/helm/nuna-catalog -n "$NS" -f catalog-values.yaml
helm upgrade nuna-catalog deploy/helm/nuna-catalog -n "$NS" -f catalog-values.yaml

Each pod carries a checksum of its ConfigMap and of the Secret the chart makes, so an upgrade that changes either rolls the pods.

Status

helm -n "$NS" status nuna-catalog
kubectl -n "$NS" get deployment nuna-catalog nuna-maintenance nuna-audit-tables
kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-catalog

A catalog pod is ready when GET /ui/config.json on port 8181 answers. The worker has no probe; the writer has a readiness probe on its OTLP port only when it takes the audit log over OTLP (Health checks).

Logs

kubectl -n "$NS" logs deployment/nuna-catalog --since=1h
kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h
kubectl -n "$NS" logs deployment/nuna-audit-tables --since=1h
kubectl -n "$NS" logs <pod> --previous

logs deployment/… reads one pod. Each line is a JSON object (Log lines). --previous reads the run before a restart, which is where a server that refused to start says why.

Restart after a Secret change

A Secret you manage yourself, named in existingSecret, is not part of the chart, so changing it does not roll the pods. Restart them:

kubectl -n "$NS" rollout restart deployment/nuna-catalog
kubectl -n "$NS" rollout status deployment/nuna-catalog

The catalog servers roll one at a time. Each stopping pod waits 5 seconds (preStop) for the Service to stop sending it requests, and has 45 seconds to finish. The writer has 70 seconds, to finish a commit in flight.

Roll back

helm -n "$NS" history nuna-catalog
helm -n "$NS" rollback nuna-catalog <revision>

Not documented yet: whether every release can roll back past a database schema change. Schema steps added so far only add, so servers of the previous release keep serving, but there is no stated rule.

Describe a failing pod

kubectl -n "$NS" describe pod <pod>
kubectl -n "$NS" get events --sort-by=.lastTimestamp

Compaction Jobs

The worker starts compaction Jobs in a namespace of their own, named in compaction.namespace, each called nuna-compact-id-date:

kubectl -n nuna-compaction get jobs
kubectl -n nuna-compaction logs job/<job>

Environment variables

VariableMeaning
NSThe namespace the releases are installed in. The commands on this page read it; set it in your shell first.

In the demo

The demo runs in the kind cluster nuna, context kind-nuna, namespace nuna-demo, with Deployments nuna-catalog, nuna-maintenance and nuna-audit-tables. Bring it up and down with demo/demo.sh, not with Helm (demo.sh).
