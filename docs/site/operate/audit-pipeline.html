Run the audit pipeline

Where each audit record goes after the server writes it: the audit log, the outbox relay, the optional Kafka copy, the audit tables writer and the archive, and how to check each is current.

For platform operators Audited

The record of audit is a log. Every audit record is one INFO line of the logger nuna.audit, holding the record's CloudEvent JSON. Everything else, the Kafka copy, the audit tables behind the console's Audit page, and the seven-year archive, is fed from that log or alongside it.

Before you begin

  • The catalog servers running, with telemetry set up if you want the log over OTLP (Send telemetry).
  • For the console's Audit page: the audit tables writer (Install the audit tables writer).

What is written, and when

  • Reads, denials, authentication failures, audit reads and credential issues are written before the server answers the request they record.
  • Changes (commits, drops, grants, governance and hold changes) go into the outbox in the change's own database transaction. The outbox relay writes each to the log shortly after its commit, every nuna.audit.relay-interval (250 ms by default), at least once. A change stays in the database until the relay has written it, so a server that dies first leaves it to the next relay.
  • A server that stops writes a run-end record, nuna.catalog.run-end, as its last line. It goes to the log only.

Each line carries two CloudEvent extensions: nunarun, the server run's id, and nunaseq, the line's number in that run, from 1. The archive check uses them to find records that never arrived. logging.level.nuna.audit is INFO, and the server refuses to start with it coarser.

Feed the audit tables

The console's Audit page reads the audit table nuna_audit.audit.events. The audit tables writer fills it from the audit topic (nuna.audit-tables.source kafka, the default) or from the catalog's log (otlp), so the page needs no Kafka.

  1. Set the writer's source to otlp.

    Set nuna.audit-tables.source: otlp and a shared token of at least 32 characters in nuna.audit-tables.otlp.token, kept in the chart's Secret. The writer listens for POST /v1/logs on port 4318.

  2. Point the catalog's logs at the writer.

    telemetry:
  logsEndpoint: http://nuna-audit-tables:4318/v1/logs
  logsTokenSecret: {name: audit-receiver-token, key: token}

    The catalog sends the token in X-Nuna-Audit-Token. A request without it is refused with 401. The writer keeps only records whose scope is nuna.audit, so the whole log can be sent to it.

Check it worked

The writer logs Wrote n audit records from the log to the audit table about once a minute, and the console's Audit page shows recent records.

Rows are deduplicated by CloudEvent id: an id seen in the last nuna.audit-tables.otlp.dedup-window (15 minutes) is dropped as it arrives, and an older record is looked up among its day's rows. The writer commits every nuna.audit-tables.commit-interval (1 minute) or max-rows.

A writer that dies loses its waiting rows from the table

The writer answers the catalog when it takes records, before its commit. If it dies, the table lacks what arrived since its last Wrote … line. The records are still in the catalog's stdout, so the record of audit is whole. Each row keeps its record's run and number in log_run and log_seq; compare them with the nunarun and nunaseq of the stdout lines to find the missing rows.

Keep the archive

The seven-year record is a hash-chained archive in an S3 bucket created with Object Lock. The audit tables writer, with the source otlp, writes it; the catalog servers only read and check it. The writer refuses an archive with the source kafka.

  • On the writer: nuna.audit-tables.archive.bucket and the other nuna.audit-tables.archive.* settings.
  • On the catalog: nuna.audit.archive.bucket, .profile (the storage profile that reaches the bucket) and .prefix (audit by default, the writer's).

Each server run's records form one chain, written in segments of at most 10,000 records or 1 minute of waiting, each locked in COMPLIANCE mode for the retention, at least 2,557 days. The writer writes a checkpoint after every round of segments, and every 5 minutes when it wrote none. When the archive cannot take records, the writer answers 503 with Retry-After and the catalog's exporter retries.

The archive check

Every catalog server with an archive checks it a minute after it starts and hourly after that: it verifies each chain up to the newest checkpoint and follows each run's numbers. Read the last result with GET /management/v1/audit/archive (reference) or on the console's Audit page.

How a loss shows in the check
What is lostHow it shows
Records lost between a server and the writerRanges in missing, once later records of the run arrive.
The last lines of a server that was killedNo run-end record: the run is unended once its highest number has stood still for a day.
The writer down, or unable to reach the bucketCheckpoints late, older than twice the interval.
A segment or checkpoint changed or replacedA problem: a delete marker or second version, or a chain whose hashes do not link.
A record archived twiceNothing is lost; counted in repeats.

Between checks, each server sends nuna.audit.logged, the number of the last record it wrote in its run, and nuna.audit.archive.highest, the highest number the check verified, both by run. The nuna catalog dashboard's archive row compares them (Dashboards and alerts).

In the demo

The demo's catalog audits to its log, not to Kafka, and configures no archive. Its audit tables writer takes the log over OTLP.

If it fails

  • Reads or vends answer 503 Audit is unavailable…. See Troubleshooting.
  • The writer refuses the catalog's exports with 401. The token in logsTokenSecret and nuna.audit-tables.otlp.token differ.
  • The writer stops at a record. See Troubleshooting.
  • The audit table was dropped under the writer. The writer makes it again and logs a WARN; the earlier rows stay in the dropped table. Undrop it rather than keep the new one.
