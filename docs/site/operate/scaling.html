Scaling

How to size the catalog servers, the database and the maintenance worker, and what nuna's load and resilience tests measured.

For platform operators

The catalog servers hold no state of their own beyond caches: every server reads and writes the same database, so you scale them by adding replicas. The database takes every commit, and the maintenance worker runs as one replica that starts compaction Jobs elsewhere in the cluster.

Before you begin

  • Metrics reaching your monitoring, so you can see where time goes (Dashboards and alerts).

javaToolOptions-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError: the heap takes 75% of the memory limit.
  • Add replicas when every server is busy: helm upgrade with a higher replicaCount. The disruption budget keeps all but one serving during node drains.
  • Raise the metadata cache when loads read metadata files from the object store: the dashboard's cache hit share falls. nuna.rest.metadata-cache-chars is 268,435,456 characters by default and lives in the heap, so raise the memory limit with it.
  • Each server caches its own credentials and metadata. Conditional loads (304) still work behind a balancer that does not pin clients to one server.

The database

Every commit is one database transaction that moves the table's pointer, and every request reads grants and pointers. When commits slow, look at the database first: the nuna.store timer by operation shows which calls take the time.

  • Commits to different tables do not wait on each other.
  • Commits to one table do: each must see the pointer the last one left. Writers that lose retry. Many writers on one hot table manage only a few commits a second between them; give each writer its own table, or batch commits, where you can.
  • /v1/transactions/commit locks every pointer it changes, up to nuna.rest.max-transaction-tables tables.

The maintenance worker

The worker runs one replica, replaced with the Recreate strategy. One scan covers every catalog. Its own work is light; compaction runs in Kubernetes Jobs in their own namespace.

  • More compaction at once: raise nuna.maintenance.compaction.max-jobs (2 by default), if the Jobs' namespace has room.
  • Bigger Jobs: compaction.memory (2Gi) and compaction.driver-memory (1g).
  • Scans that outgrow the interval: lengthen scan-interval (NunaScansSlowerThanInterval).

What the tests measured

nuna's load and resilience tests run two servers on PostgreSQL with a synchronous standby:

Rolling upgrade from the previous releaseThe first new server migrated the schema under traffic. No 5xx; history and journal whole.

The latency objectives are load p99 under 50 ms, 304 p99 under 10 ms, commit p99 under 300 ms, and at least 500 commits a second.

Not documented yet: throughput and latency on production hardware. The only objective run so far shared one laptop between the clients, two servers, the database, Kafka and the object store, and shows relative behaviour only.

If it fails

  • Pods restart with an out-of-memory exit. Raise resources.limits.memory; the heap follows at 75%.
  • Latency objectives burn. Follow the runbooks for NunaLoadSloBurnFast and NunaCommitSloBurnFast.
