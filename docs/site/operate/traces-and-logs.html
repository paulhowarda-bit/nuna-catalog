Traces, logs and the request id

The spans each request and each maintenance scan make, the JSON log lines, and how to follow one request from its client to the audit record.

For platform operators

The server and the maintenance worker send traces and logs over OTLP/HTTP once an endpoint is set (Send telemetry), and always write their log lines to stdout as JSON. One key, the request id, joins a request's trace, its log lines, its audit record and the STS session it opened.

Before you begin

  • A collector that takes OTLP over HTTP, and a trace store and log store behind it.
  • OTEL_EXPORTER_OTLP_ENDPOINT set on both programs, or the charts' telemetry.endpoint.

The request id

The server settles each request's id once, as the request starts:

  • A client's X-Request-ID header of 1 to 128 characters, not blank, is kept.
  • Otherwise the id is the request's trace id, 32 hex characters. When the client sent a W3C traceparent, that is the client's trace id.

Every response carries X-Request-ID, errors included. The same id is in:

  • each log line written while the request ran, as requestId;
  • each audit record the request made, as actor.requestId;
  • the STS session of a credential vend, in its nuna-request session tag and in its session name, and so in CloudTrail.

To follow a call, send your own id and look for it afterwards (curl):

curl -sS -i "$NUNA/v1/trading/namespaces/equities/tables/fills" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Request-ID: fills-check-0001"

The answer's headers repeat X-Request-ID: fills-check-0001. Search the logs and the audit records for that value.

The server's spans

Each HTTP request the server answers is a server span named for its method and route template, such as http get /v1/{prefix}/namespaces/{namespace}/tables/{table}. A caller's traceparent is honoured, so an engine's trace continues into the catalog. Beneath it, each call to the database, the object store, STS and Kafka is a child span with a timer of the same name (Metrics):

Child spans of a request
SpanOne perAttributes
store method, such as store commit or store readPointerCall to the catalog database; each is one transaction.backend, operation, outcome, exception
objectstore method: write, read, metadataFiles, tableLocations, exists, bytesRequest for metadata files to the object store.profile, operation, outcome, exception
sts assume-roleAssumeRole for a credential vend. A vend served from the credential cache makes none.profile, access (read or read-write), outcome, exception
audit publishAudit record sent to Kafka inside the request, from the send to the acknowledgement.topic, event, outcome, exception

The outcome names what the call came to:

  • Store: a commit is committed, conflict or inactive; another write applied, unchanged, missing, name-taken, version-mismatch or refused; an idempotency key absent, claimed, in-flight, done or mismatch; a commit lookup committed or not-committed; a read that may find nothing found or absent; anything else ok.
  • Object store: written, intact, mismatch (the bytes read do not hash as the pointer recorded), listed, found, absent or read.
  • STS: issued. Kafka: acknowledged.
  • A call that threw: error, with exception the simple name of what it threw, otherwise none.

A commit's trace looks like this:

http post /v1/{prefix}/namespaces/{namespace}/tables/{table}
  store findTrustedEngine    absent
  store findCatalog, findNamespace, findObject, ...   found
  store grantsFor, attributesOf, ...                  ok
  store readPointer          found
  objectstore write          written
  store commit               committed
  sts assume-role            issued
  audit publish              acknowledged

A load whose metadata file and credentials are already cached reads the pointer and publishes its read record, and makes no objectstore or sts span.

Failed calls

Every answer of 500 or more ends the server span with status ERROR, and no answer below 500 does. The span records one exception event, AnswerFailed, whose message is the status and the class behind the answer, such as 503 nuna.catalog.store.StoreUnavailableException. A failed child span has status ERROR and an exception event naming only the exception's class. Messages, causes and stack traces stay out of spans because they can name a table, a location or a principal; the log line for the failure holds them. A failure that escapes the routes is written in full to the log as request failed outside the routes.

Not every 5xx route marks its span

On the Iceberg REST routes every 5xx marks the server span. On the management API and the console, a 5xx marks it only when its failure escapes the routes.

What is not traced

Calls made outside a request make neither spans nor timers: the outbox relay's claims every 250 ms and its publishes to Kafka, the server's start-up (database migration, storage profiles, declared catalogs), and the hourly audit archive check.

The worker's spans

Each maintenance scan is a trace of its own. Its root span is maintenance scan, with a maintenance part span for each part and an HTTP GET, HTTP PUT or HTTP POST span for each call to the catalog or to the identity provider. The worker's calls carry the trace, so the server's spans for them join it.

A part that threw has outcome error. The scan's own outcome is success when it read the whole work list, otherwise failure. No attribute of the worker's spans names a table, namespace, location, catalog or person; a call's uri is its route, such as /management/v1/catalogs/{catalog}/objects/{id}/purge-claim. The WARN log line for a failure names the table.

Sampling

The charts keep 10% of new traces (telemetry.sampling: "0.1", sent as OTEL_TRACES_SAMPLER=parentbased_traceidratio with that ratio), and every request whose caller's trace was sampled. Without the charts the default is also 10%. Metrics and logs are never sampled.

  • Head sampling, what the charts run: the decision is made before the request runs, so most failed calls leave no trace. Find them by their request id in the logs and the audit records.
  • Tail sampling, with a collector that runs it: set telemetry.sampling: "1.0", route spans by trace id through a loadbalancing exporter tier, and keep traces in a tail_sampling tier. Because every 5xx ends its server span with status ERROR, a policy on status ERROR keeps every failed call. Traces then show about 30 s late, the policy's decision wait.

In the demo

The demo's collector runs one tail_sampling tier with three policies: errors (status ERROR), slow (over 300 ms) and a-tenth-of-the-rest. It has a single collector, so it needs no loadbalancing tier.

Log lines

Both programs write one JSON object per line to stdout in Elastic Common Schema. A line written during a request carries traceId, spanId and requestId, besides service.name, log.level, log.logger, message and error.* with the stack trace when there is one. Over OTLP the trace and span ids are the record's own and requestId is an attribute.

To write Logstash's or GELF's format instead, set LOGGING_STRUCTURED_FORMAT_CONSOLE to logstash or gelf.

Two loggers carry records other tools depend on:

  • nuna.audit: every audit record, as one INFO line holding its CloudEvent JSON. It is never sampled (Run the audit pipeline).
  • nuna.alerts: one line for each alert counter's rise, such as metadata-integrity object=… location=… expected-sha256=… actual-sha256=… at ERROR (runbook).

No metric label or span attribute names a person or holds a filter value. The server span records the request's path, which names namespaces and tables.

If it fails

  • No traces arrive. Check that an endpoint is set: nothing is exported without one. The collector must take OTLP over HTTP; gRPC on port 4317 is not supported.
  • A failed call has no trace. Under head sampling that is expected for 9 calls in 10. Search the logs for its request id.
  • The collector is down. Requests are not slowed: spans and log records wait in queues of 2,048 and are dropped when they fill. Each failed export logs a warning, and a stopping program waits up to 10 s for its last exports.
