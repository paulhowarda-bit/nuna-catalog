Alert runbooks

What to do when each of nuna's 29 alert rules fires: what it means, its impact, what to check and how to fix it.

For platform operators

The rules are in deploy/grafana/rules/ (Dashboards and alerts). Commands below assume the releases are named nuna-catalog and nuna-maintenance, NS holds their namespace, NUNA the catalog's address and TOKEN a platform operator's token (curl).

NunaLoadSloBurnFast

What it means

More than 1% of loads answered 200 took longer than 50 ms, fast enough to spend a month's error budget in days: 14.4 times the allowed rate over the last hour and 5 minutes, or 6 times over 6 hours and 30 minutes. Severity page. It keeps firing 10 minutes after the burn stops.

Impact

Engines wait longer for their tables. Nothing fails: the answers still arrive.

Check

Open the nuna catalog dashboard's SLOs row, then the time spent by part. Look at the store and object store timers for the same window:

kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-catalog

A server restarting or out of memory shows here. Then check the database and object store figures on the server's health route (reference):

curl -sS "$NUNA/management/v1/health/server?store=true" \
  -H "Authorization: Bearer $TOKEN"

In the traces, find the slow spans: a slow store span points at the database, a slow objectstore read at the object store, a slow sts assume-role at STS.

Fix

  • If the database is slow, fix it there first: connections, locks, a failover in progress.
  • If one server is slow and the others are not, restart it: kubectl -n "$NS" delete pod pod. The rollout keeps the others serving.
  • If every server is busy, add replicas (Scaling).
  • If metadata files are being read from the object store, the metadata cache may be too small: compare cache hits and misses on the dashboard and raise nuna.rest.metadata-cache-chars.

If that does not fix it

Collect the dashboard's SLOs row for the window and a few slow traces, with their request ids, and take them to whoever runs the database and the object store. If neither is slow, raise it with the team that runs nuna.

NunaLoadAvailabilityBurnFast

What it means

More than 0.1% of loads (loadTable) were answered 5xx, fast enough to spend a month's error budget in days: 14.4 times the allowed rate over the last hour and 5 minutes, or 6 times over 6 hours and 30 minutes. 4xx answers, 409 conflicts among them, count on neither side. Severity page. It keeps firing 10 minutes after the failures stop.

Impact

Engines cannot read the tables whose loads fail.

Check

Open the nuna catalog dashboard: Failed loads and Refused, unknown and failed commits name the error types. Then:

kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-catalog
kubectl -n "$NS" logs deployment/nuna-catalog --since=1h | grep '"ERROR"'

The commonest 5xx answers and their causes:

  • 503 ServiceUnavailableException with Retry-After: 2: the catalog's database cannot be reached. The server's health route says so too.
  • 503 while checking a token: the identity provider's keys could not be fetched, logged as Couldn't retrieve JWK set from URL.
  • 503 on reads or vends: an audit record that had to be written first was not.
  • 500 CommitStateUnknownException: the database answer to a commit was lost; the commit may have happened.

Fix

  • Database unreachable: restore the database or its network path. The servers recover on their own once it answers; nothing needs restarting.
  • Identity provider unreachable: restore it, or the network path to its JWKS URL.
  • One server failing alone: delete its pod and let the Deployment replace it.
  • After a release: roll back with helm rollback nuna-catalog -n "$NS" (Helm and kubectl recipes).

If that does not fix it

Collect the error types from the dashboard, a few failing request ids and the matching log lines, and raise them with the team that runs nuna. See Troubleshooting for each message.

NunaMetadataIntegrity

What it means

A metadata file read from the object store no longer hashes to the SHA-256 its pointer recorded when it was committed, in the last 15 minutes. Something changed or damaged the file after nuna wrote it. Severity page.

Impact

For a regulated table, nuna refuses to serve the file. For other tables it serves the file as it now reads and raises the alert. Exports and row and column reads of the table are refused with 500 MetadataIntegrityException.

Check

The nuna.alerts log line names the table's id, the file and both hashes:

kubectl -n "$NS" logs deployment/nuna-catalog --since=1h | grep metadata-integrity
metadata-integrity object=<table id> location=s3://<bucket>/<path>.metadata.json expected-sha256=<hash> actual-sha256=<hash>

Check the object's history in the object store: its versions, who wrote it last, and when.

Fix

  • Restore the file's earlier version from the object store's versioning, or from the DR replica, so that it hashes as recorded.
  • Find who could write to the table's location and remove that access: only the catalog and the engines it vends credentials to may write there.

If that does not fix it

Treat it as a security incident if nobody can account for the change. Keep the log line and the object store's access logs, and raise it with your security team.

NunaRegulatedSchemaChange

What it means

A commit changed a regulated table's schema or partition spec in the last 15 minutes. Severity warning.

Impact

None on serving. Downstream reports and controls that depend on the table's columns may need review.

Check

kubectl -n "$NS" logs deployment/nuna-catalog --since=1h | grep regulated-schema-change

The line names the table's id and the commit's id. Find the commit and who made it in the audit records (Audit page).

Fix

  • If the change was planned, record its approval as your change process asks. Nothing else is needed.
  • If it was not, ask the table's owners. To undo it, an engine commits the earlier schema again.

If that does not fix it

Take the commit id and the audit record to the table's data stewards.

NunaLargeMetadata

What it means

A table's metadata file is larger than nuna.rest.alert-metadata-chars (1,048,576 characters by default) or holds more snapshots than nuna.rest.alert-snapshots (1,000 by default). Each server alerts once per file. Severity warning.

Impact

Every load and commit of the table reads and writes that file, so they get slower as it grows, and it takes more of the metadata cache.

Check

kubectl -n "$NS" logs deployment/nuna-catalog --since=1h | grep large-metadata

The line names the table, its location, its size and snapshot count, and both limits. Check the table's health and maintenance policy in the console: is snapshot expiry on, and when did it last run?

Fix

  • Make sure snapshot expiry runs for the table (Table health), and shorten its snapshot retention if it keeps many.
  • Branches and tags keep snapshots alive: end branches no longer needed.
  • A table written in many small commits grows fast; ask its writers to batch.

If that does not fix it

Raise it with the table's owners with the size and snapshot count from the log line.

NunaCatalogGone

What it means

No catalog server has sent nuna_catalog_alerts_metadata_integrity_total for 10 minutes. Every server sends it each minute from its start, busy or idle, so either no server runs or their telemetry does not reach Prometheus. Severity page.

Impact

If no server runs, every engine and the console are down. If only telemetry is lost, serving is fine but every other catalog alert is blind.

Check

kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-catalog
curl -sS -o /dev/null -w "%{http_code}\n" "$NUNA/ui/config.json"

200 means a server answers, so look at telemetry: the collector, its pods and its logs, and the telemetry.endpoint value.

Fix

  • Servers down: read why with kubectl -n "$NS" describe pod pod and the logs of the last run (kubectl -n "$NS" logs pod --previous). A server that refuses to start says why in its last lines (Troubleshooting).
  • Telemetry lost: restore the collector, or the network path from the servers to it.

If that does not fix it

If servers run and the collector receives, check Prometheus' OTLP receiver and the name translation (Dashboards and alerts).

NunaCatalogSilent

What it means

One catalog deployment, a job, sent metrics within the last day and has not for 10 minutes, while other deployments still do. Severity page.

Impact

As for NunaCatalogGone, for that deployment alone.

Check

The alert's job label is namespace/nuna-catalog. Set NS to that namespace and check its pods:

kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-catalog

Fix

  • Follow NunaCatalogGone for that namespace.

If that does not fix it

If the deployment was removed on purpose, the alert resolves after a day.

NunaRequestSeriesMissing

What it means

A deployment has sent metrics for over an hour, but nuna_catalog_requests_milliseconds_count has had no sample for an hour. Either its request series arrive under other names, so every objective rule reads nothing, or no Iceberg call has reached a server since it started. Severity page.

Impact

Every latency and availability rule for the deployment is blind.

Check

In Prometheus, look for the series under other names: nuna_catalog_requests_seconds_count, a native histogram nuna_catalog_requests_milliseconds, or names with dots. Then check that engines are calling the deployment at all.

Fix

  • Names changed: fix the translation in Prometheus or the collector, or change the rules (Dashboards and alerts).
  • No calls: if a quiet hour is normal for the deployment, lengthen the rule's window or make it a warning.

If that does not fix it

Raise it with whoever runs Prometheus and the collector.

NunaSloBucketMissing

What it means

A latency objective's answers arrive in nuna_catalog_requests_milliseconds_count, but no _bucket series has the objective's le bound (10, 50 or 300) for 10 minutes. The alert's slo label names which. Severity page.

Impact

That objective's burn-rate rules return nothing.

Check

In Prometheus, list the le values of nuna_catalog_requests_milliseconds_bucket. Values written as 50.0 already match; others, or none, do not.

Fix

  • Buckets dropped or changed by the collector or a relabelling rule: undo it.
  • Native histograms in use: change the rules to histogram_fraction.

If that does not fix it

The buckets are set in nuna's code, not by a setting. Raise it with the team that runs nuna.

NunaWorkerNotScanning

What it means

The maintenance worker's last successful scan ended more than three scan intervals ago (30 minutes at the default), and that has lasted an hour. Severity page.

Impact

Snapshots are not expired, dropped tables are not purged, due files are not deleted, and nothing is compacted. Storage grows and loads slow over days.

Check

kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-maintenance
kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h | grep '"WARN"'

Look for the work list failing (kind work-list), the token request failing, or the worker restarting before a scan ends. The console's Service page shows when the worker last reported.

Fix

  • Catalog unreachable from the worker: check catalog-uri and the network path.
  • Token refused: check the worker's client id and secret, and that its principal is in nuna.security.maintenance-principals.
  • Restarting: read kubectl -n "$NS" logs deployment/nuna-maintenance --previous; an out-of-memory exit needs more memory.
  • A first scan on a new deployment runs every table's orphan scan and can take long: wait for it.

If that does not fix it

Collect the worker's log lines from the last scan and raise them with the team that runs nuna.

NunaWorkerGone

What it means

No maintenance worker has sent nuna_maintenance_scan_last_success_seconds for 15 minutes. Severity page.

Impact

As for NunaWorkerNotScanning, or only the worker's telemetry is lost.

Check

kubectl -n "$NS" get pods -l app.kubernetes.io/instance=nuna-maintenance

Fix

  • Not running: check the Deployment and its events with kubectl -n "$NS" describe deployment nuna-maintenance.
  • Running: check its telemetry.endpoint and the collector.

If that does not fix it

Raise it with the team that runs nuna.

NunaPurgesFailing

What it means

Purges of dropped objects failed in the last hour and none completed, for 20 minutes. Severity warning.

Impact

Dropped tables' files stay in storage after their window ends.

Check

kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h | grep '"WARN"' | grep -i purge

The WARN lines name the objects. A purge the catalog refuses or rate-limits is skipped, not failed.

Fix

  • Storage denies the delete: check the worker's storage identity and the bucket's delete policy (Install the maintenance worker).
  • A namespace frozen for DR refuses purge claims: lift the freeze when the reconcile is done (Freeze for DR).

If that does not fix it

Raise it with the team that runs the object store, with the object ids from the log.

NunaDeletionsFailing

What it means

Deletions of due files failed in the last hour and nothing was deleted, for 20 minutes. Severity warning.

Impact

Expired snapshots' and orphans' files stay in storage.

Check

kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h | grep '"WARN"' | grep -i delet

Fix

  • The cause is most often the worker's storage identity or the bucket's delete policy: only the worker's identity may delete, and it may list and delete but never read.
  • A store whose endpoint the worker cannot match to the catalog's storage profiles is skipped and logged (kind storage-prefixes).

If that does not fix it

Raise it with the team that runs the object store.

NunaMaintenanceJobFailing

What it means

Jobs of one kind (the alert's kind label) failed in every 30 minutes for 3 hours. Severity warning.

Impact

That kind of work is not done for the tables it fails on. See Failure kinds for what each kind covers.

Check

kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h | grep '"WARN"'

Each WARN line names the table or object.

Fix

  • table-changed is normal after a drop and re-create; it clears on its own.
  • table-load: the worker's group needs read on the table; a governance rule may refuse it.
  • compaction: check the Jobs' namespace with kubectl -n nuna-compaction get jobs and the failing Job's logs.
  • report: the catalog refused the worker's report; the work itself went on.

If that does not fix it

Raise it with the team that runs nuna, with the WARN lines.

NunaScansSlowerThanInterval

What it means

Over the last hour the mean scan took longer than the scan interval (600 seconds at the default). Severity warning.

Impact

Scans run back to back, and work waits longer to be picked up.

Check

Open the nuna maintenance worker dashboard's time by part to see where scans spend their time.

Fix

  • The work list has outgrown one worker: lengthen scan-interval, and change the rule's 600 to match.
  • A store or the catalog is slow: see the latency runbooks above.

If that does not fix it

Raise it with the team that runs nuna.

NunaCompactionFallingBehind

What it means

Each day for 3 days, tables that needed compaction were left over when the cleanup window closed, or Jobs were cut off by its end. Severity warning.

Impact

Small files build up; scans and loads of those tables slow.

Check

Read the last nights in the console's Maintenance page or with the nights route (Maintenance nights): jobs-cut-off and how long the Jobs ran.

Fix

  • Lengthen the cleanup window.
  • Raise nuna.maintenance.compaction.max-jobs if the cluster has room for more Jobs at once.
  • Give each Job more memory if they run slowly (compaction.memory, compaction.driver-memory).

If that does not fix it

Raise it with the team that runs the cluster the Jobs run in.

NunaFilesOutsideTable

What it means

In the last day the worker found unreferenced files that lie outside their table's own location. Severity warning.

Impact

The worker never records or deletes such files, so they stay in storage.

Check

kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h | grep '"WARN"'

The WARN lines name the table. Find which engine writes outside the location.

Fix

  • Configure the engine to write under the table's location.
  • Remove the stray files by hand once nobody needs them.

If that does not fix it

Raise it with the table's owners.

NunaDrLagging

What it means

The DR verifier's largest lag is over 15 minutes, for 5 minutes: some commit has not reached the DR store whole for that long. Severity page. It fires only on a worker with a DR replica named.

Impact

If the primary region were lost now, recovery would lose the commits not yet in the DR store.

Check

curl -sS "$NUNA/management/v1/dr/watermarks" \
  -H "Authorization: Bearer $TOKEN"

The answer names the tables behind (Back up and recover). Then check the object store's replication status for those buckets.

Fix

  • Replication behind or stopped: fix it in the object store.
  • The verifier cannot read the DR store: check its keys and endpoint, and the worker's WARN lines.

If that does not fix it

Raise it with the team that runs the object store's replication.

NunaDrVerifierNotPassing

What it means

The DR verifier has not finished a pass for 15 minutes. Severity page.

Impact

Until a pass succeeds, the DR lag is not known.

Check

kubectl -n "$NS" logs deployment/nuna-maintenance --since=1h | grep '"WARN"'

A pass fails when it cannot read the DR work list. The worker logs DR pass done after each pass that ends.

Fix

  • Catalog or identity provider unreachable: as for NunaWorkerNotScanning.

If that does not fix it

Raise it with the team that runs nuna.
