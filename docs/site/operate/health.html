Health checks

Check that each nuna server is up, read the whole deployment's health over the last day, and read the database self-check the server ran at start-up.

For platform operators Needs a platform operator

Before you begin

  • The probes need nothing: Kubernetes calls them without a token.
  • The health routes answer only a platform operator: a member of a group in nuna.security.platform-operator-groups.
  • The curl examples use NUNA and TOKEN as Use the APIs with curl sets them.

Liveness and readiness

The server has no separate health endpoint for Kubernetes and no Spring Boot Actuator: /actuator/health answers 404. The catalog chart's three probes read the console's settings file, /ui/config.json. The server answers it without a token and without reading the database, so a 200 says only that the server is up and answering HTTP.

The catalog chart's probes, all GET /ui/config.json on port http (8181)
ProbePeriodTimeoutFailures allowedWhy
Start-upstartupProbe.periodSeconds, default 5 sKubernetes' defaultstartupProbe.failureThreshold, default 120The first start of a release runs the database migrations, so the chart allows 10 minutes.
Readiness5 s3 s3Takes a server that stops answering out of the Service.
Liveness10 s5 s6Restarts a server that has stopped answering for about a minute.

The probes do not read the database on purpose. When the database cannot be reached, every server answers loads and commits with 503 ServiceUnavailableException and Retry-After: 2; taking servers out of the Service would not help. Watch the availability alerts for that instead (NunaRequestAvailabilityBurnFast).

Check one server by hand:

curl -sS -o /dev/null -w '%{http_code}\n' "$NUNA/ui/config.json"
200

The other two programs: the maintenance worker has no HTTP port and no probe; its health is its metrics (NunaWorkerNotScanning). The audit tables writer has a readiness probe only with the source otlp: a TCP check of its otlp-http port every 5 s.

The server's health over the last day

GET /management/v1/health/server answers the figures of the one server that answers it, over its last day: the day up to now, or since the server started if that is later. A restarted server counts again from zero.

curl -sS "$NUNA/management/v1/health/server" \
  -H "Authorization: Bearer $TOKEN"

The whole deployment's health

GET /management/v1/health/catalog adds every other server's figures to this server's and judges them against the latency objectives. The server finds the others through nuna.health.peers, which the chart sets to its headless Service, and asks each with your own token. A server that does not answer within nuna.health.peer-timeout (3 s by default) is listed with why, and its figures are missing.

curl -sS "$NUNA/management/v1/health/catalog" \
  -H "Authorization: Bearer $TOKEN"
{
  "alerts": {"metadata-integrity": 0, "regulated-schema-change": 0, "large-metadata": 0},
  "audit": {"acknowledged": 0, "failed": 0},
  "credential-vends": {"issued": 403, "cached": 3846, "none": 0, "failed": 0, "failures": {}},
  "slos": {
    "load": {"objective-ms": 50, "count": 2965, "within": 2841, "met": false, "p99": {"at-most-ms": 300}},
    "not-modified": {"objective-ms": 10, "count": 1282, "within": 694, "met": false, "p99": {"at-most-ms": 300}},
    "commit": {"objective-ms": 300, "count": 2, "within": 1, "met": false, "p99": {"over-ms": 300}}
  },
  "to": "2026-11-27T03:26:51.245590684Z",
  "answered": 1,
  "silent": 0,
  "servers": [{"id": "bb06eee7-159b-493c-a12b-918371ef3622", "name": "nuna-catalog-6c65d6c9dd-lw69w",

An objective is met when at least 99 in 100 answers finished within objective-ms; p99 names the histogram bucket the 99th percentile falls in. The demo above misses all three because its host was short of memory. audit counts the audit records Kafka acknowledged; it stays at 0 where the server audits to its log alone. The console shows the same figures on the Service page.

The database self-check

Before it migrates the schema, every server checks that the database keeps a committed change through the loss of a node. A finding stops the start, unless nuna.database.allow-unsafe names its code. A server that refuses has changed nothing in the database. A self-check that cannot run refuses the start too.

What each database is checked for
CodeDatabaseWhat it found
pg.sync-commit-offPostgreSQLsynchronous_commit is neither on nor remote_apply.
pg.no-sync-standbyPostgreSQLsynchronous_standby_names is empty, or no standby streams in sync or quorum state. The catalog's role needs pg_monitor to see the standbys.
pg.fsync-offPostgreSQLfsync or full_page_writes is off.
pg.commit-cancel-timeoutPostgreSQLstatement_timeout or idle_in_transaction_session_timeout is not 0: a timeout can cancel a commit's wait for the standby.
crdb.replicasCockroachDBA zone holding catalog data has fewer than 3 voting replicas.
crdb.fsync-offCockroachDBkv.raft_log.synchronization.unsafe.disabled is not false, or cannot be read (the role needs VIEWCLUSTERSETTING).
crdb.read-committed-offCockroachDBA READ COMMITTED transaction runs at another isolation: set sql.txn.read_committed_isolation.enabled to true.
ora.no-data-guardOracleNo synchronized Data Guard standby in MAXIMUM AVAILABILITY or MAXIMUM PROTECTION.
ora.no-transaction-guardOracleThe service does not have COMMIT_OUTCOME true.
ora.commit-replayOracleThe service's FAILOVER_TYPE replays transactions (Application Continuity).
ora.commit-nowaitOracleCOMMIT does not wait for its redo to be written.
ora.linguistic-sortOracleNLS_SORT is not BINARY.
ora.journal-job-downOracleThe job that makes the journal's partitions ahead of time cannot run.
mongo.not-replica-setMongoDBThe server is not a replica set member.
mongo.too-few-votersMongoDBFewer than 3 voting data-bearing members.
mongo.weak-write-concernMongoDBThe default write concern is not majority, or majority writes are not journaled.

A refused start ends with an exception whose message starts The catalog's database is unsafe, so the server does not start, lists each finding as its code and detail, and ends Make the database safe. Only a test or demo database may run so, by naming each code in nuna.database.allow-unsafe. Each finding allowed is logged at WARN as The catalog's database is unsafe, allowed by nuna.database.allow-unsafe: code: detail.

Read what a running server found with ?store=true, which also asks the database for its product and version on this server's own connection:

curl -sS "$NUNA/management/v1/health/server?store=true" \
  -H "Authorization: Bearer $TOKEN"

The answer carries the figures above and a store object. This one is the demo's, whose single-node PostgreSQL is allowed one finding:

{
  "store": {
    "configured": "postgresql",
    "backend": "PostgreSQL",
    "version": "18.7",
    "pitr-window-seconds": 604800,
    "self-check": {
      "at": "2026-11-26T23:42:22.744177875Z",
      "allowed": [{"code": "pg.no-sync-standby",
                   "detail": "synchronous_standby_names is '' and 0 standbys stream in sync or quorum state (the catalog role needs pg_monitor to see them)"}]
    }
  }
}

configured is nuna.database.backend (CockroachDB runs as postgresql and is told apart by its version). When the database does not answer, unreadable holds why in place of backend and version. pitr-window-seconds is nuna.governance.pitr-window as declared; the server cannot read the database's own backup setting.

A healthy deployment answers every server and allows no finding

/ui/config.json answers 200 on every pod, /management/v1/health/catalog shows "silent": 0, and self-check.allowed is empty on every server.
