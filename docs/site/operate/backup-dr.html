Back up and recover

What nuna keeps and where, how the DR verifier tracks what the DR region holds whole, and how to bring each table back to such a version after losing the primary region.

For platform operators Audited

nuna keeps its state in two places: the catalog database, which holds every catalog, namespace, pointer, grant, journal entry and DR watermark, and the object store, which holds the tables' metadata and data files. Both replicate to the DR region with their own tools, asynchronously, and neither waits for the other. After losing the primary region, the DR database may name files the DR store never got, or the DR store may hold commits the DR database never saw. The steps below bring each table back to a version the DR region holds whole.

Before you begin

  • The catalog database and the object store each replicate to a DR region.
  • You are a platform operator: every step on this page is a platform operator's.

Not documented yet: a backup procedure for the catalog database and the object store beyond their replication. nuna has no backup command of its own; use the database's and the store's tools, and keep the two consistent.

Run the DR verifier

Before any disaster, run the maintenance worker's DR verifier in the primary region. For each store the worker uses, name its DR replica: the same buckets and paths on the DR region's endpoint, with keys that may only read there.

config:
  nuna:
    maintenance:
      dr:
        verify-interval: PT1M
        replicas:
          onprem:
            endpoint: https://rgw-dr.example.internal:7480
            region: us-east-1
            access-key-id: nuna-dr-reader
            ca-bundle: /etc/nuna/storage-ca/onprem-dr.crt
secrets:
  values:
    nuna.maintenance.dr.replicas.onprem.secret-access-key: …

The replica's name, here onprem, is the name of the worker's store under nuna.maintenance.storage. On AWS S3 leave out endpoint; with no keys the AWS SDK's default chain is used. Settings: nuna.maintenance.dr.

Every verify-interval the verifier reads the catalog's DR work list, checks each table's and view's newer versions in the DR store, and reports each one's DR watermark: the newest version whose every file, data included, the DR store holds. The watermarks live in the catalog database, so they reach the DR region with it.

Not documented yet: whether the console shows the DR watermarks or lag.

List the tables behind their watermark and their lag (curl, reference):

curl -sS "$NUNA/management/v1/dr/watermarks" \
  -H "Authorization: Bearer $TOKEN"

NunaDrLagging pages when a commit has not been whole in the DR store for 15 minutes, and NunaDrVerifierNotPassing when no pass has finished for 15 minutes. The verifier's meters are on Metrics.

Recover in the DR region

Promote the DR database, and start the catalog servers on it and on the DR store. Then, for each catalog:

  1. Freeze the catalog.

    Before anything writes or cleans up (Freeze and unfreeze for disaster recovery):

    curl -sS -X PUT "$NUNA/management/v1/catalogs/trading/dr-freeze" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"reason": "DR recovery"}'

    Commits, creates, drops, renames, undrops and purges are refused, and the maintenance worker's scans pass the frozen tables by.

  2. Verify.

    Start the maintenance worker in the DR region with its replicas naming the DR store itself, and wait for one DR pass to end after the start: nuna.maintenance.dr.pass.last.success moves, and the worker logs DR pass done. The pass moves each watermark as far as the DR store allows, frozen tables included.

  3. Read the plan.

    curl -sS -X POST "$NUNA/management/v1/catalogs/trading/dr-reconcile" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"rewind": true}'

    The answer lists, under tables and views, each one above its watermark, the watermark it would move back to, and its lost commits (version, commit id, time, principal): the commits the DR region does not hold whole. Hand the lost commits to the tables' owners. One with "watermark": null has no version known whole in DR; it is not moved, and its owner decides.

  4. Rewind.

    Send the same with {"rewind": true, "apply": true}. Each frozen table and view above its watermark moves back to it in one journaled commit. One that did not move says why in apply-problem; if a pointer moved since the plan, read the plan again.

  5. Walk forward.

    Right after the rewind, send {} to see what the walk would do, then {"apply": true}. Each table moves along its metadata files, one step at a time, only while the DR store holds every file a step adds, and stops before the first that lacks one; its problem names the file. Table locations no catalog holds are listed under unknown-locations.

    Rewind before you walk

    Until the verifier's next pass, walked versions are above the watermark, and a rewind after the walk would give them up.

  6. Check the branches and tags.

    The same answer lists under refs every branch and tag that names a metadata file the DR store lacks, with the objects concerned under missing. Nothing rewinds or walks a ref. Delete each listed ref with DELETE /management/v1/catalogs/{catalog}/refs/{ref}, which the freeze does not refuse, or keep it for the primary region's return. A ref with a problem was not fully checked: send the request again.

  7. Lift the freeze.

    curl -sS -X DELETE "$NUNA/management/v1/catalogs/trading/dr-freeze" \
  -H "Authorization: Bearer $TOKEN"

    Then register any unknown locations by name, if you want them: a register is refused under a freeze.

Check it worked

GET /management/v1/dr/watermarks lists no table behind once the verifier has passed again, and engines can load and commit to the catalog's tables.

The rewind's commits reach the audit trail like any other commit.

If it fails

  • A step answers 403. Every step needs a platform operator.
  • A table did not move in the rewind. Read its apply-problem, and run the plan again if its pointer moved.
  • The walk takes nothing for a table. Its problem names the first missing file. If it says to rewind, the table is still above its watermark: rewind it, then walk.
