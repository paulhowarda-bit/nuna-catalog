Grants

Grant a group a privilege on a catalog, namespace, table or view, take it back, and read who holds what, under /management/v1/catalogs/{catalog}/grants.

A grant always goes to a group, never to one person. A privilege granted on a catalog or namespace reaches everything beneath it (see Identity and access). The examples use curl with $NUNA and $TOKEN set as curl shows. Errors take the form the API reference describes.

Every route here answers a caller who holds nothing in the catalog with 404 NoSuchWarehouseException, The given warehouse does not exist: catalog, and audits the refusal. A refusal on a namespace, table or view the caller holds nothing on is answered with that object's not-found error, also audited.

Granting and revoking

The grant, revoke and preview routes take the same body. A grant is refused in this order: a privilege that means nothing on the object or on a branch (400), a grant to a group you belong to (403), and a grant that would give the group two duties that must stay separate (403). See Authorization for the duties.

POST /management/v1/catalogs/{catalog}/grants

Grants one privilege on one object to one group. A grant the group already holds is answered the same way and changes nothing. Without branch, the grant holds through every ref, main included. With branch, it holds through that catalog branch only, and only write and modify may be granted that way: reads, listings and every change other than a commit ask through main.

The check that keeps duties apart runs inside the database's write of the grant, so two grants made at the same time cannot together break it.

Needs manage-grants on the object or above it Audited

Parameters

NameInTypeRequiredDescription
catalogpathstringYesThe catalog's name.
securablebodyobjectYesThe object: type (catalog, namespace, table or view), namespace (its levels, as an array) and name (for a table or view).
groupbodystringYesThe group the grant goes to.
privilegebodystringYesOne of describe, select, write, modify, create, manage-grants, manage-tags.
branchbodystringNoA live catalog branch the grant holds through, by name. Only with write or modify.

Request body

{
  "securable": {"type": "namespace", "namespace": ["equities"]},
  "group": "trading-analysts",
  "privilege": "select"
}

Responses

StatusWhen
204The group holds the privilege, whether this request granted it or it was held already.
400

The body is wrong. The messages include:

  • A grant names the group it goes to; grants never go to individuals …
  • A privilege is needed, or unknown privilege 'x'; known: [describe, select, write, modify, create, manage-grants, manage-tags]
  • A securable needs a type: catalog, namespace, table or view, Unknown securable type 'x'; expected catalog, namespace, table or view, A table needs a name, A namespace, table or view needs its namespace levels
  • create means nothing on a table: it creates namespaces, tables and views in a catalog or namespace (and the same for a view)
  • write means nothing on a view: it has no rows; select reads it, and modify changes its definition
  • privilege is not granted on one branch: a grant that names a branch gives write or modify, what a commit on it needs; reads and every other change ask through main
  • A grant names a branch, and name is a tag, which takes no write
  • A JSON body is needed, or Invalid JSON body: …
403You hold no manage-grants on the object or above it; or you belong to the group (no one grants to a group they belong to: group); or the grant would break separation of duties. The last two are audited with the reason separation-of-duties.
404The catalog, the object (Namespace does not exist: equities, table does not exist: equities.fills) or the branch (Branch does not exist: name; an expired branch counts as missing) is not there, or it went away during the write (The branch no longer exists: …, The securable no longer exists: …).
500The database did not say whether the write happened: The grant may or may not have been applied; repeat it: …. Sending the same grant again is safe.
503The catalog's database cannot be reached. Nothing was applied; the answer carries Retry-After.

The separation refusals read like these:

  • group platform-operators operates the platform and may hold no grant
  • group grant-admins administers grants on every catalog and may hold no other grant
  • group trading-engineers holds write in this catalog, a data duty that manage-tags (tags) must stay separate from

Example

curl -sS -i -X POST "$NUNA/management/v1/catalogs/trading/grants" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"securable": {"type": "namespace", "namespace": ["equities"]},
       "group": "trading-analysts", "privilege": "select"}'
HTTP/1.1 204
X-Request-ID: 4f0c9e2a7b1d4c8e9a3f5b6d7e8c9a01

POST /management/v1/catalogs/{catalog}/grants/revoke

Revokes one grant. The body names the grant exactly as it was made: the same object, group, privilege and branch. A revoke may name a branch that has expired. A revoke is not checked against separation of duties or your own groups.

Needs manage-grants on the object or above it Audited

Parameters

The same as a grant's.

Request body

{
  "securable": {"type": "table", "namespace": ["equities"], "name": "fills"},
  "group": "trading-engineers",
  "privilege": "write",
  "branch": "dev"
}

Responses

StatusWhen
204The grant is gone.
400The body is wrong, with the messages a grant gives.
403You hold no manage-grants on the object or above it.
404The group holds no such grant: No such grant: write to trading-engineers on branch dev (NotFoundException). Or the catalog, object or branch is not there.
500The revoke may or may not have been applied; repeat it: …
503The catalog's database cannot be reached. Nothing was applied.

Example

curl -sS -i -X POST "$NUNA/management/v1/catalogs/trading/grants/revoke" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"securable": {"type": "table", "namespace": ["equities"], "name": "fills"},
       "group": "trading-engineers", "privilege": "write", "branch": "dev"}'

POST /management/v1/catalogs/{catalog}/grants/preview

Says what the same body sent to the grant route would do, through the same checks in the same order, and writes nothing. The answer is admitted, unchanged (the group holds it already, with who granted it and when) or refused (with the refusal and the message the grant route would give). Separation of duties is read here, not inside a write, so a grant made in the meantime can still change the real answer.

Needs manage-grants on the object or above it

Parameters

The same as a grant's.

Responses

StatusWhen
200The answer follows, as a grant preview. Answers are not audited.
400The body cannot be read, as for a grant. A privilege that means nothing on the object is not a 400 here: it is a refused answer.
403You hold no manage-grants on the object or above it. This refusal is audited.
404The catalog, object or branch is not there.

Example

curl -sS -X POST "$NUNA/management/v1/catalogs/trading/grants/preview" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"securable": {"type": "catalog"}, "group": "trading-engineers",
       "privilege": "manage-tags"}'
{
  "securable": {"type": "catalog", "id": "9f1c2a4e-3b7d-4e8a-a6c5-1d2e3f405162"},
  "group": "trading-engineers",
  "privilege": "manage-tags",
  "answer": "refused",
  "refusal": "separation-of-duties",
  "reason": "group trading-engineers holds write in this catalog, a data duty that manage-tags (tags) must stay separate from"
}

Reading grants

The listing routes page with pageToken and pageSize. The page size defaults to 100 (nuna.rest.default-page-size) and a larger request is cut to 1000 (nuna.rest.max-page-size). A page size that is not a whole number of at least 1 is answered 400 Invalid page size: x, and a token the route did not give is answered 400 Invalid page token: …. Grants come in order of group, then privilege. Reading grants writes no audit record.

GET /management/v1/catalogs/{catalog}/grants

Lists the grants held by groups. Without group, it lists your own groups' grants, which anyone who holds something in the catalog may read. Naming a group you do not belong to needs manage-grants on the catalog.

Needs manage-grants on the catalog for another group's grants

Parameters

NameInTypeRequiredDescription
catalogpathstringYesThe catalog's name.
groupquerystringNoA group whose grants to list. Repeat it for several. Default: your own groups.
pageTokenquerystringNoThe next-page-token of the page before.
pageSizequeryintegerNoMost grants in one page. Default 100, at most 1000.

Responses

StatusWhen
200{"grants": [grant, …], "next-page-token": …}. next-page-token is there while more grants follow. A caller with no groups gets an empty list.
400The page size or token is wrong.
403You named a group you do not belong to and hold no manage-grants on the catalog.
404You hold nothing in the catalog, or it does not exist.

GET /management/v1/catalogs/{catalog}/grants/effective

Lists every grant that reaches one object: the grants on the catalog, on each namespace above it and on the object itself, from the catalog down. It also names the deployment's grant-admin groups, which manage grants on every catalog without a grant. The answer is not paged.

Needs manage-grants on the object or above it

Parameters

catalog, type, namespace and name, as for the grants on an object.

Responses

StatusWhen
200{"securable": securable, "grants": [grant, …], "grant-admin-groups": [group, …]}.
400The object is not named fully.
403You hold no manage-grants on the object or above it.
404The catalog or object is not there.

GET /management/v1/catalogs/{catalog}/grants/groups

Lists the groups that hold at least one grant in the catalog, each with the duties and privileges it holds there, and the deployment's grant-admin and platform-operator groups. The catalog knows groups only from its grants: it does not read the directory, so a group that holds nothing in the catalog is not listed. The answer says so in note.

Needs manage-grants on the catalog

Parameters

NameInTypeRequiredDescription
catalogpathstringYesThe catalog's name.
pageTokenquerystringNoThe next-page-token of the page before.
pageSizequeryintegerNoMost groups in one page. Default 100, at most 1000.

Responses

StatusWhen
200The groups follow, by name.
403You hold no manage-grants on the catalog.
404You hold nothing in the catalog, or it does not exist.

Example

curl -sS "$NUNA/management/v1/catalogs/trading/grants/groups?pageSize=1" \
  -H "Authorization: Bearer $TOKEN"
{
  "groups": [
    {"group": "data-stewards", "duties": ["read", "tags"], "privileges": ["manage-tags", "select"]}
  ],
  "grant-admin-groups": ["grant-admins"],
  "platform-operator-groups": ["platform-operators"],
  "note": "Only groups that hold a grant in this catalog are listed, and the deployment's grant-admin and platform-operator groups: the catalog knows groups from its grants and does not read the directory, so a group that holds nothing here is not listed.",
  "next-page-token": "AAAADWRhdGEtc3Rld2FyZHM"
}

Checking access

POST /management/v1/catalogs/{catalog}/grants/check

Asks, for each check in the body, whether you hold a privilege on an object, as the server would decide it for a real request. With branch, it asks through that catalog branch; without it, through main. An object you hold nothing on is answered as missing, with no securable in its result.

Needs any grant in the catalog

Parameters

NameInTypeRequiredDescription
catalogpathstringYesThe catalog's name.
checksbodyarrayYesOne or more checks, each with securable, privilege and, optionally, branch.

Request body

{
  "checks": [
    {"securable": {"type": "table", "namespace": ["equities"], "name": "fills"}, "privilege": "select"},
    {"securable": {"type": "table", "namespace": ["equities"], "name": "fills"}, "privilege": "write", "branch": "dev"}
  ]
}

Responses

StatusWhen
200{"results": [result, …]}, one result per check, in order. The answers are not audited.
400No checks: Nothing to check: send {"checks":[{"securable":...,"privilege":...}]}. Or a check names an unknown privilege or an incomplete object.
404You hold nothing in the catalog, or it does not exist (audited); or a check names a branch that does not exist.

Example

curl -sS -X POST "$NUNA/management/v1/catalogs/trading/grants/check" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"checks": [{"securable": {"type": "table", "namespace": ["equities"], "name": "fills"},
                   "privilege": "select"}]}'
{
  "results": [
    {
      "privilege": "select",
      "securable": {
        "type": "table",
        "id": "7a8b9c0d-1e2f-4a3b-8c4d-5e6f7a8b9c0d",
        "namespace": ["equities"],
        "name": "fills",
        "state": "active"
      },
      "allowed": true
    }
  ]
}

Objects

Securable

How an answer names an object.

FieldTypeDescription
typestringcatalog, namespace, table or view.
idstringThe object's id, a UUID.
namespacearray of stringsThe namespace levels: the namespace itself, or the one a table or view is in. Absent for a catalog.
namestringA table's or view's name.
statestringA table's or view's state, in lower case: active, or dropped while it can still be restored.

Grant

FieldTypeDescription
securableobjectThe object the grant is on, as a securable.
groupstringThe group that holds it.
privilegestringThe privilege.
branchstringThe catalog branch the grant holds through. Absent for a grant on every ref.
granted-bystringThe subject who made the grant.
granted-atstringWhen, as an ISO-8601 instant.

Grant preview

FieldTypeDescription
securable, group, privilege, branchThe grant asked about. branch only when the body named one.
answerstringadmitted, unchanged or refused.
refusalstringWith refused: privilege-not-on-object, privilege-not-on-a-branch, self-grant or separation-of-duties.
reasonstringWith refused: the message the grant route would answer.
granted-by, granted-atstringWith unchanged: who made the grant the group already holds, and when.

Group entry

FieldTypeDescription
groupstringThe group's name.
dutiesarray of stringsThe duties its privileges in this catalog give: read (describe, select), data (write, modify, create), grants (manage-grants), tags (manage-tags).
privilegesarray of stringsThe privileges it holds anywhere in the catalog.

Check result

FieldTypeDescription
privilegestringThe privilege asked about.
branchstringThe branch asked through, when the check named one.
securableobjectThe object, as a securable. Absent when it is missing or you hold nothing on it.
allowedbooleanWhether you hold the privilege.
reasonstringWhy not, when allowed is false: the denial's message, or the object's not-found message.
