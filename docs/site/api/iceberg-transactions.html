Iceberg REST: transactions

Commit changes to several tables together, or to none of them, with POST /v1/{prefix}/transactions/commit.

A transaction applies every table's commit in one database transaction: either all of them land or none does. It does not give readers a view of the tables at one instant: a reader loading two tables while the transaction lands may see one before and one after. The examples use curl with NUNA and TOKEN set as Use the APIs with curl describes. See Commit to several tables at once.

Endpoints

Transaction endpoints
MethodPathWhat it does
POST/v1/{prefix}/transactions/commitCommits changes to several tables at once.

POST /v1/{prefix}/transactions/commit

Each entry is one table's commit, judged as a table commit is: the same privileges (write for data changes, modify for anything else), the same rules and the same refusals. Every table must already exist, and each may appear once. Through a branch, each table must be one the branch holds, and the transaction changes only the branch. Through a tag it is refused. Takes an Idempotency-Key.

If another commit changes one of the tables first and every requirement still holds, the server applies the transaction again on top, as it does for a single table.

Needs write or modify on each table Audited

Body

NameInTypeRequiredDescription
table-changesbodyarrayYesOne entry per table: identifier ({"namespace": […], "name": "…"}), requirements and updates, as in a table commit. At most nuna.rest.max-transaction-tables entries, 100 by default.

Responses

StatusWhen
204Every table's change landed. Load the tables for their new metadata.
400A transaction may change at most 100 tables; this one names n; Table table is named more than once in the transaction; a refused update; or the prefix names a tag.
403You lack the privilege one table's change needs, or one table is held or frozen.
404Table does not exist: … for any table.
409A requirement failed (CommitFailedException), its message starting with the table's name; or Transaction lost to concurrent commits n times; its tables changed too often to apply it. Nothing landed: load the tables and redo the changes.
500The outcome is unknown (CommitStateUnknownException). Repeat with the same Idempotency-Key.
503Catalog store unavailable; nothing was applied: …, with Retry-After: 2.

Example

This moves two tables' main to snapshots already written, together: a publish after write-audit-publish. Engines build these bodies themselves; the snapshot ids come from loading each table.

curl -sS -X POST "$NUNA/v1/trading/transactions/commit" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: eod-2026-11-25-publish" \
  -d '{"table-changes": [
    {"identifier": {"namespace": ["equities"], "name": "fills"},
     "requirements": [{"type": "assert-ref-snapshot-id", "ref": "main", "snapshot-id": 4012}],
     "updates": [{"action": "set-snapshot-ref", "ref-name": "main", "type": "branch", "snapshot-id": 4019}]},
    {"identifier": {"namespace": ["equities"], "name": "orders"},
     "requirements": [{"type": "assert-ref-snapshot-id", "ref": "main", "snapshot-id": 7730}],
     "updates": [{"action": "set-snapshot-ref", "ref-name": "main", "type": "branch", "snapshot-id": 7741}]}
  ]}'

Objects

The request is the standard's commit-transaction request; the answer has no body.
