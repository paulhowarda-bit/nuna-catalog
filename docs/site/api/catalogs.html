Catalogs

List the catalogs you can see and read a catalog's own properties, under /management/v1/catalogs.

The API creates no catalog and deletes none. The server creates each catalog named in nuna.storage.catalogs when it starts, bound to the storage profile, KMS key set and legal entity set there, and records the creation as an audit record. A catalog's binding never changes: a server whose settings disagree with what the catalog's database holds refuses to start. See Catalogs, namespaces, tables and views and Storage profiles and credential vending.

The examples use curl with $NUNA and $TOKEN set as curl shows.

GET /management/v1/catalogs

Lists the catalogs the deployment declares that you hold something in, by name, sorted without regard to case. You hold something in a catalog when one of your groups holds a grant on it or on anything in it. Grant admins and platform operators see every catalog. A caller who holds nothing gets an empty list, not a refusal.

Each catalog says what your groups may do somewhere in it, and the answer says whether you read the audit feed and operate the deployment. These come from your own grants and groups, so asking writes no audit record. Each route still decides for itself: these flags say only what the console offers.

Needs a signed-in caller

Responses

StatusWhen
200{"catalogs": [catalog entry, …], "may": {"operate", "read-audit-feed"}}.
401The request carries no token, or one the server does not accept: Not authorized: the bearer token is missing or was not accepted (NotAuthorizedException), with WWW-Authenticate: Bearer.

Example

curl -sS "$NUNA/management/v1/catalogs" -H "Authorization: Bearer $TOKEN"
{
  "may": {"operate": false, "read-audit-feed": true},
  "catalogs": [
    {
      "audit": false,
      "name": "trading",
      "may": {"manage-grants": false, "manage-tags": true, "modify": false, "select": true}
    },
    {
      "audit": true,
      "name": "nuna_audit",
      "may": {"manage-grants": false, "manage-tags": false, "modify": false, "select": true}
    }
  ]
}

GET /management/v1/catalogs/{catalog}/properties

Reads a catalog's own properties: the storage profile, KMS key set and legal entity it was declared with, and where its tables live. The Iceberg REST API has nothing at the catalog level, which is why this route exists. Nothing secret is answered and nothing that names an identity: the profile's access keys, its STS role, the maintenance principal, its CA bundle's path and its KMS key ARN stay out. The answer says whether writes use a KMS key, not which key.

Needs any grant in the catalog

Parameters

NameInTypeRequiredDescription
catalogpathstringYesThe catalog's name.

Responses

StatusWhen
200The catalog properties follow.
404You hold nothing in the catalog, or it does not exist: The given warehouse does not exist: catalog (NoSuchWarehouseException). The refusal is audited.

Example

curl -sS "$NUNA/management/v1/catalogs/trading/properties" -H "Authorization: Bearer $TOKEN"
{
  "name": "trading",
  "kms-key-set": "trading-keys",
  "legal-entity": "Example Trading",
  "storage-profile": {
    "name": "onprem",
    "kind": "CEPH",
    "endpoint": "https://s3.example",
    "region": "us-east-1",
    "table-root": "s3://trading-lake/tables",
    "allowed-prefixes": ["s3://trading-lake/tables"],
    "encryption": "sse-kms"
  }
}

Objects

Catalog entry

FieldTypeDescription
namestringThe catalog's name, as nuna.storage.catalogs declares it.
auditbooleanTrue for the catalog that holds the audit tables (nuna.audit.tables.catalog).
mayobjectselect, modify, manage-grants and manage-tags, each true when one of your groups holds a grant that implies it on the catalog or on anything in it. A grant admin's manage-grants is always true.

The answer's may

FieldTypeDescription
operatebooleanTrue when you belong to a platform-operator group.
read-audit-feedbooleanTrue when you hold select on the audit tables' catalog, which the audit feed needs.

Catalog properties

FieldTypeDescription
namestringThe catalog's name.
kms-key-setstringThe KMS key set it was declared with.
legal-entitystringThe legal entity it was declared with.
storage-profile.namestringThe storage profile's name.
storage-profile.kindstringThe object store: S3, MINIO or CEPH.
storage-profile.endpointstringThe object store's endpoint, as configured.
storage-profile.regionstringThe region, as configured.
storage-profile.table-rootstringWhere new tables are placed.
storage-profile.allowed-prefixesarray of stringsThe prefixes a table's location may lie beneath.
storage-profile.encryptionstringsse-kms when the profile names a KMS key, otherwise bucket-default.
