API reference

nuna serves two HTTP APIs: the Iceberg REST catalog API under /v1, which engines use, and the management API under /management/v1, which the console and operators use. This page covers what they share and lists every endpoint.

The two APIs

APIBase pathWhat it is
Iceberg REST catalog/v1The standard Iceberg REST catalog API, which Spark, Trino, PyIceberg and other engines speak. nuna serves the endpoints it advertises in GET /v1/config and refuses the rest. Catalog routes sit under /v1/{prefix}, where the prefix names a catalog and, for a branch or tag, a ref (The prefix).
Management/management/v1nuna's own API: grants, governance, audit, branches and tags, lifecycle, maintenance, health and disaster recovery. A catalog's routes sit under /management/v1/catalogs/{catalog}, and an object's under its namespace's path, …/namespaces/{namespace}/tables/{table} or …/views/{view}.
OPA decisions/opa/v1Access decisions, row filters and column masks for Trino's OPA access control (OPA decisions).

The version is in the path; there is no version header or field. Both APIs take and answer JSON.

In the Iceberg API, a namespace of more than one level is one path segment, its levels joined by the byte 0x1F, written %1F: equities%1Fdaily for equities.daily. The management API takes the same form for {namespace}.

Examples on these pages use curl with NUNA and TOKEN set as Use the APIs with curl describes.

Authentication

Every request carries an access token from your organization's identity provider as a bearer token: Authorization: Bearer token (Get a token). The only routes that take none are /v1/oauth/tokens, which refuses every call, the console's own files, and the /opa/ routes, which check the end user's token that Trino sends in the request body.

An engine that acts for an end user adds one of these. Its client must be registered as a trusted engine (Engines); a request from any other client that names an end user is refused with 403.

Headers that name an end user
HeaderValue
X-Nuna-End-UserThe end user's id, beside the engine's own token in Authorization.
X-Nuna-End-User-GroupsThe end user's groups, separated by commas, each percent-encoded. Only with X-Nuna-End-User: groups without a user are refused with 401.
X-Nuna-Engine-AuthorizationBearer engine token, when Authorization carries the end user's own token. When both carry the same token, the engine acts as itself. It cannot be sent beside X-Nuna-End-User: an engine names its end user one way.

A refused token answers 401 with a WWW-Authenticate header: Bearer when there was no token, Bearer error="invalid_token" when the token was not accepted, and Bearer error="invalid_request" when the headers contradict each other. The body never says why a token was refused; the audit record does.

Authorization

Each endpoint needs a privilege on its object, from a grant to one of your groups on the object or on anything above it (Privileges). A caller who holds nothing on the object gets 404, as if it did not exist, so names are not disclosed. A caller who holds something, but not what the endpoint needs, gets 403 with a message naming the privilege. Every refusal is written to the audit trail.

Errors

Every error answer from both APIs has the same JSON body, the Iceberg REST standard's error model. type is the name of the error class an Iceberg client maps the answer to; the management API uses the same field for its own types.

{
  "error": {
    "message": "Namespace does not exist: equities",
    "type": "NoSuchNamespaceException",
    "code": 404
  }
}

A few 409 answers add fields beside error: a branch merge that conflicts adds ref and conflicts, and a change refused because refs changed adds refs. Error responses lists every status and type, when each comes and what to do.

Two statuses ask you to repeat the request, and send Retry-After in seconds: 503 when the catalog's database or another service it needs cannot be reached and nothing was applied (Retry-After: 2), and 429 when a rate limit is reached (Retry-After: 60).

Paging

Listings that page take a pageToken query parameter and answer a next-page-token field. Pass the token back for the next page; a null token means the last page.

  • In the Iceberg API, a listing without pageToken answers every item at once and ignores pageSize. Send an empty pageToken to ask for the first page. pageSize defaults to 100 (nuna.rest.default-page-size); a larger size than 1000 (nuna.rest.max-page-size) is cut to it.
  • Management listings name their own size parameter and default on each endpoint's page.
  • A token is opaque: pass it back as it came, with the same other parameters. A token the server did not make answers 400, Invalid page token: ….

Writes and retries

Idempotency keys

Every write in the Iceberg API, and these management writes, take an Idempotency-Key header: creating, renewing and deleting a branch or tag. A repeat with the same key gets the first request's answer, and nothing is applied twice.

  • A key is 1 to 128 characters. Any other answers 400, Invalid Idempotency-Key: must be 1 to 128 characters.
  • The server keeps a key for 24 hours, and says so in GET /v1/config as "idempotency-key-lifetime": "PT24H".
  • A key belongs to one caller, route and body. Reusing it for a different request answers 400, Idempotency key … was used for a different request.
  • An answer of 500 or above frees the key, so the repeat runs again. A repeat sent while the first is still running waits for its answer.

If-Match

Row filters and column masks carry a version. Setting or removing one takes If-Match: "version", the version as the rule's listing gives it, in double quotes. When the rule has moved on, the answer is 412 (PreconditionFailedException) and nothing changes: list the rules again (Row and column rules). No other endpoint takes If-Match; Iceberg commits carry their own requirements in the body.

ETags

Loading a table answers an ETag. Send it back in If-None-Match and the server answers 304 with no body while nothing has changed (Load a table).

Request ids

Every answer carries X-Request-ID. Send your own, 1 to 128 characters, and the server uses it; otherwise it uses the request's trace id, or makes one. The id is in the server's log lines and in the audit record of the request, so quote it when you report a problem.
