OPA decisions

The three endpoints Trino's OPA access control calls to learn each user's row filter and column masks on a table, under /opa/v1.

For platform operators

The server answers these calls itself, in the form Trino's OPA access control expects; no OPA server sits between them. Trino points three settings of its access-control.properties here, and forwards each user's own catalog token as the extra credential token. Use OPA shows the Trino side. The filters and masks come from the rules a grant admin sets with the Row and column rules API.

These endpoints take no Authorization header: Trino's calls to OPA carry no token of their own. What they answer depends only on the user's token inside the body, which the server verifies as it verifies any token, and they fail closed. They write no audit record and store nothing.

Endpoints

OPA decision endpoints
MethodPathWhat it doesTrino setting
POST/opa/v1/allowAllows every operation Trino asks about.opa.policy.uri
POST/opa/v1/row-filtersGives the user's row filter on one table.opa.policy.row-filters-uri

How the server decides

Trino sends {"input": {"context": {"identity": {…}}, "action": {…}}}. For the two rule endpoints the server works out its answer in this order:

  1. It looks up the table's Trino catalog, ignoring case, in nuna.opa.catalogs. A Trino catalog not listed there gets no filter and no masks: name every Trino catalog that reads the server.
  2. It reads the user's token from input.context.identity.extraCredentials.token and verifies it. Trino's own user and groups are ignored: the user and their groups come only from the token.
  3. It finds the table in the warehouse the Trino catalog maps to. The warehouse is a catalog, or catalog@ref to read through a live branch or tag. The Trino schema name is split on dots into namespace levels, so equities.daily is the namespace equities, daily.
  4. It takes the rules on the table for the user's groups.

In a listed Trino catalog, the answer is closed when the token is missing or blank, when the server does not accept it, when the schema or table name is missing, or when the table does not exist or the user holds no grant on it or above it. Closed means no rows (the filter false) and every column NULL. The answer is the same for a table that does not exist as for one the user may not know of.

Rules from several groups add up:

  • A table with no rules gets no filter and no masks.
  • A table with rules, none of them for the user's groups, gets the filter false: no rows.
  • The user's filters are joined with OR, each in brackets. A rule of theirs with no filter admits every row, so the answer then has no filter.
  • A column is masked only when every one of the user's rules masks it. If they all mask it the same way, that expression is the mask; if they differ, the mask is NULL.

POST /opa/v1/allow

Answers yes to every question, whatever the body holds. The server's own routes decide what a user may reach when Trino asks the catalog for a table, so OPA has nothing more to refuse.

Responses

StatusWhen
200Always {"result":true}.

Example

curl -sS -X POST "$NUNA/opa/v1/allow" -H "Content-Type: application/json" -d '{"input": {}}'
{"result":true}

POST /opa/v1/row-filters

Gives the row filter the user gets on one table, Trino's GetRowFilters question.

Parameters

NameInTypeRequiredDescription
input.context.identity.extraCredentials.tokenbodystringYesThe user's own catalog token, which Trino forwards.
input.action.resource.table.catalogNamebodystringYesThe Trino catalog.
input.action.resource.table.schemaNamebodystringYesThe namespace levels, joined by dots.
input.action.resource.table.tableNamebodystringYesThe table.

Request body

{
  "input": {
    "context": {
      "identity": {"user": "lee", "groups": [], "extraCredentials": {"token": "…"}}
    },
    "action": {
      "operation": "GetRowFilters",
      "resource": {"table": {"catalogName": "trading", "schemaName": "equities", "tableName": "fills"}}
    }
  }
}

Responses

StatusWhen
200
  • {"result":[{"expression":"filter"}]}: the user's filter.
  • {"result":[{"expression":"false"}]}: no rows, because the answer is closed or none of the user's groups has a rule on a table that has rules.
  • {"result":[]}: no filter, because the table has no rules, a rule of the user's has no filter, or the Trino catalog is not in nuna.opa.catalogs.
400The body is not JSON (BadRequestException).
503The user's token could not be checked; retry later (ServiceUnavailableException), with Retry-After: 2. The issuer's keys could not be fetched, so the server gives no answer and Trino fails the query rather than run it with rules that might be wrong.

Example

curl -sS -X POST "$NUNA/opa/v1/row-filters" \
  -H "Content-Type: application/json" \
  -d @row-filters.json
{"result":[{"expression":"desk = 'EQ'"}]}

POST /opa/v1/column-masks

Gives the mask of each column Trino asks about, Trino's batched GetColumnMask question. Trino asks for every column of a table it reads in one batch, under the names its schema gives them. Column names are compared without regard to case. The answer lists only the columns that have a mask, each by its position in the request, counted from 0.

When the user's rules mask a column the batch does not name, the rules and the schema Trino read disagree: the column has another name in that schema, for example in an older snapshot or on a branch. Masking by name would leave that column bare under its other name, so every column of that table is NULL instead.

Parameters

NameInTypeRequiredDescription
input.context.identity.extraCredentials.tokenbodystringYesThe user's own catalog token.
input.action.filterResourcesbodyarrayYesOne {"column": {"catalogName", "schemaName", "tableName", "columnName", "columnType"}} per column. The columns may come from several tables.

Request body

{
  "input": {
    "context": {
      "identity": {"user": "lee", "extraCredentials": {"token": "…"}}
    },
    "action": {
      "operation": "GetColumnMask",
      "filterResources": [
        {"column": {"catalogName": "trading", "schemaName": "equities", "tableName": "fills",
                    "columnName": "fill_id", "columnType": "bigint"}},
        {"column": {"catalogName": "trading", "schemaName": "equities", "tableName": "fills",
                    "columnName": "account_id", "columnType": "varchar"}}
      ]
    }
  }
}

Responses

StatusWhen
200{"result":[{"index":n,"viewExpression":{"expression":"mask"}}, …]}, one entry per masked column. {"result":[]} when no column asked about is masked.
400The body is not JSON (BadRequestException).
503The user's token could not be checked; retry later (ServiceUnavailableException), with Retry-After: 2.

Example

curl -sS -X POST "$NUNA/opa/v1/column-masks" \
  -H "Content-Type: application/json" \
  -d @column-masks.json
{"result":[{"index":1,"viewExpression":{"expression":"'***'"}}]}

Not documented yet: the answer to a row-filter or column-mask request whose body is valid JSON but names no Trino catalog. No test covers it.

Objects

Every answer is one object with a single field, result.

The result of each endpoint
Endpointresult
/opa/v1/allowtrue.
/opa/v1/row-filtersAn array of at most one {"expression"}: the SQL predicate the user's rows must meet.
/opa/v1/column-masksAn array of {"index", "viewExpression": {"expression"}}: the position of the column in the request, and the SQL expression Trino shows in its place.
