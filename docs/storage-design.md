# Storage design (M1)

The contract every backend implements, designed against all three families at once (PostgreSQL-wire, Oracle, MongoDB) so no single database shapes it [D7b]. Decisions cited in brackets are rows of `decision-ledger.md`; sections refer to `build-plan.md`.

## 1. Scope of M1

- The interface for the whole storage layer is designed here (section 3). M1 **implements** only the commit core: pointer read, atomic commit, ambiguity lookup, self-check, migrations. The other operation groups (namespaces, objects, grants, idempotency reads, outbox relay, governance, refs) are added to the Java interface when M2 builds them, following section 3's signatures.
- The shared suite (section 6) covers the commit core in M1 and grows with each operation group.
- Spikes: PostgreSQL (primary + synchronous standby), Oracle Free (single instance), MongoDB (three-node replica set). CockroachDB and YugabyteDB join the SQL family in M2a.

## 2. Records (logical; each backend maps them)

| Record | Key | Fields |
|---|---|---|
| pointer | (object_id, branch) | metadata_location, version (starts at 1, +1 per commit), sha256 (hex), projection (bytes), last_commit_id, updated_at |
| journal | (commit_id, object_id, branch) | seq (backend-assigned, monotonic), committed_at, principal, end_user, engine, requirements (JSON), updates (JSON), old_location, new_location, old_version, new_version |
| outbox | seq | commit_id, created_at, type, payload (JSON) |
| idempotency | key | principal, request_hash, status, body, expires_at |
| durability_barrier | singleton | counter (all three backends; see the M1 deviations) |
| catalog | id | name_norm (unique), name (M0) |

- `branch` is `main` for every v1 commit. Keying pointers by (object, branch) from v1 means branches in v1.x add rows, never a migration [D33].
- No foreign key from pointer to an objects table in M1; it arrives with the objects record in M2.
- Projection is stored whole in M1; chunking above the size budget is M2 [D8.5].

## 3. Interface

Java package `fidice.catalog.store`. All methods are one atomic unit; reads of pointers go to the primary/leader only [D8.3]. Section 9 replaces the M2 sketch below with the whole contract; the M1 core is now `CommitStore`.

```java
public interface CatalogStore {
    Optional<CatalogRecord> findCatalog(String normalizedName);                 // M0

    // --- commit core (M1) ---
    Optional<Pointer> readPointer(PointerKey key);
    CommitResult commit(CommitBatch batch);        // throws CommitOutcomeUnknownException
    CommitLookup findCommit(UUID commitId, PointerKey anyKeyInBatch);
    List<SafetyFinding> selfCheck();
    void migrate();

    // --- added in M2, signatures fixed here ---
    // namespaces: create, drop, load, listChildren(paged), updateProperties(CAS on version)
    // objects:    createIfAbsent, softDrop, undrop, rename, register, list(paged), purgeEligible
    // grants:     put/revoke (+outbox row), check(batch), listByPrincipal, listByObject
    // idempotency: claim, read, awaitCompletion, expire   (the result row is written by commit)
    // outbox:     claimBatch(ordered), markRelayed
    // governance: retention classes, holds, classifications, trusted engines, storage profiles
    // journal:    readRange(objectId, branch, from, to); refs (v1.x)
}
```

Value types (all records, all immutable):

- `PointerKey(UUID objectId, String branch)`
- `Pointer(String metadataLocation, long version, String sha256, byte[] projection)`
- `PointerSwap(PointerKey key, Optional<Pointer> expected, Pointer next, JournalEntry journal)` — `expected` empty means create; `next.version` must be `expected.version + 1`, or 1 on create. The swap succeeds only if the stored pointer equals `expected` on **both** location and version.
- `JournalEntry(String principal, String endUser, String engine, String requirementsJson, String updatesJson)`
- `OutboxEvent(String type, String payloadJson)`
- `IdempotencyResult(String key, String principal, String requestHash, int status, String body, Instant expiresAt)`
- `CommitBatch(UUID commitId, Instant committedAt, List<PointerSwap> swaps, List<OutboxEvent> outbox, Optional<IdempotencyResult> idempotency)` — `commitId` is generated by the caller **before** the transaction begins [D8.1]. Swaps are applied in ascending (objectId, branch) order on every backend, so multi-table commits (v1.x) cannot deadlock [D15].
- `CommitResult`: sealed, `Committed(UUID commitId)` or `Conflict(PointerKey key, Optional<Pointer> actual)`. A conflict is definite: nothing was written.
- `CommitOutcomeUnknownException(UUID commitId, Throwable cause)`: the backend cannot tell whether the transaction committed (connection lost after COMMIT was sent, failover mid-commit). The caller must call `findCommit`.
- `CommitLookup`: `COMMITTED` or `NOT_COMMITTED`, both definite. If `findCommit` itself cannot decide, it throws `StoreException`; the server then answers 500 CommitStateUnknown [D9].
- `SafetyFinding(String code, String detail)`: an empty list means the backend's durability settings are safe [D8.2].

## 4. Commit algorithm (all backends)

1. Begin a transaction (SQL: READ COMMITTED with row locks; MongoDB: snapshot transaction, majority write concern).
2. For each swap in key order: lock the pointer row (`SELECT … FOR UPDATE`; MongoDB: the update itself), compare with `expected`. Mismatch → roll back, return `Conflict` with the actual pointer.
3. Write each new pointer, one journal row per swap, the outbox rows and the idempotency result.
4. COMMIT. A clean error before COMMIT is sent → roll back, throw `StoreException`. Any failure after COMMIT is sent, or while waiting for its answer → `CommitOutcomeUnknownException`.
5. Never retry a commit at the driver or pool level [D8.4]: pools must not replay statements, and the JDBC/Mongo retryable-write features stay off for commit transactions, except MongoDB's own `commitTransaction` retry, which is idempotent.

## 5. Ambiguity protocol (`findCommit`)

Common rule: first wait until no transaction that could still commit `commitId` is in flight, then look the commit up in the journal with a read that only sees durable data.

### 5.1 PostgreSQL

1. New connection. `SELECT … FOR UPDATE` on the pointer row for `anyKeyInBatch`. This blocks until the original transaction (if still alive on the server) commits or rolls back.
2. Look up `commit_id` in the journal.
3. **Durability barrier:** a commit whose wait for the synchronous standby was cancelled is committed locally but may not be replicated. Before answering `COMMITTED`, increment `durability_barrier.counter` in its own transaction and commit it; with synchronous commit, that commit returns only after the standby has flushed WAL past the earlier commit.
4. Settings: no `statement_timeout` or `idle_in_transaction_session_timeout` that can cancel a COMMIT's replication wait for the catalog role; client socket timeout is allowed (it fails the client, not the server's COMMIT).

### 5.2 Oracle

1. On a recoverable error, take the connection's Logical Transaction ID (`OracleConnection.getLogicalTransactionId()`).
2. New connection: `DBMS_APP_CONT.GET_LTXID_OUTCOME(ltxid, committed, user_call_completed)`. The call is definitive and also blocks the original transaction from committing afterwards.
3. Requires a service with `COMMIT_OUTCOME = TRUE`. If the spike shows Transaction Guard unavailable on Oracle Free, use 5.1 steps 1–2 locally (row lock + lookup) and keep Transaction Guard as a work-hardware gate.

### 5.3 MongoDB

1. On `UnknownTransactionCommitResult`, retry `commitTransaction` on the same session (idempotent) a bounded number of times.
2. If the session is gone: start a transaction that writes a marker field on the pointer document for `anyKeyInBatch` (this write conflicts with any in-flight transaction on that document; retry on `WriteConflict`), commit with majority, then read the journal document for `commitId` with read concern majority from the primary.

## 6. Shared suite (test-jar of `catalog-store-api`)

An abstract JUnit class that each backend extends by supplying a `StoreUnderTest`: the store, plus a `Faults` handle (Toxiproxy between client and database; stop/start primary). The store accepts a `CommitHook` test seam invoked immediately before COMMIT is sent, so a test can cut the link at the exact moment that makes the outcome ambiguous. Production passes a no-op hook.

| # | Test | M1 |
|---|---|---|
| 1 | CAS linearizability: N writers from one base, exactly one `Committed`, the rest `Conflict`; version advances by exactly 1; repeated (10,000 in the nightly profile, 200 in CI). | yes |
| 2 | Atomicity: cut the link before COMMIT; pointer, journal, outbox and idempotency rows are all absent. Multi-swap batch with one stale `expected` → `Conflict`, nothing written. | yes |
| 3 | Ambiguity: cut the response path after COMMIT is sent → `CommitOutcomeUnknownException` → `findCommit` says `COMMITTED` and the pointer advanced. Cut the request path so COMMIT never arrives → `findCommit` says `NOT_COMMITTED`. Never a `Conflict`. | yes |
| 4 | Failover: stop the primary during a stream of commits; every commit acknowledged before the stop is present after promotion. | PostgreSQL, MongoDB |
| 5 | Self-check: the safe environment reports no findings; each unsafe setting reports its finding code. | yes (Oracle: unsafe only; safe is a work gate) |
| 6 | Read-after-commit with injected replica lag. | PostgreSQL, MongoDB (`hasReplica`) |
| 7 | Size: large projection, journal partition rollover (section 9 (g)). | M2: `SizeSuite` |
| 8 | Names. | M2: `NamespaceSuite`, `CatalogObjectSuite` |
| 9 | Idempotency key concurrency and replay. | M2: `IdempotencySuite` |
| 10 | Rolling schema upgrade. | M2: `UpgradeSuite` |

Each test gets a bite run: break the check it guards (e.g. drop the version compare, skip the barrier) and see it fail.

| | `pg.no-sync-standby` | `synchronous_standby_names` empty, or no standby in `pg_stat_replication` with state `sync`/`quorum` |

| Oracle | `ora.no-data-guard` | `v$database.protection_level` not MAXIMUM AVAILABILITY/PROTECTION |

The server refuses to start while findings exist (wired in M2). For local development on a single node, the operator may accept specific finding codes by name in configuration; each accepted finding is logged at startup. Accepting is per code, never a blanket switch.

## 8. Branches and tags (design review for v1.x)

- v1 already stores pointers by (object, branch) and journals every commit with `seq`, so branches add rows only.
- **Open problem, decided in v1.x:** a tag must be a consistent cut across tables. A journal `seq` from a backend sequence is not commit-ordered (a lower `seq` can commit after a higher one). Candidate protocols: (a) commits hold a shared lock and tag creation takes it exclusively for an instant, then records max(`seq`); (b) per-backend commit-ordered clocks (Oracle SCN, CockroachDB commit timestamp, MongoDB cluster time) with a PostgreSQL fallback of (a); (c) materialize the tag as a copy of (object, version) pairs. None changes the v1 storage layout; (a) adds a lock to the commit path.

## 9. The whole contract (M2)

`CatalogStore` is `CommitStore` (the M1 core of sections 3 to 5, renamed) plus one interface per operation group of build-plan 2.3: `NamespaceStore`, `CatalogObjectStore`, `GrantStore`, `IdempotencyStore`, `OutboxStore`, `GovernanceStore`, `JournalStore`, `SchemaStore`. The javadoc is normative: each method lists the outcomes it can return. Every method is one atomic unit on every backend. This section replaces the M2 sketch in section 3.

**Writes.** Every non-commit mutation takes a `Change(id, at, outbox, idempotency)`. The id is generated before the transaction, like a commit id; `at` is the change's time (a drop's dropped-at, a purge's "now"). The mutation and its change records (outbox events, idempotency result) are one transaction. It returns a `WriteResult`; only `Applied` wrote anything. A COMMIT that fails or warns throws `CommitOutcomeUnknownException` carrying the id, as a commit does. Changes have no `findCommit`: the server resolves an unknown change through its idempotency key (the retry finds `Done`, or the claim lapses and the change runs again), and a change is safe to retry without one (`putGrant` answers `Unchanged`; a create answers `NameTaken` naming the caller's own id). Each write locks what it checks: the record it changes for update, the records it depends on (parent namespace, securable, storage profile) for share, so a create and a drop of what it depends on serialize. A write that takes a name or key inserts under a unique index, which waits for an open writer of the same name (the M1 lesson: an in-flight create is invisible to `SELECT … FOR UPDATE`).

**(a) Create-table atomicity.** `createObject(ObjectCreation)` is its own method, not a `CommitBatch` variant. One transaction checks the namespace, inserts the object under the active-name index, and applies the first commit (pointer version 1, journal, outbox, idempotency) through the unchanged commit path. Reasons: a commit swaps pointers and knows nothing of names or namespaces, so every backend's bite-tested commit path stays as it is, while a creation needs the name check and namespace lock a commit does not. The first commit's id is the creation's id, so an unknown outcome resolves with `findCommit(firstCommitId, object.mainKey())`. Registering a table is a creation whose first pointer names an existing metadata file.

**(b) Outbox order.** Every backend guarantees: every committed event is claimed eventually, at least once; the events of one change keep their order; of two changes that touched the same record, the one that committed first is claimed first. There is no order across unrelated changes, so no backend needs a global counter. No gaps: the relay always takes the lowest remaining entries and `markRelayed` deletes them, so an entry whose transaction commits after higher entries were relayed is still taken; there is no high-water mark to skip it. The order key is assigned after the change has locked what it touched. PostgreSQL: the identity `seq`, drawn at insert, after the locks. YugabyteDB: the same with sequence cache 1 (a per-node cache breaks the guarantee). CockroachDB: a sequence, not `unique_rowid()`. MongoDB: a Lamport clock: each record document carries a clock; a change stamps its entries with one more than the largest clock among the documents it writes and sets their clocks to that value; ties between unrelated changes break by entry id. One relay drains at a time under a lease judged by the caller's clock; a lapsed lease passes to the next relay, and the old holder's `markRelayed` is refused.

**(c) Paging tokens.** Opaque: base64url of the last item's sort key (`PageToken`). Listings are keyset pages that resume strictly after that key, so rows inserted before or after the position never shift it, and every item present throughout is listed once. Each listing has a total order with a unique tiebreak: namespaces by normalized name (unique per parent); objects by (normalized name, id); grants of groups by (group, securable id, privilege); grants on a securable by (group, privilege); purge-eligible objects by (purge-after, id); journal by version. Tokens survive restarts and never expire. A token the store did not issue is an `IllegalArgumentException`. Each page is a fresh read, not one snapshot across pages.

**(d) Names.** `Name(normalized, display)`: the core normalizes (NFC, then `Locale.ROOT` lower case); the store compares and orders normalized forms only, as bytes (SQL `COLLATE "C"`, Oracle binary comparison, MongoDB simple collation). Unique: catalogs by name; namespaces per parent; tables and views share one name space per namespace, among active objects only. A create whose normalized name is held answers `NameTaken(holder)`, so a case-only collision keeps the first display case. A rename to a case-only variant of the object's own name changes only the display name. A drop frees the name at once, and two dropped objects may share a name; undrop and rename need the name free and answer `NameTaken` otherwise. Two objects swap names through a third. Namespaces do not rename in v1.

**(e) Shared value types.** Records and a few small sealed results: `WriteResult` (`Applied`, `Unchanged`, `Missing(subject)`, `NameTaken(holder)`, `VersionMismatch(actual)`, `Refused(reason)`), `KeyState` (`Absent`, `Claimed`, `InFlight(changeId, leaseUntil)`, `Done(result)`, `Mismatch`), and M1's `CommitResult` and `CommitLookup`; plus `Page`, `PageRequest`, `Change`, `Name`, `Securable` and each group's records. No backend type crosses the interface.

**(f) Other rules.**

1. *Idempotency (D10).* A request claims its key with a lease and the commit or change id it will write with; only a write with that id completes the claim, in its own transaction. With no live record the write records the result directly; otherwise (another claimant, already done) it fails cleanly with `StoreException`. A definite 4xx is recorded with `completeKey`; a 5xx releases the claim. A record past `expiresAt` is absent whether or not `expireKeys` has deleted it. A `Done` answer is durable before it is returned (5.1 step 3). On PostgreSQL a claim that finds the key done commits the transaction that locked its row, and that COMMIT waits for the standby as the barrier's does; `readKey` and `awaitKey` commit the barrier.
2. *Holds (D24).* Drop and purge check holds on the record, every namespace above it and its catalog, inside their transaction. Namespaces never move, so each stores its ancestors; each object stores its namespace path and keeps it after the namespace is gone.
3. *Soft drop (D25).* Drop sets dropped-at to `change.at()` and fixes purge-after; the id, pointer, journal and grants stay. Purge marks the object `PURGED` (kept as history) and deletes its grants; it is refused before purge-after or under a hold.
4. *Size (D8.5).* A projection above the piece budget is stored in pieces keyed by pointer version and read in the same statement as the pointer. The budget is per backend (PostgreSQL: 1 MiB).
5. *Refs (D33).* The ref record (build-plan 2.4) exists from v1 with no operations; v1 storage needs nothing else from it.
6. *Schema (D8.7).* `schemaVersion()` reports the newest applied step. Every step keeps the previous release's statements working: additions and relaxed constraints only.
7. *Commit hook.* Called before the COMMIT of every write that carries an id: commits, changes, and idempotency claims, completions and releases. The relay lease and key expiry carry none; an unknown outcome there is safe to repeat, so it is a `StoreException`.

**(g) Suite.** The commit suite (tests 1 to 6) plus one abstract suite per group, which a backend runs as `@Nested` classes inside its commit suite so they share its backend and after-each restore: `NamespaceSuite` and `CatalogObjectSuite` (both carry test 8), `GrantSuite`, `IdempotencySuite` (test 9), `OutboxSuite`, `GovernanceSuite`, `JournalSuite`, `SizeSuite` (test 7), `UpgradeSuite` (test 10), and `MutationSuite`, which drives every non-commit mutation through tests 2 and 3: it applies with exactly its change records; a lost answer is unknown, carries the change id, and was written; a link cut before COMMIT is unknown and wrote nothing. Capabilities, each skipping through an assumption with its reason: `supportsFailover` (test 4), `hasSafeEnvironment` (test 5), `hasReplica` (test 6). `storeOfAnotherProcess` is the seam for a store that shares no memory with the committing one. Journal partition roll-over is not a shared test: how a backend partitions by time cannot be seen through the interface (PostgreSQL and YugabyteDB use declarative ranges, CockroachDB splits ranges itself, Oracle's interval partitions create themselves, MongoDB has none), so test 7 checks what a caller sees, journal entries years apart written and read back in one range, and each backend proves its own roll-over in its own module.

## Deviations (M1, PostgreSQL commit core)

Found while implementing sections 4, 5.1 and 7 in `catalog-store-sql`. Each is bite-tested in the shared suite.

1. **5.1 step 1 misses an in-flight create.** `SELECT … FOR UPDATE` waits only for a row that exists. When the transaction in doubt *created* the pointer (`expected` empty), its row is uncommitted and invisible, so the lock returns no row at once; findCommit would answer `NOT_COMMITTED` while that COMMIT can still complete. The implementation takes `SELECT … FOR UPDATE` as written and, only when it finds no row, inserts a placeholder pointer with `INSERT … ON CONFLICT DO NOTHING` (rolled back afterwards). The insert waits for an in-progress insert of the same key. Evidence: shared-suite test 3 has an in-flight-create case (COMMIT held waiting for a stalled standby); without the placeholder it fails with findCommit already completed as `NOT_COMMITTED`. MongoDB's marker write (5.3) has the same gap, but the shared test cannot show it there (see the MongoDB deviations). If M2 adds a foreign key from pointer to objects, the placeholder must satisfy it.

Clarifications, not deviations:

2. **A cancelled replication wait is an unknown outcome (4, step 4).** PostgreSQL answers a COMMIT whose wait for the synchronous standby is cancelled (`pg_cancel_backend`) with success plus a WARNING, though the commit may not be replicated. Any warning on COMMIT is treated as `CommitOutcomeUnknownException`; the durability barrier's own COMMIT is treated the same way (findCommit then throws `StoreException`).
3. **Swap order (3, D15).** "Ascending (objectId, branch)" compares the object id as an unsigned 128-bit number (its canonical text order, and PostgreSQL's `uuid` order; `java.util.UUID.compareTo` is signed and differs), then the branch. `CommitBatch` holds its swaps in that order, so backends do not sort.
4. **`pg.no-sync-standby` needs `pg_monitor`.** PostgreSQL shows `pg_stat_replication.sync_state` only to roles with `pg_monitor` or `pg_read_all_stats`. Without it the check reports the finding, so it fails closed; the catalog role needs `pg_monitor`.

## Deviations (M1, Oracle commit core)

Found in `catalog-store-oracle` against Oracle AI Database Free 23.26.3 with Transaction Guard on. Each is bite-tested.

1. **Transaction Guard answers COMMITTED before the redo is written.** With the log writer frozen, `GET_LTXID_OUTCOME` returned committed within 1.5 s while the original session waited 7 s in `log file sync`. findCommit therefore commits the durability barrier before answering `COMMITTED`, on both paths. Evidence: suite test 3's in-flight cases fail without it.
2. **findCommit has two paths.** The LTXID is held in memory by the store that sent the commit; a restarted or different process does not have it. Without an LTXID, findCommit uses 5.1 steps 1–2 (row lock, placeholder insert for a create, journal lookup), then the barrier.
3. **`ora.no-data-guard` reads `protection_level`, not `protection_mode`** (table in section 7 corrected). A MAXIMUM AVAILABILITY primary whose standby is not synchronized keeps its mode but drops its level.
4. **The idempotency body is nullable.** Oracle stores `''` as NULL, and a 204 response has an empty body.
5. **Grants.** The catalog role needs EXECUTE on `DBMS_APP_CONT` and SELECT on `V_$DATABASE` and `V_$SERVICES`.
6. **Licensing.** Oracle's licensing guide lists Transaction Guard as not included in Free; it works there technically. Confirming it is licensed on the work estate is a work question.

Proposed findings for M2: `ora.commit-nowait` (`COMMIT_WAIT=NOWAIT` or `COMMIT_LOGGING=BATCH` lets COMMIT return before the redo is written), and a finding for a service with `FAILOVER_TYPE` TRANSACTION or AUTO, which can replay a COMMIT (or require `oracle.jdbc.enableACSupport=false` on the pool).

## Deviations (M1, MongoDB commit core)

Found in `catalog-store-mongo` against a three-member `mongo:8.0.34` replica set. Each is bite-tested.

1. **5.3 step 2's marker is an upsert in a transaction that is always aborted.** A plain update on a key whose create is still open matches nothing without conflict; an upsert hits `WriteConflict` and waits. The shared in-flight-create test cannot show this on MongoDB: it stalls replication after the create committed locally, and snapshot transactions read the newest local data, so even the plain marker sees the pointer. A MongoDB-only test holds the transaction at the CommitHook, before `commitTransaction` is sent, and fails with the plain marker. The marker retries on `WriteConflict` for up to 2 × `transactionLifetimeLimitSeconds` + 10 s.
2. **Durability comes from the barrier.** The marker transaction uses w:1, because a majority abort that writes nothing silently waits for replication and hid a missing barrier. Durability is a majority `$inc` on `durability_barrier`, then a majority read of the journal in a new causally consistent session.
3. **No backend `seq` for journal or outbox.** A global counter document would be a write hot spot. Journal order per key is `new_version`; outbox entries are keyed by (commit_id, position). Section 8's tag protocols must not assume a MongoDB `seq`.
4. **Reads use readConcern majority on the primary**, so `readPointer` and `findCatalog` never show a commit that could roll back.
5. **The driver resends `commitTransaction` itself.** `TransactionOperation` hard-codes retryWrites for commit, so each `commitTransaction()` call may send the command twice whatever the client setting. With three attempts that is up to six sends on the same session; the transaction body is never replayed [D8.4].
6. **`WriteConflict` before commit** aborts and re-runs the body on a fresh snapshot for up to 10 s, before `commitTransaction` is ever sent.
7. **Role.** The catalog role needs `clusterMonitor` (for `getParameter`, `replSetGetConfig` and `getDefaultRWConcern`).

## Suite changes for M2 (done)

- `StoreUnderTest.hasReplica()`: test 6 skips through an assumption on a backend without a replica (Oracle Free).
- `openCreateIsWaitedFor` and `openUpdateIsWaitedFor` moved from the MongoDB module into `CommitSuite` and run on every backend.
- `StoreUnderTest.storeOfAnotherProcess()`: a store that shares no memory with the committing one. Oracle returns a store without the LTXID map; MongoDB and PostgreSQL return a second store on the same database, since their stores keep nothing in memory.
- The `Faults` javadocs say what `healLink`, `lagReplicaApply` and `stallReplication` guarantee.
- `CommitSuite.stopBackend` skips the close when the backend never started.

## Deviations (M2 prep, PostgreSQL whole contract)

Found while implementing section 9 in `catalog-store-sql` (Flyway V3). Bite runs are named by id in the M2 prep report.

1. **The journal is not partitioned by time yet (2.4, D8.5).** M1's journal is a plain table with an identity column, written by M1 nodes during the upgrade. Converting it in place needs an exclusive lock on the journal and a way to create next month's partition before a commit lands in it, so it belongs in its own step with its own roll-over test in this module, not in V3. Proposed V4: rename `journal` to `journal_m1`, drop its identity default, create a partitioned `journal` by range on `committed_at` with the identity restarted above the old maximum, attach `journal_m1` as the range below the cut-over, and pre-create monthly partitions twelve months ahead; a maintenance job keeps the horizon (YugabyteDB the same; CockroachDB needs none). Until then test 7 checks only what a caller sees: entries 800 days back and 400 days ahead are written and read in one range; bite S6 (a CHECK standing in for missing partitions) fails it.
2. **Namespace drop is a hard delete (2.4 lists a namespace dropped-at).** Nothing in v1 undrops a namespace, and a dropped name must be free at once. Objects keep their `namespace_id` and `namespace_path` after the namespace is gone, so dropped tables, their holds and the journal still resolve. If namespace undrop is ever wanted, the record gains a state and dropped-at as objects have.
3. **Objects have a third state, `PURGED` (2.4 lists active and dropped).** A purge keeps the row as history (id, name, location root, drop and purge times) so audit and journal still resolve the id; grants go with it, and a purged object cannot be undropped, granted or held. Evidence: `purgeRefusesNotDueAndHeld`; bite O13.
4. **No foreign key from pointer to object (section 2 said it arrives in M2).** The commit suite commits pointers with no object record, and findCommit's placeholder insert (M1 PostgreSQL deviation 1) has no object to satisfy one. `createObject` writes the object and its first pointer in one transaction, which is what the key would protect.
5. **A previous-release node reads only the first projection piece.** M1's `readPointer` reads `pointer.projection` alone, so during a rolling upgrade an M1 node returns a projection above 1 MiB written by an M2 node truncated. M1 never shipped, so V3 accepts it. Section 9 (f) 6 keeps statements working but not new data layouts; the rule for later layouts is that a release learns to read one a release before any release writes it.
6. **V3 builds its indexes inside the migration transaction.** `CREATE INDEX journal_by_pointer` holds a SHARE lock on the journal while it builds, which blocks previous-release commits. Every journal is empty today, so the build is instant; a later migration on a populated table needs `CREATE INDEX CONCURRENTLY` in a non-transactional Flyway step.

Clarifications, not deviations:

7. **Times are kept to the microsecond.** `timestamptz` drops nanoseconds; the suite's clock is in milliseconds so round trips compare equal. MongoDB keeps milliseconds, so callers must not rely on anything finer.
8. **"List by principal" (2.3) is `listGrantsOfGroups`.** Grants go to groups [D18, D19]; the server resolves a principal to its groups and asks for theirs.
9. **A claim needs no separate barrier on PostgreSQL.** Its row lock gives the claim transaction an id, so its COMMIT waits for the synchronous standby. Bite I13 (the barrier call removed from the claim) left `idempotentReplayWaitsForTheStandby` green, so the call was dropped; bite I14 (the barrier removed from `readKey`) fails that test.

## Deviations (M2c, MongoDB whole contract)

Found while implementing section 9 in `catalog-store-mongo` (schema step 3) against a three-member `mongo:8.0.34` replica set. MongoDB behaviour is checked against the 8.0 manual and the Java driver 5.14 documentation, cited by page. Bite runs are named by id (B01 to B50) in the M2c report. PostgreSQL deviations 2, 3 and 4 (hard namespace drop, the `PURGED` state, no pointer-to-object key) hold on MongoDB as written, and so does 5: a previous-release node reads only the first projection piece, here the first 8 MiB.

1. **No shared locks: a write marks what it depends on (section 9, Writes).** MongoDB has no `SELECT … FOR SHARE`, and a transaction's reads take no lock a writer waits for. A write that depends on a record it does not change sets that record's clock to its own stamp. That is a real write: a child namespace marks its parent namespace; a grant, attribute or hold marks its securable; an object create, rename or undrop marks the namespace. The mark conflicts with an open drop or purge of the record, so the dependent re-runs after it and finds the record gone. Catalogs and storage profiles are never removed, so nothing marks them, and creates under one catalog or profile do not conflict. Evidence: `dependentWritesWaitForAnOpenDrop` (each dependent against a drop or purge held open before `commitTransaction`) and `childCreateRacingParentDropLeavesNoOrphan`; bites B12 to B17.
2. **A name is taken by a lookup, then a unique index (9, Writes and d).** A create looks for the holder in its snapshot and answers `NameTaken(holder)`. When two creates of one name are open together, both miss the lookup. The second's insert under the unique index (`catalog_name`, `namespace_name`, `object_active_name`, `grant_key` or `engine_key`) meets the first's open key, fails with `WriteConflict`, and re-runs after it. `object_active_name` is partial on `{state: "ACTIVE"}`, because a partial filter cannot use `$ne` ([partial indexes](https://www.mongodb.com/docs/v8.0/core/index-partial/#partial-index-with-unique-constraints)). Where the parent is marked (objects, grants), the mark already serializes creates, so those indexes are a backstop. Evidence: bites B18 to B22, B24 and B26 fail their tests. B23 and B25 (the object and grant indexes removed) pass every test, as expected for a backstop. `catalog_name` has no concurrent test; its lookup is bite B21.
3. **Outbox order: the Lamport clock of 9 (b), with removals marking.** Before it fixes its stamp (one more than the largest clock), each change reads the clock of every document it writes, marks or deletes. It then writes the stamp to those documents and to its outbox entries. Entries are `{_id: ObjectId, commitId, position, createdAt, type, payload, clock}`, and the relay takes them by `(clock, _id)`. A removal deletes its document, so it also marks what a later re-create will read: a namespace drop marks the parent namespace or catalog, and a revoke, attribute removal or hold release marks the securable. A trusted engine has no parent, so a removed engine stays as a tombstone (`removed: true`) that the next put reads. Entries written by previous-release nodes carry no clock and sort first, so order between the two releases' events is not kept during an upgrade; M1 never shipped. Evidence: `relayOrderFollowsChangesNotProcessClocks`, where the later change of each pair comes from a process whose ObjectIds are an hour behind; bites B04 to B11.
4. **Projection pieces are read in a snapshot session, not in one statement (9 f 4).** The budget is 8 MiB, half the 16 MiB document limit ([limits](https://www.mongodb.com/docs/v8.0/reference/limits/)). The pointer document holds the first piece and the piece count; the rest are `projection_piece` documents keyed by (object, branch, version, piece). `readPointer` reads the pointer, then its pieces by the pointer's version, in a snapshot session. Such a session reads one majority-committed point in time ([read concern snapshot](https://www.mongodb.com/docs/v8.0/reference/read-concern-snapshot/)). A swap deletes the old pieces. A previous-release node writes the projection whole and leaves the count and the old pieces behind, and the read by version finds none of them. Evidence: `piecesAreReadFromOneVersion` (a reader against 300 commits, with 1 KiB pieces through a test seam), `previousReleaseOverwriteOfPiecesReadsAsWritten` and the size suite; bites B01 to B03.
5. **A large projection needs a large cache.** The server refuses a transaction whose dirty data passes 0.75 of the dirty-cache limit, itself 20% of the WiredTiger cache. The error is `TransactionTooLargeForCache` (388), which is not retried ([parameters](https://www.mongodb.com/docs/v8.0/reference/parameters/)). A commit therefore needs a cache of about seven times its size: the size suite's 40 MiB projection fails on a 0.25 GB cache, so the test replica set runs with 1 GB. Proposed self-check finding: `mongo.small-cache`, raised when the cache is below seven times the largest projection the catalog accepts.
6. **A done key is durable through the majority commit, not a barrier (9 f 1).** A claim that finds the key done commits its transaction, which wrote nothing, with w:majority. The manual makes a transaction's snapshot reads majority-committed only when it commits with w:majority ([transactions](https://www.mongodb.com/docs/v8.0/core/transactions/#transactions-read-concern-snapshot)). `readKey` and `awaitKey` read with majority read concern. Evidence: `doneKeyIsAnsweredOnlyWhenDurable` (replication stalled after the completion applied on the primary). Bite B38 (`readKey` with local read concern) fails it. Bite B36 removed a write to the key's record that this path first made, and the test passed, so the write is gone. Bite B37 (abort instead of commit) also passes: on 8.0.34 a w:majority abort waits for replication too (M1 deviation 2), but the manual does not promise that, so the claim commits.
7. **Schema step 3 indexes no pointer or journal field.** An index build locks its collection exclusively at its start and end, and shared while it drains ([index builds](https://www.mongodb.com/docs/v8.0/core/index-creation/)). A transaction waits at most `maxTransactionLockRequestTimeoutMillis` (5 ms by default) for a lock, then aborts. Previous-release commits that write outbox events or an idempotency result touch `outbox` or `idempotency`, which step 3 indexes; such a commit may fail cleanly before `commitTransaction`, and can be repeated. Evidence: bite B50 (a journal index added to step 3) fails the upgrade test, with previous-release commits failing before `commitTransaction`.
8. **Only `WriteConflict` re-runs a transaction (M1 deviation 6 stands).** Inside a transaction, an insert that meets a unique key another transaction holds open, or committed after this snapshot, fails with `WriteConflict`, not `DuplicateKey`. A `DuplicateKey` retry, which this section first had, was removed: without it (bite B49), all eight concurrency tests it could matter to still pass. Bite B48 (no `WriteConflict` retry) fails `exactlyOnePropertiesUpdateWins`.
9. **The relay lease is one document.** `outbox_relay` holds `{_id: "relay", relayId, leaseUntil}`. A claim takes it with one `findOneAndUpdate` when it is free, lapsed or already the caller's. Inside its transaction, `markRelayed` re-checks the lease with a write to that document, filtered on the holder and an unexpired lease, so a takeover conflicts with it rather than racing it. Evidence: bites B45 and B46.

Clarifications, not deviations:

10. **Names compare by code point.** No index or query names a collation, so strings compare by the simple binary comparison: Unicode code point order, which is UTF-8 byte order ([comparison order](https://www.mongodb.com/docs/v8.0/reference/bson-type-comparison-order/)). Java's `String.compareTo` differs above U+FFFF. Evidence: `namesListInByteOrder`; bite B47 (an English collation on the namespace listing) fails it.
11. **Two contract guards are tested only in the MongoDB suite:** a namespace drop refused under a hold on the namespace, an ancestor or the catalog, and a grant naming a catalog other than its securable's (`heldNamespaceRefusesTheDrop`, `grantNamesTheSecurablesCatalog`; bites B27, B28, B31 and B35). They belong in `NamespaceSuite` and `GrantSuite` when those next change.
12. **Multi-read lookups use one snapshot session.** `findNamespace` walks the path, and the purge scan reads dropped objects and then their holds, each in one snapshot session, so each answer is one point in time. The purge itself re-checks holds in its transaction (bite B33).
13. **Key expiry re-checks expiry in its delete.** `expireKeys` finds up to `limit` expired keys, then deletes those still expired, so a key claimed afresh between the two is kept. No test can time that race: bite B42 (delete by key alone) passes, and so does B41 (the find unfiltered), because the delete re-checks.
