# Decision ledger

Branches from `reports/Enterprise Iceberg REST catalog plan.md` (D1–D34). Each branch is OPEN, RESOLVED or BLOCKED-ON. Resolved in the grilling session of 2026-11-06; all 41 branches RESOLVED.

**This ledger supersedes the report where they differ.** Paul's decisions that depart from the report's recommendations:
- D7: four backends (PostgreSQL, CockroachDB, Oracle incl. Exadata/RAC, MongoDB), all in v1. The report's "never: pluggable multi-backend persistence" is overridden. YugabyteDB was a fifth until Paul dropped it on 2026-11-11 (D7's amendment).
- D12: new tables default to v3 (report: v2).
- D28: unlimited namespace depth (report: capped).
- D33: catalog-wide Nessie-style branches, tags and merges, designed in v1 and shipped in v1.x. The report's "never: long-lived branches and merges" is overridden.
- New since the report: D35 (SingleStore as a client), D36/D36a (one deployment, on-prem or AWS, managing tables on both), D37 (zero loss in-region, async DR).

| D7 | Database | RESOLVED | Multi-backend, decided after the evaluation in research_notes/Catalog database evaluation/. Supported backends: PostgreSQL and CockroachDB (one PostgreSQL-wire SQL implementation with dialect switches), Oracle including Exadata/RAC (own implementation: UCP + FAN, Transaction Guard for ambiguous commits, service affinity so a table's pointer row isn't pinged between RAC instances), and MongoDB (own implementation: multi-document transactions, w:majority, primary reads). Laptop can't test RAC; that is validated on work hardware. **Amended 2026-11-11: YugabyteDB dropped.** It was the third PostgreSQL-wire backend and passed the shared suite in M2a. Asked "Should I drop YugabyteDB support?", Paul answered "Drop it". What he was told before deciding: (1) YugabyteDB took 33 of the heavy build's 112 minutes, and every test on it ran about 8 times slower than on PostgreSQL; (2) writers queued on one pointer row are released about 200 ms apart (under 2 ms on PostgreSQL), so the 8-writer CAS test cost 2.1–3.4 s a round; two wait-queue flags were ruled out and the cause was never found; (3) it failed in all three attempts at the two-modules-at-once heavy build. The cost he accepted: CockroachDB becomes the only distributed-SQL backend, and CockroachDB has been under a proprietary licence since 24.3; YugabyteDB was the Apache-2.0 option. The SQL store now refuses a YugabyteDB server rather than run on it as PostgreSQL. Everything removed stays in git history, and the shared suite could re-qualify it later. | |

| D8 | Persistence invariants | RESOLVED | Enforced in code for every backend: (1) one atomic write per commit (CAS on the (table, branch) pointer by location + version, plus projection, hash, journal, outbox, idempotency; commit_id generated before BEGIN); (2) quorum/synchronous durable acks, with a startup self-check that refuses to run on unsafe settings; (3) primary/leader-only pointer reads, content from the version-keyed cache; (4) ambiguity protocol: lock pointer row then look up commit_id (Transaction Guard on Oracle; durability barrier and no COMMIT timeouts on PostgreSQL; the pool never replays a commit, cf. Iceberg JdbcCatalog #18743); (5) size budget, chunk large payloads, journal partitioned by time; (6) case-insensitive, case-preserving names; (7) versioned storage format, online migrations, rolling-upgrade tests; (8) no plug-in API; (9) the shared fault-injection suite is the support gate for each backend. | |
| D9 | Commit loop and 409-vs-5xx contract | RESOLVED | Strict contract. 409 only when a precondition failed on a consistent read or the swap definitely lost. Ambiguous outcomes are reconciled by re-reading pointer and journal; 500 only if truly unknown; never 503 on commit routes; no gateway maps a timeout to 409. Server-side retry only while the client's preconditions still hold. Skip no-op commits. Clock-skew guard (~1 min). Files from unknown outcomes are left for cleanup. | |

| D33 | Git-style branching | RESOLVED | Catalog-wide branches and tags, required for all four use cases: atomic multi-table release, dev/test isolation, point-in-time reproducibility, PR-style data CI/CD. Design: a tag is a named point in the commit journal; a branch is a tag plus an overlay of per-table pointers for tables changed on it (unchanged tables read as of the base; no copying). Merge is per table, Nessie semantics: changed only on the branch → main takes it; changed on both → conflict. All tables move in one bounded multi-table transaction. Branch selected by REST prefix (e.g. trading@dev) so stock clients work. Commits still lock one (table, branch) pointer, so D6 holds. Cleanup protects files referenced by every branch and tag. Phasing: v1 storage keys pointers by (table, branch) and journals every commit; branches, tags and merge ship in v1.x with /transactions/commit. Branch lifetime/limit defaults to be set in the detailed plan. | |

| D35 | SingleStore as a client | RESOLVED | SingleStore's Iceberg connector is one more client in the compatibility matrix, nothing more; no egress design. From research_notes/SingleStore Iceberg integration/: it acts as a stock Iceberg Java REST client and needs config, loadTable (snapshots=all), vended S3 creds in storage-credentials and config, metrics 204 or not advertised, and auth the stock client can do. It reads only v1/v2 Parquet tables (input to D12). **Amended 2026-11-11: SingleStore also writes, through a connector of ours.** Paul asked to replace Trino with SingleStore in the demo and to sync SingleStore and Iceberg both ways, and approved the design ("Yes, build it"). Iceberg to SingleStore stays SingleStore's Iceberg pipelines, the stock client above (the engine matrix found they read v3 tables too). SingleStore to Iceberg is `singlestore-change-feed`: a connector pipeline (SingleStore's Kafka Connect runtime, with no Kafka) that reads one table's change feed (`OBSERVE`) and commits to an Iceberg table through the catalog with vended credentials, like any writer. The catalog has no SingleStore-specific code. Its rules: (1) the table's primary key must be its shard key, so a delete, which carries only the key, names one row for life; updates and deletes become equality deletes on that key, and partition columns must be in it; (2) each commit records the change feed's offsets in the Iceberg snapshot summary, and a commit fails if anything else committed since, so the feed resumes from Iceberg after any failure with nothing copied twice or skipped; (3) when SingleStore no longer holds the log after those offsets, the feed takes a new snapshot and records the gap (`fidice.changefeed.gap-after` in the summary, `gap_after` in the receipt row SingleStore keeps); Paul chose that over failing; (4) no pipeline may load a table the feed writes, or rows would loop back (Paul's rule): the connector checks SingleStore's pipelines at start and every minute, and stops if one does; (5) a receipt is read from its snapshot alone, and after a batch SingleStore failed to write, the restarted task sends again every receipt after the last one SingleStore stored (the pipeline's offset), so the receipt rows, gaps included, match Iceberg's history. The feed imports Iceberg (same pinned version) outside catalog-iceberg: D2's one-adapter rule is read as the catalog's own use of iceberg-core, and the feed is a client of the catalog, so IcebergImportBoundaryTest exempts it by name. Details in research_notes/SingleStore Iceberg integration/ (update of 2026-11-11) and demo/README.md. | |
