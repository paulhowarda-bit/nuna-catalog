What was done:
- Worker: each failed job on a table (table-load, table-changed, snapshot expiry, manifest rewrite, orphan scan,
  compaction, the requested jobs too) is named in the scan's report as `failed-jobs`: its kind, the table's catalog,
  namespace, name and id, a reason and the message the worker met, one line cut to 300 characters. The first 20 a
  scan meets are named; `failures` still counts them all by kind, for the console and an older catalog. The reason is
  `closed` when the catalog's 403 says the table is "closed until it is classified" (the authorizer's UNCLASSIFIED
  words; the refusal has no type of its own yet, item 324's amendment asks for one), `refused` for any other 403,
  `not-found`, `changed`, else `error` (`ScanReport.reason`).
- Catalog: `FailedJob` in catalog-store-api, a `failedJobs` component on `MaintenanceScan` (at most 20; the 9-argument
  constructor names none). The scans were columns, not a JSON blob, and the only unbounded text column is
  `worker_storage`, so this needed a schema change: a nullable `failed_jobs` column (PostgreSQL V20, CockroachDB V19,
  TEXT; Oracle V22, CLOB), tab-separated lines (`FailedJob.write`), and a `failedJobs` field on MongoDB. A server of
  the previous release neither writes nor reads the column. `PUT /maintenance/scans/{id}` takes `failed-jobs` and
  refuses a bad one (400); `GET /maintenance/scans` returns it, `[]` for a scan that names none.
  docs/observability/table-health.md says so.
- Console: the Worker scans panel (`workerPanel`, on Service and Maintenance) names the last ended scan's failed
  jobs by kind, each table linked to its page: "1 table could not be loaded: brokerage.party.beneficial_owners,

  sub line names the tables not assessed yet (at most 5, then "and n more"), each linked to its Maintenance tab, one

Open question, for catalog-security and the observability expert (not changed here, as Atelier's note asks): the
worker loads a table as any principal does, so a table closed until classified refuses it, and maintenance silently
skips that table every scan: no snapshot expiry, orphan removal or compaction, for as long as it stays closed. The
scan now names it, but nothing alerts on it and nothing says how long it has been skipped. Should the maintenance
principal be exempt from the closure, as it is from a row/column policy (`Authorizer`, the maintenance exemption), so
the table is kept in shape while its data stays closed to readers? Or should a table skipped for N scans raise an
alert (a metric labelled by kind and reason, not by table)? Item 324 also asks for a distinct error type for the
closed refusal, which would let the worker stop matching its words.
