# 37. Sanitize scan-report filters before a metrics report leaves the catalog, and keep unknown report types

Status: done
Done: 2026-11-15 on claude/obs37-report-sanitize-83a9ec
Added: 2026-11-15 by Iceberg observability review, at Paul's request
Touches: catalog-iceberg/src/main/java/keel/catalog/iceberg/RestRequest.java catalog-iceberg/src/test/ catalog-server/src/main/java/keel/catalog/server/rest/MetricsSink.java catalog-server/src/test/java/keel/catalog/server/MetricsReportTest.java bites/D13/

A metrics report (`POST /v1/{prefix}/namespaces/{namespace}/tables/{table}/metrics`, D13) leaves the catalog as it
came, filter values included. The spec's `ScanReport.filter` is a plain `Predicate`. The stock Java client sanitizes
it before sending (`SnapshotScan` builds its report with `ExpressionUtil.sanitize(struct, filter, caseSensitive)`, seen
with javap on iceberg-core 1.12.0), but nothing obliges another client to. The server forwards whatever arrives to the
`keel.telemetry.metrics` logger (`MetricsSink.java`), and from there to whatever pipeline reads the logs.

Evidence (2026-11-15: `RestRequest.reportMetrics` run on iceberg-core 1.12.0 with hand-written reports):

    unsanitized scan -> type=scan-report table=cat.hr.staff
       forwarded={"report-type":"scan-report",...,"filter":{"type":"eq","term":"ssn","value":"123-45-6789"},...}
    future report type -> type=unknown table=
       forwarded={"report-type":"unknown"}

The second is the other defect. The spec's `report-type` is a free string; a type the parser does not know round-trips
as `{"report-type":"unknown"}`, so the type the client sent is lost. Answering 204 is right; losing the name is not.

Done when:
- A scan report's filter is sanitized on the server (`ExpressionUtil.sanitize` on the parsed, unbound expression)
  before it is forwarded, whatever the client sent. A test sends the literal above and finds no literal in what is
  forwarded.
- A report of an unknown type is forwarded with the `report-type` the client sent, its table name if it gave one, and
  the body's size, never the body itself (its values cannot be sanitized). A test shows it.
- The route still answers as the spec says (204, 400 on a bad body, 404 NoSuchTableException):
  `RestRoutesTest#metricsCredentialsAndTokens` still passes.
- The sanitizing is recorded as a bite in `bites/D13/`, against a test that fails on its assertion.

What was done: `RestRequest.reportMetrics` sanitizes a scan report's parsed, unbound filter with
`ExpressionUtil.sanitize` before the report is forwarded; a filter the Java client already sanitized is hashed again,
so no string the client chose leaves. A report of an unknown type is forwarded as the `report-type` and `table-name`
the client sent and the body's UTF-8 size (`MetricsSummary.bytes`), never the body. `MetricsSink` logs it as
`unknown-report … bytes=… report={"report-type":…,"table-name":…}`, the client's strings only inside escaped JSON,
so a type holding a newline cannot forge a line. Tests: `MetricsReportRequestTest` (catalog-iceberg, 7) and
`MetricsReportTest` (catalog-server, 4, read from the `keel.telemetry.metrics` logger behind the route);
`RestRoutesTest#metricsCredentialsAndTokens` still passes. Bites in `bites/D13/`, each BITES on its assertion:
`metrics-filter-unsanitized`, `metrics-unknown-body-forwarded`, `metrics-unknown-type-leads-the-line`.
`status/2026-11-15-obs37-report-sanitize-83a9ec.md` has the build runs.

Left over: Iceberg's sanitizer hash can be reversed for short values (an SSN in 8.2 s); backlog 45 asks Paul what a
filter value may become. A known report's `metadata` map and other strings still go as sent; this item named only the
filter.
