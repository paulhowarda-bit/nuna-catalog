Found while building item 157 (security finding 7). Item 157 refuses a namespace drop while a ref's cut names a
table or view of it, read in the drop's transaction as its emptiness check is. That read sees only refs that have
committed, and nothing makes a namespace drop wait for a ref create in flight:

- PostgreSQL and CockroachDB (`SqlRefs.create`): the create locks the catalog's row `FOR UPDATE`, reads its cut in
  one `INSERT ... SELECT`, then commits. The namespace drop locks only the namespace. So: the cut's statement
  snapshot sees table T active in namespace N; T's drop commits; N's drop commits, seeing no active object and no
  committed entry naming T; the ref commits, naming T, whose namespace main no longer has. The window is the cut
  statement and the commit, longer on a large catalog. Oracle (`OracleRefs.create`) is the same at one SCN.
- MongoDB (`MongoRefs.create`): the cut is read in a snapshot session, its entries are written in batches outside
  any transaction, then one transaction inserts the ref, so the window also holds every batch. The drop marks its
  parent (the catalog, for a top-level namespace), which the ref's transaction marks too, so only drops that overlap
  that last transaction conflict with it.

The result is the state finding 7 describes (a read through the ref loses the namespace's `regulated` flag), reached
by a race instead of in sequence. It needs a ref create from main in flight across both drops.

Done looks like:
- SQL stores: the namespace drop locks the catalog's row before the namespace, `FOR SHARE` on PostgreSQL and
  CockroachDB, for update on Oracle (no shared lock), the order `putGrantIf` takes (catalog, then securable), so a
  drop waits for a ref create in flight and then reads its entries, and a create waits for a drop in flight and then
  cuts without the namespace. Check every write that locks a namespace and then the catalog first: none did when this
  item was written.
- MongoDB: the ref's insert transaction refuses or retries the create when a table or view of its cut no longer has
  its namespace on main, or another way to the same end that does not read the whole cut in one transaction.
- A `RefSuite` case on all four stores (heavy): a ref create held open before its COMMIT (the commit hook, as
  `NamespaceSuite`'s `duringAnOpenDrop` holds a drop) while a table of the cut and then its namespace are dropped; the
  namespace drop answers `Refused(REFERENCED)` or the ref's cut leaves the table out, never both applied. Bites in
  `bites/D33/`.

**From the security review (Nuna Security Expert session, 2026-11-23):** item 158 may follow item 157; it is no
go-to-work condition. The race needs a ref create in flight across two drops, by a caller already holding drop rights
on the namespace, and its harm is finding 7's low one (the namespace's `regulated` flag and the D17 switch stop
applying to reads through that ref); it grants no new access. A second way to close it, the builder's choice:
`GovernanceChain.of` now stops when the object's namespace is gone; refusing a ref read whose object's namespace is
missing (fail closed, audited as a denial) closes this race and any other path to the same state, without the lock
order change on three stores or MongoDB's check. Item 157's check stays either way, so reads do not start failing.

## Done, 2026-11-25 (branch worktree-agent-ac5aa9e6de1840a97)

The store-level fix the item describes; the code showed nothing that stops it.

- PostgreSQL and CockroachDB, `SqlNamespaces.drop` (catalog-store-sql/.../SqlNamespaces.java:132): reads the
  namespace's catalog unlocked (it never changes), locks the catalog's row `FOR SHARE` (line 139), then the namespace
  `FOR UPDATE` as before, then the emptiness, ref and hold checks. A ref create locks the catalog's row `FOR UPDATE`
  before its cut, so a drop waits for a create in flight and then sees its entries (`Refused(REFERENCED)`), and a
  create waits for a drop in flight and then cuts without the namespace.
- Oracle, `OracleNamespaces.drop` (OracleNamespaces.java:124, lock at 131): the same, the catalog's row for update.
- MongoDB, `MongoNamespaces.drop` (MongoNamespaces.java:150, write at about 180): the drop marks its parent namespace
  (if any) and sets the catalog's `trimmed` and clock to its stamp, as a removal from refs (item 156) does.
  `MongoRefs.create` already compares `trimmed` in its insert's transaction with what its snapshot read and cuts again
  when it moved, so a drop committed while the cut's batches were written makes the create cut again, and a drop open
  while the insert's transaction runs conflicts with it on the catalog's document (MongoDB retries the loser). No
  whole-cut read in one transaction.
- Lock order checked: no write locks a namespace and then its catalog. `docs/storage-design.md` section 9 (f) rule 8
  now lists every write that locks a catalog's row and the order it takes; section 8's item 157 bullet says how 158
  closed the race; the MongoDB section says where the catalog's document is written.

Tests:
- `RefSuite#aNamespaceDropWaitsForAnOpenRefCreate` (heavy, all four stores; written and compiled, not run): a tag
  created from main is held before its COMMIT (the commit hook, through the new `GroupSuite#whileOpen`); meanwhile a
  table of the cut is dropped and then its namespace (nested, so MongoDB's old drop, which marked only the parent
  namespace, did not conflict). The drop must wait, and then either is refused with the ref naming the table and the
  namespace kept, or applied with no ref naming the table.
- `RefSuite#everyTableInACutHasItsNamespace` (heavy) now also checks that every table a cut names has its namespace on
  main, which covers MongoDB's window between the snapshot read and the insert.
- `SqlLockOrderTest#aNamespaceDropLocksTheCatalogForShareBeforeTheNamespaceAndReadsRefsAfterBoth` (fast, passing; no
  database: the new test helper `ScriptedDatabase` answers and records each statement).

Bites (recorded, not run), in `bites/D33/`: `sql-namespace-drop-catalog-unlocked`,
`oracle-namespace-drop-catalog-unlocked`, `mongo-namespace-drop-leaves-the-catalog` (each against its store's
`aNamespaceDropWaitsForAnOpenRefCreate`), and `sql-namespace-drop-locks-catalog-last` (against the fast test).

Choices made (Paul may overrule):
- The store fix, not the review's alternative of failing closed in `GovernanceChain.of`: it keeps the state from
  arising at all, so reads through a ref never start failing, and the lock order holds against every other write
  (rule 8). Failing closed would still be a second line of defence if another path to the state were found.
- PostgreSQL and CockroachDB take the catalog's row for share, not update, so namespace drops in one catalog do not
  wait for each other or for namespace and object creates; Oracle has no shared lock, so its drops take turns with
  every write that locks the catalog's row.
- MongoDB's drop writes the catalog's document every time, so namespace drops of one catalog conflict with each other
  and with ref creates, purge claims and removals in that catalog; MongoDB retries the loser. Namespace drops are rare.
