Item 14 hid names on the Iceberg routes (D18 as amended 2026-11-19, "Hide names"): a caller that holds nothing on a
namespace, table or view, or above it, or (for a namespace) on anything inside it, gets the 404 a missing one gets.
The management API under `/management/v1/catalogs/{catalog}/...` still looks the name up first and asks second, so a
signed-in caller can tell a name that exists (403) from one that does not (404):

- `GovernanceRoutes`: governance, attributes, holds, policies and DR freezes, on a namespace, table or view, resolve
  the target with `management.target(...)` (404 `NoSuchTableException` and the like) before `guard.require(...)`
  (403). For example `GET .../namespaces/hr/tables/staff/governance` as a caller with nothing on `hr`.
- `GrantRoutes`: a grant, a revoke and the listing of grants on an object resolve the securable with
  `Securables.resolve` (404) before the privilege check (403); `SecurityGateTest#separationOfDutiesHoldsForEveryGrant`
  shows the 403 for a namespace the granter holds nothing on.
- `AuditReadRoutes` and `HealthRoutes` take a target through the same lookups.

The `/check` route answers `allowed: false` alike for a missing and a refused object, so it does not leak.

D18's amendment names HEAD, loads and the metrics route on the Iceberg API; whether hiding reaches the management
API, whose callers are mostly stewards, grant admins and operators, is Paul's call. If it does, the Iceberg routes'
rule and `Guard`'s check of grants inside a namespace (the catalog list's rule, item 20) are the model, and the hidden
refusal is audited as every refusal is.

- The rule is item 14's, not a second one: a caller that holds any privilege on the namespace, table or view or above
  it, or for a namespace on anything inside it (item 20's rule), may see the name and is refused with 403; any other
  caller is answered with the target's own 404 (`NoSuchNamespaceException`, `NoSuchTableException`,
  `NoSuchViewException`, word for word as for a missing name). `rest/` was held by item 15, so the rule moved into a
  public `security/Holdings` that the management side asks; `rest/Guard` still has its own copy until it asks
  `Holdings` too (item 77). A grant admin sees every name (`manage-grants` on every catalog); a platform operator,
  holding no grant, sees none ("Catalogs, not objects"). A refusal on the catalog itself stays 403 (item 68).
- `Management.target` and `Securables.resolve` give each target its missing answer, and a table or view path whose
  namespace does not exist answers the table's or view's 404, so a hidden table's answer does not tell the namespace
  is there. `ManagementGuard.require` and `GrantRoutes.require` audit the refusal first, then answer 403 or the 404.
  Routes: governance, attributes, holds, policies and freezes (`GovernanceRoutes`), the audit trail
  (`AuditReadRoutes`), a table's health (`HealthRoutes`), dropped objects (`LifecycleRoutes.dropped`), grant, revoke,
  the grant listing on an object and the check (`GrantRoutes`). The check is not audited, as before: it is a question.
- The DR freeze stays an operator's (D37): a non-operator that holds nothing on the target gets the 404, one that holds
  something 403; an operator still freezes any name. Whether that, the DR reconcile's table list and the routes by
  object id (undrop, export, purge) should hide too is not settled by the decision: item 78, for Paul.
