## What is wrong

- **Expressions are not checked.** Setting a rule checks only its length and NUL characters
  (`RuleRoutes.java:219-228`). A predicate or mask that does not parse is stored, and fails only when Trino runs a
  query, for every user of that group.
- **A set replaces another admin's edit silently.** The set route takes no If-Match, so two grant admins editing one
  rule lose the first edit with no warning.

The security expert, 2026-11-24, found no privilege problem in expressions: nuna's OPA answer carries no identity
(`OpaAnswers.java:72`, `91`), so Trino runs an expression as the querying user and every table it reads goes through
nuna's authorization for that user.

## Decided

Paul, 2026-11-24 (D20): expressions may hold subqueries and read other tables, so entitlements can come from a lookup
table (`desk IN (SELECT desk FROM entitlements WHERE ...)`): "Allow subqueries".

## Done when

- Setting a rule parses its predicate and masks as Trino SQL expressions (Trino's own parser, or one that matches
  it) and refuses one that does not parse, saying where. Subqueries and references to other tables parse and are accepted (D20).
- Each rule carries a version, the list gives it, and a set or remove with a stale If-Match answers 412.
- Route tests and a bite for each.

## What was done

**Expressions are parsed when a rule is set,** with Trino's own parser, `io.trino:trino-parser` 484 (Apache-2.0, the
release of 2026-10-16, built for Java 25), and its standalone-expression rule, the one Trino's analyzer uses for a
row filter and a column mask (`RuleExpressions`, catalog-security). One that does not parse is refused 400, saying
which and where: "row-filter is not a Trino SQL expression: at line 1, column 16, mismatched input ...", or "The mask
of trader is not ...". A statement, two expressions or trailing text after one do not parse. Subqueries and other
tables parse and are accepted (D20, amended 2026-11-24). Only syntax is checked: names, types and functions are
Trino's to resolve when it runs the rule.

- The filter is parsed by `RuleColumns.check`, which now reads the filter's columns from the parse tree: each
  identifier that is not part of a qualified name, a type, a lambda's parameter or a subquery. The word list of SQL
  keywords is gone. The schema-change guard (`RuleColumns.taken`) still reads every identifier in the filter's
  words: it must also read rules stored before this item, and it should over-count.
- The masks are parsed by `RuleRoutes`.
- The dependency is pinned in `gradle.properties` (`trino-parser.version`, with its license) and declared in
  `catalog-security/build.gradle.kts`. It brings `trino-grammar` 484, Guava 33.6.0-jre with `failureaccess` 1.0.3
  and `j2objc-annotations` 3.1, and ANTLR's `antlr4-runtime` 4.13.2, about 5.2 MB of jars;
  `jakarta.annotation-api` and `jspecify` were already on the class path. Guava's `error_prone_annotations` 2.47.0
  is excluded, so Caffeine's 2.49.0 stays the one version (the build's convergence check fails otherwise).
  `docs/install-at-work.md` lists the new artifacts for the mirror.

**Each rule has a version** (`RowColumnRule.Stored.version`), which the list gives as `"version"`. A set writes the
write's time in microseconds since 1970, or one past the old version if the clock is behind it
(`RowColumnRule.nextVersion`). So a rule removed and set again never comes back at a version a client read before,
as it would if versions restarted at 1.

- `POST .../row-column-rules` (set) and `POST .../row-column-rules/remove` take `If-Match: "<version>"` (quotes
  optional). A stale version answers 412 `PreconditionFailedException`, naming the current version, and writes
  nothing. A set naming a version when the group's rule has been removed since also answers 412. A removal with
  If-Match of a rule that is gone answers 404 as before.
- A weak tag, `*`, a list of tags or anything not a number is refused 400. Without If-Match, a set or removal acts
  on whatever rule there is, as before; nothing requires the header.
- The store checks the version inside the write (`putRule` and `removeRule` take an `OptionalLong`). SQL and Oracle
  now lock the table's row in a removal too, as a put does, so a removal and a set cannot interleave under READ
  COMMITTED. MongoDB's write conflicts do the same.
- The version persists on all four stores: a nullable `rule_version` column (PostgreSQL `V16`, CockroachDB `V15`,
  Oracle `V17`) and a `version` field in MongoDB. A rule written before, or by a server of the previous release,
  reads as version 1.

**The console sends the version** (item 243's rules panel, `rules.js` and `api.js`): an edit and a removal send
`If-Match` with the version the list gave; adding a rule sends none. A 412 shows "Another grant admin changed this
rule. The list now shows theirs; make your change again." and redraws the list. `ConsoleRowColumnRulesBrowserTest`
checks a stale edit; bite `bites/UI/console-rule-edit-without-version` BITES.

`ConsoleFlaggedTableBrowserTest` (item 241) set a rule naming `desk` on a table whose only column is `id`, which item
240's schema check refuses; its rule now filters on `id`.
