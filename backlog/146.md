Effort: S, one more tab on the view page reusing the governance tab item 140 built, its words made right for a view, and a browser test; waits on nothing

Paul approved it on 2026-11-22. Views carry labels: their loads hand classification, owner and retention class to
engines (D27, labels built 2026-11-12), and the catalog keeps holds on them. But the console's view page has no
Governance tab, so a view's labels and holds can be seen and set only through the API, while a catalog's, a
namespace's and a table's are set in the console (item 140).

Evidence:
- `table.js`: `VIEW_TABS` is Overview, Versions, Grants and Audit; `TABLE_TABS` has Governance. The prototype had none
  for a view either.
- The server takes a view at every governance route (`GovernanceRoutes`: `VIEW + GOVERNANCE`, `VIEW + ATTRIBUTE`,
  `VIEW + HOLDS`, `VIEW + HOLD`, `VIEW + POLICY`, `VIEW + FREEZE`).
- `panels.js` `governanceTab` already leaves out the retention class for a view and offers the regulated mark only on
  a catalog or namespace; nothing calls it for a view.
- What each does on a view:
  - classification and owner: labels a view's load carries to engines (`GovernanceChain.labels`).
  - retention class: it sets the youngest snapshot a commit or maintenance job may remove (D11, D30); a view has no
    snapshots and no data files, so it does nothing to a view in the catalog. A class inherited from above still
    reaches engines with the view's load, and the tab shows it.
  - regulated: it closes only tables (`Authorizer.decide` checks `CatalogObject.Kind.TABLE`); on a view it would close
    nothing, and the console marks regulated areas on catalogs and namespaces only (item 140).
  - row/column policy: it gates storage access, which a view never hands out; the console sets it nowhere.
  - a legal hold: the store refuses to drop a held object, table or view (`SqlObjects.drop`, `Guards.held`), and a
    dropped one is never purged while held (`LifecycleRoutes`); a view's definition can still be replaced
    (`Rules.retentionHold` guards only table snapshots).
  - a DR freeze: it refuses a view's replace (`Rules.drFreeze`), but the console freezes for DR on a namespace only,
    for tables as well; a freeze above shows on the view's tab.
  - the maintenance policy: maintenance runs on tables; the console sets no policy on the governance tab of anything.
- The tab's words are a table's: a hold "Snapshots cannot be removed", "Snapshot expiry" among what the catalog
  enforces, commits "to groups holding write" (replacing a view needs `modify`, `Guard.REPLACE_VIEW`), and the
  classification dialog's "A table in a regulated area stays closed".

What done looks like:
- The view page has a Governance tab between Versions and Grants: each label with where it was set, the holds, what
  the catalog enforces on a view, "Set a classification", "Set the owner" and "Place a hold", in item 140's words made
  right for a view; no retention class, regulated mark, DR freeze or policy, for the reasons above.
- A browser test (`heavy`, a new class) that sets a view's classification and owner and places a hold from the tab,
  reads each back with provenance `console` and the steward's name, finds the view's drop refused under the hold, and
  checks the tab offers no retention class or regulated mark and speaks of no snapshots.
