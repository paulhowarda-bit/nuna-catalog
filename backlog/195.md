What is wrong: D23 made Kafka the catalog's audit path. `AuditTrail.requireRecorded` throws when Kafka is not
configured or does not acknowledge, so the catalog hands out no storage credential without Kafka
(`AuditRuntime.java:56`: "audit is unavailable ... no credential is handed out"); without Kafka, changes pile up in the
outbox; `RecentAudit` reads the audit topic; and the audit table writer (`catalog-audit-tables`), behind the console's
Audit page, reads only the topic. Paul, 2026-11-23: "Log as the main audit path", "People use Prometheus and otel not
kafka for this" (D23, amended).

Done looks like:
- Every audit record (reads, denials, authentication failures, credential issues, the outbox's changes and the
  notices) is written as its CloudEvent JSON to logger `nuna.audit`, synchronously, before the catalog answers. It
  reaches stdout as ECS JSON and the OTLP log exporter like every log line (docs/observability). That log is the record
  of audit.
- With no Kafka configured, the server starts, serves and vends; the outbox relay drains changes to the log; nothing
  answers 503 for want of Kafka. Where Kafka is configured, records also go to the audit topic and the change stream,
  best effort: an outage there blocks nothing. The archive (D23's Object Lock archive) still needs Kafka, as now.
- Whatever reads the topic in the server (`RecentAudit`, and anything else found) works without Kafka, or says plainly
  that it needs it.
- The audit table writer has a second source, chosen by setting: an OTLP/HTTP logs receiver (`POST /v1/logs`, protobuf
  and JSON, port 4318) that keeps the records of logger `nuna.audit` and writes them as it writes the topic's today,
  deduplicated by CloudEvent id instead of topic offsets. The Kafka source stays.
- The charts take it: the catalog's `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` can name the writer, and the writer's chart
  offers the receiver's port and Service.
- Tests for each point, bites recorded for the new checks, D23's text and the docs say what the code does.

**What was done.** Every audit record is written as its CloudEvent JSON at INFO to logger `nuna.audit` (`AuditTrail`):
reads, denials, authentication failures, credential issues and notices before the catalog answers; the outbox's
changes by the relay, which now runs with or without Kafka, at least once. The server refuses to start with
`nuna.audit` coarser than INFO (`application.yaml` sets it). The `nuna.audit.fallback` log and `requireRecorded` are
gone: nothing refuses a credential or answers 503 for want of Kafka. With Kafka configured, records and relayed
batches also go to the audit topic and change stream, best effort, skipped for `probe-interval` after a failure; the
relay marks a batch relayed once it is logged, so an outage's changes miss the topic, change stream and archive. The
archive still needs Kafka; `GET .../audit` (`RecentAudit`) answers 503 saying it needs Kafka, as before.
The audit table writer has `nuna.audit-tables.source: kafka|otlp`. `otlp` runs `OtlpLogsReceiver` (`POST /v1/logs`,
port 4318, protobuf or JSON, gzip) that keeps only scope `nuna.audit`, asks every request for the token
`otlp.token` in `X-Nuna-Audit-Token`, and feeds `LogWriter`: dedup by CloudEvent id over `otlp.dedup-window` (15m,
read back from the table on start and after a failed commit), rows in `topic_partition` -1 with a rising
microsecond number as `topic_offset`, recorded in the snapshot summary. Charts: the catalog's
`telemetry.logsEndpoint` and `logsTokenSecret`; the writer's `source`, the `otlp-http` container port and Service.
Docs: `docs/observability/audit-log.md`, `deploy/README.md` ("Audit"), `catalog-audit-tables/README.md`; D23's
amendment says what was built. Bites in `bites/D23/` (14 new), OBS-41's recorded again, M7's
`credentials-not-fail-closed` removed with its check. Not run here: `KafkaOutageTest` (rewritten) and the other heavy
tests, and the bites, which the overnight run checks.
