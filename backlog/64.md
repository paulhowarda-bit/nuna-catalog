# 64. CloudBeaver sign-in sometimes answers 500, then works on retry

Status: done
Done: 2026-11-19 on worktree-csrf-per-request
Added: 2026-11-19 by Paul (from the install at work)
Touches: demo/k8s/cloudbeaver.yaml
Effort: S, one setting on the sign-in proxy

Reported from the Nuna install at work on 2026-11-19 (`for-paul/pending/001-cloudbeaver-sign-in-sometimes-answers-500.md`
there, fixed on work's `main` in 6060d6c). Opening CloudBeaver (8185) and signing in through Keycloak sometimes ends on
oauth2-proxy's 500 page at `/oauth2/callback`; going back to the address opens CloudBeaver, already signed in.

Cause, from that report: two sign-ins run at once in one browser, the page's and one started by CloudBeaver's service
worker (its `HEAD /` and `/service-worker.js` requests reach oauth2-proxy unsigned and are sent to Keycloak too).
oauth2-proxy keeps the PKCE code verifier in one CSRF cookie, so the second sign-in overwrites the first's; when the
page's code comes back the proxy redeems it with the wrong verifier and Keycloak refuses it. Evidence at work: Keycloak
logged `CODE_TO_TOKEN_ERROR ... clientId="cloudbeaver", error="pkce_verification_failed", reason="Code mismatch"`,
oauth2-proxy logged `Error redeeming code during OAuth2 callback: token exchange failed: oauth2: "invalid_grant" "Code
not valid"`, and the front door returned 500 for that callback.

The home demo has the same setup: the `signin` container in `demo/k8s/cloudbeaver.yaml` runs oauth2-proxy v7.15.6 with
`code_challenge_method: S256` and no per-request CSRF setting, and `oauth2-proxy:v7.15.6 --help` lists
`--cookie-csrf-per-request`.

What done looks like: the `signin` container sets `OAUTH2_PROXY_COOKIE_CSRF_PER_REQUEST: "true"`, as work's `main`
does, so each sign-in has its own CSRF cookie; a proxy run with that setting names its CSRF cookie after the sign-in's
state.

Done: the `signin` container in `demo/k8s/cloudbeaver.yaml` sets `OAUTH2_PROXY_COOKIE_CSRF_PER_REQUEST: "true"`. An
oauth2-proxy v7.15.6 run with a cut-down copy of the demo's alpha config showed the change: two `/oauth2/start` calls
both set `nuna_cloudbeaver_signin_csrf` without it, and `nuna_cloudbeaver_signin_sBNqN4TI_csrf` and
`nuna_cloudbeaver_signin_P7f_JRGG_csrf` with it. The race itself was not reproduced at home, and the running demo
picks the setting up only when it is next rebuilt (`demo/demo.sh up`).
