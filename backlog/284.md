# 284. The audit table writer stops for good when its table is dropped under it

From `docs/from-work/005-github-secret-scanning.md`, item 4: the writer makes `nuna_audit.audit.events` only as it
starts. When the catalog's PostgreSQL is new but the writer's pod is not (a Helm upgrade that changes nothing leaves
it running), the Audit page answers 503 "the audit table nuna_audit.audit.events does not exist yet" for good, and
the writer logs `NoSuchTableException: Table does not exist: audit.events` every 10 seconds while holding its
records. Work's stopgap restarts the writer from `demo.sh`; work says the better fix is the writer making its table
again. catalog-security (2026-11-25): `LogWriter.reload()` reopens only when `table == null` (LogWriter.java:229-232),
so once the table is gone every reload fails; TableWriter has the same shape.

Done when, on `NoSuchTableException` only (never on a 403, which would hide a revoked grant), the writer drops its
cached table and opens it again through the opener that creates it, logs a WARN that a dropped audit table should be
undropped rather than replaced, and writes the records it held; a test drops the table between two commits and sees
both commits' records in the new table.

## Done, 2026-11-25 (worktree-agent-ae3bdd6ce5d407333)

- `LogWriter.reload` and `TableWriter.reload`: when reading the table again answers `NoSuchTableException`, and only
  then, the writer drops its cached table, logs a WARN (the table is gone; a dropped audit table should be undropped
  rather than replaced; undrop needs the name free), opens it again through its opener, which makes it, and goes on.
  The log writer writes the records it holds; the topic writer, the new table holding no offsets, writes the topic
  from the earliest record Kafka keeps. A refusal (403) is thrown as before. Production finds the drop at the reload
  whichever step failed first, since the REST catalog's refresh is a GET that answers 404.
- What a new table lacks: from the log, the rows committed before the drop (they are in the dropped table and on the
  catalog's stdout); from the topic, records older than the topic keeps. The log writer cannot put the first commit's
  records in the new table, so its test checks the held records; the topic writer's test sees both commits' records.
- Tests (fast): `LogWriterTest` and `TableWriterTest` +2 each, a table dropped between commits and a refusal never
  opening the table again. `FaultyCatalog` answers a dropped table's refresh with `NoSuchTableException`, as REST
  does (Iceberg's in-memory catalog would keep the old metadata), and can refuse as a 403 would.
- Bites: `bites/OBS-284/` (4), each seen to fail with its break applied; `bites/D23/restart-forgets-written-ids`
  recorded again against the moved code.
