The storage design says the server runs the store's `selfCheck()` at startup (D8.2). It does not: no class in
`catalog-server/src/main` calls it (checked 2026-11-14). `build-plan.md` lists it as an M8 follow-up, and
`docs/install-at-work.md` says to check the database's safety settings by hand and ask Paul before wiring it.

Done when Paul has said how a failed check should act (refuse to start, or warn), and the server does that on each
of the four backends, with a test and a bite.

**Decided 2026-11-19 (D8):** a failed self-check refuses to start the server ("Refuse to start"). Test containers and the demo run single-node with fsync off, so they need an explicit setting that allows an unsafe database.

**Done 2026-11-20.** `StoreWiring` runs the store's `selfCheck()` before `migrate()` and refuses to start with an
error naming each finding's code and detail, unless `nuna.database.allow-unsafe` (new in `DatabaseSettings`, empty by
default) names that code; each finding allowed is logged as a warning. A self-check that cannot run refuses too. The
setting is per code, as docs/storage-design.md section 7 says ("Accepting is per code, never a blanket switch").
It is on wherever a server starts on a single-node database: the server's test settings
(`catalog-server/src/test/resources/config/application.yaml`, which also reaches catalog-maintenance's `TestCatalog`
through the tests jar), `ConformanceServer`, the DR drill's DR-region server, the demo and engine matrix
(`demo/k8s/catalog-values.yaml`) and `deploy/local/values.yaml`. The chart exposes it, empty. Tests:
`StoreWiringTest` (a store double: a finding refuses and names each one, each finding must be allowed by its code,
an allowed one is logged and the server starts, a safe database starts either way, a check that cannot run refuses)
and `DatabaseSettingsTest`. Bite `bites/M8/self-check-finding-only-warns.patch`, run once: 2 of 6 failed.

Left: no test that starts a server on a database ran (all heavy or overnight); the next heavy and overnight runs
are the first to start servers with the check. No server test runs on CockroachDB at all, so the check there is
covered only by the store suite's self-check tests and the backend-independent wiring. In a real DR the promoted
database has no synchronous standby, so servers there refuse to start unless `pg.no-sync-standby` is allowed; the
DR runbook (PLT-4, at work) has to say which, a question for Paul.
