Paul, 2026-11-24, told that the demo keeps no volumes, so its data goes with every pod: "can we fix this. I don't want
to lose the data each time the demo goes up and down."

**What is wrong.** Every stateful pod keeps its data in its container's own layer (`demo/README.md`: "No volumes: the
data lives as long as the pods"), and `demo.sh down` deletes the namespace. So each down, each overnight run (which
takes the demo down at midnight and brings it up after) and each Docker Desktop restart loses the catalog's
PostgreSQL, Silo's warehouse, Kafka's topics and SingleStore's databases; `up` writes fresh sample data. A pod that
dies alone (an out-of-memory kill of PostgreSQL or Silo) leaves the catalog and the files out of step.

**What to build.**

- A PersistentVolumeClaim (Docker Desktop's default `hostpath` class) for PostgreSQL, Silo, Kafka and SingleStore,
  each in the manifest of the pod that mounts it, so the engine matrix, which applies `stack.yaml` and `kafka.yaml`
  in a namespace of its own, gets them too and loses them with its namespace.
- `demo.sh down` removes everything but the claims (and the seed's marker, which says the data in them is
  complete); the switches' stops (`ss stop`, `stop_kafka`) keep their claims, so SingleStore and Kafka pick up where
  they stopped.
- `demo.sh wipe`: down, and the claims with it, so the next `up` writes fresh sample data, as `down` did before.
- The CDC leg stays as it is: `cdc stop` deletes its databases, topics and connector offsets by design. `down` while
  it runs does the same, so a later `cdc` never meets offsets for databases that are gone.
- Keycloak keeps no volume: its realm is imported from `keycloak-realm.json` at each start, and the catalog names
  people by `preferred_username`, so nothing kept refers to a Keycloak id.

**Done when** on the live demo a table written before `down` reads the same after `up`, the generator resumes
(its log says it has already sent what it sent before), SingleStore still holds its orders, and `wipe` then `up`
starts from fresh sample data.

**What was done** (2026-11-24). `stack.yaml`, `store-silo.yaml`, `kafka.yaml` and `singlestore.yaml` each give their
pod a claim (`postgres-data` 5Gi, `s3-data` 20Gi, `kafka-data` 5Gi, `singlestore-data` 10Gi, Docker Desktop's
`hostpath` class) and `strategy: Recreate`, so two pods never share a data directory; Kafka names its cluster id and
log directory so the volume's log is its own at every start. `demo.sh`: `unapply` leaves a manifest's claims, so
`ss stop` and `gen stop` keep the data; `down` uninstalls every Helm release and deletes everything in the namespace
but the claims and configmap `demo-seeded` (and deletes a running CDC leg as `cdc stop` does, through the new
`cdc_delete`); `wipe` is `down` and the namespace. README, `overnight.sh`'s header and CLAUDE.md say the overnight
run keeps the data; the generator's Kafka-lost message names `wipe`. D52.

Checked on the live demo: `wipe`, then `up` from the branch, wrote fresh sample data onto new volumes; `gen` brought
up Kafka and SingleStore on theirs. With a marker namespace made, `down` left the four claims and `demo-seeded`, and
the next `up` skipped the seed: the marker and `trades`' snapshot were unchanged, Kafka's offsets carried on
(journal-lines 62,786 before, 63,255 after), the generator logged "already sent {... JOURNAL_LINES=62788 ...}" and
replayed the past days without sending, and SingleStore's `brokerage.orders` went on from 1,721 to 1,734. Not
covered: a Docker Desktop restart, and the CDC leg's `down` path (it was off).
