What is wrong: `CommitEngine.register` and `revive` take the client's `metadataLocation` and never check
`TableFiles.onBranch`. So main's pointer, and main's journal, can be set to a branch's metadata file
(`<v>-<uuid>.branch-<refid>.metadata.json`). Reconcile skips marked files when it builds main's chain (item 111), so
after a regional failover a main pointer at a branch file is invisible to recovery. The merge's base walk (item 107)
also accepts main's journal entry for such a file as main's position at a cut. That is true (main really was at that
file), so no commit is overwritten, but it is a file main should never hold. Doing it needs create and drop on main.

Done when register and revive refuse a location `TableFiles.onBranch` marks, with 400 `BadRequestException`, on main
and through a branch alike; a fast `CommitEngine` test for each; a bite recorded (`git diff` of the check removed,
checked with `git apply --check`, not run).

## Done, 2026-11-25 (worktree-agent-a0c883588be136143)

- `CommitEngine.register` (`CommitEngine.java:553`) refuses a `metadata-location` that `TableFiles.onBranch` marks
  with 400 `BadRequestException`, before it reads the file. Register and revive both go through it (revive is reached
  only from register), for a table and a view, and an engine `on` a branch registers as main's does, so the refusal
  holds on main and through a branch alike. The register's javadoc says so.
- Fast tests in `BranchCommitTest` (its store double now also takes `createObject`): `aRegisterRefusesABranchsFile`
  (a table's and a view's branch-marked file no object holds, registered through `engine()` and `on(dev)`: 400, no
  object, pointer or event) and `aReviveRefusesABranchsFile` (an unregistered table registered again by the file its
  branch wrote, both engines: 400, the table stays unregistered at main's pointer). Both pass.
- Bite `bites/D33/register-takes-a-branch-file.patch` (the check removed), recorded and checked with
  `git apply --check`, not run.
- Item 107's javadoc fix rides with this branch: `MergeMetadata.journal`'s javadoc now says `cut-version` is main's
  version at the branch's cut, the merge's base, not "the cut's version" (words only).

Every other route that takes a client's metadata location:
- `POST …/register` and `POST …/register-view` (`TableRoutes.register`, `ViewRoutes.register`): through the engine's
  register, so covered. Through a ref the REST layer already refuses them (`OnRef.mainOnly`, 400).
- Revive: only a register revives; the management undrop (`LifecycleRoutes.undrop`) takes no location and brings the
  object back at main's own pointer. Covered.
- `PUT …/dr-watermark` (`DrRoutes.record`): the location must be the one main's journal or pointer records for that
  version, so it can name a branch file only if main already held one, which register no longer allows. Covered.
- `POST …/dr-reconcile` `accept`: the walk never takes a marked file as one of main's (item 111, bite
  `reconcile-takes-branch-files`), so an `accept` naming one is never chosen. Covered.
- No import route exists.

Choices made (Paul may overrule):
- One check in `register`, before the file is read, rather than one in `register` and one in `revive`: every revive
  comes through it, and a refused location costs no storage read.
- The tests sit in `BranchCommitTest`, the fast engine test with a store double and branches; `RegisteringTest`, where
  registers live, needs PostgreSQL (heavy).
