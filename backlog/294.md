# 294. kind's node caps every container at 307 tasks: SingleStore's pipelines, and the JVMs, run out of threads

Status: done
Done: 2026-11-26 on kind-tasks
Added: 2026-11-26 by local_d697e3a0-9dcf-4401-b754-2b759dcc6b79
Touches: deploy/kind/kind.sh, status/
Effort: S, one function in kind.sh that kind_up runs each time, and a check on the running node

What is wrong: since the move to kind on Podman (backlog 287), every container in cluster nuna may run at most 307
tasks (processes and threads together). Podman starts the node container `nuna-control-plane` with its default
PidsLimit of 2048, and systemd in the node gives every unit it starts, each container's cri-containerd scope among
them, DefaultTasksMax=15% of that: 307. Docker Desktop set no limit, so its Kubernetes had none. The node as a whole
is capped at 2048 too, and with the demo, SingleStore and the generator running it held 1,192.

Evidence (the data generator session, 2026-11-26, item 238): SingleStore runs 284 tasks idle, and `demo.sh ss`
fails at load.sql's first Iceberg pipeline with `ERROR 1933 ... Process died unexpectedly or didn't start`: the
extractor JVM cannot make its threads. `systemctl set-property --runtime <its scope> TasksMax=infinity` in the node
and the same pipeline loads. Trino, Kafka Connect, Keycloak and the catalog server are JVMs under the same cap.

Done when `kind.sh up` (which demo.sh, the chart's local install, the overnight run and the tests run) leaves the
node and every container in it without a task limit, on a new cluster and on this one, and a pod started afterwards
has none either; checked on the running node.

What was done: `kind.sh up` runs `kind_tasks` each time the node is up. It lifts the node container's limit
(`podman update --pids-limit -1` while Podman's PidsLimit is above 0) and writes the drop-in
`/etc/systemd/system.conf.d/nuna-tasks.conf` (DefaultTasksMax=infinity) in the node with a daemon-reload, once. Then
it sets TasksMax=infinity on each container scope still capped, the ones started before the drop-in. Checked on the
running node: with the drop-in removed and PidsLimit set back to 2048, `kind.sh up` left PidsLimit -1, the node's
pids.max `max`, DefaultTasksMax infinity, and all 41 container scopes at `max`. A pod started afterwards got pids.max
`max`. Not checked: a restart of the node or the Podman machine; `kind.sh up`, which every user of the cluster runs
first, lifts the limits again in any case.
