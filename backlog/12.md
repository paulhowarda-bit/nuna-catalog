# 12. A revive can bring an object back in a namespace it later left

Status: done
Done: 2026-11-19 on worktree-agent-a538d80ba8aa39256
Added: 2026-11-14 by Change Manager, from build-plan.md at Paul's request
Effort: M, one namespace comparison in each of four stores, a store-suite test and a bite

`build-plan.md`, review fixes of 2026-11-12, "Not guarded": an object undropped, renamed into another namespace and
dropped again by other callers between the engine's read and the store's revive would come back in the namespace it
first left, because the store does not compare the namespace.

Done when the store compares the namespace under its lock on all four backends, with a store-suite test and a bite.

Done: the race was real on every store. `reviveObject` locked the object by id and state only, and undrop, rename and
drop leave the main pointer alone, so the pointer check did not catch it. Now the SQL store (PostgreSQL and CockroachDB
share `SqlObjects`) and Oracle lock the object row and compare its namespace under that lock. MongoDB compares it in
the snapshot transaction that writes the object, so a move committed since makes the write conflict and the retry
sees it. A moved object is `Missing(OBJECT)`, which the engine already answers with 409; `catalog-core` is unchanged.
The suite has `reviveComparesTheNamespace` (new), and `reviveBringsTheObjectBack` now revives in the object's own
namespace. Bites: `bites/D13/revive-ignores-moved-namespace-{sql,oracle,mongo}.patch`, recorded, not run
(`status/2026-11-19-agent-a538d80ba8aa39256.md`).

tests. Docker is off (Paul, 2026-11-19), so the last build only compiled main and test code and checked that all 291 bites
