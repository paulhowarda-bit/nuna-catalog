Backlog 312 (20a855c8) made the grant export publish an `Export` record through `Denials.record`, which goes
through the `AuditPublisher` seam, as denials and other reads do. In production that seam is `AuditTrail.record`
(`GovernanceWiring.auditPublisher`), which logs it to `nuna.audit`. SecurityGateTest replaces the seam with
`AuditSinkForTests` (`@Primary`), so the record lands in the sink; only the outbox relay's records (grants, engines)
reach the log the test's `AuditLogCapture` reads. The assertion 312 added looked in the log, so it could never pass.
SecurityGateTest is tagged heavy, and 312 landed on the fast build, so no build ran it until this one.
`RowColumnReadRoutesTest`, from the same commit, checks its export in the sink and passes.

The product is right: the export is audited, once, with who took it and how many. The test was wrong about where
the record goes in its own context. (The other message named in the report, "Expecting empty but was:
[Denial[operation=readAudit, ... cora holds n…", is `ConsoleBrowserTest`'s, not this test's.)

What done looks like: the test checks the sink for exactly one `Export` of `grants` on catalog gate, by gina,
with `returned` equal to the grants the answer holds; `SecurityGateTest` passes with `-Pheavy`.
