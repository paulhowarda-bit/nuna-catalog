What was done: the cause was an int overflow in the audit table writer, not the archive or the reconcile.
`LogWriter.offer` refused when `rows.size() >= 2 * maxRows`; the M8 stack's archive leg (`ArchiveFromLog`, since
backlog 262, b38c610c) builds its writer with `maxRows` `Integer.MAX_VALUE`, so the bound was -2 and every offer threw
`Busy`. The receiver archives a batch before it offers it to the writer, so each record did reach the archive, but the
answer was 503, and the servers' OTLP/HTTP log exporter (OpenTelemetry 1.62) retries 503 with backoff (5 attempts, 1 s
growing to 5 s) while its batch processor sends one batch at a time. Each batch held the next back by seconds, and the
drill kills its primary servers a second or two after the last commits, so the batches holding each table's last swap
were still queued and never sent. Before 262 the archive was written from Kafka and none of this applied, which is why
the 2026-11-25 run (639b0da5, before 262) passed. Neither 289 (the store's time), 263 (late copies) nor the refs in the
report played a part: the report's empty `refs` and its one unknown location (the late table) are what the test
expects.

The bound is now taken in long (`2L * maxRows`), so a `maxRows` past 2^30 no longer refuses every offer; a deployment
could set `nuna.audit-tables.max-rows` that high too, since only a lower bound is checked. `LogWriterTest` gains
`aMaxRowsPastHalfTheIntRangeStillTakesRecords`, and its bite is `bites/OBS-303/max-rows-doubled-in-int.patch`
(checked with `git apply --check` only). `DrDrillTest` passed in the worktree, both tests (the first dry run with the
archive proved every tip), and the fast build passed. Left: the overnight run's nightly leg, which closes the item as
written.
