Work runs OpenTelemetry, with Prometheus and Grafana behind it. Today the catalog gives them nothing:
- No metrics: no Micrometer, no Actuator, no metrics endpoint (`catalog-server/build.gradle.kts` has webmvc and jdbc
  only).
- No traces.
- Logs are plain text and carry no request ID. The server takes the client's `X-Request-ID` or makes one
  (`Authentication.java:150`, `RequestContext.java`) and puts it in audit events and STS session tags
  (`keel-request`), but never in a log line and never in the response.
- The worker (`catalog-maintenance`) logs a line per scan and nothing else.

This item lays the foundation that the metric and span items (39, 40, 41) build on.

What to use. Spring Boot 4.1.2, our version, ships `spring-boot-starter-opentelemetry`: Micrometer metrics exported
over OTLP (`micrometer-registry-otlp` 1.17.2), tracing through `micrometer-tracing-bridge-otel` 1.7.2, and
`opentelemetry-exporter-otlp` 1.62.0, all managed by Boot's BOM. With `management.opentelemetry.map-environment-variables`
(default true) it reads the standard `OTEL_*` variables (`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`,
`OTEL_EXPORTER_OTLP_*_ENDPOINT`, headers, certificates, sampler, propagators), so whatever work's platform injects is
honoured without Boot configuration. Its OTLP exporter depends on `opentelemetry-exporter-sender-okhttp`, which brings
OkHttp and the Kotlin standard library; use `opentelemetry-exporter-sender-jdk` instead, so work's mirror needs neither
(PLT-6). Catalog code uses Micrometer's API (Observation, MeterRegistry) only, never the OpenTelemetry SDK, so a later
switch to Prometheus scraping is a dependency and configuration change, not a code change.

Done when:
- The server and the worker export metrics and traces over OTLP when an endpoint is configured, and export nothing,
  quietly, when none is: the tests, the demo and a laptop run have no collector. A test runs a small OTLP receiver and
  sees a span and a metric from a REST call arrive.
- Logs go to stdout as structured JSON (Boot's structured logging), and also over OTLP when a logs endpoint is
  configured. Every line written while a request runs carries its trace ID, span ID and request ID.
- When a client sends no `X-Request-ID`, the request ID is the trace ID, so an audit event, an STS session tag (seen in
  CloudTrail), a log line and a trace share one key. Every response carries `X-Request-ID`, error responses
  included, whether the client sent it or not. The 128-character limit and the cleaning for STS tags stay as they are.
  Tests show each; each guarded rule is recorded as a bite in `bites/OBS-38/`.
- The Helm charts (`deploy/helm/keel-catalog`, `deploy/helm/keel-maintenance`) take the OTLP endpoint, headers, CA
  and sampling as values, set `OTEL_SERVICE_NAME` and resource attributes, and leave export off by default.
  `deploy/README.md` says how.
- `docs/install-at-work.md` lists the new artifacts for the mirror. `docs/observability/README.md` says what is
  exported, how to point it at a collector, and that audit stays on Kafka (D23): telemetry never replaces it, and an
  export that fails never fails or slows a request.
- No metric label or span attribute names a person (principal, end user) or holds a filter value.
