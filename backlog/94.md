Reported from the Nuna install at work on 2026-11-20 (`for-paul/pending/002-the-demo-s-object-store-on-its-own-port-for-engine.md`
there, fixed on work's `main` in a1f2ba0). Work queries the demo's tables from two other servers, not only from
inside the cluster. The catalog's port, 8181, was reachable from them, but Silo's S3 API was not, so an engine off
the machine could load a table's metadata and credentials and then could not read a single file.

The home demo has the same gap: `demo/k8s/ports.yaml` publishes 8180 to 8186 and none of them is Silo's S3 API
(8184 is its console, port 9001).

What done looks like: the front door listens on 8187 and passes it to `s3:9000`, with a LoadBalancer Service
`s3-public`, as work's `main` does; `demo.sh up` checks 8187 is free like the other ports; an S3 client signing for
`https://localhost:8187` reads and writes through it.

The catalog still vends `s3.endpoint` `http://s3:9000`, which resolves only inside the cluster, so each outside
engine sets its own `s3.endpoint` to the public address. Item 96 asks Paul whether the catalog should vend it.

Done: the front door (`demo/k8s/ports.yaml`) listens on 8187 and passes it to `s3:9000`, published by LoadBalancer
Service `s3-public`; `demo.sh up` checks 8187 is free; demo/README.md lists the port and says an outside engine sets
`s3.endpoint` to `https://<host>:8187`. Checked with nginx 1.30.6 running the ConfigMap's own template and the demo's
certificate in front of Silo, in a Docker network of their own: the AWS CLI, signing for `https://localhost:8187`,
made a bucket, wrote a 3,000,000-byte object, listed it and read it back byte for byte, and a wrong key got 403. The
running demo publishes 8187 only when it is next rebuilt (`demo/demo.sh up`).
