When the catalog cannot fetch an issuer's signing keys (the IdP is down, or slower than the 5 s read timeout item 60
gave the JWKS fetch), `TokenAuthenticator` refuses the token as invalid: 401 with `Bearer error="invalid_token"`. That
tells the client its good token is bad, so it throws the token away or sends its user to sign in again, when the
fault is the IdP's and passes. `JwksRefreshTest#anUnreachableJwksMeansNoTokenIsAccepted` asserts the 401 today.

Done 2026-11-20 on worktree-agent-a225efaee6734118d:
- The 401 path is the server's own filter, `security/Authentication.java`, which calls `TokenAuthenticator`; Spring
  Security's resource-server chain is not used, and `ErrorResponses` is not on the path (the `Touches:` line now
  names the filter). Nimbus raises a key fetch that failed or timed out as a `JWKSetUnavailableException`
  (`JWKSetRetrievalException`), which Spring's `NimbusJwtDecoder` makes the direct cause of a plain `JwtException`
  (a bad token comes as a `BadJwtException` or `JwtValidationException`). `TokenAuthenticator` tells the two apart
  there and throws `AuthenticationFailure` with status 503; the filter answers it 503 `ServiceUnavailableException`,
  `Retry-After: 2`, no `WWW-Authenticate`, the body "The token could not be checked: its issuer's signing keys could
  not be fetched; retry later", logs a warning, and audits the `AuthFailure` with the reason, as for a 401.
- Nimbus's rate limit (two fetches in 30 s) refuses a refetch with a `RateLimitReachedException`, which is not a
  `JWKSetUnavailableException`. Mapping only the latter would have left an IdP that stays down answering 401 to
  every request but two in each 30 s. `TokenAuthenticator` now takes Nimbus's health reports
  (`JWKSourceBuilder.healthReporting`): a refused refetch is an outage when the last fetch failed, and a bad token
  (a key id the issuer does not publish) when it succeeded. No token is accepted unchecked: an outage throws, and
  keys already held keep checking tokens.
- `Retry-After` is `StoreOutage.RETRY_AFTER_SECONDS`, 2 s, the value the routes and the filter's store-outage 503s
  send. The rate limit keeps retrying clients from reaching the IdP more than twice in 30 s.
- `JwksRefreshTest` (Java only) asserts 503 for an unreachable JWKS (`anUnreachableJwksMeansNoTokenIsAccepted`, now
  503), for one slower than the 5 s timeout (6 s, `aJwksSlowerThanTheReadTimeoutIsAnOutage`), for an IdP that stays
  down past the rate limit, and for a key not held while the IdP is down; 401 for a wrong signature against a held
  key, an expired token, another audience and an untrusted issuer, both while the keys are reachable and while held
  keys serve during an outage; and 401 for each made-up key id the rate limit refuses. `IdpOutageTest` (new, Java
  only) drives the real filter and authenticator with Spring's mock servlet objects: the 503, its header, body and
  audit; a bad signature's 401 with the challenge; a good token reaching the route.
- Bites in `bites/D16/`: `jwks-outage-answers-401.patch` (the fetch failure mapped back to 401, against the 503
  tests), `jwks-refetch-limit-bad-token.patch`, `jwks-refetch-limit-outage.patch` and
  `idp-outage-without-retry-after.patch`; `jwks-read-timeout-500ms.patch` recorded again, its context having moved.
  Each was checked with `git apply --check` and seen to bite in a fast build with its break applied (`--continue`):
  the first failed the four outage tests and `IdpOutageTest`'s 503 test; the second the two rate-limit outage tests;
  the third `unknownKeyIdsCannotForceAFetchEachTime`; the fourth the 503 test's `Retry-After` assertion. Each build's
  other tests passed. `bites/run.sh` was not run.
- Clients: the console signs its user out on a 401 (`catalog-server/src/main/resources/nuna/ui/api.js`) and shows
  any other error in place, so an IdP outage no longer signs anyone out; they see the 503 and can try again. The
  Iceberg Java client (iceberg-core 1.12.0, read from its sources, `ExponentialHttpRequestRetryStrategy`) never
  retries a 401 (`NotAuthorizedException`) and retries a 503 carrying `Retry-After` for any method, up to five
  times, waiting the header's seconds, then throws `ServiceUnavailableException`. The maintenance worker's own calls
