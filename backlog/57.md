Silo, the demo's S3 store, carries MinIO's console ("SILO Console"), but the demo publishes only its S3 API, on
Service `s3` port 9000, inside the cluster. With no `--console-address`, Silo puts the console on a random port
at each start (the pod's log of 2026-11-16: `WebUI: http://10.1.2.17:38755`), so even a `kubectl port-forward`
has to look the port up first. A port-forward to it on 2026-11-16 served a page titled "SILO Console". Paul
asked for it to be published like the demo's other UIs (2026-11-16, "Yes, publish it").

Done when Silo starts its console on a fixed port, `ports.yaml` publishes it on localhost:8184 (DuckDB's old
port), `up` checks 8184 is free like the others, the console signs in as Silo's root `keeltest` on
<http://localhost:8184>, and the README and the text `demo.sh` prints say where it is and how to sign in.

What was done: Silo starts its console on the pod's 9001 (`store-silo.yaml`), `ports.yaml` publishes it on
localhost:8184 as Service `silo-console`, `up` checks 8184 with the other ports, and the README (the stack's
files, the ports, the accounts table) and `print_access` say where it is and that `keeltest` signs in. Checked in
a scratch namespace with the changed manifests: the console answered on <http://localhost:8184> and signed in
as `keeltest`. Not applied to the running demo, whose Silo keeps no volume; it takes effect on the next fresh `up`.
