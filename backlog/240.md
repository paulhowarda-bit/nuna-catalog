## What is wrong

A column mask (backlog 115) is stored under the column's name and nothing checks that name against the table's
schema. If the column is renamed, Trino asks for the new name, finds no mask and returns the column unmasked. A typo
in the name masks nothing. A dropped column's mask is silently ignored. A row filter that names a dropped or renamed
column makes every query for that group fail.

## Evidence

The security expert, 2026-11-24:

- masks are matched by name, ignoring case: `OpaAnswers.java:84-87`, `137-140`;
- setting a rule checks only length and NUL characters, never the schema: `RuleRoutes.java:219-248`;
- a schema change is committed with no look at the rules that name its columns.

## Done when

- Setting a rule refuses a mask, or a filter, that names a column the table's current schema lacks, in words.
- A schema change that renames or drops a column a rule names is refused, saying which rule, or the masks follow
  the column by its Iceberg field id so a rename keeps it masked. Either way, a rename never unmasks a column.
- Tests cover a rename, a drop and a typo, and a bite breaks each guard.

## What was done

**Design: refuse the schema change, not key masks by field id.** A schema change that renames or drops a column a
rule names is refused, naming each rule's group. Keying masks by Iceberg field id was turned down for three reasons:

- a row filter is SQL text that names columns by name, so only a refusal keeps a filter right;
- a column dropped and added again under the same name gets a new field id, and would come back unmasked;
- it would change the rule's stored form on all four stores, and nuna would have to read the table's metadata to
  answer each of Trino's questions.

The three guards:

- **Setting a rule** (`RuleRoutes.schemaColumns`, `RuleColumns.check` in catalog-security): every mask must name a
  column of the table's current schema on main, compared ignoring case, and is stored under the schema's spelling.
  Every column the filter names must be in that schema. Otherwise the answer is 400, naming what is missing. A filter's
  columns are read from its words, not parsed: identifiers that are not keywords, function names, qualified names,
  typed literals' or casts' types, lambda parameters, or inside a subquery. Item 244's parser can replace this method.
  The schema is read through `TableColumns` (rest), after authorization.
- **A schema change** (`RuleColumnGuard`, a `CommitRule`): a commit whose current schema loses a column (compared
  ignoring case) that a rule names is refused 403 and audited as a denial with reason `row_column_rule`. A filter
  counts every identifier it holds, subqueries included. The commit engine judges branch commits, transactions and
  merges with the same rules. `TableFacts` now carries the current schema's top-level columns.
- **Trino's answer** (`OpaAnswers.columnMasks`): if the user's masks name a column that Trino's batch does not ask
  about, every column of that table comes back NULL. This covers the case the guard cannot see:
  - the guard reads the rules before the pointer swap, so a rule set at the same instant as a rename can still slip
    through;
  - a query of an old snapshot, or of a branch whose schema named the column differently.

  Trino asks about every column of a table in one batch: Trino's `StatementAnalyzer.analyzeFiltersAndMasks` passes the
  whole relation. This was read in Trino's source (master), not checked live: the demo was down.
