D45, amended 2026-11-22. Paul: "I would like to be able to set properties' in the UI, but properties that mean
something." The console shows every Iceberg property read-only (tools and SQL may still set any key) and lets people
edit only keys that do something, chosen from a list, each with a label, a plain explanation and a checked value. A
catalog's settings stay read-only. Free-form key entry leaves the console.

Evidence:
- A namespace's Properties tab (`browse.js`, `propertiesTab`, `setProperty`, `removeProperty`) takes any key and
  any value, and removes any key.
- The redesign's prototype (`docs/design/console/prototype.html`, the `ns-prop` action) offers "Set a property"
  with any key on a catalog and on namespaces. A catalog keeps no free-form properties: `CatalogProperties.java`
  answers only its declared settings, which change only through item 22 (deferred, D41).
- A table's properties are shown only as a line of `key=value` (`table.js`, `propsDd`), with no editor.
- The namespace page's subtitle reads `owner` from the namespace's Iceberg properties (`browse.js`,
  `namespaceTab`), while the owner the catalog enforces is the governance label (D27, item 140).

What done looks like:
- Tables: every property listed read-only; an editor for the write settings engines honour, each with its label,
  explanation, allowed values or range, and its default when unset. Candidates, to settle against the Iceberg table
  spec's write properties and the commit rules (`Rules.java`, D11): `write.format.default` (parquet, avro, orc),
  `write.parquet.compression-codec` (zstd, gzip, snappy, lz4, brotli, uncompressed) and
  `write.parquet.compression-level`, `write.target-file-size-bytes`, `write.distribution-mode` (none, hash, range),
  `write.delete.mode`, `write.update.mode`, `write.merge.mode` (copy-on-write, merge-on-read),
  `write.metadata.delete-after-commit.enabled`, `write.metadata.previous-versions-max`,
  `write.metadata.metrics.default`. Left out: the path properties `Rules.PATH_PROPERTIES` police (the catalog assigns
  locations, D28), `encryption.key-id` (fixed at create, D26), `format-version` (an upgrade, not a setting), and the
  snapshot-expiry keys (`history.expire.*`), which the maintenance policy governs (D30): the editor links to the
  policy instead. A change goes through the table's normal commit (`set-properties` / `remove-properties`), so
  every commit rule, `modify` and the audit trail apply as for any engine.
- Namespaces: every property listed read-only; an editor for `comment` and `location`. Before building `location`,
  check what it does in nuna: under D28 the catalog assigns every table's location, never from the namespace, so a
  namespace's `location` may change nothing. If so, ask Paul whether to leave it out (his decision named it).
- The catalog's Properties tab stays read-only and links to its maintenance policy; no "Set a property" there.
- No free-form key entry anywhere in the console.
- The namespace subtitle's owner is the governance owner, not an Iceberg property.
- `docs/design/console/README.md` notes what was built.
- A browser test (`heavy`): a listed setting changed and removed through its editor and read back from the table's
  metadata; an unlisted property shown and not editable; a value outside the allowed ones refused in the dialog.
  Bites for any new guarded check.

What was done (2026-11-22):
- `settings.js`, a new console module, holds the settings and draws the Properties tab of a table (new) and of a
  namespace (rebuilt): the settings first, each with its label, what it does, its value or default, Change and Reset;
  then every property read-only, with a note on each the console does not list. The dialog checks a value before it
  sends anything (a choice from a list, a whole number in a range, a size such as "512 MB" sent as bytes). A table's
  change is a commit with `set-properties` or `remove-properties`, asserted against the table's UUID
  (`api.tableProperties`); a namespace's goes through its properties route. Both are refused, audited and answered as
  an engine's would be.
- Table settings, each honoured by an engine's writer or by the catalog: `write.format.default` (parquet, avro, orc);
  `write.parquet.compression-codec` (zstd, snappy, gzip, uncompressed; lz4, brotli and lzo left out, since engines
  ship no brotli or lzo codec and Parquet's lz4 is a framing other readers do not read);
  `write.parquet.compression-level` (zstd 1 to 22, gzip 1 to 9, none for the other codecs);
  `write.target-file-size-bytes` (16 MB to 4 GB; compaction keeps the policy's own target, and the setting links to
  it); `write.distribution-mode` (none, hash, range); `write.delete.mode`, `write.update.mode`, `write.merge.mode`
  (copy-on-write, merge-on-read; merge-on-read refused on a format-version-1 table); `write.metadata.metrics.default`
  (none, counts, truncate(16), full); `write.metadata.previous-versions-max` (1 to 10,000; the catalog's metadata
  builder trims the log to it).
- Left out: `write.metadata.delete-after-commit.enabled` changes nothing in nuna. The catalog writes every metadata
  file (`Metadata.commitTable`), never deletes one on commit, and Iceberg's REST client (`RESTTableOperations`, 1.12.0)
  deletes none; the orphan scan removes the files that fall off the log (`OrphanScan`: reachable is what the log
  still lists). It is shown read-only with that note. The snapshot-expiry keys (`history.expire.*`) note and link the
  maintenance policy; the path properties and `encryption.key-id` note why they are the catalog's; `format-version`
  is not a property.
- Namespace: `comment` only. A namespace's `location` changes nothing nuna does: every table's location comes from
  `files.newLocation(id)` (`CommitEngine.create`, `ProfileTableFiles.newLocation`, the storage profile and the
  table's id), never from its namespace (D28), and nothing in the server reads a namespace's properties. So it is left
  out, by Paul's rule of properties that mean something (`location` was a suggestion, not his), and is shown
  read-only noting that it changes nothing. An Iceberg `owner` property notes that the enforced owner is the
  governance label.
- The namespace page's subtitle names the governance owner (`effective.owner`), not the Iceberg property. The
  catalog's Properties tab says the console sets none and links to its maintenance policy. The old free-form "Set a
  property" and per-key Remove are gone; nothing in the console takes a key.
- `ConsoleSettingsBrowserTest` (`heavy`): a setting changed, a size typed in words, and a reset, read back from the
  table and audited as a commit; values out of range refused in the dialog and never sent; a caller without `modify`
  shown the catalog's 403 with its request id, audited as a denial; a tool-set key shown read-only; a namespace's
  comment set, its owner from governance, and exactly the listed settings with no key entry on catalog, namespace
  and table. Bites `bites/UI/console-settings-value-unchecked.patch` and `console-settings-unlisted-editable.patch`.
- Not run here: the browser test and the bites need Docker and run in the overnight heavy build. Checked by hand in a
  static harness (the modules over sample data, light and dark, 375 px wide): the tab draws, the dialog refuses
  "3 TB" and shows a refusal with its request id, and nothing overflows the phone width.
