Effort: L, every script and test that ran pods in Docker Desktop's Kubernetes moves to a kind cluster, checked live with the demo and the compaction tests

Paul, 2026-11-26: "we have installed podman desktop and are removing docker desktop can you make this switch." Asked
whether to keep the demo's data, which lived on Docker Desktop's disk: "Start fresh, but make sure that there are
persistent volumes for all data. The data should not be in the container."

What is wrong: everything that runs pods named Docker Desktop's Kubernetes (context `docker-desktop`) and leaned on
what Docker Desktop gives it: its nodes run images straight from the local Docker engine, it serves LoadBalancer
Services on localhost, it keeps volumes in its `hostpath` StorageClass, and its pods reach this machine as
`host.docker.internal`. Podman Desktop has no Kubernetes of its own; its Kubernetes is kind. The Docker CLI and
kubectl that came with Docker Desktop go with it.

Evidence (2026-11-26): Docker Desktop stopped, its engine pipe gone; `podman` 6.2.0 with machine
`podman-machine-default` (WSL, rootful) running; Windows' Docker pipe `docker_engine` answers from Podman, so
Testcontainers already runs on Podman (a heavy build that morning pulled its images there). kind 0.33.0 and kubectl
1.37.3 installed from winget with Paul's yes.

Done when:

- `deploy/kind/` makes one kind cluster, `nuna` (context `kind-nuna`), and loads images Podman built or pulled onto
  its node; the demo, `deploy/local/run.sh`, the overnight run, `CompactionCluster` and the engine matrix use it.
- The demo comes up on it with every page on its port, its data on volumes, and survives a node restart.
- The compaction tests pass on it, or what stops them is written down.
- The docs that named Docker Desktop name the kind cluster.
