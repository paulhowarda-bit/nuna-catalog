Done: it still held on 2026-11-19. `GrantRoutes` read the group's grants (`listGrantsOfGroups`), asked
`Separation.refusal`, and only then called `putGrant` in a transaction of its own, so two grants to one group made at
once (say `write` on one namespace and `manage-tags` on another) each passed on a read that missed the other, and the
group held two separated duties. Now the check and the write are one unit on all four stores:
- The store API gains `GrantStore.putGrantIf(grant, grantedBy, change, admits)`: inside the write's transaction the
  store reads the privileges, by wire name, that the group holds anywhere in the grant's catalog, asks `admits`, and
  puts the grant only if it accepts; otherwise it answers `Refused(NOT_ADMITTED)` (a new `WriteResult.Reason`) and
  writes nothing. Conditional puts in one catalog are serialized. The store learns nothing about the duties: the rule
  stays in `Separation.refusal`, which the route passes as `admits`; a refusal is audited and answered 403
  `separation-of-duties` as before, with the same message.
- PostgreSQL and CockroachDB (`SqlGrants.putIf`) and Oracle (`OracleGrants.putIf`) lock the catalog's row
  (`SELECT … FOR UPDATE`) first, then read the group's grants: READ COMMITTED reads after the lock, so each put sees
  what the one before it committed. MongoDB (`MongoGrants.putIf`) marks the catalog's document, as its writes already
  mark what they depend on, so of two racing puts the later conflicts and runs again on a snapshot holding the
  other's grant.
- Why per catalog and not per group: separation of duties is judged per catalog (D18), the catalog's row exists on
  every store, so no schema step is needed on any of the four, and grants are rare administrative writes. A per-group
  guard row would let grants to different groups in one catalog run side by side, at the cost of a new table or
  collection on every store. The lock is taken before the securable's, and no write takes a namespace or object lock
  and then its catalog's, so it cannot deadlock (Oracle does not retry a deadlock).
- `putGrant` is unchanged; only `GrantReplay` (rebuilding grants from the audit archive, D37) still calls it, since a
  replay restores what was checked when it was granted.
- Tests: `GrantRaceTest` (new, Java only): two grants raced through the real route, authorizer and `Separation` over a
  store double that keeps `putGrantIf`'s contract and holds both requests until each has reached the store; four
  conflicting pairs each end with one grant applied and the other refused and audited, a compatible pair both apply,
  and a grant that conflicts with one held is refused. `GrantSuite` (every store; heavy): what `admits` is shown,
  refusals and Missing write nothing, and eight conditional puts racing to one group, each admitted only while the
  group holds nothing in the catalog: exactly one applies.
- Bites: `bites/D18/separation-checked-outside-the-write.patch` (the route checks against grants it read itself:
  `GrantRaceTest` fails with both grants applied, run once by hand), and one per store that drops the catalog lock
  or mark (`grant-check-unlocked-sql`, `-oracle`, `grant-check-unmarked-mongo`, heavy, not run).
  `bites/M5/sod-not-checked-on-grant.patch` recorded again against the route's new code.
