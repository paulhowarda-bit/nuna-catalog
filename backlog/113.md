Item 26's design (2026-11-20) builds branches with a table's grants holding on every ref (its choice 12), so whoever
may write a table on a branch may also write it on main. A grant that names a branch would let a group write on `dev`
without writing main, which changes D18's model (grants to groups on catalog objects) on all four stores.

Paul put it off on 2026-11-20 (D33, amended: "No, later"): it is not part of the branches milestone. On 2026-11-25
he asked for it: "lets do this now" (D33, amended 2026-11-25).

Done when a grant can name a branch, a write on a branch is allowed by a grant naming it or by the table's grant on
every ref, the governance routes and the console show the branch, and a test on each store shows it.

From the security review of 2026-11-22 (finding 11, low, recorded by item 105): a branch's vended write credentials
cover the table's whole prefix, main's files included, so a group allowed to write only on `dev` could still write
main's files with them. A grant that names a branch needs credentials scoped to the branch rather than the table's
whole prefix; the catalog marks only a branch's metadata files (`<version>-<uuid>.branch-<ref id>.metadata.json`), so
the engines' data and manifest files would need a place of the branch's own too.

## What was done

- **Stores.** A grant may name a branch: `Grant.branch`, empty for a grant on every ref. A branch grant lives in a
  table or collection of its own, `ref_grant` (PostgreSQL V19, CockroachDB V18, Oracle V20, MongoDB step 15), so
  `grant_record` is unchanged and a server of the release before keeps working beside a new one. Reads go through the
  view `any_grant`, whose `ref_scope` is `*` or the branch's id (MongoDB: `$unionWith`). A branch grant locks the
  catalog, then the branch for update, then the securable (rule 8's order); a tag or a branch that is gone answers
  Missing REF. Deleting or merging a branch, dropping a namespace and purging an object delete its branch grants.
  `GrantSuite#aGrantMayNameABranch` runs on every store.
- **Authorization.** `Authorizer` takes the ref a request goes through, and a grant holds only on its own branch or,
  naming none, on every ref. A commit on a branch is allowed by a grant naming it or by one on every ref.
- **Only write and modify may name a branch**, since a commit is all a branch grant is for; reads and every other
  change still ask through main. A choice made here, which Paul may overrule.
- **Credentials (security finding 11).** A writer who may write through the branch but not main gets credentials that
  read the whole table and write only beneath `<table>/branches/<ref id>/` (`SessionPolicy`, `writeUnder` in the
  vending request, the cache key and the audit's `writePrefix`), and the load response sets `write.data.path` and
  `write.metadata.path` there, so the writer's files never land among main's. The ETag covers those places.
- **Routes.** Grant, revoke, preview and check take `"branch": "<name>"`; listings and exports name a branch grant's
  branch. A tag answers 400, a missing branch 404, and any privilege but write or modify 400
  (`PRIVILEGE_NOT_ON_A_BRANCH`).
- **Audit.** `grant` and `credential-issue` gain version 2 (`branch`, `branchId`; `writePrefix`). Each is written as
  version 1, as before, unless those fields are set, so a reader of the release before reads every record it could
  have written; the codec and the audit tables read both versions.
- **Console.** A branch grant shows as "write on @dev only" in every grants list, its revoke names the branch, the
  export's CSV has a branch column, and the ref notes say a grant of write or modify may name one branch.
- **Docs.** `docs/refs.md` describes branch grants.
- **Bites:** seven, in `bites/D33/` and `bites/D23/`.
