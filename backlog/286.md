# 286. demo.sh takes a deployment for gone only when kubectl says NotFound, so gen stop never stops Kafka under a running generator

Status: done
Done: 2026-11-25 on worktree-brokerage-routes
Added: 2026-11-25 by local_0484717c-9adc-4b18-af93-2db236201f4a
Touches: demo/demo.sh
Effort: S, two one-line checks in demo.sh made into one that retries, checked against a stub kubectl

Paul, 2026-11-25, told that `demo.sh gen stop` stopped Kafka but left the generator running: "Yes, fix it".

**What is wrong.** `running` (`k get deployment "$1" >/dev/null 2>&1`) and `cdc_running` (the same, for `backoffice`)
answer "not running" whenever kubectl fails, not only when the deployment is missing. While Windows pages the
Docker VM out, the API server times out, and a deployment that is there is taken for gone.

**The evidence.** On 2026-11-25, with Windows at 212 to 340 MB free and 20,000 to 48,000 pages in per second, the
first `demo/demo.sh gen stop` switched gen off, skipped stopping the generator (`running brokerage` failed) and then
stopped Kafka, Kafka Connect and kafbat, since nothing seemed to need them, leaving the generator running on route
kafka with no Kafka. A second `gen stop` found the deployment and removed it. Kafka kept the topics and Connect's
offsets on its volume, so nothing was lost. `cdc_running` has the same flaw: through `kafka_needed`, a timeout there
could stop Kafka under the CDC leg.

**What done looks like.** `running` says a deployment is gone only when kubectl answers NotFound. On any other
failure it asks again, each try bounded by a request timeout, for about three minutes, then stops the script naming
kubectl's last answer instead of guessing. `cdc_running` is `running backoffice`. A stub kubectl that times out
twice then finds the deployment gets "running"; one that answers NotFound gets "not running" at once; one that
never answers stops the script with its message.

**What was done** (2026-11-25). `running` asks `k get deployment <name> -o name --request-timeout=10s` up to 12 times,
5 s apart: it answers yes on success, no only when kubectl's answer says NotFound, and after the last try stops the
script with kubectl's answer (`kubectl could not tell whether deployment <name> is there: …`), so `gen stop`, `ss
stop`, `kafka stop` and every other caller never act on a guess. `cdc_running` is `running backoffice`. No caller runs
it inside `$(…)`, so the `exit` stops the script. Checked with `demo.sh`'s own `running` and `cdc_running` against a
stub `k`: two timeouts then the deployment gives yes after 3 calls and 2 sleeps; NotFound gives no after 1 call; a
kubectl that never answers stops the script after 12 calls and 11 sleeps, also inside an `if` as `gen_stop` calls it;
`cdc_running` after one timeout gives yes. Not run against the demo, which is down.
