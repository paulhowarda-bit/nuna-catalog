The prototype shows a catalog's and a namespace's properties (D45). Loading a namespace through Iceberg REST may
cover the namespace half. Nothing gives the console a catalog's own properties.

What done looks like: the console can read both, through an existing route where one fits, and a route test covers
any new one.

## Done

What the console uses for each half:

- **A namespace's properties:** the Iceberg REST load that already exists, `GET /v1/{prefix}/namespaces/{namespace}`
  (levels joined by `%1F`), answering `{"namespace": [...], "properties": {...}}`. It needs describe on the namespace
  (`loadNamespaceMetadata`). The console's `api.js` already calls it (`namespace(catalog, levels)`); its writes are
  `POST .../namespaces/{namespace}/properties`. No change.
- **A catalog's properties:** new, `GET /management/v1/catalogs/{catalog}/properties`, in
  `governance/CatalogProperties.java`. It answers `{"name", "kms-key-set", "legal-entity", "storage-profile": {"name",
  "kind", "endpoint", "region", "table-root", "allowed-prefixes": [...], "encryption": "sse-kms" | "bucket-default"}}`:
  the boundary the catalog was declared with (D28) and where its tables live. Anyone who holds something in the
  catalog reads it, as the catalog list shows it to them; any other caller gets 404 NoSuchWarehouseException, as for a
  catalog that does not exist, and the refusal is audited as `readCatalogProperties` (D18). The profile's access keys,
  STS role, maintenance principal, CA bundle path and KMS key ARN stay out; whether writes use a KMS key is said, not
  which.
- The Iceberg REST API has no catalog-level properties, and the catalog holds none of its own. The prototype's
  catalog `owner`, `comment` and `default-format-version` rows, and its "Set a property" on a catalog
  (`updateCatalogProperties`), have nothing behind them. A catalog's owner, like a namespace's, is a governance
  attribute (`GET /management/v1/catalogs/{catalog}/governance`).

The route is a `@RestController` found by component scanning, as every route in `governance/` is, so
`GovernanceWiring.java` is unchanged. It is not yet in `build-plan.md`'s M7 table: item 128 held `build-plan.md` (and
`bites/D45/`), so the claim left them out and the bite is in `bites/D18/`, the rule it guards.
