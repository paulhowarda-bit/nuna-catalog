# 320. demo.sh's aml_cases hold check fails at random under pipefail

Status: done
Done: 2026-11-27 on fix-hold-check
Added: 2026-11-27 by local_0484717c-9adc-4b18-af93-2db236201f4a
Touches: demo/demo.sh
Effort: S: two checks in one script, read whole instead of piped into grep -q.

## What is wrong

`gen` warned "brokerage.party, money_movement and compliance are not all governed: the world's sink stops at a table
the catalog closes until it is", though every step of `brokerage_backoffice_governance` had been done: each table
classified, money_movement and compliance regulated, the flagged tables flagged with their rules, the owners set and
the aml_cases hold placed (checked live on 2026-11-27; the sink went on writing all three for an hour after).

The function ends by asking whether aml_cases already has its hold: `tls_curl -fs … | grep -q '"placed-by"'`.
`grep -q` exits at its first match; `curl` can then fail writing the rest of the answer, and `demo.sh` runs with
`set -o pipefail`, so the pipeline fails though the hold is there. Ten runs of that pipeline against the live catalog:
one failed. On a miss the function posts the hold again. Only one hold stands, so that run's post failed (the Podman
machine was overloaded: load 83, Windows paging, the Kubernetes API timing out), the function returned 1 and `gen`
warned. Had the post gone through, aml_cases would have had a second hold. A read that fails outright, not only one
cut short, missed the same way: one in twenty while the machine was overloaded.

`brokerage_governance`'s done check (`… | grep -q '"regulated"'`) has the same race: a miss reruns the whole
world's governance (setting a value again changes nothing, but it is slow and can fail the same way).

## Done when

Both checks read the answer whole and then match it, and a read of aml_cases' governance that fails places no hold
but fails the step, so the next `gen` tries again.

## Done

2026-11-27: `brokerage_governance` reads the ledger's governance into `[[ "$(curl …)" == *'"regulated"'* ]]`, and
`brokerage_backoffice_governance` reads aml_cases' governance into a variable, failing the step if the read fails,
and posts the hold only when the answer has no `"placed-by"`. Twenty runs of the new check against the live catalog
under `set -euo pipefail`: the one miss was a failed request, which now places nothing. Not run in a live `gen`: the
Podman machine was overloaded at the time.
