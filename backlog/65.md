The nightly of the overnight run of 2026-11-19 (testing d34547f) failed

properties under 'keel.security' ... keel.security.issuers names no trusted token issuer".

The previous release is commit 2b1af36 (`catalog-tests-load/build.gradle.kts`), from before the rename to nuna (item
59), and it reads its settings under `keel.`. Since the rename `Stack.server` gives every server, the previous
release's too, its settings under `nuna.` only (`Stack.java:84-95`, and `TestS3.serverProperties`). The test passed
on 2026-11-18, the last run before the rename. The rename left the Flyway migrations alone, so only the settings
broke. It also renamed the default Kafka topics (`keel.catalog.audit` and `keel.catalog.changes` became
`nuna.catalog.audit` and `nuna.catalog.changes`), so old and new servers would also write two audit streams.

What done looks like: a server started from another jar than this release's gets its `nuna.` settings under `keel.`
and writes to this release's two topics; the next overnight run passes `RollingUpgradeTest`.

Done: `Stack.server` passes a server started from another jar than this release's through `PreviousRelease.settings`,
which renames `--nuna.` and `--logging.level.nuna.` to `--keel.` and `--logging.level.keel.` and adds
`--keel.audit.audit-topic=nuna.catalog.audit` and `--keel.audit.change-topic=nuna.catalog.changes`. The mapped names
are exactly the 13 `Stack` used before the rename, plus `TestS3`'s `keel.storage.` names; the two topic settings are
in 2b1af36's `AuditSettings`. Left: `RollingUpgradeTest` itself is an `overnight` test, so the next overnight run is
its check.
