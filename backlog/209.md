Evidence, 2026-11-23:

- The console's browser tests (`ConsoleBrowser`: six classes on the governance tests' server and `ConsoleSignInTest`)
  took 444 s of `catalog-server`'s 955 s of class time in the 2026-11-23 overnight heavy build, 35 tests, up from 334 s
  and 12 tests on 2026-11-19 (`.overnight/runs/*/heavy-results`). `ConsoleBrowserTest` alone has gone from 7 tests to
  22, with 167 waits and 76 page loads.
- Each class starts a Chrome container of its own in `@BeforeAll` and stops it in `@AfterAll`, although all six
  governance classes drive the same server: 3 to 19 s of each class ran outside its tests.
- Every wait polls the page every 500 ms, Selenium's default: a step that is ready a moment after the first look waits
  out the rest of the half second.
- Beside the nuna-demo stack the tests do not finish. The console session ran four browser classes by hand at 20:49
  with the demo up (`gen` and `ss` on, about 6.9 GB of Kubernetes' 7.5 GB requested): at 21:21 Windows had 295 MB free
  and paged about 2,800 pages a second, `docker stats` did not answer in two minutes, and the run had gone 34 minutes
  where the same classes take about 4 overnight, with sessions refused (`UnreachableBrowserException`) and waits run
  out, none of them the change's fault. Kubernetes' own API server restarted during the run.

Done looks like:

- The governance classes share one Chrome, started by the first that needs it and stopped when their server's test
  context closes; each test still opens a fresh browser profile. `ConsoleSignInTest`, on its own network, keeps one
  of its own.
- Waits poll every 100 ms.
- A browser test refuses to start Chrome while the nuna-demo stack's pods run, saying why and that
  `-Pnuna.demo-beside` runs it anyway.
- CLAUDE.md says so.

What was done, 2026-11-23:

- `ConsoleBrowser` keeps one container for the classes that join no network, the six on the governance tests' server,
  started by the first and kept while it runs and serves the same ports; `close()` ends only its session. A listener
  in `catalog-server`'s `META-INF/spring.factories`, `ConsoleBrowser.StopWithServer`, stops it when the test context
  whose `local.server.port` it serves closes. The module's test jar, which `catalog-maintenance`'s tests use, leaves
  that file out. `ConsoleSignInTest`, on Keycloak's network, keeps a container of its own.
- Waits poll every 100 ms.
- Before a browser container starts, Docker is asked for containers labelled `io.kubernetes.pod.namespace=nuna-demo`;
  with any running, it refuses, saying why and that `-Pnuna.demo-beside` runs the tests anyway (a Gradle property that
  `catalog-server`'s test task passes as the system property `nuna.demo-beside`).
- CLAUDE.md (Builds) says both.

Checked: the module's tests compile; the test jar holds `ConsoleBrowser` and no `spring.factories`; the fast build
passed, its Spring Boot applications in `catalog-server` (`ExportNeedsEndpointTest`) starting and closing with the
listener registered. The label query, run as `docker ps`, listed the demo's 15 running containers.

Not checked: the shared container, its stop and the refusal against Docker. A run of two browser classes and a later
context was refused by this session's permission check while the demo was down for the console session's own browser
tests. The overnight heavy build is the first run of them.
