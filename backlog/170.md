Effort: M, a read of which live refs hold an object (and the drop's actor, from the drop's journal or audit record), a fast route test with bites, and three states on the table page

Atelier's design (`docs/design/console/wireframes.html`, chapter 6, 6.4) draws three edge states of a table page
that item 109's eleven gaps do not cover, each marked "gap" in the design:

- Dropped on main, read on main: the catalog's `404 NoSuchTableException`, then "{actor} dropped it on {time}. Main
  has no such table. A ref made before then still reads it: @{ref}, …", or "No ref holds it." Needs which refs hold
  a path, and the drop's time and actor.
- Dropped on main, read through a ref: a "Dropped on main {d Mon}" pill and "{actor} dropped {path} on main on
  {time}. @{ref} was made before then, so it still reads the table as it was; main answers 404 for it." Needs the
  drop's time and actor.
- Made after the ref's point, read through the ref: the catalog's 404, then "{path} was made on {time}, after
  @{ref}'s point, {cut}. A ref holds only what main held then." Needs the table's making time and the cut's time
  (item 168).

Item 109 shows the catalog's 404 as it answers, verbatim, in each case, without the words after it. The merge's dry
run already gives a dropped table's `dropped-at` (item 107), but not who dropped it.

Done looks like: a route (or a field on an existing answer, the builder's choice) that names the live refs holding an
object by id or path, and the drop's actor and time; fast tests with bites in `bites/D33/`; the three states on the
table page with the design's words.

### The read (from 279, "What it stands on")

- **No read lists the refs that keep a table.** `RefRoutes` calls `store.listRefPointers(object.id())` only inside the removal. Item 170 needs the same fact. Build it once, in 170, which is starting now, and have 279 wait on it. If 279 starts first, it builds the read to this spec and 170 adds the drop's actor.
  - **The read:** by path (namespace and name; the route's shape is the builder's choice) and by id. For each table or view at that path that is not purged, live or dropped, newest first:
    - `id`, `kind`, `state`, `dropped-at`, `dropped-by`, `purge-after`;
    - `refs`: each ref whose cut keeps it, with `name`, `kind`, `created-at`, `expires-at`, `expired` (past expiry, name still held), and `own-version` (a branch's own pointer for it, if any);
    - `may: {remove}`: whether the caller holds `manage-tags` on it.
  - Objects the caller holds nothing on are left out. It is gated by `describe`, with a 404 for a caller holding nothing, as Holdings does.
- **Why not Overview:** Overview, Schema and History load through `loadTable`, which needs `select` (`Guard.LOAD_TABLE`). A tag steward (the TAGS duty, kept apart from DATA by D18) may not hold it. A dropped table also answers 404 on main by path, so the governance read that gives the console its object id fails too.

### 170 (a table dropped on main, or made after a ref's point): three changes

1. **The read serves 279.** It is the read in the spec above. It lists every dropped object at the path, not only the newest (a name dropped, made again and dropped again is two objects).
2. **A fourth state** from item 156, which came after my 2026-11-22 design: a table taken out of the ref answers the same 404 through it. Without this state the console would wrongly say "made after the point".
   - If main's object at the path was made before the ref's point and the ref does not keep it, show the catalog's 404, then `@{ref} no longer keeps {path}, though main had it at the point: it was taken out of it.`
   - Add ` {actor} took it out on {time}.` when the audit is readable, through 169's subject filter.
3. **The words move to the verb "keeps".**
   - "Dropped on main, read on main" ends `A ref made before then still keeps it: @{ref}, …`, with 279's button for `may.remove` and 279's steward line for others. `No ref holds it.` becomes `No branch or tag keeps it. Cleanup can purge it and delete its files.`
   - "Dropped on main, read on a ref" adds `It stays readable here, and its files stay, until it is taken out of every branch and tag that keeps it.` The phrase `taken out of` links to the Access tab's panel.

### The read
- `GET /management/v1/catalogs/{c}/namespaces/{ns}/objects/{name}/refs` (by path) and
  `GET /management/v1/catalogs/{c}/objects/{id}/refs` (by id): `RefRoutes.keptAt` and `kept`
  (`catalog-server/src/main/java/nuna/catalog/server/governance/RefRoutes.java:1023`, `:1037`). By path it gives the
  live object, then every dropped and purging one at the path, newest drop first (`atPath`, `:1060`); by id the one
  object until it is purged or unregistered. Answer: `{objects: [...]}`, each with `id`, `kind`, `namespace`, `name`,

  {principal, end-user}`; `refs` (each ref whose cut or own pointer keeps it, by name: `name`, `kind`, `created-at`,
  `expires-at`, `expired`, `own-version`); `may.remove` (`manage-tags` on it) (`keptObject`, `:1120`).

  caller holds nothing on is left out; when that leaves none, the refusal is audited through `ManagementGuard.require`

  `dropped-at` and a second after, matched by the object's id, only for a caller who holds `select` on the audit
  catalog; each lookup is audited as an `AuditRead` of the object.

## The Nuna Security Expert's review, 2026-11-25: two fixes

Relayed by the coordinator: what the read discloses is clear; two fixes before landing, one check, one heads-up.

1. **Rate limit.** `AuditDrops.droppedBy` calls `feed.page` once per dropped object, and nothing limits it, which gets
   around the feed's per-caller limit. Count each lookup against that limiter, or look up `dropped-by` for the newest
   5 drops only and leave it out for the rest; either way the answer says when it was left out, and the console words
   handle that.
   - Built: the newest `RefRoutes.DROPPERS_READ` (5) drops the caller may describe are looked up; each past them has
     `dropped-by-left-out: true` and no lookup. The console takes the words without an actor for those.
     `RefRoutesTest#whoDroppedItIsLookedUpForTheNewestFiveDropsOnlyAndTheRestSayItWasLeftOut`; bite
     `bites/D33/ref-kept-droppers-unbounded`.
2. **Bound `atPath`.** It walks every dropped and purging object of both kinds in the namespace to match one name.
   - Built: the store has no lookup of dropped objects by name (`CatalogObjectStore.findObject` finds the live one
     only), and adding one means a query and a heavy suite in each of the four stores, so the walk stops once it has
     read `RefRoutes.KEPT_WALK_LIMIT` (10,000) objects, and the answer adds `cut-short: true` with what it found. The
     page then says, under the dropped tables on main: "The catalog stopped looking before it had read every dropped
     table in this namespace, so an earlier table at this path may be missing here." (the builder's words; Atelier has
     not seen them). `RefRoutesTest#theWalkOfANamespacesDroppedObjectsStopsAtItsLimitAndSaysSo`; bite
     `bites/D33/ref-kept-walk-unbounded`.
3. **Confirmed:** a path the caller holds nothing on answers the same 404 as one with nothing there, the refusal
   audited. `RefRoutesTest#whichRefsKeepATableNeedsDescribeAndOffersTheRemovalOnlyWithManageTags`: hugh, holding
   nothing on `sales`, gets `404 NoSuchObjectException "No table or view sales.orders in gate"`, the same shape as
   `hr.nope`, which does not exist; the refusals are audited as `readObjectRefs` denials of `describe` on
   `sales.orders`, and a path with nothing adds none ("nothing there is no refusal").
4. **Heads-up:** item 169 adds `branch` and `subject` to `EventsReader.Query`; whichever lands second adds two nulls to
   the `EventsReader.Query` that `AuditDrops.droppedBy` builds.
