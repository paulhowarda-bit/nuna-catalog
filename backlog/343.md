# 343. Podman's VM runs short of contiguous memory and Windows' connections to test containers hang: Cockroach and conformance tests fail together

Status: open
Decided: 2026-11-28, D57
Added: 2026-11-28 by local_a0cd9c35-a22f-4dde-8b48-c0c950e2d9e0
Touches: deploy/kind/kind.sh, the Podman machine's settings (outside the repo)
Effort: S, two kernel settings in the Podman machine

The heavy build of 2026-11-28 (by hand, 06:26 to 07:19) failed 6 of `CockroachStoreSuiteTest`'s 218 tests and
`ClientOperationsTest#expiryOnAHeldTableIsRefused`, all between 06:59 and 07:06, all the same way: a connection
from Windows to a container's mapped port was accepted and then never answered. The Cockroach tests read
`SocketTimeoutException: Read timed out` in the driver's SSL negotiation (`enableSSL`) or in Flyway's first
connection; the conformance test's S3 `putObject` to the silo container timed out six times over 187 s, and its
server logged nothing from 11:59:59 to 12:06:53 UTC.

Cause: the environment. The Podman machine (WSL2, 7,785 MB) runs out of free contiguous memory and its kernel cannot
open the VMBus channels that carry Windows' connections into it. Its kernel log, `page allocation failure: order:7
... Workqueue: hv_pri_chan vmbus_add_channel_work`, with about 110 MB free and 3.9 GB of page cache, per minute:

```
06:37 1, 06:51 1, 06:59 4, 07:00 4, 07:01 4, 07:02 4, 07:03 4, 07:04 3, 07:05 4, 07:06 4, 07:07 4, 07:08 3, 07:09 4
```

The burst starts when `catalog-tests-conformance` started its stack (PostgreSQL, the S3 store, Kafka) beside the
Cockroach cluster (three nodes and Toxiproxy), which `org.gradle.workers.max=2` allows. It happened again on a rerun
of `CockroachStoreSuiteTest` alone the same morning: all six earlier failures passed, but at 07:48 another agent's
catalog-server stack (PostgreSQL, the S3 store, Kafka, then Chrome) started beside the cluster, the kernel logged
eight failures from 07:48:48 to 07:50:55, and `Refs: of creates racing for a catalog's last places` failed at 07:49
with the same `Read timed out` while connecting. Windows was short too (473 MB available, 22,000 pages read in a
second, `vmmemWSL` 3.4 GB resident of 8 GB), but the VM's own log shows the failure that matters.

So "a three-node cluster plus one other stack is what fits" holds for RAM but not for the kernel's contiguous
memory. Either fix belongs to Paul's call, since one changes the machine and the other his rule on what runs at once:

- the machine: in the Podman machine raise `vm.min_free_kbytes` (45056 now) and `vm.compaction_proactiveness` (20
  now), persistently, so order-7 blocks stay free; or
- the build: run `catalog-store-sql-raft`'s tests on their own in the heavy build, as `./nightly.sh` runs its first
  step with `--max-workers=1`.

Done when a heavy build runs the Cockroach suite and the conformance tests with no `page allocation failure` in the
machine's kernel log over their run, and neither fails on a connection that read timed out.

Running the suite alone settled it (08:07 to 08:18, `podman ps` listing no other test containers): 3 of 218 still
failed on connections that never answered (`could not connect`, `schema migration failed`, `The connection attempt
failed`), and the kernel logged `page allocation failure: order:7` at 08:17:12, 08:17:50 and 08:18:12. The
three-node cluster alone breaks the free memory up, so running it alone is no fix.

Paul, 2026-11-28: "Tune the Podman VM". Set at 08:31 in the machine, in `/etc/sysctl.d/90-nuna-memory.conf` (read at
every boot): `vm.min_free_kbytes = 262144` (was 45056) and `vm.compaction_proactiveness = 50` (was 20).
`deploy/kind/kind.sh up` writes the same file when it is missing, so a recreated machine gets it.
