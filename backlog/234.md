# 234. Demo SingleStore refuses order writes once its pipelines' extractors fill the table-memory cap

Status: done
Done: 2026-11-24 on worktree-singlestore-table-memory
Added: 2026-11-24 by local_0484717c-9adc-4b18-af93-2db236201f4a
Touches: demo/k8s/singlestore.yaml
Effort: S, one SingleStore global in the demo's manifest

On 2026-11-24, at the first live trading of the brokerage world (D48, real clock, item 181), the generator crash-looped
(CrashLoopBackOff, 4 restarts) within minutes of 09:30 New York: "order 1401 was not written", SingleStore answering
"Leaf Error (127.0.0.1:3307): Memory used by MemSQL (1740.50 Mb) has reached the 'maximum_memory' setting". The leaf's
`Total_server_memory` sat at 1,740 MB, its `maximum_table_memory`, while its tables held only 240 MB: the pipelines held
1,237 MB (`Alloc_pipelines`), the Java extractors SingleStore runs for them (two change feeds at `-Xmx384M`, three
Iceberg extractors), which it counts against the leaf's memory. So the leaf refused every write.

The dev image sets `maximum_table_memory` to 63% of `maximum_memory` (2,764 MB of the 3Gi limit). Done looks like: the
demo's SingleStore sets it to 2,400 MB on both nodes (`SINGLESTORE_SET_GLOBAL_MAXIMUM_TABLE_MEMORY`, which the image's
start script applies with `--all`), leaving the master aggregator its own ~560 MB inside the 3Gi limit, and the
generator writes orders through a trading day. Set by hand on the running demo the same day (`SET GLOBAL` on the
master and on the leaf, port 3307); the generator then caught up and wrote orders live.

Done: `demo/k8s/singlestore.yaml` sets `SINGLESTORE_SET_GLOBAL_MAXIMUM_TABLE_MEMORY=2400`, which the image's start script
applies to the master and the leaf. The running demo got the same value by `SET GLOBAL` on both nodes; its leaf then
fell to 1,272 MB once the generator restarted, and orders came in live (1,413 at 09:42 New York). The manifest's
variable takes effect at SingleStore's next start (the next `up`, or `ss` after `ss stop`), not yet seen there.
