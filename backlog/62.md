What was done: the cause was the test's budget, not export. Its 20 s covered a cold JVM on the whole test class path,
the worker's Spring context and the first export, and beside a heavy build's tests that start alone can take longer:
on 2026-11-19 the worker's context in the test JVM (the in-process case) took 74 s to start, against about 3 s
usually. `theStandardVariablesAloneTurnExportOn` now waits first for the worker's own `Started WorkerApplication in …`
line in `worker.log`, for up to 5 minutes (`START`), and only then gives `ARRIVAL` (20 s) to the metric and the log
line, as the in-process case already does (its `SpringApplication.run` returns only once the context has started).
Every failure now carries `worker.log` (all of it, or its last 80 lines), and says which it was: "the worker did not
start within PT5M", "the worker exited with <code> before it started", or "no matching metric arrived within PT20S
after the worker started". The start line goes to the test's output, so each run's results show how long the start
took. Measured with the class alone (`:catalog-maintenance:test --tests 'nuna.maintenance.TelemetryTest'`, 2026-11-19):
six cold starts took 5.8 to 8.4 s ("process running for"), and the metric arrived 1.2 to 1.9 s after the start line.
The three failure messages were checked once with temporary tests (a worker missing its settings, a 0.5 s allowance,
an endpoint nothing listens on), then removed.
