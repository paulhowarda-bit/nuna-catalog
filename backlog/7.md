# 7. Oracle and MongoDB stores answer an outage with 503, not 500

Status: done
Done: 2026-11-19 on worktree-agent-abefa39293b4b238c
Added: 2026-11-14 by Change Manager, from build-plan.md at Paul's request
Effort: L, two store modules, each with its own driver errors and a heavy fault test

`build-plan.md`, M8 follow-ups: the Oracle and MongoDB stores do not raise `StoreUnavailableException`, so a
database outage there answers 500 where PostgreSQL answers 503 with Retry-After. Still so on 2026-11-14: neither
store module's main code names the exception.

Done when both stores raise it for a database that cannot be reached, is failing over or is out of connections,
when nothing was applied, and a heavy test on each shows a 503 with Retry-After.

Done: each store now classifies in one place, its `Transactions.failed`, as the PostgreSQL store does. It is used on
every path before COMMIT is sent and by `findCommit`, so the commit engine's read-back waits within its budget there
too. A failed COMMIT of a write that carries an id stays `CommitOutcomeUnknownException`.
- Oracle counts as unavailable what ojdbc 23 raises as `SQLRecoverableException` (ORA-00018/00020 sessions or
  processes exhausted, 00028, 01033/01034/01089/01090/01092, 03113/03114, 12514, 16456, and its own 17002/17008/
  17410), any Oracle Net error (SQLState 66000: a refused connect is ORA-12541, the listener's 12516/12519/12520/
  12521/12528 among them), connection classes (08, the connect timeout ORA-12170), ORA-03135 and ORA-16000 (a write
  that reached a standby), and a pool's timeout (`SQLTransientConnectionException`, HikariCP's), looking through a
  pool's wrapping (UCP's UCP-29) to the driver's error.
- MongoDB counts as unavailable what the driver's retryable-writes rules retry on (socket errors, not primary,
  recovering, a cleared pool, the retryable codes), `MongoTimeoutException` (no server, or no pooled connection, in
  time), and NoSuchTransaction (251) only with the TransientTransactionError label, for a new primary that never saw
  the transaction. A write conflict carries that label too and stays a plain failure.
- Tests: `UnavailableFailuresTest` in each module (Java only: the drivers' own exceptions and codes, and each store
  against a local port that refuses or drops the connection); the shared suite's
  `CommitSuite#linkDownBeforeCommitIsACleanFailure` now requires `StoreUnavailableException` from commit and read on
  every backend; `MongoStoreSuiteTest#commitWhileFailingOverIsUnavailable` (new) commits with the primary killed and
  no new one elected. Bites: `bites/M8/store-outage-not-recognised-{oracle,mongo}.patch`, recorded, not run.

Left: the 503 with Retry-After is shown at the store, not at the routes. The routes' mapping is store-independent, but
no test runs the server on Oracle or MongoDB with the database away: item 70 (`catalog-server` was held by other
agents). UCP's own exhaustion (UCP-29 over UCP-45064, all connections in use, with no driver error beneath) is not
classified; the server pools with HikariCP, whose timeout is. Not run here: the heavy suite cases above, which need
Docker; they run in the overnight heavy build.

Found by the heavy build of 2026-11-22, its first to reach the Oracle suite since this landed: Oracle's
`UnavailableFailuresTest#aConnectionDroppedAtOnceIsUnavailable` and `CommitSuite`'s "link down before the commit"
case got a plain `StoreException`. When the other end closes the connection during logon, ojdbc raises a plain
`SQLException` with ORA-17800 ("Got minus one from a read call") as often as a recoverable one: 128 of 300 repetitions
of the dropped-connection test failed. `Transactions.UNAVAILABLE_ERRORS` now holds 17800, and the ORA list in
`UnavailableFailuresTest` names it; 300 repetitions then passed, and both cases passed in two full heavy builds
(`worktree-heavy-fixes`). The bite `bites/M8/store-outage-not-recognised-oracle` still applies.
