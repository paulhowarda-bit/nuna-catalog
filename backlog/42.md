# 42. Per-table health metrics from commit summaries (Paul decides)

Status: open
Added: 2026-11-15 by Iceberg observability review, at Paul's request
Touches: none

Every commit carries a snapshot summary, and the table spec names optional totals in it: `total-data-files`,
`total-delete-files`, `total-position-deletes`, `total-equality-deletes`, `total-records`, `total-files-size`
(`spec/spec.md`, "Optional Snapshot Summary Fields"). The catalog sees each summary as it commits, so it could report
each table's file count, average file size and delete build-up without reading any object store. Those are the
signals that a table needs compaction or a delete rewrite before its readers slow down. Not every writer fills in the
totals; a missing one must show as missing, never as zero.

The question for Paul: where should per-table figures go?
- **Prometheus metrics labelled by table.** Grafana can chart and alert per table. Each table adds about six series:
  ten thousand tables make sixty thousand, which work's Prometheus team may refuse, and table names land in the
  metrics store.
- **One structured log line per commit, with only table-free distributions as metrics** (for example, files per
  table across all tables). Nothing per table reaches Prometheus; per-table questions are answered from work's log
  store, if it has one.
- **Not now.** The maintenance worker already acts on tables; this waits.

Done when Paul has decided, the decision is in the ledger, and an item for the work exists if he wants one.
