# 72. Oracle's self-check does not notice a journal-partition job that cannot run

Status: done
Done: 2026-11-20 on worktree-agent-a8afb8a5ef014bf7a
Decided: 2026-11-20, D8
Added: 2026-11-19 by agent-a3dc4bb4c858dc2c8, from item 9

Effort: S, one more query in one store's self-check and a heavy test

Oracle keeps its journal's horizon with migration V5's Scheduler job, `JOURNAL_PARTITIONS_AHEAD`, which creates
this month's partition and the next two every day (item 9 checked it; `OracleStoreSuiteTest#
schedulerJobCreatesJournalPartitionsAhead`, heavy). The job runs only while `JOB_QUEUE_PROCESSES` is not 0, and
only while it stays enabled and keeps succeeding (V5's own comment). When it does not run, nothing says so: the
store's `selfCheck()` reads `V_$PARAMETER` for other findings but not `job_queue_processes`, nor the job's
`enabled`, `state` or `failure_count` in `user_scheduler_jobs`. Interval partitioning still takes every commit, but
each month's first commit then creates its partition inside the commit, which took 0.5 to 2.6 s on Free (M2b) and
can run past the pool's read timeout, which fails that commit (docs/storage-design.md, M2b deviation 9).

Done when the self-check reports a job that cannot run (`job_queue_processes` 0, the job missing, disabled or
failing), with a heavy test that disables the job on a fresh schema and finds the report.

Paul decides: since item 6 (D8, amended 2026-11-19) the server refuses to start on any self-check finding. Should a
job that cannot run refuse the start, as the other findings do, or only be reported (the commits still land)?

**Decided 2026-11-20 (D8, amended):** a journal-partition job that cannot run is a finding like the others and refuses the start, unless the operator allows it by its code ("Refuse, like others").

**Done 2026-11-20.** `OracleCatalogStore.selfCheck()` reports one finding, `ora.journal-job-down`, when the job
cannot run, its detail naming each cause and what to do: `job_queue_processes` is 0 (read from `V_$PARAMETER` with
the other parameters); the job is missing from `user_scheduler_jobs` once the schema has V5; it is disabled, BROKEN,
or ended (COMPLETED, FAILED, SUCCEEDED); or its last 2 logged runs (`user_scheduler_job_run_details`) both failed,
with the newest run's ORA error. Like every finding it refuses the start unless `nuna.database.allow-unsafe` names
it. The judging is `JournalJob.judge`, pure; the reads need no new grant. `docs/storage-design.md` lists the code
(section 7) and the choices (M2b deviation 9).

- A missing job counts only once the schema is at V5 or later: the server runs the self-check before `migrate()`
  (item 6), so on a fresh schema the job does not exist yet, and every first start would refuse.
- "Keeps failing" is the last 2 logged runs both failed, with no success after them. One failed run is not: the
  last success made this month's partition and the next two, so nothing runs short for a month or more, and the next
  day's run puts a transient failure right. A success clears it. `failure_count` is not used: the Reference gives it
  as the times the job has failed, not since its last success, so one old failure would refuse every start.
- The test containers run the job: `schedulerJobCreatesJournalPartitionsAhead` (heavy, the same image since M1)
  finds its first run with `failure_count` 0, and passed in the heavy passes of 2026-11-10 and 2026-11-12. So the
  server's test settings still allow only `ora.no-data-guard` for Oracle.

Tests: `JournalJobTest` (Java only, 12 of 12 passed); in `OracleStoreSuiteTest` (heavy)
`selfCheckReportsAJournalJobThatCannotRun` (a fresh schema: none as V5 makes it, then disabled, enabled, dropped)
and `selfCheckReportsAJournalJobThatKeepsFailing` (its procedure made to raise ORA-20072, run with `RUN_JOB`: none
after one failure, reported after two, none once a run succeeds); `OracleFree` stages the code for the shared
self-check tests. Bite `bites/M8/oracle-journal-job-unchecked.patch`, checked with `git apply --check`, not run.
