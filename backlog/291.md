# 291. Heavy tests on Podman: a Docker call made after 10 s without one fails, since Podman's API closes idle connections and Testcontainers reuses them (TwoIssuersTest)

Status: done
Done: 2026-11-26 on worktree-agent-a9b0e66eec65621d8
Added: 2026-11-26 by Paul (2026-11-26, item 26's gate)
Touches: settings.gradle.kts build.gradle.kts catalog-tests-docker/ bites/
Effort: S, one small test-support module and one line in the root build; the heavy tests that failed are rerun

Since the move to Podman (item 287), `catalog-server`'s `TwoIssuersTest` fails all three tests in the gate run of
2026-11-26: the Spring context does not load, with `NoHttpResponseException: localhost:2375 failed to respond` under
`CreateContainerCmdExec`, creating `postgres:18.7`. Its log shows the Keycloak container starting at 14:04:42, its
wait taking 36 s, then the PostgreSQL create failing 3 ms after it was sent. `ConsoleSignInTest` and `SpanTreeTest`
failed the same way that morning, with Keycloak or Kafka.

Cause: Podman's API service (`podman system service`, run by the machine's `podman.service` with no `--time`)
closes a keep-alive connection idle for 10 s. Measured through `//./pipe/docker_engine` on 2026-11-26 by sending
`GET /_ping` twice on one connection: answered after 9 s idle, an empty read after 10 s. Docker Desktop never closed
one. docker-java's pool (in Testcontainers) keeps connections forever and never checks them before reuse
(`validateAfterInactivity` -1), so the first request after a quiet spell goes out on a dead connection. A GET is
sent again by the HTTP client and succeeds; a POST (create container, exec, start) is not, and the test fails. Any
heavy test whose fixture starts a container, or execs in one, after 10 s or more without a Docker call can fail so:
here, a container started after another's long wait.

The fix (`catalog-tests-docker`, `FreshPipeStrategy`, named by the root build in
`TESTCONTAINERS_DOCKER_CLIENT_STRATEGY`) has a side effect outside the repo: Testcontainers takes a strategy it is told
to use only if it may record it, and it writes `docker.client.strategy=nuna.catalog.tests.docker.FreshPipeStrategy`
to `~/.testcontainers.properties` on every nuna test run. Another project's JVM, without the class on its path, reads
that line, logs "Can't instantiate a strategy from nuna.catalog.tests.docker.FreshPipeStrategy
(ClassNotFoundException)" and falls back to Testcontainers' own pipe strategy, then writes that one back. Its tests run
as before, with Podman's 10 s problem unfixed for them. A nuna test run from an IDE without Gradle gets the strategy
from that file while the class is on its path.

Done looks like: every test JVM's Docker client never reuses a connection older than Podman keeps an idle one, a
heavy test showing that a POST after 12 s idle succeeds, and `TwoIssuersTest`, `ConsoleSignInTest` and
`SpanTreeTest` passing on Podman.

What was done (2026-11-26): `catalog-tests-docker` holds `FreshPipeStrategy`, Testcontainers' named-pipe client with
a 5 s time to live on pooled connections, set by reflection, since docker-java offers no setting for it. The root
build puts the module on every module's test runtime path and names the strategy in
`TESTCONTAINERS_DOCKER_CLIENT_STRATEGY`, so the fix covers every module, not one suite. It applies on Windows only;
elsewhere Testcontainers picks its usual strategy. `FreshPipeStrategyTest` (heavy) waits 12 s and then sends a POST.
Bite `TEST-291/connections-reused-at-any-age` fails it with the gate's own `NoHttpResponseException`. Results are in
`status/2026-11-26-two-issuers-on-podman.md`.
