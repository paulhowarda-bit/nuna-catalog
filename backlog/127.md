The overview's ice line draws every table at once (D45). A table in shape sits above the line. A queued table hangs
below it, deeper the higher its score. `GET /management/v1/maintenance/tables` lists only the neediest tables, so it
cannot draw the tables in shape (wireframes.html, overview note 3).

What done looks like:
- One row per table the caller may `select`, giving:
  - its score and reasons;
  - its data-file count;
  - any hold or freeze, and whether it is closed until classified;
  - whether last night fixed it.

  The read is paged, for a large catalog.
- Route tests, including that a table the caller may not select is not counted.

What was done (docs/observability/table-health.md, "Every table", has the whole of it):

- **The read** is `GET /management/v1/maintenance/estate?pageSize=&pageToken=`, in `MaintenanceRoutes`, built by the
  new `MaintenanceEstate`. It answers `night` and a page of `tables`. Each row gives the table's id, catalog,
  namespace and name, its `assessment` (`assessed-at`, `needs-compaction`, `reasons`, `score`, `data-files`), and
  `held`, `frozen`, `closed` and `fixed-last-night`. `next-page-token` is there while more may follow.
- **Tests:**
  - `MaintenanceEstateTest` (fast, 7 tests): the real route and authorizer over a store double;
  - `MaintenanceEstateRoutesTest` (heavy): the route through the server, with real reports, holds, freezes, grants
    and classifications.
- **Bites:** five, in `bites/D45/`, each against `MaintenanceEstateTest`, each run here and biting.

The choices, settled on the recommendation that fits D30 and the existing maintenance reads:

- **The path** is `/management/v1/maintenance/estate`, the name the wireframes give it.
- **Every catalog, by id.** The rows walk the active tables as the work list does (`listActiveObjects`), each naming
  its catalog, like the neediest list and the nights. There is no `catalog` filter: the ice line draws every table,
  so the console reads every page and groups the rows itself.
- **Who counts.** A row is given when the authorizer allows `select`, the operation `listMaintenanceEstate`. A table
  closed until classified (D27) also counts, with `closed` true, for a caller whose grants give `select` on it. The
  authorizer refuses such a caller `select` only because of the closure, so the caller holds the grant, and D27 keeps
  the table's name open (describe stays allowed). Otherwise `closed` could never be true, since the authorizer refuses
  `select` on every closed table. A caller with no `select` grant never sees the table, closed or not.
- **No totals.** Counting across pages would read every table on every call. The console counts the rows it has
  read.
- **Paging** is as the neediest list pages: `pageSize` 200 by default, from 1 to 500, and at most 2,000 tables looked
  at a page. A page may hold fewer rows, even none, with a token. The token is the store's own.
- **Held and frozen** mean a hold or a DR freeze on the table or on any level above it, as the governance summary
  counts them (item 128).
- **Last night** is the newest night that has a job, as `GET /management/v1/maintenance/nights` counts it. Each page
  names it in `night`. A table was fixed last night when that night's compaction Job of it succeeded. A Job cut off,
  failed or running fixed nothing. The read takes one listing of that night's compaction Jobs.
- **The assessment** gives only what the ice line draws: the verdict, reasons, score and data-file count. A table's
  health route gives the rest.
- **No store change.** Each row's health is read with the existing `readTableHealth`, one read per row on the page.
  Holds and attributes are read in batches of 500 levels, as the governance summary reads them. A store read that
  joins health to the active tables would take one query a page instead, but would add a method to all four stores.
