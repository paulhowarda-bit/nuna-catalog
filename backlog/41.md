What was done: each call a request makes to the catalog store (on any backend), to the object store for metadata
files, to STS for AssumeRole, and each synchronous audit publish to Kafka up to its acknowledgement, is a Micrometer
Observation: a child span of the request's and a timer (`keel.store`, `keel.objectstore`, `keel.sts`,

(`keel.catalog.server.tracing`) are applied where the collaborators are wired; the stores, catalog-audit and
catalog-objectstore are unchanged. A failed call's span names the exception's type, never its message. Calls made
outside a request (the outbox relay, the archive, startup) are not observed, so they start no traces of their own.

With 38, a request gets a server span and nothing beneath it. A slow load or commit cannot be split into the
database, the object store, STS and Kafka, which is the split anyone at work will ask for first: every load waits for
the read audit's Kafka acknowledgement (D23), and every commit writes metadata to the object store and moves the
pointer in the database.

Done when each of these is an Observation (one span and one timer), named for what it does, with its outcome:
- the store's transactions (the commit's pointer move, reads), on whichever backend is configured;
- metadata reads and writes on the object store;
- STS AssumeRole for a vend;
- publishing an audit event to Kafka, up to its acknowledgement.

And:
- Attributes are bounded and name no person, table path or credential; no span carries a filter value, a key or a
  token.
- A test with an in-memory span exporter shows a commit's span tree (server span, then store, object store and Kafka)
  and a load's (server span, then Kafka). The tree is recorded as a bite in `bites/OBS-41/`.
- `docs/observability/spans.md` lists the spans and their attributes.
