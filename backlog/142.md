agent found three that still answer 403 and publish nothing:

- A namespace drop refused by a legal hold: `NamespaceRoutes.java`, line 201, `Http.forbidden(... "is under a legal
  hold and cannot be dropped")`.
- A snapshot removal refused by the minimum snapshot age: `Rules.snapshotMinimumAge` (`Rules.java`, line 104) returns
  a plain rejection, which reaches the client as a `CommitReply.Failure` with no refusal.

denial on any of them. Item 134's report also notes that the view routes and the table register route call
`Guard.refused` but have no test of their own.

What was done (2026-11-22):
- Each refusal above publishes a `nuna.catalog.denial` record through `Denials`, naming the operation and the object,
  with the reason and then the message the caller gets. The answer is unchanged: 403 ForbiddenException, same message.
  - Namespace drop under a legal hold: `NamespaceRoutes.drop` refuses through `Guard.refuse`, which gained an overload
    for a namespace: `dropNamespace` on the namespace, reason `legal_hold`. Like item 134's table drop, the refusal is
    now `AccessDenied`, not a `CatalogError`, so an idempotency key no longer records this 403 and a retry runs
    afresh.
  - Snapshot removal younger than the minimum age: `Rules.youngestRemoved`, which the deployment's minimum and a
    retention class's both use, rejects with `Rejection.refused("snapshot_min_age", ...)`. The engine passes the
    reason on as `CommitReply.Failure.refusal`, and the routes' existing `Guard.refused` call publishes it:
    `updateTable` on the table, or `commitTransaction` for a transaction.
  - Unregister the store refuses as flagged: the engine answers `WriteResult.Reason.FLAGGED` with
    `Failure.refused(object, "flagged", ...)`, which `TableRoutes.unregister`'s `Guard.refused` call publishes. Nothing
    audited it before. `TableRoutes.unregister` audits the refusals it makes itself through `Guard.refuse`
    (`regulated`, `flagged_table`), but they come before the engine runs; the store answers `FLAGGED` only when a
    steward set a flag after that check, so one request never gets two denials. The reason is `flagged`, not either
    existing one: the store answers `FLAGGED` for a regulated flag and a row/column-policy flag alike and does not say
    which.
