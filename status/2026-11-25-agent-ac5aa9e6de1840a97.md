# 2026-11-25, backlogs 158 and 171: the catalog's row first, and held levels locked before holds are read

- 158: a namespace drop now takes turns with a ref create in flight. On PostgreSQL and CockroachDB it locks the
  catalog's row `FOR SHARE` first, and on Oracle `FOR UPDATE`. On MongoDB it writes the catalog's `trimmed`, so a
  create cuts again and the open insert conflicts with the drop.
- 171: a purge claim and a removal from refs lock the catalog's row (the claim only; the removal already did), the
  object and the namespaces above it before they read holds and freezes. On PostgreSQL and CockroachDB those locks are
  shared, so a hold or DR freeze placement now locks its target for update. On Oracle every lock is for update. On
  MongoDB the writes mark the catalog and the namespaces.
- `docs/storage-design.md` section 9 (f) rule 8 gives each write's lock order and why no cycle can form.
- Tests: `SqlLockOrderTest` (fast, 4 tests, passing, run with `./gradlew :catalog-store-sql:test --tests
  SqlLockOrderTest`). Three heavy suite cases, on all four stores, are written and compiled but not run:
  `RefSuite#aNamespaceDropWaitsForAnOpenRefCreate`, `RefSuite#aRemovalWaitsForAnOpenHoldAboveTheTable` and
  `CatalogObjectSuite#aPurgeClaimWaitsForAnOpenHoldAboveTheObject`. `RefSuite#everyTableInACutHasItsNamespace` also
  checks main.
- Bites: 16 new (4 for 158, 12 for 171) and 4 recorded again against the moved code. All were checked with
  `git apply --check`. None were run.
- Not covered: an object drop, an unregister and a namespace drop still read holds above them without locking those
  levels. The heavy cases first run overnight.
