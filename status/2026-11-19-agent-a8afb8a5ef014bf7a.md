# 2026-11-19, Oracle's self-check reports a journal-partition job that cannot run (backlog 72)

Paul decided on 2026-11-20 (D8, amended): a journal-partition job that cannot run is a finding like the others and
refuses the start unless allowed by its code ("Refuse, like others"). `OracleCatalogStore.selfCheck()` now reports one
finding, `ora.journal-job-down`, when migration V5's job `JOURNAL_PARTITIONS_AHEAD` cannot run, naming each cause and
what to do: `job_queue_processes` is 0 (read from `V_$PARAMETER` with the other parameters); the job is missing from
`USER_SCHEDULER_JOBS` once the schema has V5; it is disabled, BROKEN, or ended (COMPLETED, FAILED, SUCCEEDED); or its
last 2 logged runs in `USER_SCHEDULER_JOB_RUN_DETAILS` both failed (the newest run's ORA error is named). The judging
is `JournalJob.judge`, pure. Only `catalog-store-oracle/` changed in code; `docs/storage-design.md` section 7 and M2b
deviation 9 list the finding.

Two choices:
- The server runs the self-check before `migrate()` (item 6), so on a fresh or pre-V5 schema the job does not exist
  yet. A missing job counts only once the schema's newest migration is V5 or later; otherwise every first start, and
  every Oracle server test on a fresh container, would refuse.
- "Keeps failing" is the last 2 logged runs both failed, with no success after them. One failed run is not: the last
  success made this month's partition and the next two, so nothing runs short for a month or more, and a transient
  failure is put right by the next day's run. A success clears it. `FAILURE_COUNT` is not used: the Reference gives it
  as the times the job has failed, not since its last success, so one old failure would refuse every start.

The test containers run the job: `schedulerJobCreatesJournalPartitionsAhead` (same image,
`gvenzl/oracle-free:23.26.3-slim-faststart`, since M1) waits for the job's first run and finds `failure_count` 0, and
passed in the heavy passes of 2026-11-10 and 2026-11-12. So a healthy test database gains no finding, and
`catalog-server`'s test settings still allow only `ora.no-data-guard` for Oracle.
