# 2026-11-21, items 116 and 117: the two failures of the overnight run of 2026-11-21

- **Item 116.** `AuditTablesTest`'s catalog server now names the test PostgreSQL's two self-check findings in
  `nuna.database.allow-unsafe` (`pg.no-sync-standby,pg.fsync-off`), as `ConformanceServer` does. The other tests that
  start a server on a test PostgreSQL already had them: `catalog-server`'s own tests and `catalog-maintenance`'s
  `TestCatalog` through `catalog-server`'s test `config/application.yaml` (its `testJar`), the conformance server in
  its properties, and the load stack (`Stack`, `DrDrillTest`) on the command line.
- **Item 117.** The cause was the rename to nuna (backlog 59, c9e82a9): a storage profile's id is
  `UUID.nameUUIDFromBytes("<project>-storage-profile:<name>")`, so the previous release, 2b1af36, derives
  `20f6730e-…` for profile `s3` from `keel-storage-profile:s3`, and this one `cee40642-…` from
  `nuna-storage-profile:s3`, exactly the two ids in the failure. No install holds a keel-era id: the work install has
  not happened and the demo is rebuilt from nothing every night. So the rolling upgrade now starts from a60daba, the
  landing of the rename, by the rule Paul used when he chose 2b1af36 ("after the rename"); its PostgreSQL schema
  stops at V8, so the test crosses V9 to V11 and is renamed `upgradingOneServerAtATimeAcrossV9ToV11LosesNothing`.
  Choice made (Paul may overrule): the test no longer crosses V5 to V8. a60daba reads its settings under `nuna.`
  and writes this release's topics, so item 65's translation for a keel-era release (`PreviousRelease.settings`) is
  gone and `Stack` gives every server the same settings. A new fast test, `ProfileIdTest`, pins the id of profile
  `s3`, so a change to what the id is made from fails the fast build, not the next upgrade.
