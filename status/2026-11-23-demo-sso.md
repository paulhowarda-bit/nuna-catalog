# 2026-11-23, every demo UI signs in through Keycloak (backlog 174)

Paul asked to go through the demo's UIs one by one and make sure each signs in by single sign-on. Five already did
(the console, Keycloak's account page, kafbat, Studio by SAML, CloudBeaver); two took passwords of their own.

- Silo's console (8184) signs in through Keycloak: client `silo` in realm `nuna`, its client role `diagnostics`
  given to `demo-operators` and put in the ID token's `policy` claim. `demo/k8s/silo-signin.yaml` patches the
  demo's Silo only (the engine matrix applies `store-silo.yaml` without Keycloak). Its init container waits for
  Keycloak, since Silo reads the discovery document as it starts. `nunatest` keeps its access-key sign-in.
- Keycloak's admin console for realm `nuna` (8180/admin/nuna/console/) signs the operators in, read-only:
  `demo-operators` holds realm-management's view roles. Keycloak runs with `--hostname-backchannel-dynamic` so
  Silo, inside the cluster, reaches the token and key endpoints at `http://keycloak:8080`.
- `demo.sh up` waits for Silo's rollout before the seed job makes the warehouse bucket. The first rebuild failed
  at the lake writer because the patch replaced Silo's pod after the bucket was made in the old one.
- `demo/README.md`: the UI table, the accounts table and the sign-in section say who gets in where. Item 110's
  three corrections to the branching walk ride along.

Checked in the running demo, rebuilt from this branch (`demo.sh down` and `up`, exit 0), with a script that types a
password once at the console and then opens every other UI with the same cookies:

- `oscar` (operator): 7 of 7 sign in without a password; Silo's session carries the diagnostics actions only
  (`admin:ServerInfo`, `admin:Prometheus`, `admin:ConsoleLog`, `admin:ServerTrace` and the like, no `s3:` action);
  listing realm `nuna`'s users answers 200.
- `ana` (analyst): 5 of 7; the two others refuse her as intended: Silo answers "policy claim missing from the JWT
  token", and listing users answers 403.

Not covered: Kafka Connect's REST API (8186) and Silo's S3 API (8187), which are APIs, not UIs; changing the realm
stays with the master realm's `admin`.
