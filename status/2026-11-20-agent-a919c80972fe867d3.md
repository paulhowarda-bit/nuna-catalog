# 2026-11-20, a JWKS fetch waits 5 s for the IdP (backlog 60)

The 401 that failed `CredentialExpiryTest` in the overnight run of 2026-11-18 was a JWKS fetch that timed out. The
test's one `audit.fallback` line held the reason all along: "Couldn't retrieve JWK set from URL: Read timed out".
`TokenAuthenticator` used Nimbus's JWKS retriever with its 500 ms read timeout, and the test's in-JVM `TestIdp`
answered later than that in a JVM slowed by the build beside it: the context took 30.8 s to start, against 5.3 s on
2026-11-16, while `catalog-maintenance`'s `KubernetesCompactionTest` ran Spark Jobs in Docker Desktop's Kubernetes.
The nightly `LargeExpiryTest` of 2026-11-19 logged the same refusal.

- `TokenAuthenticator`: a JWKS fetch waits up to 5 s to read the IdP's answer (`JWKS_READ_TIMEOUT`). Connecting
  keeps Nimbus's 500 ms, and the cache, refresh-ahead and rate limit are unchanged.
- `TestIdp.slowFetches(Duration)` answers each JWKS fetch late. `JwksRefreshTest#aSlowJwksIsWaitedForNotTakenForAnInvalidToken`
  (Java only) accepts a token whose JWKS answers after 1 s, after one fetch. Bite:
  `bites/D16/jwks-read-timeout-500ms.patch` (the 500 ms back), checked with `git apply --check`.
- `CredentialExpiryTest`'s status assertions carry the response's status, `WWW-Authenticate` and body, and on a 401
  point to the `nuna.audit.fallback` line, since a 401's body never names the reason.

Checked: the fast build with the new test before the fix failed only that test, with the overnight's message
(`catalog-security`, 47 tests, 1 failed). With the fix, after merging main, `./gradlew build` passed: "BUILD
SUCCESSFUL in 1m 27s", all 362 bites apply, `catalog-security` 47 tests, 0 failed.

Not covered: `CredentialExpiryTest` is tagged heavy, so it did not run (no heavy build tonight); the overnight run
