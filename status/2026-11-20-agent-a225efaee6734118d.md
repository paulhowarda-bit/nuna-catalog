# 2026-11-20, an issuer whose keys cannot be fetched answers 503 with Retry-After (backlog 90, D16)

Paul's answer on item 90 (D16, amended 2026-11-20: "503, Retry-After") is in. When a token needs signing keys the
catalog does not hold and they cannot be fetched (the IdP down, or slower than the 5 s read timeout), the request
answers 503 `ServiceUnavailableException` with `Retry-After: 2`, no `WWW-Authenticate` challenge, and the token is
neither accepted nor called bad. A token bad on its own (wrong signature against a held key, expired, another
audience, an untrusted issuer, a key id the issuer does not publish) is still 401 `invalid_token`, also while the IdP
is down. The audit's `AuthFailure` names the reason, as before.

- The 401 path is the server's own filter, `security/Authentication`, which calls `TokenAuthenticator` directly;
  Spring Security's resource-server chain is not used. Nimbus raises a fetch failure as a `JWKSetUnavailableException`
  (`JWKSetRetrievalException` for a failed or timed-out fetch), which Spring's `NimbusJwtDecoder` wraps as the direct
  cause of a plain `JwtException`. `TokenAuthenticator` tells it apart there and throws `AuthenticationFailure` with
  status 503; the filter answers it with `Retry-After` and the Iceberg error shape, and logs a warning.
- The rate limit (two fetches in 30 s) refuses a refetch with a `RateLimitReachedException`, which is not a
  `JWKSetUnavailableException`. Mapping only the latter would have made an IdP that stays down answer 503 twice and
  401 to every other request in each 30 s. So `TokenAuthenticator` listens to Nimbus's health reports
  (`JWKSourceBuilder.healthReporting`): a refused refetch is an outage when the last fetch failed, and a bad token
  when it succeeded (a made-up key id).
- `Retry-After` is `StoreOutage.RETRY_AFTER_SECONDS`, 2 s, the value every other 503 sends; the rate limit keeps
  retrying clients from reaching the IdP more than twice in 30 s.
- Tests, all Java only: `JwksRefreshTest` asserts the 503 for an unreachable JWKS (`anUnreachableJwksMeansNoTokenIsAccepted`),
  for one slower than the timeout (6 s, `aJwksSlowerThanTheReadTimeoutIsAnOutage`), for an IdP that stays down past
  the rate limit, and for an unheld key while the IdP is down; 401 for bad tokens while the keys are reachable and
  while held keys serve during an outage; and 401 for each made-up key id the rate limit refuses. The new
  `IdpOutageTest` drives the real filter and authenticator with Spring's mock servlet objects: 503, `Retry-After`,
  no challenge, the error body, one audited `AuthFailure` naming the reason; 401 with the challenge for a bad
  signature; and a good token reaching the route.
- Bites in `bites/D16/`: `jwks-outage-answers-401.patch` (the fetch failure mapped back to 401),
  `jwks-refetch-limit-bad-token.patch`, `jwks-refetch-limit-outage.patch` and `idp-outage-without-retry-after.patch`.
  `jwks-read-timeout-500ms.patch` is recorded again: its context moved.
- Clients: the console signs its user out on a 401 (`api.js`) and shows any other error in place, so an IdP outage
  no longer signs anyone out. Iceberg's Java client (1.12.0, read from its sources) never retries a 401 and retries a
  503 that carries `Retry-After` for any method, up to five times, waiting the header's seconds. The worker's own
  calls fail the scan on either status, as before.
