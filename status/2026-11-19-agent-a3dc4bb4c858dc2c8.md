# 2026-11-19, PostgreSQL's store keeps the journal's horizon without a migration (backlog 9)

Of the four backends, PostgreSQL and Oracle partition the journal by month; CockroachDB splits ranges and MongoDB
keeps one collection, so they have no horizon. Oracle's V5 Scheduler job already keeps this month and the next two
ahead daily, and a commit past them creates its own partition; nothing changed there. PostgreSQL extended its
partitions only in `migrate()`. Now `SqlCatalogStore`, once a day at most, extends them twelve months ahead of its
clock before a write that journals (commit, create, revive): the day's first writer on each server does it, the
others go on. It waits at most a second for each lock and logs a failure at WARNING without failing the write; the
default partition still takes a commit past the horizon. The rule (when, how far) is `JournalHorizon`, on an
injected clock. Only `catalog-store-sql/` changed in code.

Tests: `JournalHorizonTest` (new, Java only, 8 tests, with a moving clock and PostgreSQL and CockroachDB faked at the
JDBC interface); `PostgresStoreSuiteTest#journalHorizonIsKeptWithoutAMigration` (new, heavy: two servers commit
monthly for fourteen months after one migration, every commit in its month's partition, none in the default; an
extension behind an open reader gives up within a second and its commit lands). Bites: four new
`bites/M8/journal-horizon-*.patch`, each naming a `JournalHorizonTest` case, and `migration-lock-no-wait.patch`
recorded again against the moved code; checked with `git apply --check`, the files restored with `git checkout`.
