# 2026-11-19, a revive compares the object's namespace under its lock (backlog 12)

The race in `build-plan.md`'s review fixes of 2026-11-12 ("Not guarded") was real on every store: `reviveObject`
locked the object by id and state only, then placed it in the namespace the engine passed. Undrop, rename and drop
leave the main pointer alone, so an object undropped, renamed into another namespace and dropped again between the
engine's read and the store's write passed the pointer check and came back in the namespace it first left.

Now the store compares the namespace too, on all four backends:
- PostgreSQL and CockroachDB share `SqlObjects.revive`, and Oracle has `OracleObjects.revive`. Both lock the object
  row (`SELECT … FOR UPDATE`, which now also reads `namespace_id`) and compare its namespace under that lock.
- MongoDB (`MongoObjects.revive`) compares it in the snapshot transaction that writes the object document, so a move
  committed since then makes the write conflict, and the retry finds the object where it now is.
- An object no longer in that namespace is `Missing(OBJECT)`, which `CommitEngine` already answers with 409 ("was
  brought back, purged or otherwise changed while being registered"). `catalog-core` is unchanged.
- `CatalogObjectStore#reviveObject` now says the object must be in state `from` in `namespaceId`.

Tests, in the shared suite (`CatalogObjectSuite`):
- `reviveComparesTheNamespace` (new) plays the interleaving: the object is read as dropped in `home`, then undropped,
  renamed into `away` and dropped again. A revive into `home` is `Missing(OBJECT)` and writes nothing, and the object
  stays dropped in `away` with its pointer unchanged. A revive into `away` then applies.
- `reviveBringsTheObjectBack` used to revive into another namespace, which the store now refuses. It now revives in
  the object's own namespace and checks that another namespace is `Missing(OBJECT)` with nothing written.
