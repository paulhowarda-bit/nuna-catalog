# 2026-11-19, the separation-of-duties check runs inside the grant's write (backlog 13, D18)

The race was real: `GrantRoutes` read the group's grants, asked `Separation.refusal`, then called `putGrant` in a
transaction of its own, so two grants to one group made at once (`write` on one namespace, `manage-tags` on another)
each passed on a read that missed the other. Now the store asks the check inside the write: `GrantStore.putGrantIf`
reads the privileges the group holds in the grant's catalog in the grant's transaction, asks the caller's `admits`,
and writes only if it accepts (else `Refused(NOT_ADMITTED)`, nothing written). Conditional puts in one catalog are
serialized: PostgreSQL, CockroachDB and Oracle lock the catalog's row `FOR UPDATE` before reading; MongoDB marks the
catalog's document, so the later of two racing puts conflicts and runs again. The rule stays in `Separation`, which
the route passes as `admits`; the store learns no duties. Per catalog rather than per group because D18 judges
separation per catalog, the row exists on every store (no schema step on any of the four), and grants are rare.
`putGrant` is unchanged, for `GrantReplay`. `GrantReplayTest`'s store double (catalog-audit) gained the new method,
so the claim was extended to that one file.

Tests: `GrantRaceTest` (new, Java only, 3 cases): grants raced through the real route, authorizer and `Separation`
over a store double that keeps `putGrantIf`'s contract and holds both requests until each has reached the store;
`GrantSuite` (heavy, every store): 3 new cases, among them eight conditional puts racing to one group, exactly one
applied. Bites: `bites/D18/separation-checked-outside-the-write.patch` (Java only), `grant-check-unlocked-sql`,
`grant-check-unlocked-oracle` and `grant-check-unmarked-mongo` (heavy); `bites/M5/sod-not-checked-on-grant.patch`
