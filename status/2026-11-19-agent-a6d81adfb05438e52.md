# 2026-11-19, the server refuses to start on an unsafe database (backlog 6, D8)

Paul decided item 6 on 2026-11-19 (D8): a failed self-check refuses to start the server. `StoreWiring` now runs the
store's `selfCheck()` before `migrate()` and throws, naming each finding's code and detail, unless
`nuna.database.allow-unsafe` (new, `DatabaseSettings`, empty by default) names that code; each finding allowed is
logged as a warning. A self-check that cannot run (its exception) refuses too. The setting is per code, not a
switch, as docs/storage-design.md section 7 says ("Accepting is per code, never a blanket switch").

The setting is on wherever a server starts on a single-node database:
- `catalog-server/src/test/resources/config/application.yaml`: every server this module's tests start, and through
  the tests jar catalog-maintenance's `TestCatalog`: `pg.no-sync-standby`, `pg.fsync-off` (Testcontainers runs
  PostgreSQL with fsync off), `ora.no-data-guard`, `mongo.too-few-voters` (what `OracleBackendTest` and
  `MongodbBackendTest` already assert the self-check reports).
- `ConformanceServer`: `pg.no-sync-standby`, `pg.fsync-off`.
- `DrDrillTest`'s DR-region server, on the promoted DR database, which has no synchronous standby:
  `pg.no-sync-standby`, through a new `more` argument of `Stack.server`. The load tests' other servers run on the
  primary with its synchronous standby and fsync on, with nothing allowed.
- `demo/k8s/catalog-values.yaml` (the demo and the engine matrix) and `deploy/local/values.yaml`:
  `pg.no-sync-standby` (their PostgreSQL has fsync on).
- The Helm chart exposes `config.nuna.database.allow-unsafe: []`.
