# 2026-11-20, a table's first DR watermark is the newest whole version; each DR pass logged at INFO (backlog 99, 101)

- **Item 99** (D37, amended again 2026-11-20: "Newest whole version"). The versions to test come from the journal,
  through the work list: `GET /management/v1/maintenance/dr-work` (`DrRoutes`) now names, for an object with no
  watermark, its newest journaled versions up to the pointer's, at most 100, oldest first; `oldest-unverified-at` is
  still its first commit. With a watermark it names the oldest 100 above it, as before. The journal, not the metadata
  log or the listing, because it holds the version number the catalog checks a report against, and it still names
  the older versions when the pointer's own metadata file is the one in flight. `DrVerify`'s whole check takes,
  newest first from the pointer's, the first of those versions whose every file every snapshot reaches is in its one
  listing. What bounds it: at most 101 versions; one whose metadata file the listing lacks is not read; each other
  is read once and passed over without a walk of the whole table when a file it adds to the next older one held is
  missing, or when it reaches a file a newer one lacks (missing, but not among what that one adds to it). So in
  the cases seen there is one walk of the whole table a check, as before: in-flight versions fail on their own
  files, and a file lost long ago is carried down without a walk per version. A view with no watermark gets the
  newest version whose metadata file is there, from the same list. The verifier reports it as before; the lag then
  runs from the version after it, and the next pass checks from it version by version.
