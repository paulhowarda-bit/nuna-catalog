# 2026-11-22, a refusal by a legal hold or DR freeze is audited (item 134)

- Every refusal item 134 named now publishes a `nuna.catalog.denial` record through `Denials`, naming the operation
  and the table, with reason `dr_freeze` or `legal_hold` and then the message the caller gets. The answer is the
  same 403 ForbiddenException with the same message.
  - The commit engine answers its refusals as a reply, so the reply now says which 403s are these:
    `CommitRule.Rejection.denial` (set by `Rules.drFreeze` and `Rules.retentionHold`, through `Rejection.refused`)
    becomes `CommitReply.Failure.refusal`, the object refused and the reason; the unregister's hold and freeze
    refusals set it too (`Failure.refused`). `Guard.refused` publishes the denial for such a reply; the table
    create, commit, register and unregister routes, the view create, replace and register routes and the
    transaction route call it before rendering the reply. A transaction's denial names the table the rule refused.
  - A drop the store finds held refuses through `Guard.refuse`, a purge claim the store finds held through the new
    `ManagementGuard.held`. Both are now `AccessDenied`, which an idempotency key does not record, as item 132 made
    the freeze's.
  - A failure replayed by an idempotency key carries no refusal and is not audited again: its first answer was.
