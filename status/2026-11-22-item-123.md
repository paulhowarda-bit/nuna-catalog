# 2026-11-22, item 123: the heavy build's 30 s stalls were Docker running out of memory

Paul asked for item 123 to be fixed. The nuna-demo stack was taken down for the runs (`demo/demo.sh down`, at his word)
and brought back up at the end.

What stalls: the Docker VM's memory, not its port forwarding. Two runs of the second heavy build's pairing
(`:catalog-server:test`, `:catalog-maintenance:test`, `:catalog-store-mongo:test`, `:catalog-store-oracle:test`,
`-Pheavy --continue`, two at a time) with a sampler logging each second the VM's `/proc/pressure` counters, free memory,
swap, and a fresh request to a container through a mapped port:

| | before | after |
|---|---|---|
| time | 30m41s | 20m50s |
| tests failed | 2 (`TwoIssuersTest`, `DrRewindRouteTest`) | 0 |
| swap used, peak (of 2 GB) | 2.0 GB, full | 0.4 GB, as at the start |
| least memory available | 1.5 GB | 2.7 GB |
| every task stalled on memory | 77 s; 312 s at 10% or more | 20 s; 76 s at 10% or more |
| containers' memory, peak | 5.0 GB | 3.8 GB |
| catalog-server's tests | 23.6 min | 14.8 min |

Both failures fell while swap filled and memory stalls reached 10 to 50% of each second; the mapped port answered within
about 1 s throughout. catalog-server's test JVM held every container it started until it exited: Oracle, MongoDB, two
Keycloaks, a Kafka per governance context and a PostgreSQL per context, about 4 GB idle. Now it keeps one Spring context
at a time (`catalog-server/src/test/resources/spring.properties`), and the four initializers that start containers
register their stop with their context (`StopWithContext`). CLAUDE.md (Builds) has the rule for new tests.

Item 123 stays open until ten overnight heavy builds in a row lose no test to a wait running out. The fast build passed
before landing. The full heavy build, the Ceph leg and the bites were not run here; tonight's overnight run runs them.
